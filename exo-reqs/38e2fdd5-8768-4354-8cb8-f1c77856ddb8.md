# req(exo): one-tap profile CONTEXT switching — an active-profile indicator plus a switcher whose first row is the context you came from

## Job Story

When I want to move between my work context and my personal context, I want to **see which context I am in right now** and **get into the other one in at most two taps**, so that switching context stops being a command-palette expedition and becomes something I actually do — on the desktop and on the iPhone alike.

## Why "context switching", not "speed-up" (P0 falsification, 2026-08-02)

The parent project's falsification gate (`8b8466bb`, task P0) measured the real vaults and concluded that **mounting less through profiles does NOT materially help**: the active profile already resolves to 100 % of vault-my (8 738 / 8 738), 100 % of vault-tbank and 99.4 % of vault-exodev, because the transitive `exo__AssetSpace_dependsOn` closure drags almost the whole vault in. The "minimal profile that still has my data" saves **58 files (0.7 %)**, and the measured index delta was **−0.6 %**.

Its verdict named exactly **two** levers that do work, and this task carries one of them:

> **Switching context** (mount the work one, unmount the personal one): **−44 %** (6 120 → 3 409 ms). Real, but it changes *what is available*, not *the speed of the same thing*. Valuable ⇒ **P3 keeps its point**, if Andrey is willing to work in one context at a time.

and, for this task specifically:

> **P3 (quick-switch) — keep.** It carries the single measured large win (−44 %) — **but it must be sold as "fast context switching", not as "speed-up".**

This requirement implements that re-scope. It therefore deliberately does **not** promise faster indexing, does **not** add a granular "turn individual AssetSpaces off" surface (the gate measured that as worthless *and* it is a footgun — `exocmd` is not part of the TS floor, so freely unmounting it silently kills the homoiconic commands), and does **not** show the index-cost figure again in the indicator: P1 (`6171f443`) already surfaces the honest closure cost **inside the picker**, which is where a mount decision is actually made.

## What "at a glance" can mean on each platform

`Plugin.addStatusBarItem()` is documented in the Obsidian API as **"Not available on mobile"** — verified in `obsidian.d.ts` at the version this repo builds against. A status-bar-only indicator therefore cannot satisfy the desktop **and** iPhone acceptance at the same time, so the affordance is split by surface, never by capability:

| | desktop | iPhone / mobile |
|---|---|---|
| see the active profile | status-bar item (always visible) | ribbon entry's tooltip / accessible label |
| open the switcher | click the status-bar item | tap the ribbon entry |
| taps to switch | 2 | 2 |

The **capability** (see the context, switch it in ≤2 taps) exists on both platforms — only the surface carrying it differs, because one of the two surfaces does not exist on mobile. This is consistent with the Desktop↔Mobile Command Parity invariant, which forbids gating a *command* away on a platform; it does not require a platform to render a UI chrome it has no concept of.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: One-tap profile context switching

  Background:
    Given the plugin already records the last-applied profile as `activeProfileUid`
    And it already records the profile active before that as `previousProfileUid`
    And the existing "Apply profile" picker already applies a chosen profile

  Scenario: AC1 — the active profile is readable at a glance
    Given a profile named "Personal" was the last one applied
    When the indicator is refreshed
    Then it reads out the label "Personal", not the profile's UID
    And when no profile has ever been applied it says so explicitly
      # never a blank or a stale label

  Scenario: AC2 — the context I came from is the FIRST row of the switcher
    Given "Personal" is active and "Work" was the profile active before it
    When the switcher is opened
    Then "Work" is the first row offered
    And every other profile keeps its existing relative order
    And so switching back to the previous context costs one tap after opening

  Scenario: AC2b — opening the switcher and choosing is at most two taps
    Given the indicator is visible
    When I activate the indicator
    Then the profile switcher opens directly
      # the same picker the "Apply profile" command opens — one code path, not a copy

  Scenario: AC3 — the affordance exists on desktop AND on mobile
    Given the plugin is running on iOS, where Obsidian has no status bar
    When the plugin loads
    Then a ribbon entry is registered that opens the switcher and names the active profile
    And no `node:fs` and no desktop-only capability is required to render or refresh it

  Scenario: the indicator follows the profile it reports
    Given the indicator currently reads "Personal"
    When a profile apply completes and makes "Work" active
    Then the indicator reads "Work" without reloading the plugin

  Scenario: zero-regression — with no previous profile the switcher order is untouched
    Given no profile has ever been switched away from
    When the switcher is opened
    Then the rows appear in exactly the order they appeared before this feature
```

## Mechanism

**No new engine, no new picker, no change to what is mounted.** Every path reuses what is already shipped: `ProfileCommands.invokeApplyProfile` (the apply flow), `ProfileFuzzyModal` (the picker, including P1's cost line), `PluginLocalDataStore.getActiveProfileUid` / `getPreviousProfileUid` (the two device-local slots, already written by `ProfileApplyManager`).

1. **Pure domain** — `packages/obsidian-plugin/src/domain/profile/quickSwitch.ts`, a sibling of the shipped `indexCost.ts` / `closureGap.ts`:
   - `formatActiveProfileIndicator(label | null) → string` — the short text the status bar shows and the tooltip repeats. A `null` label yields an explicit "no profile" wording, never an empty string.
   - `orderProfilesForQuickSwitch(choices, previousUid) → choices` — moves the previously-active profile to the front and leaves the relative order of everything else untouched. When `previousUid` is `null` or matches nothing it returns the input order, which is what makes the zero-regression scenario **structural** rather than argued.
2. **Surface adapter** — `ProfileIndicator`, owning the two surfaces and one `refresh()`:
   - a ribbon entry, registered on **both** platforms (this is the mobile affordance and a second desktop entry point);
   - a status-bar item, registered only where `addStatusBarItem` exists;
   - both activate the **same** callback, which is the existing apply-profile invocation — so there is exactly one switching code path.
3. **Wiring** — the plugin mounts the indicator at load and refreshes it after an apply or an undo completes; the picker's option list is passed through `orderProfilesForQuickSwitch` before it is handed to the modal.

`FuzzySuggestModal` presents `getItems()` in order while the query box is empty, which is precisely the state the picker opens in — so "previous first" is what the user sees on the tap that matters.

## Out of scope (siblings)

- Any change to what is mounted, to the apply/undo mechanics, or to the closure computation.
- A granular per-AssetSpace toggle surface (P2 of the same project — the gate measured it as not worth its footgun risk without a reverse-reference warning).
- A dedicated "switch to previous profile" command: `Undo last profile apply` already applies the previous profile and is already bindable to a hotkey; adding a second command with the same effect would be palette noise.
- Any index-time estimate, and any repetition of the P1 cost figure outside the picker.
