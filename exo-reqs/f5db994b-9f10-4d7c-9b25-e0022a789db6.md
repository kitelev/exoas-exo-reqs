# req(exo): query predicate analyzer — which predicates a query needs, or a full load with the reason

## Job Story

When the CLI is about to answer a SPARQL query over a vault, I want to know in advance which predicates
the engine will actually read for THIS query, so that later phases can load only those triples (less
memory and time per CLI call) — and I want the analyzer to refuse with a named reason whenever it cannot
bound the set, because a wrong cut silently changes answers (RFC `308a52c3` «Загрузка по запросу», §Д1;
ticket `03523fef`).

## Mechanism (read on `origin/main` `c416f3fe`)

The CLI translates a query to algebra (`ExoQLAlgebraTranslator`), runs `AlgebraOptimizer.optimize`
(which does not read the store) and executes it through two store decorators:
`ClassHierarchyResolvingStore` (maps a symbolic class IRI to its file IRI through a label index built
from `exo:Asset_label` / `rdfs:label` literals) and `PropertyHierarchyResolvingStore` (widens a constant
predicate to its transitive sub-properties through an index it builds FROM THE STORE out of
`exo:Property_superProperty` and the `exo:Asset_label` of the declaration ends). Nothing today tells
which predicates a query reads; every call loads the whole graph.

## Statement (Gherkin)

```gherkin
Feature: query predicate analyzer — P' or full load with the reason

  Scenario: constant predicates of the query form P after prefix expansion
    Given a query whose triple patterns and property paths use constant predicates
    And none of the full-load rules below applies to it
    When I call analyzeAlgebraPredicates on its algebra
    Then the verdict is "prune" and P' holds every such predicate as an expanded IRI
    And a plain query (no class bridge, no sub-property, no namespace filter) adds no skeleton predicate

  Scenario: sub-property fixed point
    Given a sub-property index (parent → transitive sub-properties) taken from the decorator itself
    When an ontology predicate of P (under https://exocortex.my/ontology/, except exo:Class_superClass and
      exo:Instance_class, which the decorator never widens) has sub-properties
    Then P' holds the whole transitive chain
    And a W3C predicate or one of those two bridge predicates is not widened: P' stays exact
    And P' also holds exo:Property_superProperty and exo:Asset_label, which the decorator reads to build its index
    And the engine over the store cut to P' sees exo:Asset_relates through concept:Concept_related

  Scenario: the class bridge skeleton follows the mechanism, over the whole P'
    Given a hierarchy predicate in P', or a membership predicate whose object is a variable, a blank node or an ontology IRI
      (a constant of the query, a predicate admitted by a namespace filter, or a member of the sub-property closure)
    Then P' holds the six bridge predicates: exo:Class_superClass, rdfs:subClassOf, rdfs:label, exo:Asset_label,
      exo:Instance_class, rdf:type
    And a membership predicate with any other constant object does not pull the bridge

  Scenario Outline: what the analyzer cannot bound is a full load with a named reason
    Given a query with <form>
    Then the verdict is "full" and its reasons contain <reason>
    Examples:
      | form                                                                            | reason                                   |

      | a zero-length path (*, ?, + or ^ over such, a sequence of such, an alternative  | zero-length-path-free-subject            |
      |   with such a branch) whose subject is a variable (a blank node is counted free |                                          |
      |   conservatively: it can only add a full-load reason)                           |                                          |
      | a free-subject path over a bridge predicate, or whose sub-property closure      | class-bridge-path-free-subject           |
      |   reaches one                                                                   |                                          |

      |   aggregate or GROUP BY with variables (row order changes the answer: SUM/AVG   |                                          |
      |   add floats in order; a group is keyed by lexical value and returns the term   |                                          |
      |   of its FIRST row — engine defect da2d78ac). A GROUP BY EXPRESSION is dropped  |                                          |

      | a variable predicate admitted by a namespace filter, with any of the            | namespace-filter-order                   |

      | exo:byUUID in any expression (FILTER, BIND, HAVING, ORDER BY)                   | uuid-lookup                              |

  Scenario: VL-3 — a namespace filter bounds a variable predicate only in its own group
    Given a top-level conjunct CONTAINS(STR(?p), "lit") or STRSTARTS(STR(?p), "lit") in the group of ?p
    And the list of predicates present in the store
    Then P' holds the store predicates matching the literal the way the engine matches them
    And a filter inside OPTIONAL, MINUS, a UNION branch, a subquery or EXISTS does not bound the outer ?p
      (LATERAL starts a new group too: an aggregate subquery in it returns a row even when its filter rejects everything)
    And several conjuncts on the same ?p intersect
    And a disjunction or a negation of namespace tests does not bound ?p

  Scenario: the walk is exhaustive
    Given any algebra operation or expression the translator produces
    Then the analyzer reads it: EXISTS / NOT EXISTS patterns, BIND, HAVING, subqueries,
      every UNION branch, the MINUS, OPTIONAL and LATERAL sides, the inputs of DISTINCT, REDUCED and ORDER BY,
      ORDER BY comparators, both sides of comparisons and arithmetic, every operand of a logical operator,
      the tested expression and the list of IN, both arguments of an aggregate, every item of a property path
    And an unknown operation type throws instead of being skipped

  Scenario: a prune verdict keeps the answer — differential guarantee on the real engine
    Given a store built by the real NoteToRDFConverter and the engine with both decorators, on the CLI path
      (translate → AlgebraOptimizer.optimize → execute)
    When the verdict is "prune" for a deterministic query (not RAND, NOW and the like) whose full answer is not empty
    Then the answer over the store cut to P' equals the answer over the full store
      (the same set of rows, the same CONSTRUCT triples, the same ASK result)
    And for the reasons variable-predicate, zero-length-path-free-subject, class-bridge-path-free-subject,

      uuid-lookup and a namespace filter scoped to OPTIONAL there is a query whose
      answer over the store cut to its own predicates plus the skeleton differs — the full load is needed,

  Scenario: nothing in production changes
    Then the analyzer has no caller in packages/*/src besides the export from packages/core
    And the output of `query` and the cache format are unchanged
```

## Verification

- Axes `packages/core/tests/integration/sparql/query-predicate-analyzer.test.ts` — PA (verdict) and
  PD (differential on the real engine) axes, each title `<axis> @req:<this uid> …`.
- Mutants `packages/core/tests/integration/sparql/query-predicate-analyzer-308a52c3.spec.json` — each
  mutant in the spec reddens exactly its own set of axes (sets pairwise distinct); control 0 red.
- Not pinned by an axis, on purpose: wrong implementations that only ADD predicates or full loads
  (precision, never a changed answer) and ones that are harmless on this engine — a blank-node subject
  counted as bound, a sequence counted nullable when SOME item is,
  the namespace predicates widened by sub-properties, a string function name not lower-cased; and the
  OPTIONAL condition (`leftjoin.expression`), read defensively — the translator never sets it for sparqljs
  input (a FILTER inside OPTIONAL stays a filter of the optional side); a non-literal needle in a namespace
  test (removing that check breaks the types); an unknown expression type throwing (the translator cannot
  produce one). The fixture axes PA0/PA21 guard the fixture forms, not the analyzer.

## Non-goals

- `query --prune-report` (phase 1b), the query corpus (1c), the oracle (2), the cache layout by predicate
  (3b) — separate tickets of project `0c25a8cb`.
- Narrowing the bridge skeleton from six predicates to the two label predicates the bridge actually reads
  (independent review: identical results on 14 392 queries) — a cost question for the layout spike;
  this statement keeps the RFC's six.
- Pruning `exo:byUUID` queries — needs a UUID index of loaded subjects in the cache manifest (phase 3b).

## Amendments before Active (2026-11-12/13, independent review of the implementation, round 1)

- Two prune verdicts changed the answer and are now full loads: a namespace-admitted variable predicate
  with an order-sensitive modifier (`namespace-filter-order`), and SUM/AVG over a free-subject path
  (`free-subject-path-order`). Axes PD51–PD54; mutants M43–M45.
- Clauses narrowed to what the code and the axes show: the constant-predicate scenario, the widening
  scenario (only ontology predicates the decorator widens), the blank-node subject, LATERAL, the
  OPTIONAL condition, the exhaustive-walk list and the Verification clause.
- The review's witnesses ported as axes PA21–PA38, PA40, PA41 / PD39–PD56 with mutants R1–R48 (shared red sets split
  into distinct axes); a guard term whose removal can change an answer now has a mutant.

## Amendments before Active (2026-11-13, independent review of the implementation, round 2)

- GROUP BY with variables is order-sensitive (the engine keys a group by lexical value and returns the
  first row's term — defect da2d78ac): over a free-subject path or a namespace-admitted variable predicate
  it is a full load. Axes PD57–PD59; mutant M46; the boundary (a group without keys stays prunable) — PD60, M47.
- The claim that LATERAL in the outer group is harmless was false and is removed; axis PD61, mutant R49.
- Two admitted variable predicates keep the order flag — axis PD62, mutant E12.
- The guarantee is stated for deterministic queries; the namespace-order rule is named broader than its
  mechanism (precision only).

## Amendments before Active (2026-11-13, independent review of the implementation, round 3 — APPROVE)

- Every GROUP BY form is pinned: with HAVING (PD63, G6), inside a subquery (PD64, G7), with several keys
  (PD65, G11).
- The rule's dependency on defect 38328fcc (GROUP BY by expression) is named in the table above.
