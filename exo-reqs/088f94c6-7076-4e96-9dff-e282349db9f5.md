# req(exo): `trash` записывает причину отдельным ассетом и не переписывает тело задачи

## Job Story

Когда я выбрасываю задачу, я хочу сказать **почему** — так, чтобы причина жила в графе отдельным ассетом и находилась запросом, а текст самой задачи остался нетронутым.

До этого требования `trash` (композит `d612e5f5`) четвёртым из пяти шагов применял личный шаг «Add Trashed Comment» (`d3412530`, exoas-my) типа `body_template`, который **заменяет** тело задачи заготовкой «## Trash Reason / - ». На 2026-10-11 это стёрло тело как минимум у одной задачи (`58e2b3f7`, восстановлено из копии); у 8 из 11 задач в Trashed тело равно пустой заготовке — причину не вписали ни разу. Трекинг дефекта: ems__Bug `b090c2e8`.

## Statement (Gherkin)

```gherkin
Feature: trash записывает причину отдельным ассетом

  Background:
    Given задача T класса ems__Task со статусом Backlog и телом B
    And T лежит в папке F и определена онтологией O (exo__Asset_isDefinedBy)

  Scenario: причина становится собственным ассетом, задача на неё ссылается
    When выполняется `apply trash <T> --input '{"label":"Переехало в другой проект"}'`
    Then создан новый ассет R класса ems__EffortTrashNote с меткой «Переехало в другой проект»
    And R определён той же онтологией O и лежит в папке O (в co-located vault это папка F)
    And R ссылается на T через exo__Asset_relates (новое → старое, однонаправленная ссылка)
    And у R нет ems__Effort_parent — ни при задаче, ни при проекте
    And статус T — Trashed, ems__Effort_resolutionTimestamp проставлен
    And тело T побайтно равно B

  Scenario: без причины команда отказывает и ничего не меняет
    When выполняется `apply trash <T>` без ключа label
    Then команда отказывает, назвав недостающий ключ label
    And файл T побайтно не изменился
    And новых ассетов класса ems__EffortTrashNote не создано

  Scenario: публичная команда не ссылается на приватные ассеты
    Given vault, где смонтированы только публичные ассетспейсы (без exoas-my)
    Then каждый шаг композита trash резолвится в этом vault

  Scenario: прежние значения причин не тронуты
    Then экземпляры EffortTrashReasonNoLongerRelevant и EffortTrashReasonStartedNotFinished остаются на месте
    And у ранее выброшенных задач ems__Effort_trashedReason не меняется
    And шаг «trashedReason → NoLongerRelevant» остаётся: категория причины пишется как прежде
```

## Устройство (данные команды, код движка не меняется)

- Новый ввод `exocmd__Grounding_inputSchema` у `trash`: `label` (строка, «Причина»), обязательный — отказ даёт существующий pre-flight (req `656bd2d9`).
- Новый шаг `create_instance`: класс `ems__EffortTrashNote`, онтология — та же, что у задачи (универсальный шаблон по умолчанию), папка — папка этой онтологии (`$isDefinedByFolder`); метка — введённый текст. Собственное правило наследования шага на `ems__Effort_parent` (условие никогда не срабатывает) отключает для него универсальные правила, которые иначе сделали бы причину дочерним эффортом задачи или проекта.
- Связь — от причины к задаче: значение по умолчанию нового ассета `exo__Asset_relates = $target` (токен `4c4b6a77`). Шаг «trashedReason → NoLongerRelevant» (`cc209698`) не меняется.
- Шаг создания причины стоит ПЕРВЫМ: отказ создания обрывает команду до мутации задачи.
- Шаг «Add Trashed Comment» (`d3412530`) из композита убирается.
- Всё в `exoas-exocmd` (публичный, закреплён в exocortex сабмодулем).

## Вызовы, которые обязаны передать причину (перевод — часть поставки)

- Кнопка 🗑 дайджеста PO (`~/dotfiles/scripts/po_digest_callback.py`) — подставляет «Отклонено в дайджесте PO <дата>».
- Общие инструкции ботов (ассет `96426819`, «в корзину: `{exo} apply trash <path>`») — причина из сообщения человека.
- Скиллы `executive-assistant`, `project-manager`, `product-owner` — `--input '{"label":"…"}'`.

## Non-goals

- Условное создание (заметка только при непустой причине): в движке нет условных шагов, решение фаундера — причина обязательна.
- Выбор категории причины из списка.
- Перенос ранее выброшенных задач на новые ассеты причин.
- Восстановление потерянных тел — отдельный шаг под ems__Bug `b090c2e8`.

## Поправка 2026-10-11 (после одобрения, выбор фаундера)

- В одобренной редакции стояло «ems__Effort_trashedReason задачи указывает на R (подстановка созданного ассета, req `c0122d7f`)». Это неверно: `$createdInstance` резолвится только в значениях по умолчанию шага `create_instance`; шаг `property_set` созданный ассет не получает (`GroundingExecutor.execute`, case PROPERTY_SET). Фаундер выбрал связь от причины к задаче — данными, без правки движка.

## Поправка 2026-10-11, вторая (ревью PR #4555, выбор фаундера)

- Класс причины — новый `ems__EffortTrashNote`, а не `ems__EffortTrashReason`. Поле `ems__Effort_trashedReason` предлагает в выпадающем списке все экземпляры класса из своего `range` вместе с подклассами; с прежним классом каждый текст причины вставал бы рядом с двумя категориями. Новый класс намеренно не подкласс категорий.
- У причины нет `ems__Effort_parent` (ревью HIGH): универсальные правила наследования смотрят на класс задачи, по которой нажали, а не на создаваемый ассет.
- Папка причины — папка её онтологии (`$isDefinedByFolder`), чтобы причина не наследовала неверное расположение задачи.

## Открытый пункт (закрыт)

- Отказывает ли pre-flight на ПУСТОЙ строке `label` (`""`), не было установлено. Замер 2026-10-11: и `""`, и строка из пробелов отказываются как непереданный ключ, задача не меняется (ось R8). Форма плагина пустое обязательное поле тоже не пропускает.
