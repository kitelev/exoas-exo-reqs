## Job Story

When I mutate an existing asset through a `service_call` command — `apply set-planned-start`, `set-planned-end`, `set-start-timestamp`, `set-end-timestamp`, `set-scheduled-date`, `set-result`, `plan-for-evening`, `clean-properties`, `fix-missing-label`, `rename-to-uid` — from the CLI or from a plugin button, I want the asset's `exo__Asset_updatedAt` to record that modification exactly as it does for a `property_set` write (req `454ccedf`), so that "when did this asset last change" stays one invariant across every grounding type instead of stopping at the executor's own eight write points.

## Context

- Ticket `8421b014-d8c9-4cb5-a278-27f04f5bc79d` (parent techbacklog `bbac67ce`), the puzzle req `454ccedf` (ticket `533856e4`, PR #4251) left in its §Not governed: "`service_call` groundings (17 commands) mutate inside `packages/services` past these write points".
- Repro on the published CLI 16.240.10 over a temp vault (control `apply set-criticality-high`, a `property_set`, bumped `2026-01-01T00:00:00 → 2026-09-17T18:19:15`): `apply set-planned-start` (`createUpdatePropertyService` → `fsAdapter.updateFile`), `apply plan-for-evening` (`TaskStatusService.planForEvening` → `vault.modify`), `apply clean-properties` (`PropertyCleanupService` → `vault.modify`) and `apply rename-to-uid` (`RenameToUidService` → `vault.process` + `vault.rename`) each changed the file's content and left `exo__Asset_updatedAt` at the seeded value. n = 4 commands over 3 distinct write channels, by execution.
- Mechanism (`packages/core/src/services/GroundingExecutor.ts` @ `d0216a8a`): `executeServiceCall` (`:1129`) resolves the registered service and returns `{ success: true }` right after `await service.execute(serviceTargetIRI, mergedInput)` (`:1289`); `stampUpdatedAt` (`:598`) is applied only to the content the executor itself writes. The services write through FOUR channels that the executor never sees — `IVaultAdapter.modify` (`ArchiveAssetService:50`, `PropertyCleanupService:27`, `FixMissingLabelService:38`, `TaskStatusService:41`), `IVaultAdapter.process` + `rename` (`RenameToUidService:58/:50`), `IFileSystemWriter.updateFile` (`grounding-service-factories.ts:557/:582/:612` — updateProperty / removeProperty / setStatus) and the create channels of the satellite services. The ticket's proposed "one carrier `IVaultAdapter.updateFrontmatter` / `applyPatch`" does not exist on this path: `packages/services/src` calls `updateFrontmatter` 0 times. There is therefore no single service-side write point to stamp at; the single point is the executor, AFTER the service returned.
- Blast radius (SPARQL over the 74 `exocmd__Command` with a cliName, `--no-cache`): **17** `service_call` commands. 2 already stamp (convert-to-task / convert-to-project short-circuit into `executeConvertToTask/Project` before `service.execute`, req `454ccedf`); **10** mutate the target and never bump (the six `updateProperty` date/result setters + plan-for-evening, clean-properties, fix-missing-label, rename-to-uid); 1 moves the file without touching its content (repair-folder); 4 create a SATELLITE and leave the target untouched (create-note / createAsset, duplicate-asset, create-narrower-concept, create-subclass). Services without a cliName (`archiveAsset`, `removeProperty`, `setStatus`, `createRelatedTask/Project`, `instantiatePrototypeSubtree`) run as composite steps through the same dispatcher and fall into the same classes.
- Homoiconicity Q3 — same guard rail as req `454ccedf`: the "last modified" invariant belongs to the executor, not to each of N services (which would regress the moment an N+1th service forgets it). The plugin executes buttons through the same `GroundingExecutor`, so Desktop / Mobile / CLI parity holds by construction; the service's own write channel (Obsidian `vault.modify`, Node `fs`) is irrelevant to the stamp because the executor compares the target's bytes before and after the call.
- Not governed: (i) files a service changes BESIDES its target — `rename-to-uid` rewrites incoming wikilinks in OTHER assets (`RenameToUidService` → `IVaultAdapter.updateLinks`); those link-holders are not stamped; (ii) the satellite files created by `create-note` / `duplicate-asset` / `create-narrower-concept` / `create-subclass` / `createRelatedTask` / `createRelatedProject` — their own `exo__Asset_updatedAt` is the CREATE side of the invariant (`createAsset` writes `createdAt` only; `duplicateAsset` copies the source's `updatedAt` verbatim) — a follow-up under `bbac67ce` after dedup (task `1af85afd`, Done, covers only the data-side bump step of 17 composites, not the service-created satellites); (iii) the timezone of the stamp — `DateFormatter.toLocalTimestamp(clock.now())` exactly as `stampUpdatedAt` writes it (the TZ-source unification `6ffac10e` part 1 is deferred to an RFC by the founder's decision of 2026-09-17).

## Statement (Gherkin)

```gherkin
Given an existing asset whose frontmatter carries exo__Asset_updatedAt "2020-01-01T00:00:00"
When a service_call grounding whose service writes the asset (e.g. `apply set-planned-start … --input '{"value":"2026-07-25T09:00:00"}'`, `apply plan-for-evening`, `apply clean-properties`) runs
Then the service's own change is on disk
  And exo__Asset_updatedAt is no longer "2020-01-01T00:00:00" and has the local-timestamp shape YYYY-MM-DDTHH:mm:ss (DateFormatter.toLocalTimestamp of the executor clock — the same form req 454ccedf stamps on a property_set write)

Given the same seeded asset
When the service writes it through ANY channel — IFileSystemWriter.updateFile, IVaultAdapter.modify, IVaultAdapter.process — not only the executor's own fileWriter
Then exo__Asset_updatedAt is stamped exactly the same way (the executor decides by comparing the target's bytes before and after `service.execute`, not by hooking a writer)

Given an asset with NO exo__Asset_updatedAt key
When a service_call service writes it
Then the key is added with the local-timestamp value

Given a service_call whose service leaves the target UNCHANGED (a no-op: clean-properties on an asset without empty properties, set-planned-start to the value already on disk)
When it is applied
Then the file is byte-identical and exo__Asset_updatedAt is NOT touched (no spurious ExoSync delta — same rule as req 454ccedf and remove-property "bumps only when a change occurs")

Given a service_call whose service creates a SATELLITE asset and does not write the target (create-note / duplicate-asset / create-related-task shape)
When it is applied
Then the target is byte-identical and the executor writes nothing to the satellite (the create side of the invariant is not this requirement's)

Given a service_call whose service rewrites the target AND renames it to `<same folder>/<exo__Asset_uid>.md` (rename-to-uid: UUID-canon)
When it is applied
Then exo__Asset_updatedAt is stamped on the file at its NEW path (the executor re-locates the target by the exo__Asset_uid it read before the call); the old path no longer exists

Given a service_call whose service only MOVES the target to another folder without changing its content (repair-folder)
When it is applied
Then no file is written by the executor (nothing changed, nothing to stamp)

Given a service_call whose service is told to write exo__Asset_updatedAt itself (updateProperty / removeProperty with property = exo__Asset_updatedAt)
When it is applied
Then the file carries exactly ONE exo__Asset_updatedAt key holding the value the service wrote (the executor does not write a second stamp — same rule as the composite step 49e00287 under req 454ccedf)

Given a service_call whose service THROWS
When it is applied
Then the result is { success: false } and the executor stamps nothing (the stamp lives strictly on the success path after `service.execute` returned); a failure while re-reading or writing the stamp is likewise { success: false } with the error named — never a silent half-stamp

Given a composite grounding with a service_call step followed by the explicit "Bump updatedAt" step 49e00287 (`$nowLocal`)
When the composite runs
Then the file carries exactly ONE exo__Asset_updatedAt key

Given a composite whose service_call step opted into exocmd__Grounding_targetsCreatedInstance (Issue #4046) and whose service mutates the just-created instance
When the composite runs
Then the stamp lands on the created instance's file and the click-target is byte-identical
```
