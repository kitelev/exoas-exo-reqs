# req(exo): TBox declares the two goal↔requirement traceability edges (onto-RFC f52be424, G1 Phase 1)

## Job Story

When I (or the autonomous dev-loop) want to record that a strategic initiative refines a
parent initiative, or that a requirement realizes a strategic goal, I want those edges to be
**authorable through the sanctioned CLI mutation path and range-validated by SHACL** — instead
of being rejected as unknown property names and living only in label numbering (`I1` → `I1.4`)
— so that the strategy graph and the requirements graph stop being disconnected islands and a
single property-path query can trace "why does this work exist" up to the Vision layer.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: the TBox declares strategy↔requirement refinement edges

  Background:
    Given a vault mounting the `strategy` ontology (exoas-public) and the `req` ontology (exoas-req)
      And the exocortex-cli property-name guard is active (req c616a289 / 40a9a81b)

  Scenario: an initiative-refinement edge is authorable
    When I run `set-property <an-initiative> --property strategy__Initiative_refines --value "[[<parent-initiative-uid>]]"`
    Then the command does not reject the property name as unknown
      And the property is written as a wikilink to the parent initiative

  Scenario: a requirement→goal edge is authorable
    When I run `set-property <a-requirement> --property req__Requirement_realizesGoal --value "[[<initiative-uid>]]"`
    Then the command does not reject the property name as unknown
      And the property is written as a wikilink to the initiative

  Scenario: both edges are declared as object properties with the RFC-fixed domain and range
    Then `strategy__Initiative_refines` has domain `strategy__Initiative` and range `strategy__Initiative`
      And `req__Requirement_realizesGoal` has domain `req__Requirement` and range `strategy__Initiative`
      And both carry `exo__Instance_class = exo__ObjectProperty`
      And both are co-located in their ontology folder by `exo__Asset_isDefinedBy` ($strategy / $req)

  Scenario: the edges are 0..N (a DAG, never required)
    Then both declare `exo__Property_cardinality = Multiple`
      And neither declares `exo__Property_minCount`
      And an asset WITHOUT the edge is not a SHACL violation

  Scenario: CQ1 and CQ3 become expressible
    Then `?req req:Requirement_realizesGoal <goal-file-IRI>` is a valid, resolvable pattern (CQ1)
      And `?init strategy:Initiative_refines+ <root-file-IRI>` is a valid, resolvable pattern (CQ3)
      And both legitimately return zero rows until Phase-2 backfill authors the edges

  Scenario: no regression
    Then vault-exodev SHACL `--shapes-mode` reports zero NEW violations versus the pre-change baseline
      And the `exoas-public` and `exoas-req` assetspace CI stays green
```

## Revert-verify

Empirically captured on the real vault, both directions:

- **RED (before)** — with the two property definitions absent, the sanctioned mutation path
  refuses both names: `set-property … --property strategy__Initiative_refines` and
  `… --property req__Requirement_realizesGoal` each exit **2** with
  `UnknownPropertyError: Unknown property '<name>' — not in the mounted TBox`, offering
  fuzzy-suggestions (`strategy__Initiative_horizon`, `req__Requirement_refines`). The edges
  are literally unauthorable.
- **GREEN (after)** — with the definitions created and mounted, the same two commands are
  accepted (`--dry-run` previews the property) and SHACL reports zero new violations.

Deleting either definition reverts its own axis to RED independently (each name is validated
against the mounted TBox separately), so neither assertion is vacuous.

## Verification surface (why this requirement is not flipped to Active)

This deliverable is **pure TBox vault-data in `exoas-public` + `exoas-req`** — there is no
`exocortex` code change, and `exocortex` does not pin those two assetspaces as submodules
(only `exoas-exo`, `exoas-exocmd`, `exoas-exo-reqs`). Therefore **no faithful `@req:<uid>` jest
binding can exist** in the exocortex repo: any such test would have to hand-author its own
fixture TBox and would pass whether or not the real definitions shipped (false-positive
coverage). Per the always-on active-requirement gate, flipping this requirement to `active`
without a binding would mark it an orphan and red `requirements-trace` for **every** exocortex
PR (whole-repo blast radius).

The requirement therefore stays **`approved`**, and its standing verification surface is:

1. the `assetspace-ci.yml` reusable CI of `exoas-public` and `exoas-req` (SHACL + co-location
   + ontology-membership), which gates the definitions on every push, and
2. the `exocortex-cli` property-name guard, which is the executable RED/GREEN oracle recorded
   above.

The absence of a binding tier for pure-TBox-data requirements is a genuine gap in the SDD
model (the `req__RequirementBindingClass` enum offers only unit / component / integration /
e2e / gui-bdd / ui-acceptance) — surfaced as a follow-up observation, out of scope here.
