## Job story

When an Exocortex asset is archived, I want the archive flag to live under a TBox-declared property (`exo__Asset_archived`, `exo__DatatypeProperty`, boolean, domain `exo__Asset`) instead of the bare Obsidian-style `archived:` key, so that the flag is homoiconic (declared, validatable, queryable by its own name) while every existing bare carrier keeps working until it is migrated.

## Context

- Source: ticket `da0f73a3-dffa-4dfc-9579-090131d05724` (S7, umbrella `b255aa55`), founder decision 2026-09-15 (interview 2026-09-14/15): declare `exo__Asset_archived` and migrate carriers; readers accept BOTH forms during the transition; writers emit ONLY the new form. Approved for implementation by ORCH `main-35699` mandate at the S7 plan-gate (2026-09-15, decision `63066ddb`).
- Mechanism measured 2026-09-15: the bare key `archived: true` is indexed as `exo:Asset_archived "true"` (issue #3043 whitelist), so the graph predicate never changes; all five exocmd preconditions that gate archive/un-archive commands already test `exo:Asset_archived "true"` and see both forms by construction.
- `exo__Asset_isArchived` (code-side alias, 0 data carriers, stub `7f632d25`) stays a READ-ONLY compatibility alias; no writer emits it.

## Scenarios

### Scenario A — legacy bare key is still READ and indexed
Given an asset whose frontmatter carries the legacy bare key `archived: true`
When the vault is indexed (`NoteToRDFConverter`)
Then the triple `<asset> exo:Asset_archived "true"` is emitted
And `MetadataHelpers.isAssetArchived(frontmatter)` returns `true`.

### Scenario B — the declared key is READ and indexed identically
Given an asset whose frontmatter carries `exo__Asset_archived: true`
When the vault is indexed
Then the same triple `<asset> exo:Asset_archived "true"` is emitted (byte-identical predicate and literal to Scenario A)
And `MetadataHelpers.isAssetArchived(frontmatter)` returns `true`
And `canonicalYamlKey("exo__Asset_archived")` returns `"exo__Asset_archived"` (NOT the bare key).

### Scenario C — writers emit ONLY the declared key and drop the bare one
Given an asset (with or without a pre-existing bare `archived: true`)
When it is archived through `ArchiveAssetService.archiveAsset`, the CLI `archive` executor (`StatusCommandExecutor`), the batch `archive` operation, or a grounding `property_set` whose `targetProperty` is `archived` or `exo__Asset_archived`
Then the frontmatter carries `exo__Asset_archived: true`
And it carries NO bare `archived` key (a pre-existing bare key is removed by the same write)
And `canonicalYamlKey("archived")` returns `"exo__Asset_archived"` (bare-keyed writers are upgraded, never downgraded).

### Scenario D — removing the flag clears BOTH forms
Given an asset carrying the legacy bare `archived: true` (and/or `exo__Asset_archived: true`)
When `FrontmatterService.removeProperty(content, "exo__Asset_archived")` runs (the `un-archive` grounding `property_delete` path)
Then neither `exo__Asset_archived` nor bare `archived` remains in the frontmatter.

### Scenario E — maintenance migration verb
Given an asset carrying the legacy bare `archived: true`
When `exocortex-cli repair-frontmatter <path> --canonicalize-keys` runs
Then the key is rewritten to `exo__Asset_archived: true` (value preserved), the bare key is gone, `exo__Asset_updatedAt` is bumped
And running it again is a no-op (idempotent; exit 0, no diff)
And `--dry-run` prints the diff without writing.

### Scenario F — TBox declaration and schema lint
Given the `exoas-exo` TBox declares `exo__Asset_archived` (`exo__DatatypeProperty`, domain `exo__Asset`, cardinality Single)
When `validate schema` (legacy lint) runs on a vault carrying `exo__Asset_archived: true`
Then no "Property is not declared in the ontology" issue is reported for it
And the bare `archived` key stays whitelisted (`NON_ONTOLOGY_KEYS`) for the transition period.

### Scenario G — graph-side archived filter reads the real predicate
Given a graph node whose subject carries `exo:Asset_archived "true"`
When `GraphQueryService` loads nodes without `includeArchived`
Then the node is filtered out (the service reads `exo:Asset_archived`, not only the never-emitted `exo:Asset_isArchived`).

## Non-goals

- `draft`, `pinned`, `aliases` remain bare canonical keys (unchanged whitelist entries).
- `exo__Asset_isArchived` is not removed from readers (read-only alias); no writer emits it; the stub `7f632d25` is retyped as `exo__DeprecatedProperty` → use instead `exo__Asset_archived`.
- The data migration of the ~1270 existing carriers (three vaults, eight repos) is Phase B of ticket `da0f73a3` — it uses Scenario E on a released CLI and is not part of this requirement's code change.
- exocmd preconditions are not rewritten (they already test `exo:Asset_archived`).
