# req(exo): a frontmatter writer refuses an EMPTY LIST and a NULL value, not only the empty string

## Job Story

When I mean to **clear** a property and reach for the tool I already use for writing one, I want
every writer of that key to tell me that clearing has its own command — so that I don't end up
with a bare `prop:` (or `prop: null`) that looks like a successful clear but is a junk key nobody
asked for, and so that an existing value is never silently destroyed by it.

## Statement (Gherkin)

```gherkin
Given an existing asset that does NOT carry `youtube__Video_description`
When I run `cli set-property <path> --input '{"property":"youtube__Video_description","value":[]}'`
Then the command fails with a non-zero exit code
And the error names `remove-property` as the way to delete a property
And the asset file is left BYTE-IDENTICAL (no bare `youtube__Video_description:` key, no updatedAt bump)

Given an existing asset that DOES carry `youtube__Video_channel: "Existing channel"`
When I run `cli set-property <path> --input '{"property":"youtube__Video_channel","value":[]}'`
Then the command fails the same way
And the existing value is left untouched (the guard did not destroy it)

Given the `updateProperty` service_call grounding and a `value` of `[]`
When it runs
Then it throws, names the property and the clearing path, and writes NOTHING

Given the same grounding and a `value` of `null`
Then it throws the same way and writes NOTHING

Given the `updateProperty` service_call grounding and a value of `["a","b"]`
When it runs
Then the property is written as a YAML sequence with both items (the guard refuses only the EMPTY list)

Given `cli set-property <path> --input '{"property":"p","value":["a","b"]}'`
Then the property is written as a YAML sequence with both items

Given an existing asset
When I run `cli set-property <path> --property exo__DisplayNameSpec_separator --value " "`
Then the command succeeds (a WHITESPACE-ONLY value stays legitimate — req 501cdf2c §Границы)

Given an asset carrying an already-empty property
When the `cleanProperties` service_call runs
Then it still REMOVES that property (the repair path is unaffected: it deletes, it never writes)
```

## Почему это НОВЫЙ req, а не расширение `501cdf2c`

Активный `501cdf2c` («set-property rejects an EMPTY value instead of silently writing `prop: ""`»)
**явно вывел эти два входа из своего scope** — §«Что гвард НЕ трогает»:

| вход | что там написано |
|---|---|
| `--input {"value":[]}` | «⛔ **ВНЕ scope этого req**: пустой список — осмысленная форма, 65 живых носителей … Round-trip `[] → null` — самостоятельный вопрос, здесь НЕ решается» |
| `--input {"value":null}` | «❌ уже fail-loud … оставить как есть, гвард не нужен» |

⇒ по дискриминатору `/feature-sdd` Step 0 (§inverse tell) это **поведение, которое активный req
осознанно исключил**, а не приведение кода к уже данному обещанию ⇒ **новый sibling req**.
Статус `501cdf2c` не меняется: его клаузы про `""` остаются в силе; клауза про `[]` помечена
`SUPERSEDED by <этот uid> (2026-10-03)` в том же заходе, с причиной (замер ниже).

| писатель | `value: []` | `value: null` |

| **2. `executePropertySet` / `executePropertyAppend`** | — **недостижимо ПО ТИПУ** (`substitutedValue: string`, `resolvedValue: string`) | — то же |
| **3. `createUpdatePropertyService`** | ⛔ **ПРИНИМАЕТ** → bare `key:` | ⛔ **ПРИНИМАЕТ** → `key: null` |

⛔ **Таблица issue #4516 («все три писателя принимают оба входа») опровергнута в 3 из 6 клеток.**
Deliverable — **2 гварда в 2 писателях**, а не 3 × 2. Писателя 2 гвард НЕ получает: его значение
строкового типа, поэтому ветви `[]`/`null` там были бы **тождественно мертвы**, а ось на них —
вакуумна (`/feature-sdd` Step 0, третий дискриминатор).

### Что РЕАЛЬНО читают читатели (замер тем же прогоном)

| форма на диске | js-yaml (читатель Obsidian) | `FrontmatterService.parseObject` (путь CLI/загрузчика) |
|---|---|---|
| bare `key:` ← пишет `[]` | `null` | `[]` |
| `key: null` ← пишет `null` | `null` | **строка `"null"`** |
| `key: ""` ← закрыто #4513 | `""` | `"\"\""` |
| `key: done` (контроль) | `"done"` | `"done"` |

⛤ Это **сильнее**, чем формулировка issue («оба читаются как `null`»): у `value: null` путь
загрузчика **фабрикует литерал `"null"`**, то есть создаёт в графе значение, которого никто не
писал. Для ref-свойства это dangling-литерал вместо ребра.

## ENUMERATE-FIRST — есть ли ЗАКОННЫЙ пустой список? (мандат issue §Technical Notes)

Сплошной разбор frontmatter трёх каноничных vault, 2026-10-03: **55 429 файлов / 572 162 ключа**
— на монтировании состояния **после `exosync pull` 23:52** (`pulled 15`, карантин 0).
⛤ Замер снят ДВАЖДЫ, до и после этого pull: пред-pull монтирование дало 55 428 / 572 151, и **все
решающие числа ниже совпали побайтно** — вывод к дрейфу монтирования не чувствителен.
⛔ `# dogfood-fallback`: пустое значение **не порождает ни одного трипла по построению** (загрузчик
либо пропускает ассет, либо опускает ключ), поэтому SPARQL эту популяцию не видит вовсе; req
`501cdf2c` мерил так же.

| форма | носителей | топ |
|---|---|---|
| `key: ""` | **0** | — (4 ассета `exoas-period` вылечены оркестратором 2026-10-02) |
| `key: null` | **0** | — |
| `key: []` | **0** | — |
| bare `key:` | **82** | `aliases` 30 · `exo__Asset_relates` 29 · `concept__Concept_related` 15 · `exocmd__Grounding_propertyDefault` 3 · `exo__Class_superClass` 3 · `exo__Ontology_imports` 1 · `req__Requirement_implementedBy` 1 |
| `key: " "` (значимо-пробельное) | 22 | `exo__DisplayNameSpec_separator` 13 · `exo__PrintedLiteral_literal` 9 |

⇒ **Законного пустого списка у НАШИХ писателей нет, и это следует из МЕХАНИЗМА, а не из счёта:**
`PropertyCleanupService.isEmptyValue` (`packages/core/src/services/PropertyCleanupService.ts:125`)
возвращает `true` для `""`, `null`, `"undefined"`, `[]`, `{}` и пустого значения — то есть
**продукт сам объявляет пустой список мусором** и удаляет его командой `apply clean-properties`.
Писатель, принимающий `[]`, создаёт то, что сосед по продукту немедленно сносит.

⛤ 82 носителя bare-ключа — **состояние на диске**, а не доказательство, что писатель обязан уметь
его произвести: Obsidian пишет bare `aliases:`, когда пользователь опустошает список в UI, и
**этот** путь гвард не трогает (гвард живёт в наших писателях). Решение фаундера #4274
(2026-09-26) — «ремонт данных + видимость, **загрузчик НЕ меняем**» — остаётся в силе: уже
созданное лечится данными, а этот req останавливает **приток**.

⚠ Клауза `501cdf2c` «пустой список — осмысленная форма, 65 живых носителей» мерила **ту же
популяцию bare-ключей на диске** и из неё выводила законность **записи**. Переход неверен; число
верно. Отсюда `SUPERSEDED`-пометка, а не правка числа.

## Границы предиката

**Предикат — `value === "" || value === null || (Array.isArray(value) && value.length === 0)`.**

- ⛔ **НЕ `trim()`** — 22 живых значимо-пробельных носителя (`501cdf2c` §Границы); сохраняется как есть.
- ⛔ **НЕ «любой массив»** — непустой массив есть законная multi-value запись, замерена рабочей
  (`["a","b"]` → `key:` + два `- ` элемента). Отвергается **только** пустой.
- ⛔ **НЕ `{}`** — пустой объект уже отвергнут у писателя 1 (`assertScalarOrScalarArray`: `not object`);
  у писателя 3 он пишет `[object Object]` — **отдельный дефект другого класса** (тихая порча, не
  «похоже на очистку»), выведен в Non-goals.
- ✅ Предикат живёт **одним определением** в `packages/core/src/utilities/yamlScalar.ts` (там же
  `isUnquotedWikilink`, вынесенный #4520 ровно за этим) и экспортируется из barrel: он нужен
  двум писателям, и разъехаться они не должны.

## Non-goals (названо, чтобы следующий читатель не прочёл как недоработку)

1. **Загрузчик не меняется** — решение фаундера #4274 (2026-09-26), вариант 1.
2. **`executePropertySet` / `executePropertyAppend` гварда не получают** — `[]`/`null` до них не
   доходят по типу; ветвь была бы мёртвой, ось — вакуумной.
3. **`value: {}` у писателя 3** (пишет `[object Object]`) — другой класс, отдельный тикет.
4. **Ремонт уже существующих носителей — ЧУЖОЙ предмет, и множества РАЗНЫЕ.** Предмет этого req —
   **ЗАПИСЬ** (остановить приток); уже созданное закрывает решение фаундера #4274 («ремонт данных
   по факту») плюс детектор `vault-loader-skip-detect.py`. ⛔ Это **не** те же 82: детектор ловит
   подмножество, которое загрузчик отвергает **целиком** (на 2026-10-03 — 2 файла, оба
   `Instance_class missing`), а 82 bare-ключа загрузчик в основном **терпит**. Пересечение
   множеств не ноль только у single-value свойств (`ems__Effort_parent`, см. таблицу притока).
5. **`PropertyCleanupService.removeEmptyPropertiesFromContent`** использует
   `content.replace(re, \`---\n${cleaned}\n---\`)` — data-bearing строка во втором аргументе
   `String.replace` (`$&` / `$\`` в значении исказят файл). Пред-существующий дефект, отдельный тикет.

## Homoiconicity Gate (профиль `/onto-rfc`, Phase 0)

- **Q1 — user-configurable семантика?** **НЕТ.** «Пустое значение отвергается» — валидация ввода
  примитива мутации, а не поведение домена, которое пользователь меняет ассетами.
- **Q2 — новый класс артефактов?** Неприменим (Q1 = нет). Ни `exo__Class`, ни `exo__Property` не
  вводятся, новых SPARQL-вопросов не появляется ⇒ это не onto-RFC.
- **Q3 — под какое исключение попадает TS-реализация?** **(в) инфраструктурные guard rails**:
  правило обеспечивает корректность СТРУКТУРЫ графа (мусорный ключ в него не попадает), а не
  описывает домен пользователя.
