# req(exo): the `updateProperty` service_call refuses a NON-SCALAR value instead of writing the literal `[object Object]`

## Job Story

When a grounding (or `apply … --input`) hands a writer a value that is not a scalar, I want the
write refused with a message that says the word CORRUPTION — so that I never end up with
`ems__Effort_area: [object Object]` where my data used to be, and so that I am not sent to diagnose
a "cleared property" when nothing was cleared.

## Statement (Gherkin)

```gherkin
Given the `updateProperty` service_call grounding and a `value` of `{}`
When it runs
Then it throws, the message names the property AND the corruption (not clearing), and it writes NOTHING

Given the same grounding, an asset that ALREADY carries `ems__Effort_result: done`, and a `value` of `{"a":1}`
When it runs
Then it throws the same way and the existing value is left BYTE-IDENTICAL (the guard did not destroy it)

Given a `value` of `["a", {}]` — an array with a non-scalar element
When it runs
Then it throws and writes NOTHING (the item would have been written as `- [object Object]`)

Given a `value` of `[[1]]` — a nested array
When it runs
Then it throws and writes NOTHING (the nested list would have been FLATTENED to `- 1`)

Given a `value` of `["alpha","beta"]`
When it runs
Then the property is still written as a YAML sequence with both items (control — the populated-array path must not regress)

Given a `value` of `"plain"`, `5` or `true`
When it runs
Then the property is still written (control — every scalar form is unaffected)

Given a `value` of `""`, `[]` or `null`
When it runs
Then the refusal messages of req `501cdf2c` (#4513) and req `5d2c7ede` (#4516) are UNCHANGED
(control — the empty-value class keeps its own wording, which names CLEARING, not corruption)
```

## Почему это НОВЫЙ req, а не расширение `5d2c7ede`

Активный `5d2c7ede` (#4516) **сам вывел этот вход из своего scope** — его §Non-goals п. 3 дословно:

> **`value: {}` у писателя 3** (пишет `[object Object]`) — другой класс, отдельный тикет.

И §Границы предиката там же: «⛔ **НЕ `{}`** … у писателя 3 он пишет `[object Object]` — **отдельный
дефект другого класса** (тихая порча, не «похоже на очистку»), выведен в Non-goals».

⇒ по дискриминатору `/feature-sdd` Step 0 (§inverse tell) это **поведение, которое активный req
осознанно исключил**, а не приведение кода к уже данному обещанию ⇒ **новый sibling req**. Статус
`5d2c7ede` не меняется, его клаузы остаются в силе: ПРЕДИКАТЫ не пересекаются (`emptyPropertyValueForm`
судит `""`/`[]`/`null`, этот — не-скаляр), а СООБЩЕНИЯ обязаны расходиться, иначе отказ скажет
неправду: `[object Object]` на «очищенное свойство» не похож, он похож на порчу.

## ЗАМЕР ПОВЕДЕНИЯ — origin/main `cbff7ef5`, 2026-10-03 (сделан ДО формулировки)

Прогон через настоящие `createUpdatePropertyService` + настоящий `FrontmatterService`, байты
прочитаны обратно (jest, `packages/cli/jest.config.js` — он резолвит services в SOURCE):

| `value` | записанная строка | `FrontmatterService.parseObject` читает |
|---|---|---|
| `{}` | `ems__Effort_area: [object Object]` | `["object Object"]` |
| `{a:1}` | `ems__Effort_area: [object Object]` | `["object Object"]` |
| `[{}]` | `ems__Effort_area:` + `  - [object Object]` | `["[object Object]"]` |
| `["a",{}]` | `  - a` + `  - [object Object]` | `["a","[object Object]"]` |
| `[[1]]` | `  - 1` | `["1"]` |
| `"plain"` (контроль) | `ems__Effort_area: plain` | `"plain"` |
| `5` (контроль) | `ems__Effort_area: 5` | `"5"` |
| `true` (контроль) | `ems__Effort_area: true` | `"true"` |
| `["alpha","beta"]` (контроль) | `  - alpha` + `  - beta` | `["alpha","beta"]` |

⛤ **Замер даёт ТРИ факта сверх формулировки issue:**

1. **Данные исчезают ПОЛНОСТЬЮ, а не искажаются.** `{}` и `{a:1}` пишут одну и ту же строку:
   содержимое объекта не сериализуется вовсе, оно теряется.
2. **Читатель видит МАССИВ там, где записан скаляр.** `[object Object]` начинается с `[`, поэтому
   `parseObject` разбирает его как flow-sequence и отдаёт `["object Object"]` — то есть ломается не
   только значение, но и ЕГО ФОРМА (скаляр → список).
3. **Класс ШИРЕ `[object Object]`: вложенный массив СХЛОПЫВАЕТСЯ.** `[[1]]` пишется как `- 1`
   (`String([1])` === `"1"`), структура теряется молча и без всякого `[object Object]` в файле.
   ⇒ предикат обязан судить «скаляр или массив скаляров», а не искать подстроку `[object Object]`.

### На СУЩЕСТВУЮЩЕМ свойстве это ПОТЕРЯ ДАННЫХ, а не лишний ключ

Тот же прогон с `ems__Effort_result: done` в исходном frontmatter и `value: {}`:

| до | после |
|---|---|
| `ems__Effort_result: done` | `ems__Effort_result: [object Object]` |

⇒ реальное значение уничтожено. Это тот же вид ущерба, который req `5d2c7ede` замерил для `[]`
(`"Existing channel"` → `null`), и он подтверждает, что отказ обязан быть **до** записи, а не после.

## Достижимость входа — живая поверхность названа

`{}` выражается на боевом пути: `apply.ts` парсит `--input` через `JSON.parse` и требует лишь, чтобы
**верхний уровень** был объектом (`typeof parsed !== "object" || parsed === null || Array.isArray(parsed)`
⇒ отказ) — значения внутри не типизируются вовсе. То есть
`exocortex-cli apply set-result <path> --input '{"value":{}}'` доходит до фабрики как `value = {}`.
Плюс любой программный вызов фабрики (плагин, composite-grounding) не ограничен типом: `UserInput.value`
объявлен как `unknown`.

⛤ **Авторские грундинги сами по себе `{}` не породят** — 8 носителей `serviceId: updateProperty`
пинят только `property`, значение приходит из пользовательского ввода (замер req `5d2c7ede`,
2026-10-02). Но это аргумент за гвард, а не против: ввод — именно та сторона, которую фабрика не
контролирует, и JSON-поверхность делает не-скаляр выразимым одним символом.

## Границы предиката

**Предикат — «скаляр ИЛИ массив скаляров»**, скаляр = `string | number | boolean`:

- ⛔ **НЕ поиск подстроки `[object Object]`** в сериализованном результате: вложенный массив
  схлопывается БЕЗ этой подстроки (замер выше, строка `[[1]]`), то есть такой предикат пропустил бы
  часть класса.
- ⛔ **НЕ «любой массив»** — непустой массив скаляров есть законная multi-value запись, замерена
  рабочей; отвергается только массив с не-скалярным элементом.
- ⛔ **`null` НЕ судится этим предикатом** — он уже отвергнут ВЫШЕ (`emptyPropertyValueForm`,
  req `5d2c7ede`) со своим, более точным сообщением про очистку. Ветвь `null` в новом предикате была
  бы недостижима на этом пути — ровно та зеркальная ситуация, что `5d2c7ede` задокументировал для
  писателя 1. ⇒ порядок гвардов ЗНАЧИМ и проверяется контрольными осями.
- ✅ **Предикат живёт ЛОКАЛЬНО в `packages/services/src/grounding-service-factories.ts`, а не в
  `yamlScalar.ts`.** Это выбор, а не недосмотр: у писателя 1 своя копия (`assertScalarOrScalarArray`)
  с ДРУГИМ сообщением и ДРУГИМ порядком относительно empty-предиката, и его сообщение пинится
  контролями двух активных req. Общим был бы только `typeof`-классификатор (три строки), а
  расходится всё остальное — поверхность (`--input.value` против `userInput` грундинга), формулировка
  (аргумент-контракт против порчи данных) и позиция в цепочке. ⇒ вынос в core создал бы третьего
  владельца решения «что такое скаляр» без единого потребителя, которому нужна ровно та же пара
  предикат+сообщение.

## Non-goals (названо, чтобы следующий читатель не прочёл как недоработку)

1. **`cli set-property` не меняется** — он уже отвергает не-скаляр; его формулировка пинится
   контролями `501cdf2c`/`5d2c7ede`, и менять её под это требование значило бы ломать их оси.
2. **`executePropertySet` / `executePropertyAppend` гварда не получают** — не-скаляр до них не
   доходит по типу (ветвь мертва, ось вакуумна).
3. **Ремонт уже записанных `[object Object]` — не предмет этого req.** Предмет — ЗАПИСЬ (остановить
   приток). Существующие носители лечатся данными (`set-property` / `remove-property`); отдельный
   замер их популяции в этот req не входит.
4. **`PropertyCleanupService.removeEmptyPropertiesFromContent`** (`content.replace` с data-bearing
   строкой) — пред-существующий дефект ДРУГОГО класса (порча при РЕМОНТЕ), issue #4528, свой req.
5. **Форма сообщения у писателя 1 не унифицируется** — см. §Границы предиката, последний пункт.

- **Q2 — новый класс артефактов?** Неприменим (Q1 = нет): ни `exo__Class`, ни `exo__Property` не
