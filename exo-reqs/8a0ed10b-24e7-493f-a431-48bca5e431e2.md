# req(exo): a query by a property sees the values of its sub-properties

## Job Story

When I record the source of an exoization idea through a typed sub-property (`exoization-ideas__ExoizationIdea_video` / `_book` / `_article`, each declared `exo__Property_superProperty` → `exoization-ideas__ExoizationIdea_exoizable`), I want `?idea eideas:ExoizationIdea_exoizable ?src` to find it — the way a class query finds the instances of its subclasses — so that CQ6 is written with one branch, not a UNION that joins by label.

## Context

- RFC `14217015` (Approved 2026-10-10), decision №7: «доработать движок — запрос по свойству видит его подсвойства, как у классов». §Q3 third engine defect: no inference over `exo__Property_superProperty` anywhere (`RDFVocabularyMapper` only mirrors the edge as `rdfs:subPropertyOf`; `RDFSInferenceEngine` walks classes only). CQ6 notes: before the fix, the simple form finds 2 of 4.
- The seam: a frontmatter key `prefix__Local` is emitted as the SYMBOLIC predicate IRI, while the declaration keys on the property's FILE IRI. A `prefix__Local` `exo__Asset_label` is emitted as that same symbolic IRI (CQ6 note «метка prefix__Local эмитится тем же символьным IRI, что и предикат»), which is the bridge.
- Precedent: `ClassHierarchyResolvingStore` (query-time, zero store growth, store-scoped count-invalidated index).

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: a triple pattern by a property also matches its sub-properties

  Background:
    Given properties _exoizable, _video, _book, _article of exoization-ideas
    And _video, _book, _article each declare exo__Property_superProperty -> _exoizable (bare-UID wikilink)
    And four ideas: one records its source through _exoizable, one through each sub-property

    When "SELECT ?idea ?src WHERE { ?idea exo:Instance_class eideas:ExoizationIdea . ?idea eideas:ExoizationIdea_exoizable ?src }" runs
    Then it returns the four (idea, source) pairs
    # with resolvePropertyHierarchy:false it returns 1 of 4 (SP9 — the flip)

  Scenario: SP2 — sub-properties are transitive
    Given _youtubeVideo -> _video -> _exoizable
    Then an idea recorded through _youtubeVideo is found by _exoizable and by _video

  Scenario: SP3 — widening goes down only
    Then a query by _youtubeVideo or by _book does not return values of its parent or siblings

  Scenario: SP4 — set semantics

    Then each pair is returned once
```

## Non-goals

- `GRAPH { … }` patterns (`matchInGraph`) and a variable predicate (unbound, or bound by an earlier pattern — `BGPExecutor` matches it through `matchExactPredicate`) are not widened.
- A reified `exo__Statement` adapter whose `_predicate` is a LABEL-form wikilink (`[[exo__Property_superProperty]]`) materializes a file-IRI predicate and is not read as a declaration; the canonical bare-UID form is (review L3).
- Latent: if `exo:Class_superClass` is ever declared a sub-property of an exocortex predicate P, a query by P with an ambiguous symbolic subject would raise `SymbolicClassAmbiguityError` through the class bridge; no such declaration exists (review L4).
- SHACL: a sub-property keeps its OWN range; range is not inherited from the super-property (RFC 14217015 §2, AC2).
- The `rdfs:subPropertyOf` mirror of `RDFVocabularyMapper` is not read (it is derived from the same frontmatter); `RDFSInferenceEngine` (`index` → `--use-cache`) is untouched.
- TS consumers that call `store.match` directly (`GraphQueryService`, `getReifiedRelations`, `CommandResolver.getLinkedValue`, `LazyAssetGraphLoader`) are not routed through the executor and are unchanged.
- A walk `?p exo:Property_superProperty* X` from a SYMBOLIC property subject is not bridged to the property file (the class bridge does this for classes; no consumer needs it for properties today).
- The two-branch CQ6 form written before this requirement now returns the sub-property values TWICE (once per branch, different `?p`); CQ6 is to be written in the single-branch form.

## Behaviour change on live data

Every SPARQL query with a CONSTANT exocortex predicate that has declared sub-properties now also sees their triples (a prefix the engine does not know as W3C — `prov__`, `dcterms__` — lives under the exocortex base and is widened too). Measured 2026-10-11 (`query --no-cache`, `SELECT ?p (COUNT(?s) AS ?n) … GROUP BY ?p` against the closure of the 38 / 37 / 36 live `exo:Property_superProperty` edges; vault-exodev / vault-my / vault-tbank): `exo:Asset_relates` +2367 / +3096 / +2293, `exo:Asset_derivedAttribute` +43295 / +11438 / +8083, `ems:AreaAware_area` +291 / +447 / +408, `exo:Asset_prototype` +0 / +120 / +0, `ems:Effort_parent` +0 / +0 / +0, `prov:wasAssociatedWith` +61 / – / –, `dcterms:dateAccepted` +61 / – / – (the pmbok closure-report declarations live only in vault-exodev). Stored SPARQL (preconditions, label templates, flow criteria — a literal scan with a live canary of 18 `Effort_status` preconditions): 0 read a widened predicate except one flow criterion on `Effort_parent` (+0). Note bodies: 63 executable sparql blocks name `Effort_parent` / `Asset_prototype` / `Asset_relates` / `Effort_participants` — their before/after is recorded in the PR.

## Side effect (review round 1)

`+` / `*` / `?` paths now yield each node once also for predicates WITHOUT sub-properties (pre-existing duplicates of a reference-keyed Set, multiplied by widening; SPARQL 1.1 semantics). Touching `BGPExecutor` / `PropertyPathExecutor` paid their `no-console` debt: the literal-safety diagnostic (#2997/#3282) goes through `LoggingService.error` — same `console.error` level and message, the structured fields on the logged Error.
