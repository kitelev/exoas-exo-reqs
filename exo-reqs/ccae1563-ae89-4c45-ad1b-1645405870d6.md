The FINDING-3 mount walk (`enumerateMountFolders` in `packages/obsidian-plugin/src/infrastructure/adapters/SyncDepsFactory.ts`) is a **detection** helper: its only job is to report folders under `assetspaces/` that are mounted but not declared. It runs *inside* `collectSyncRepoSpecs`, i.e. on the sync path — so a filesystem failure while it walks must never become a sync failure.

This requirement makes that resilience property **executable**. Today it holds implicitly, guarded twice inside one function, and nothing locks it:

- **B2** — `if (!(await adapter.exists(root))) return out;` — the absent-root fast path.
- **C** — the outer `catch` that swallows any listing failure of the root.

A refactor that drops `C` (say, "the `exists` check above already covers it") turns a permission-denied `assetspaces/` — the ordinary shape on iOS sandboxes and on a folder with restricted ACLs — into a thrown error that escapes `collectSyncRepoSpecs`, taking the whole sync down with it. The AssetSpaces themselves are perfectly syncable at that moment; only the *diagnostic* walk failed.

**Why the property degrades to `[]` rather than propagating.** `mountedNotDeclared` is advisory output (a warning surface), not a correctness input: an empty list costs the user one missing hint, whereas a throw costs them the sync. The degraded value is therefore the empty list, and the sync unit derived from the declaration is still enumerated — containment, not abortion.

## Job Story

When the `assetspaces/` folder cannot be read on this device — it was never created, or the OS denies listing it — I want ExoSync to still enumerate and sync my declared AssetSpaces, so that a failure of an advisory diagnostic never costs me the sync itself.

```gherkin
Feature: the mount walk never throws into the sync path

  Background:
    Given an AssetSpace declaration carrying exo__AssetSpace_source = https://github.com/<owner>/<repo>
    And its mount path is DERIVED by AssetSpacePathDeriver as assetspaces/<owner>/<repo>

  Scenario: the mount root is absent altogether
    Given the vault has no assetspaces folder at all
    When collectSyncRepoSpecs walks the vault
    Then it returns normally rather than throwing
    And mountedNotDeclared is the empty list

  Scenario: the mount root exists but cannot be listed
    Given the assetspaces folder exists, so an existence check answers true
    But listing it fails with EACCES, as it does inside an iOS sandbox
    When collectSyncRepoSpecs walks the vault
    Then it returns normally rather than throwing
    And mountedNotDeclared is the empty list
    And the sync unit for the declared AssetSpace IS still enumerated

  Scenario: negative control — a readable mount root still reports undeclared mounts
    Given assetspaces/<owner>/<adhoc> is mounted but not declared
    And the folder can be listed
    When collectSyncRepoSpecs walks the vault
    Then mountedNotDeclared contains assetspaces/<owner>/<adhoc>
```

## Notes

- **The two guards are locked as a PAIR, and `C` additionally in isolation.** Measured by mutating a hardlink copy of `origin/main@0cc49ef2` and running the suite against it, one mutation per guard, exact-literal anchor with the replacement count asserted:

  | mutation | red before | red after |
  |---|---|---|
  | B2 alone | 0 | 0 |
  | C alone | **0** | 1 |
  | B2 + C together | 3 | 5 |

  `C alone → 0 red before` is precisely why this requirement exists rather than an extension of `@req:4eca4900-fd1f-42d2-a111-46f90a35d6f4`: the property was true but unlocked, so the checks that state it ARE its specification (`/feature-sdd` Step 0, addendum 2026-08-06).

- **`B2` is a pure fast path and has no isolable behaviour** — `C` covers the very same input — so it can only be locked as a pair. Zero-red-alone means the contract is held twice, **not** that it is untested; neither guard may be deleted as "uncovered" (`integration-test-revert-verify` §ДУБЛИРУЮЩИЕ гварды).

- **The pair was locked only INCIDENTALLY before PR #4035** — by three checks whose subject is something else entirely ("skips non-GitHub sources", "warns on a FileSpace without a source", "excludes AssetSpaces whose mount folder is absent"), each green merely because its fixture happens to omit `assetspaces/`. Adding that folder to any of them would have unlocked the pair silently. The absent-root check exists to state the contract by NAME on a fixture whose root-absence is deliberate rather than incidental.

- **Scope.** This requirement covers the plugin's mount walk only. `collectVaultSpecs` (CLI, `packages/cli/src/commands/exosync-parity.ts`) has no FINDING-3 reporter, so there is no sibling guard to lock there. The per-owner inner `catch` (one unreadable owner directory is skipped while the remaining owners are still reported) is a third, narrower guard not covered by these scenarios.

- **Scenario 3 (the negative control) is covered but deliberately UNBOUND.** It is asserted by the pre-existing check `"flags a mounted folder that has no AssetSpace descriptor (FINDING-3)"`, which walks a readable root and asserts `mountedNotDeclared` is non-empty. That check's own subject is FINDING-3 *positive* reporting — a different contract — and it merely also serves as this requirement's non-vacuity control: without it, an implementation that returned `[]` unconditionally would satisfy the other two scenarios. It is therefore left untagged rather than double-bound to a second requirement, and `req__Requirement_covers` lists exactly the **two** bound scenarios. The prose Gherkin's third scenario documents why the pair is not vacuous; it is not a claim of binding. Raised as MEDIUM by `code-reviewer` on PR #4037 and resolved this way deliberately.

- **Binding class.** `unit` — the production-shape `InMemoryAdapter` stands in for the platform boundary, and the unlistable-root case is expressed by an adapter subclass whose `list` denies the subtree while `exists` still answers (exactly what keeps the B2 fast path from firing and lets the declared AssetSpace pass its own materialization gate).

- **Approval provenance.** The design was pre-approved by the queued ALP task `e3f061b8-475c-4054-ba7c-7e8c71663cbc`, which names the contract, both Gherkin scenarios and the binding class verbatim, leaving nothing open to choose. Per `/feature-sdd` §"Autonomous-loop (ALP) worker" that is the *task-text-names-the-design* row: the loop worker formalises the one named option and flips `proposed → approved` itself rather than escalating. No scope was expanded — the requirement states exactly the two scenarios already shipped.
