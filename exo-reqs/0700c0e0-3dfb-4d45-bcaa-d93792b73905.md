## Job Story

Когда бот или я синхронизирую vault, я хочу, чтобы кэш условных запросов не стоил больше, чем
экономит, — потому что сейчас каждый запрос к GitHub тратит ~2–3 с на перечитывание и
перезапись файла кэша, и короткий push одного репо длится 50–65 с вместо нескольких секунд.

## Замеренная мотивация (2026-10-06, клон vault личного бота, read-only прокси к GitHub)

- Store личного бота `exosync-etags.local.json` = **181 МБ**: 680 записей, из них деревья —
  207 записей / **173,6 МБ** (166 тел > 512 КБ), коммиты — 450 / 0,5 МБ, refs — 23 / ~0 МБ.
  Остальные vault: архив сообщений личного бота 99 МБ, vault-exodev 88 МБ, tbank-бот 14 МБ.
- `ConditionalRequestCache` перечитывает и парсит ВЕСЬ store на каждом `etagFor` / `bodyFor` /
  `mutate`, а `touch` и `remember` ещё и сериализуют + атомарно переписывают его целиком. На
  ответ 304 это три чтения и одна запись. Цена на этом store: чтение+парсинг ≈ 0,47 с,
  сериализация+запись ≈ 0,65 с ⇒ ~2,1 с клиентской работы на один запрос.
- Тот же суженный push (`exosync push --repo kitelev/exoas-my`, одна правка): фаза `restHead`
  **9,6 с** при трёх чтениях ref по ~0,5 с; с `--no-conditional-requests` — **2,0 с**; до первой
  записи **11,4 с против 4,9 с**. В проде бот (9 REST) тратит 49–67 с на push (тикет P22
  `01a23606`, критерий P1 — медиана ≤ 8 с).
- Деревья и коммиты адресуются по SHA и уже лежат в кэше неизменяемых объектов
  (`~/.cache/exocortex/exosync-objects`, req `086df113`), который стоит СНАРУЖИ условного
  слоя: при попадании условный запрос не строится вовсе. Тела деревьев попадают в store ETag
  только на промахе кэша объектов и дальше не читаются, пока он включён.

## Statement (Gherkin)

```gherkin
Feature: кэш условных запросов не перечитывает store и не хранит крупные тела

  Scenario: store читается с диска один раз за прогон
    Given кэш условных запросов создан над непустым store
    When через него проходит N условных запросов (304 и 200 вперемешку)
    Then чтение store с диска выполняется не более одного раза
    And каждый 304 отдаёт тело, сохранённое для своего ETag, как и раньше

  Scenario: валидатор, сохранённый в этом прогоне, виден следующему запросу сразу
    Given ответ 200 с ETag только что сохранён
    When тот же эндпоинт запрашивается снова в том же прогоне
    Then запрос уходит с If-None-Match без ожидания записи на диск

  Scenario: крупное тело не сохраняется
    Given ответ 200 с ETag, тело которого больше 64 КБ
    When кэш обрабатывает ответ
    Then запись для этого эндпоинта не создаётся
    And следующий запрос к нему уходит безусловным

  Scenario: раздутый store ужимается сам
    Given в store на диске есть записи с телами больше 64 КБ
    When кэш загружает store и затем сохраняет любую запись
    Then записанный store не содержит ни одной записи с телом больше 64 КБ
    And записи с телами не больше 64 КБ сохранены без изменений

  Scenario: поведение условных запросов не меняется
    Given сценарии требования af002ec4 (304 без траты квоты, fail-open, ETag по репозиториям)
    Then все они выполняются как прежде
```

## Non-goals

- **Порог 64 КБ — значение по умолчанию**, опция `maxBodyBytes` остаётся. Для деревьев больше
  порога при ВЫКЛЮЧЕННОМ кэше объектов чтение уйдёт безусловным (потратит primary-квоту) —
  осознанная цена: на холостом прогоне дерево не читается вовсе (неизменившийся ref отвечает 304).
- **Параллельные процессы CLI на одном vault** по-прежнему не поддерживаются (так сказано в
  `--help` команды `exosync push`); прежнее перечитывание перед записью частично сливало чужие
  записи, теперь побеждает последний писатель. Кэш не несёт корректности: потерянный
  валидатор стоит одного безусловного запроса.
- Кэш объектов (`086df113`) и `syncAll`-параллелизм не трогаются.

## Приёмка (красный исход назван)

1. Ось «одно чтение»: счётчик `io.read()` на прогоне из ≥ 5 запросов равен 1.
   ⛔ Красный: больше 1 (прежнее поведение — по чтению на каждый `etagFor`/`bodyFor`/`mutate`).
2. Оси «крупное тело не сохраняется» и «store ужимается»: записанный store не содержит тел
   больше порога. ⛔ Красный: тело больше порога записано.
3. Замер на клоне vault личного бота тем же методом (read-only прокси): фаза `restHead` того же
   суженного push отличается от прогона с `--no-conditional-requests` не больше чем на 1 с.
   ⛔ Красный: разрыв остаётся порядка 7 с.
