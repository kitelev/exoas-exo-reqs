## Job story

When several `exocortex-cli` processes run back-to-back against one large vault (a Telegram-bot turn: `exosync pull` → `query --use-cache` → `apply` → `resolve-buttons`), I want the persistent triple cache (`.exocortex/cache/triples.json`, `CacheManager`) to notice that a NESTED asset under `assetspaces/**` was added / edited / deleted since it was built and to refresh only what changed, so that the consumer stops running `index --force` (full re-parse, 20 s median / 57 s max on 16 651 files) before every turn "just to be safe", and a turn with 1–3 changed files pays roughly the cost of loading the cache, not of re-parsing the vault.

## Context

- Source: GitHub `kitelev/exocortex#4263` (mirror `ems__Task 68be3e41`). Enables #4264 (`--use-cache` + write-through for `apply` / `resolve-buttons` / `create`) — NOT in this requirement's scope.
- Mechanism (origin/main 2026-09-18): `CacheManager.isCacheValid()` compares ONLY `fs.stat(vaultPath).mtimeMs` of the vault ROOT with `metadata.vaultMtime`. A write to `assetspaces/kitelev/exoas-my/my-tasks/<uid>.md` bumps that file's mtime (and its immediate parent dir), never the root — so the cache reads as valid while it is stale. `packages/cli/src/cache/vaultSignature.ts` (#3983) already names this exact blind spot for the sibling query-result cache; the triple cache was never migrated. No file→triple provenance is persisted (`CacheData.triples` is one flat array), so a partial refresh is impossible today.
- Consumer evidence: `~/dotfiles/scripts/olya-assistant/poll_assistant.py` `build_cache()` — "`--force` is required: CacheManager validity is keyed on the vault ROOT mtime".
- Cross-file dependency of the converter (why "re-parse only the changed files" is NOT enough on its own): `NoteToRDFConverter.valueToRDFObject` emits a `⟦<uid>⟧` object as the TARGET's file-IRI when the target resolves, as the synthesized `obsidian://vault/<uid>.md` when it does not, and as a SYMBOLIC ontology IRI when the target's `exo__Asset_label` / basename is a `prefix__Name` (TBox form). So adding / removing a file changes the triples of the files that LINK to it, and changing a TBox label changes every referrer. The delta pass must re-parse referrers of added/removed files and must fall back to a full rebuild when a TBox-form asset changes.
- The `index` command materializes an INFERRED layer (RDFS `Instance_class` closure + prototype-chain inheritance, `RDFSInferenceEngine` + `PrototypeChainMaterializer`) into the same cache. That layer is derived from the whole explicit set: after a delta it must be re-materialized, not left stale and not silently dropped.

## Statement (Gherkin)

```gherkin
Feature: CLI persistent triple cache — per-file manifest validity, delta refresh, shared loader (#4263)

  Background:
    Given a vault whose .exocortex/cache/triples.json was built by CacheManager from its current state
    And the cache persists, per walked .md file, the file's mtimeMs and the triples its conversion committed
      (the same file set FileSystemVaultAdapter.getAllFiles() indexes — hidden directories skipped)

  Scenario: AC1 — a nested edit invalidates the cache although the vault root mtime is unchanged
    When a file under a nested path such as assetspaces/kitelev/exoas-my/my-tasks/<uid>.md is modified, added or deleted
    And the vault root directory's own mtime is unchanged
    Then CacheManager.isCacheValid() returns false
    And loadOrBuild() returns triples that reflect the new file state (never the stale cached triples)

  Scenario: AC2 — delta refresh re-parses only the changed files
    Given the cache is warm over N files
    When k files are modified (k small relative to N)
    And loadOrBuild() is called
    Then NoteToRDFConverter.convertNote is invoked exactly for those k files (plus their referrers, see AC4),
      NOT for all N (asserted by call count, never by wall-clock)
    And the returned triple set equals, as a set, a from-scratch full rebuild on the same post-edit state
    And the refreshed cache is persisted, so the next loadOrBuild() is a plain hit

  Scenario: AC3 — a deleted or renamed file leaves no stale triples behind
    When a file is deleted (or renamed, which the manifest sees as removed + added)
    And loadOrBuild() is called
    Then no triple whose subject is the deleted path's file-IRI remains in the result or in the persisted cache
    And for a rename the triples now carry the new path's file-IRI

  Scenario: AC4 — referrers of an added or removed link target are re-parsed
    Given file A carries "⟦<uid-of-B>⟧" while B is absent, so A's object is the synthesized obsidian://vault/<uid>.md
    When B is added and loadOrBuild() is called
    Then A is re-parsed as a referrer and its object is B's real file-IRI
    And symmetrically, when B is removed, A is re-parsed and its object returns to the synthesized form

  Scenario: AC5 — a change to a TBox-form asset falls back to a full rebuild
    When a modified, added or removed file has (or had) an exo__Asset_label / basename of the form prefix__Name
      (the form whose referrers are emitted as SYMBOLIC ontology IRIs derived from that label)
    Then loadOrBuild() performs a full convertVaultWithValidation() rebuild instead of a delta
      (so every referrer's symbolic emission is recomputed)

  Scenario: AC6 — absent, corrupt, legacy or over-threshold cache falls back to a full rebuild
    When the cache file is missing, unparseable, or written in the pre-#4263 format (metadata.vaultMtime, flat triples),
      or the file walk fails, or more than half of the manifest's files changed
    Then loadOrBuild() performs a full rebuild, exactly as before this change, and writes the new format
    And `index --force` still performs a full rebuild unconditionally

  Scenario: AC7 — the inferred layer survives a delta consistently
    Given `index` (inference on) persisted an inferred layer alongside the explicit per-file triples
    When a delta refresh runs
    Then the inferred layer is re-materialized from the merged explicit set (RDFS + prototype chain, the same engines `index` runs)
      and returned together with the explicit triples — neither stale nor dropped
    And a cache built without an inferred layer stays without one after a delta

  Scenario: AC8 — one shared loader, unchanged observable behaviour
    Given the four commands that accept --use-cache (query, classes, run-query, validate-schema)
    When they load the vault
    Then they all go through loadVaultTriples(vaultPath, { useCache }) (CacheManager.loadOrBuild when true,
      NoteToRDFConverter.convertVault when false)
    And on the same fixture the SELECT bindings of `query --use-cache` are byte-identical before and after the refactor
    And without --use-cache the full-parse path is unchanged (no cache read, no cache write)
```

## Non-goals

- `apply` / `resolve-buttons` / `create` keep their direct `convertVault()` load; wiring them to `--use-cache` + write-through is #4264.
- No cross-version migration of the old cache format: a legacy cache is treated as invalid once (one full rebuild).
- Alias edits (`aliases:`) on NON-TBox assets and name-form links to human-labelled assets are not tracked as referrer changes (UID-canon vaults link by `⟦uid⟧`).
- The query-result cache (`QueryResultCache`, `computeVaultSignature`) is untouched.
