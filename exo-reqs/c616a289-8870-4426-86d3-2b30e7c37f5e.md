# req(exo): `set-property` rejects unknown property NAMES against the mounted TBox (RFC 430e84f1 P2)

## Job Story

When an LLM agent (or a human) runs `exocortex-cli set-property <asset> --property <prefix__Name> --value <v>` on a NON-guarded property and misspells the property NAME, I want `set-property` to REJECT it with a fuzzy suggestion + machine-readable structured error (as `create` already does since P1) — instead of silently writing a dead property — so that a hallucinated property name is a structurally-impossible outcome of the `set-property` CLI path too, closing the twin of the P1 hole.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: exocortex-cli set-property validates NON-guarded property NAMES against the mounted TBox

  Background:
    Given a mounted vault whose TBox defines `concept__Concept_related` (a non-guarded property)
      And an existing target asset with an exo__Asset_uid
      And the vault has property definitions (a non-empty mounted property-name set)

  Scenario: unknown-prefix non-guarded property is rejected
    When I run `set-property <asset> --property nonExisting__Prop --value x`
    Then the command exits with a non-zero code
      And the asset is not mutated
      And the error message contains "Unknown property"

  Scenario: a real non-guarded property passes with no false-positive
    When I run `set-property <asset> --property concept__Concept_related --value "[[<valid-uid>]]"`
    Then the command exits 0 and writes the property

  Scenario: known-prefix + misspelled non-guarded name is rejected with a fuzzy suggestion
    When I run `set-property <asset> --property concept__Concept_relatedTo --value x`
    Then the command exits with a non-zero code
      And the error message contains "concept__Concept_related"

  Scenario: a GUARDED property keeps its dedicated-command refusal (name-validation does NOT change it)
    When I run `set-property <asset> --property ems__Effort_status --value x`
    Then the command exits with a non-zero code
      And the error routes to the dedicated `apply` command (not "Unknown property")

  Scenario: bare Obsidian-native YAML keys are skipped
    When set-property validates a bare key such as `aliases`
    Then property-name validation does not reject it

  Scenario: degenerate mount — no property definitions -> validation is skipped (fail-open)
    Given a vault with ZERO mounted property definitions
    When I run `set-property <asset> --property anything__Prop --value x`
    Then property-name validation is skipped (it does not reject)

  Scenario: no bot-accessible escape-hatch
    Then `set-property` exposes NO `--allow-unknown-property` (or equivalent) flag
```

## Revert-verify

Production-shape integration test (real `setPropertyCommand()` over a temp fixture vault WITH property definitions). Reverting the `propertyNameValidator.validate([property])` call in `set-property.ts` (type-preserving Edit-break) makes the unknown-prefix / misspelled-name scenarios succeed (exit 0, property written) → those assertions go RED; the no-false-positive + guarded-refusal + skip + degenerate fail-open + no-flag controls stay GREEN in both states (non-vacuity). The guarded-refusal control specifically proves the validation is placed AFTER the guard checks.

Twin of P1 req `40a9a81b-729e-4dc1-9bc1-53295515a4b2` (create; shipped v16.189.0). Reuses its `PropertyNameValidator` + `UnknownPropertyError`. P3 (commands-first + `introspect --for-mutation`) remains deferred per the RFC DAG.
