Move the AssetSpace dependency-edge kind out of a TS constant and into the graph, and turn the resulting knowledge into a **pre-mutation fail-loud refusal** instead of a post-hoc warning.

Today `packages/obsidian-plugin/src/domain/profile/closureGap.ts` hardcodes `TBOX_PROVIDER_NAMESPACES = new Set(["exo", "exocmd"])` and both `closureGap.ts` and `unmountSafety.ts` derive `providesTBox` from it. That is a homoiconicity debt (Q1: which AssetSpaces provide class definitions is user-configurable semantics — the user adds AssetSpaces, so it belongs in RDF) **and it is factually wrong**: measured 2026-08-06 across the live graph, `exoas-public` supplies class definitions to **13478** cross-boundary assets and `exoas-dec` to **2163**, versus `exocmd`'s **268** — yet both are treated as non-providers today.

**Design decision (chosen autonomously per the parent task `9441acb4-f2e8-4ef1-8929-376fa9b32464`): the kind is a property of the TARGET NODE, not of the individual edge.** `exo__AssetSpace_dependsOn` is 0..N while the kind is 0..1, so a per-edge reading is not expressible; and measured across all 47 `dependsOn` edges, no target is a TBox provider for one depender and mere content for another. The existing hardcode already evaluates the **target's** namespace, i.e. it is a node property today. The new `exo__AssetSpace_dependsOnKind` therefore lives on the target's registry descriptor.

**Safe default is HARD.** An AssetSpace with no kind is treated as a TBox provider — the direction of the asymmetry is chosen deliberately: a wrong "soft" silently loses a class type at runtime, a wrong "hard" only costs an extra refusal.

## Job Story
When I apply a profile that would leave a class-definition provider unmounted, I want the apply to refuse loudly **before** it mutates the mount state, so I never end up with a vault whose assets silently lose their type (the two `sh:class` violations observed in the parent project's P5 spike).

```gherkin
Feature: typed AssetSpace dependency edges gate profile apply

  Background:
    Given the TBox declares exo__AssetSpace_dependsOnKind with the enum exo__DependencyKind
    And its values are exo__DependencyKindTBox (hard) and exo__DependencyKindReference (soft)

  Scenario: a hard-edge provider missing from the effective set refuses fail-loud
    Given a registry where AssetSpace "my" dependsOn AssetSpace "shared-private"
    And "shared-private" carries exo__AssetSpace_dependsOnKind = exo__DependencyKindTBox
    When a profile is resolved whose effective set does not contain "shared-private"
    Then the resolution throws a named error identifying "shared-private"
    And no mount-state mutation has been performed

  Scenario: a soft-edge member missing from the effective set is allowed
    Given the same registry
    But "shared-private" carries exo__AssetSpace_dependsOnKind = exo__DependencyKindReference
    When a profile is resolved whose effective set does not contain "shared-private"
    Then the resolution succeeds
    And the existing closure-gap warning still reports it as a non-TBox member

  Scenario: an AssetSpace with NO kind property defaults to hard
    Given the same registry
    But "shared-private" carries no exo__AssetSpace_dependsOnKind at all
    When a profile is resolved whose effective set does not contain "shared-private"
    Then the resolution throws the same named error
    And the default is hard, never soft

  Scenario: providesTBox is read from the graph, not from a namespace list
    Given an AssetSpace whose namespace is neither "exo" nor "exocmd"
    And it carries exo__AssetSpace_dependsOnKind = exo__DependencyKindTBox
    When the closure gap is computed for it
    Then it is reported with providesTBox = true
    And the symbol TBOX_PROVIDER_NAMESPACES no longer exists in the codebase

  Scenario: the kind value is accepted in both emitted IRI forms
    Given the kind is authored as a UID wikilink "[[<enum-uid>]]"
    Or authored as an alias wikilink "[[<enum-uid>|exo__DependencyKindTBox]]"
    Or authored as the symbolic local name
    Then all forms resolve to the same kind
    And an unrecognised value resolves to hard, not soft
```

## Notes

- Scope is the **plugin** only: the CLI (`CliProfileResolver`) carries no equivalent hardcode, so there is no UI/CLI parity debt introduced here.
- The post-apply closure-gap **warning** is retained for soft members; this requirement adds a **pre-mutation refusal** for hard ones, beside the existing TS-floor assertion, so both live at the same gate.
- Data marking shipped with the parent task: all 17 `dependsOn` targets are marked (13 hard / 4 soft; the 4 soft are the seed-empty collaborator AssetSpaces, which supply zero class definitions).
