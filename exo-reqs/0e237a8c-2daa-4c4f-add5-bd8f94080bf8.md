## Почему требование существует

`exo__Instance_class` **guarded** в CLI. Замер 2026-09-21 (`--dry-run`, ничего не мутировано):

```
set-property … --property exo__Instance_class
❌ Refusing to set "exo__Instance_class" via set-property — it has a dedicated guarded
   command … Use: exocortex apply convert-to-task|convert-to-project
```

Гвард **верен**: реклассинг есть семантическая операция с предусловием. Но перечисление слоёв даёт картину, в которой нужной операции нет ни на одном:

| слой | что умеет | годится для смены метакласса? |
|---|---|---|
| `set-property` | произвольное не-guarded свойство | ⛔ отказывает громко |
| `apply convert-to-task` / `convert-to-project` | **ЗАМЕНЯЮТ** класс | ⛔ только для `ems__Task`/`ems__Project`, не для метакласса TBox-свойства |
| `apply append-instance-class` (`e258207a`, grounding `ac0cf4ce`, тип `property_append`) | **ДОПИСЫВАЕТ** класс аддитивно | ⛔ добавляет, но не снимает исходный |
| raw `Write`/`Edit` | что угодно | ⛔ блокируется `dogfood-cli-mutation` (`instance_class` в guarded-списке) |

`resolve-buttons <property-asset> --json --show-hidden` на носителе: **2 visible** (`clean-properties`, `set-ontology`), **8 hidden**, среди них **0** команд реклассинга — ни одна не скрыта предусловием, их просто нет.

⇒ Санкционированного пути сменить метакласс свойства **не существует**, и это ровно та форма гэпа, ради которой `property_replace` (req `02de55a4`, Active, отгружен в v16.244.1) и делался: снять один элемент списка и поставить другой, не тронув со-значения.

## Что требуется

Команда **`replace-instance-class`** — сиблинг `append-instance-class` на примитиве `property_replace`:

```
exocortex apply replace-instance-class <путь> --vault <v> \
  --input '{"from":"<вики-ссылка на текущий класс>","to":"<вики-ссылка на целевой>"}' --yes
```

Grounding: `property_replace`, `targetProperty: exo__Instance_class`, `replaceFromExpression: $input.from`, `replaceToExpression: $input.to`.

## ⛔ CLI-only по построению — как у сиблинга, и по той же причине

Ни `exocmd__CommandBinding`, ни `exocmd__Command_precondition`. Это **решение**, а не недоделка, и формулировка копируется у `append-instance-class` дословно по смыслу: операция есть обход продуктового гварда `exo__Instance_class`, и давать её человеку одним кликом в 18 vault, где смонтирован `exoas-exocmd`, **никто не решал**. `apply <cliName>` резолвит команду напрямую, минуя биндинги, поэтому CLI-потребитель работает, а кнопки не появляется ни в одном vault.

⛔ Не «дозаводить» биндинг, увидев отсутствие кнопки — это не orphan-команда из `homoiconic-command-orphan-binding`.

Предусловия нет по той же причине, что у сиблинга: применимость решает вызывающий, который знает, какой класс снимает и на какой меняет. Предусловие здесь завело бы второй резолвер, молча расходящийся с первым.

## ⚠ Расхождение с прецедентом — названо, а не скрыто

`append-instance-class` отгружен **без требования**, как vault-данные под тикет `e7acd416` (SPARQL по req-корпусу: требований, покрывающих эту команду, **0**). По букве Step 0 моя команда — того же класса: чистые vault-данные, ноль кода движка, вся семантика уже принадлежит активному req `02de55a4`.

Требование заводится потому, что **так выбрал фаундер 2026-09-21** при явной постановке развилки (варианты «req-first» / «точечно без req» / «audited-окно» / «закрыть по трём носителям»), и потому что AC issue #4305 требует, чтобы решение было **заявлено**, а не выведено читателем из диффа.

## Сценарии

```gherkin
Given TBox-ассет свойства, чей exo__Instance_class содержит ровно один класс — exo__ObjectProperty
When выполняется apply replace-instance-class с from = ObjectProperty и to = DatatypeProperty
Then exo__Instance_class содержит ровно один класс — DatatypeProperty
And exo__Property_range ассета не изменён

Given TBox-ассет, чей exo__Instance_class содержит ДВА класса
When выполняется apply replace-instance-class с from = первый и to = третий
Then exo__Instance_class содержит третий и ВТОРОЙ, второй сохранил и значение, и позицию
And это и есть свойство, которого нет ни у convert-to-*, ни у property_set

Given exo__Instance_class, не содержащий значения from
When выполняется apply replace-instance-class
Then команда ОТКАЗЫВАЕТ, файл байт-идентичен
And отказ не превращается в дописывание (иначе ассет получил бы противоречивую пару классов)

Given команда resolve-buttons на любом ассете любого vault
When перечисляются visible и hidden
Then replace-instance-class отсутствует в обоих — команда CLI-only, биндинга у неё нет
```

## Non-goals

- ⛔ **Не** заводить биндинг и кнопку (см. выше — это решение сиблинга, наследуется осознанно).
- ⛔ **Не** трогать гвард `set-property` на `exo__Instance_class`: он верен, и команда его не отменяет, а даёт санкционированный обход именно для метакласса.
- ⛔ **Не** чинить в этом же цикле `FrontmatterService.parseObject` (потеря элементов после block-scalar) — issue #4314, отдельный предмет, общий с `property_append`.

## Первый носитель

`ems__AlcoholicDrinkSession_drink` (`e40a3591`, `exoas-public/ems`) — последний открытый носитель #4305: объявлен `exo__ObjectProperty` при `exo__Property_range: xsd:string`. Значения там действительно строки, поэтому верен `range`, а неверен метакласс. Замер 2026-09-21 SPARQL'ом по трём каноничным: носителей связки «ObjectProperty × xsd:*» осталось **1** (три `flow__StatusModel_*` уже починены сменой range).
