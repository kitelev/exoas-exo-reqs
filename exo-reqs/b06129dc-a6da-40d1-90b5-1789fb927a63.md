## Job story

When I run a `property_set` command whose grounding takes an asset reference from my input (`targetValueRef: $input.<key>` — `set-parent`, `set-blocker`), I want to be able to pass the reference either as a bare uid or as the wikilink I copied from another frontmatter (`[[uid]]`, `[[uid|alias]]`, `"[[uid]]"`) and get exactly ONE resolvable link on disk — or a loud refusal — so that the command never reports success while writing the broken double-wrapped `"[[[[uid]]]]"`.

## Context

- Source: ticket `52199c53-1719-4dde-9fca-002b3a86311b` (found by S3 `f27ad9f9`: `apply set-parent <path> --input '{"parent":"[[uid]]"}'` wrote `ems__Effort_parent: "[[[[uid]]]]"` with rc 0 and `✅ Parent set`; `--dry-run` precondition `passed`). Approved for implementation by ORCH `main-35699` mandate at the code-batch plan-gate 2026-09-16 (decision `25ec7e1d`: normalisation + loud refusal of the residue).
- Mechanism measured on `origin/main` `6c6c18b1` (2026-09-16): `GroundingExecutor.executePropertySet` wraps the `targetValueRef` TEMPLATE before substitution — `effectiveValue = "[[${grounding.targetValueRef}]]"` — then `substituteVariables` replaces `$input.parent` verbatim, so an already-wrapped input yields `"[[[[uid]]]]"`. The req `29e0d1b6` guard (`isUnquotedWikilink`) is silent because the value IS quoted. `FrontmatterService.updateProperty` writes it as-is.
- Population: three vault groundings carry `targetValueRef: $input.<key>` — `18f12de2` (set-parent, `$input.parent`, inputSchema `format: asset-reference`), `2b0b381d` (set blocker, `$input.blocker`, `format: asset-reference`), `bda47653` (set blocker value, `$input.value`, no format). One executor path ⇒ one fix.
- `format: "asset-reference"` in the inputSchema is INERT in the production loader: `CommandResolver.loadGroundingDefinition` maps `type: string` → a plain `text` field and never reads `format`; the plugin therefore shows a free-text field for `set-parent` and a user pasting `[[uid]]` there hits the same double wrap. Plugin and CLI share `executePropertySet`, so the fix reaches both surfaces by construction (UI/CLI parity).
- Why a NEW sibling requirement: req `29e0d1b6` (Active) chose a loud refusal (not normalisation) for `targetValueSubstitution` and its §Non-goals explicitly leave `targetValueRef` and normalisation out of scope. Here the executor OWNS the wrapping, so a `[[` inside the input has exactly one possible meaning — "this is a reference" — and there is no second contract to hide; normalising is the honest reading. The normaliser is the existing `extractAssetReference` (the same function every reader uses for `exo__Asset_isDefinedBy`), so writer and reader agree by construction.

## Scenarios

### Scenario 1 — a wrapped reference is unwrapped once and written as a single resolvable link
Given a `property_set` grounding with `targetValueRef: "$input.parent"` and `targetProperty: ems__Effort_parent`
When the command runs with `--input '{"parent":"[[<uid>]]"}'`
Then the step succeeds
And the frontmatter carries exactly `ems__Effort_parent: "[[<uid>]]"` (YAML reads it as a STRING `[[<uid>]]`, never `[[[[<uid>]]]]`).

### Scenario 2 — the aliased and the quoted forms normalise to the same bare uid
Given the same grounding
When the input is `[[<uid>|alias]]` or `"[[<uid>]]"` (surrounding YAML quotes)
Then the frontmatter carries `"[[<uid>]]"` in both cases (alias dropped, quotes dropped) — byte-identical to the bare-uid input.

### Scenario 3 — the bare uid keeps today's behaviour byte-identically
Given the same grounding
When the input is the bare `<uid>`
Then the frontmatter carries `"[[<uid>]]"` exactly as before this requirement.

### Scenario 4 — a residue after ONE unwrap is refused loudly, nothing is written
Given the same grounding
When the input is `[[[[<uid>]]]]` (nested) or `[[a]] b` (a link inside free text) — anything that still contains `[[`, `]]` or `|` after one unwrap
Then the step fails (`success: false`, CLI rc ≠ 0)
And the error names the contract ("asset-reference … takes a BARE uid or a single [[uid]] wikilink") and echoes the offending value
And `updateFile` is never called.

### Scenario 5 — the missing-input gate stays FIRST
Given the same grounding
When the command runs without `parent` in the input
Then the existing `property_set: value template references an input that was not provided (--input '{"parent":...}' required)` refusal is returned unchanged (the normaliser runs after it, never instead of it).

### Scenario 6 — a static `targetValueRef` and the sibling value-sources are byte-identical
Given a grounding with a static `targetValueRef: "<uid>"` (no `$input`), or with `targetValueLiteral` / `targetValueSubstitution` / `targetValueQuery`
When the step runs
Then the written value is byte-identical to `origin/main` before this requirement (req `29e0d1b6` Scenarios 1-4 stay green: an unquoted `[[uid]]` via `targetValueSubstitution` is still refused).

### Scenario 7 — the CLI help states the contract
Given `exocortex-cli apply --help`
When the `--input <json>` option is read
Then it says that asset-reference inputs (`set-parent`, `set-blocker`) take a BARE uid and that a copied `[[uid]]` / `[[uid|alias]]` is accepted and unwrapped.

## Non-goals

- The `service_call` `updateProperty` grounding `30b9e8d8` («Link to parent», `value` with `format: asset-reference`) — a different executor path (`packages/services` `createUpdatePropertyService`, writes `userInput.value` verbatim and requires a `userInput.property` the grounding does not supply): follow-up ticket, not changed here.
- Making `format: "asset-reference"` meaningful in the loader / the plugin form (a real reference picker for `set-parent`): follow-up ticket.
- Any change to `targetValueSubstitution` semantics (req `29e0d1b6` stays as is).
