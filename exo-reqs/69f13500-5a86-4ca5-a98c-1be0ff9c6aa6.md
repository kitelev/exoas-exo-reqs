# req(exo): plugin mount-closure completeness warning (Add-AssetSpace + Apply-profile) — issue #3956

## Job Story

When I add an AssetSpace (or apply a profile) in the Obsidian plugin and one of its `exo__AssetSpace_dependsOn`-closure members is **not** materialized — especially the `exoas-exocmd` class-TBox — I want a **clear, non-fatal WARNING** naming the missing member(s) and how to fix it, so that an incomplete mount **fails loud instead of leaving my homoiconic commands + validation silently dead** (the exact failure that broke the alpha tester). On mobile, where there is no CLI, the plugin warning is the only safety net.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: plugin mount-closure completeness warning (issue #3956)

  Background:
    Given the AssetSpace catalogue is scanned (registry mounted) so each
        AssetSpace descriptor's exo__AssetSpace_dependsOn edges are known
    And "materialized" means the AssetSpace's folder exists on disk

  Scenario: Add-AssetSpace with an unmounted TBox closure member warns (headline)
    Given "exoas-public" declares exo__AssetSpace_dependsOn -> "exoas-exocmd"
    And "exoas-public" is now materialized but "exoas-exocmd" is NOT
    When the plugin "Add AssetSpace by URL" command finishes adding "exoas-public"
    Then it emits a non-fatal WARNING that names "exocmd" as a missing
        dependsOn-closure member
    And the warning flags "exocmd" as a TBox-provider whose absence silently
        breaks homoiconic commands + validation
    And the warning suggests the remedy (Apply profile / Add AssetSpace by URL)
    And the add operation still completes (exit/success unchanged)

  Scenario: full closure materialized emits NO warning (no false-positive)
    Given "exoas-public" and its dependsOn "exoas-exocmd" are BOTH materialized
    When the plugin "Add AssetSpace by URL" command finishes
    Then NO dependsOn-closure warning is emitted

  Scenario: Apply-profile belt-and-suspenders warns on a closure gap
    Given the applied profile's includes-closure contains a member with no
        scanned descriptor (cannot be materialized)
    When apply-profile finishes materializing
    Then it emits a non-fatal WARNING naming the unmaterialized closure member(s)
```

## Notes

- Reuses the shared `transitiveDependsOnClosure` (core `AssetSpaceDependsOn.ts`) — zero new engine code.
- Desktop↔Mobile Command Parity: both the desktop and mobile (REST) apply paths carry the belt-and-suspenders warning; `Add AssetSpace by URL` is registered on both platforms.
- Sibling (out of scope): the CLI `assetspace-add`/`apply-profile` warning (CLI band).
