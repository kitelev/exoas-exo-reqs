## Зачем

Тикет P11 `a3607e3d` («Ассетспейс инструкций ботов», §3 «Защита от подмены», §4 Р0). Общие инструкции ботов переезжают в граф — в ассетспейс, смонтированный во все бот-vault'ы. Его текст становится частью СИСТЕМНОГО промпта всех ботов, а бот-vault пушат ТРИ процесса (движок, захват дневника, reminder-checker), каждый — весь vault без `--repo`. Любая локальная правка файла инструкции (обход обёртки регистром пути, путь через stdin `apply`, сквозная личная обёртка) уехала бы на GitHub и разошлась по всем ботам.

Замер спецификации (§1, клон `vault-bot-kitelev`): дописанная локально строка в файл `exoas-agent` после `exosync pull --repo kitelev/exoas-agent` даёт `pulled 0` и **остаётся** на диске — локальная правка переживает pull и ждёт push. Понятия «репо только на чтение» у синхронизации нет (`git grep -i 'readonly\|pull-only'` по `exosync-*.ts` — 0).

Решение — на уровне СИНХРОНИЗАЦИИ, а не обёрток: оно покрывает всех писателей, чья правка покидает устройство через ExoSync (движок бота, захват, reminder-checker, CLI, плагин, очередь разрешений конфликтов), включая будущих. (Уточнено по ревью PR #4544: сам список и прочее device-local состояние — доверенная конфигурация, см. «Граница доверия».) Реализуется в общем ядре (`packages/core/src/services/sync/*`), поэтому CLI и плагин получают одно поведение по построению; CLI — тонкий слой вывода.

## Модель

- Device-local файл `<vault>/.exocortex/exosync-pull-only`: по строке `owner/repo`. Пустые строки и строки, начинающиеся с `#`, игнорируются. Сравнение без учёта регистра; хвост `.git` снимается.
- Строка не формы `owner/repo` — ОТКАЗ всего прогона с текстом, называющим номер строки и её содержимое (сломанный список не должен молча снимать защиту с репо).
- Нет файла — поведение байт-в-байт прежнее.
- Для перечисленного репо:
  - push и push-фаза sync его НЕ пушат; исход репо в push — `skipped-pull-only`; общий код возврата от этого не краснеет;
  - pull и pull-фаза sync делают каталог репо ЗЕРКАЛОМ удалённого HEAD: изменённые локально файлы перезаписываются удалённым содержимым, локальные лишние удаляются, отсутствующие дописываются; перечень затронутых путей — в выводе команды и в stderr;
  - карантин, pin и outbox по такому репо не копятся (локальная правка — не «чужая работа», а подмена, которую затираем);
  - `exosync-parity` помечает репо полем `pullOnly: true` в JSON.
- Запись списка, не совпавшая ни с одним материализованным репо, — предупреждение в stdout И stderr (опечатка оставляет нужное репо двусторонним; вызывающий, выбрасывающий stdout, обязан это увидеть).

## Граница доверия

- Защищаемое — всё, что уходит с устройства через ExoSync. Сам список `.exocortex/exosync-pull-only` и прочее device-local состояние (`.exocortex/`, `.local.`-сторы плагина: watermark, ETag-кэш) — ДОВЕРЕННАЯ конфигурация устройства: процесс с произвольным доступом к файлам устройства может удалить строку, подделать кэшированный ref или подложить симлинк, и это вне защиты.
- Команды CLI, мутирующие ассеты, адресуют ассеты, а не эти файлы (`set-body` отказывает на не-ассете — проверено).

## Сценарии

### Сценарий 1 — pull восстанавливает правку файла в pull-only репо

```gherkin
Given vault, где репо R перечислено в .exocortex/exosync-pull-only
  And файл R/a.md изменён локально относительно удалённого HEAD
When запускаю `exosync pull --vault <v>`
Then содержимое R/a.md равно удалённому тексту
  And вывод называет путь a.md как восстановленный (restored), stderr — тоже
  And код возврата 0
```

### Сценарий 2 — pull удаляет лишний локальный файл и дописывает отсутствующий

```gherkin
Given R в списке pull-only
  And локально есть R/extra.md, которого нет в удалённом HEAD
  And удалённый файл R/b.md локально отсутствует
When запускаю `exosync pull`
Then R/extra.md удалён, R/b.md дописан с удалённым содержимым
  And лишний файл с `\` в имени (допустимо на POSIX) удаляется так же
  And вывод перечисляет extra.md как removed и b.md как added
```

### Сценарий 3 — push не трогает pull-only репо, соседний репо пушится

```gherkin
Given R в списке pull-only, репо S — нет
  And в R и в S есть локальные правки
When запускаю `exosync push` без `--repo`
Then для R не делается ни одного коммита, исход R — skipped-pull-only
  And правка S уходит на remote как раньше
  And код возврата 0
```

### Сценарий 4 — sync: pull-фаза зеркалит, push-фаза пропущена

```gherkin
Given R в списке pull-only с локальной правкой
When запускаю `exosync sync`
Then R становится зеркалом удалённого HEAD, ничего не пушится
  And вывод по R несёт отметку skipped-pull-only для push-фазы
  And для R не появляется ни карантина, ни pin в watermark, ни записи outbox
```

### Сценарий 5 — репо вне списка ведёт себя по-старому (контроль)

```gherkin
Given список pull-only существует, но S в нём нет
  And файл S/a.md изменён локально
When запускаю `exosync pull`
Then правка S/a.md переживает pull
When затем запускаю `exosync push`
Then правка S/a.md уходит на remote
```

### Сценарий 6 — кривая строка списка — отказ с текстом

```gherkin
Given в .exocortex/exosync-pull-only строка 3 — `kitelev/x # бот`
When запускаю `exosync pull`, `push`, `sync` или `exosync-parity`
Then команда отказывает с кодом 2 ДО любого REST-запроса
  And текст отказа называет файл, номер строки 3 и содержимое строки
```

### Сценарий 7 — нет файла — прежнее поведение

```gherkin
Given в vault нет .exocortex/exosync-pull-only
When запускаю `exosync pull` / `push` / `sync` / `exosync-parity`
Then ни одно репо не помечено pull-only, поведение совпадает с прежним
  And строка человекочитаемого отчёта parity сохраняет прежнюю форму байт-в-байт
```

### Сценарий 10 — репо, снятое со списка, возвращается к двусторонней синхронизации с точной базы

```gherkin
Given R было pull-only и зеркало выставило watermark на удалённый HEAD
When строку R убирают из списка и правят файл R локально
  And запускаю `exosync sync`
Then конфликта нет, на remote уходит ровно новая правка
```

### Сценарий 8 — exosync-parity помечает pull-only репо

```gherkin
Given R в списке pull-only
When запускаю `exosync-parity --json`
Then запись R в repos[] несёт `"pullOnly": true`, у остальных репо поля нет
  And человекочитаемый отчёт помечает строку R как [pull-only]
```

### Сценарий 9 — список называет несмонтированный репо — предупреждение, не отказ

```gherkin
Given в списке строка `kitelev/not-mounted`, такого материализованного репо нет
When запускаю `exosync pull`
Then прогон идёт как обычно
  And печатается предупреждение, что kitelev/not-mounted не материализован и защищать нечего
```

## Границы

- Мутанты: «список не читается» обязан покрасить оси восстановления и пропуска push.
- Не входит: защита обёрток ботов (Р6), принудительный pull перед сборкой промпта (Р2 демона), монтирование ассетспейса в бот-vault'ы (Р3) — другие части тикета.
- Известные пределы (названы, не скрыты): mount-папка, опустошённая целиком, читается как «не материализована» (гейт D19) и pull её не наполняет; в FileSpace удалённый файл выше лимита размера не скачивается, и его локальная копия остаётся как есть (с предупреждением).
- Зеркалится только множество синхронизируемых путей движка (`isSyncablePath` для AssetSpace, всё кроме `.local.`/`.conflict.` для FileSpace): за его пределами синхронизация файлов не видит ни в одну сторону.
