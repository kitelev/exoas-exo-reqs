# req(exo): per-ontology efforts routing (two-hop, auto-file efforts by area-ontology)

> **Origin:** Andrey's voice memo 2026-07-27 (fleeting note `03a1b613`). Vetted
> via `/council full` (5 lenses) + an empirical `GroundingExecutor` probe on
> origin/main. The council DEFERRED ontology-typing/governance (part A) as
> over-engineering without a real trigger; this requirement is part B (routing)
> only, in its **per-ontology** form (Andrey chose per-ontology targets over a
> single static default or per-area-instance property).

## Job Story

When I create a task or project from an **area** page via the homoiconic Create
button, I want the new Effort to be auto-filed into the efforts-ontology declared
on **that area's ontology** (e.g. my-areas → my-efforts, work-areas → work-efforts)
— **without** me manually picking `exo__Asset_isDefinedBy` each time — so my
area-ontologies stay clean (they hold areas, not the growing mass of efforts) and
efforts are routed per-audience by a single declarative setting I can change on
the ontology.

## Statement (Gherkin)

```gherkin
Given an area-ontology O declares exo__Ontology_effortsOntology = E (a target efforts-ontology)
And an area A whose exo__Asset_isDefinedBy points at O
And a create-instance grounding whose propertyDefault sets exo__Asset_isDefinedBy via the two-hop resolver and targetFolder = $isDefinedByFolder
When I create an Effort from area A via the Create button (no isDefinedBy chosen in the form)
Then the new Effort's exo__Asset_isDefinedBy is auto-set to E (read two-hop: A → O → O.effortsOntology)
And the new Effort file co-locates in E's folder, NOT in area A's folder
And no co-location violation is produced (isDefinedBy and the folder agree)

Given two area-ontologies O1 (effortsOntology = E1) and O2 (effortsOntology = E2)
When I create an Effort from an area under O1 and another from an area under O2
Then the first lands in E1's folder and the second in E2's folder (per-ontology routing)

Given an area whose ontology declares NO exo__Ontology_effortsOntology
When I create an Effort from that area
Then the two-hop resolver yields nothing, isDefinedBy is not routed, and the Effort co-locates with the area (opt-in / no regression for unconfigured ontologies)
```

  production-shape test driving the REAL `GroundingExecutor.executeCreateInstance`

  vault whose area's `exo__Asset_isDefinedBy` points at an ontology carrying
  `exo__Ontology_effortsOntology`. Asserts: created Effort's `isDefinedBy` = the

  folder). **Negative control** (ontology without the property) → no routing,
  co-locates with the area. **Revert-verify** RED→GREEN by neutralizing the
  two-hop resolver (or the `refToFrontmatter` dereference) → the routing
  assertions go RED; restore → GREEN.

  only `--dry-run`) reading back the created file's `isDefinedBy` + folder.
- **User docs:** document the `exo__Ontology_effortsOntology` setting (how to make
  an area-ontology auto-file its efforts elsewhere).
