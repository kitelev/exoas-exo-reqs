# req(exo): the block predicate also recognises lone-CR fences and a RUN of leading BOMs — on READ and on WRITE — and the file keeps its own line-ending style

## Job Story

**When** an asset reaches my vault from outside this machine — carrying classic pre-OS9 Mac line
endings from an old export, or a second U+FEFF stacked on by a naive "ensure a BOM" tool —
**I want** its genuinely valid frontmatter block to be indexed, its malformed one to be NAMED in
the loader's skip list, and an unrelated property write to REPLACE that block instead of
prepending a second one, **so that** "N file(s) skipped by the vault loader" stays the exhaustive
account req `fe50da38-4798-46e6-bb0a-b4b88596c340` promises, and an ordinary patch cannot turn my
frontmatter into orphaned body text.

## Why this is a NEW requirement, sibling of `c05a3565` — not an amendment of it

Active P2 req `c05a3565-7b8d-42dc-bc9f-7e71d47d9364` (#4441) widened the predicate from a literal
`\n` anchor to `\r?\n` plus a skip of **at most one** leading BOM, and **named both remaining
shapes in its own §Non-goals** with their reasons and their executable axes (**B15** lone-CR,
**B16** doubled BOM), work item **#4452**. It did not merely omit them — it pinned today's broken
behaviour, deliberately, so the gap would be visible as known rather than overlooked.

Closing those Non-goals is **new observable behaviour**: an asset that produced zero triples now
produces real ones, and a write that used to prepend now replaces. Under this repo's req-first SDD
discipline that is a sibling requirement, exactly as `c05a3565` was a sibling of `fe50da38` rather
than an extension of it.

`c05a3565` is **NOT superseded and NOT deprecated** — every clause it makes about LF, CRLF and a
single BOM stays true and stays Active, and its axes B1-B14/B17 stay green and unchanged. Two of
its §Non-goals clauses become false the moment this requirement ships, so they are marked
`SUPERSEDED by 74419202-264e-4394-a634-0b36d47357f8 (2026-09-29)` **in place**, in the same change
— a stale "we deliberately do not do this" reads as a proven fact to the next session
(`retracted-claim-outranks-its-correction`). The same correction is made to the two prose claims
inside `frontmatterBlock.ts` itself, which say in as many words that lone-CR "remains no block at
all" and that "exactly ONE is skipped".

## Decisions this requirement records EXPLICITLY (issue #4452 steps 1-2)

Both were open questions in the issue by design — resolving them implicitly during coding is the
exact gap the issue exists to close. Decided 2026-09-29 by the orchestrating session under the
founder's standing mandate, recorded as a comment on #4452 before implementation started.

1. **Lone-CR, write path: REPLACE the whole matched block; normalise NOTHING.** The file keeps its
   own line-ending style — the block is re-serialised by `js-yaml` exactly as it already is for a
   CRLF file (whose fences also come back as LF today), and the body after the block is not
   touched. Rationale: `c05a3565` already chose "preserve the file's style"; a second policy for CR
   alone would be a second state model for one property
   (`additive-migration-creates-two-state-models`), and it would cost LF/CRLF their byte-identity.

2. **A run of BOMs, write path: rewrite with EXACTLY ONE U+FEFF.** On read, the whole run is
   skipped for MATCHING only. On write, the output carries one byte. Rationale: `N>1` is
   **corruption, not a style** — no consumer produces it, and preserving N would reproduce the
   corruption on every save. This is the one place normalisation is intended, and it is an
   ASYMMETRY against decision 1 above: see §Non-goals, where it is named as such rather than left
   to be discovered.

## Scope — `NoteToRDFConverter.extractBodyContent` is IN, and why

`extractBodyContent` is the last twin of this predicate: its own regex is `\r?\n`-tolerant and
skips at most one BOM, i.e. it agrees with the predicate only on the shapes the predicate accepted
**before** this requirement. It is converted onto the shared helper here — not opportunistically,
but because the widening makes its divergence HOT:

- a lone-CR (or N-BOM) asset becomes indexable by the read path, while `extractBodyContent` still
  fails to match its block, so the WHOLE frontmatter comes back as body and every frontmatter
  wikilink is emitted a second time as `exo:Asset_bodyLink`;
- that is precisely the defect axis **B13** of `c05a3565` declares a defect for the BOM case, so
  shipping the read widening alone would re-introduce, on two new shapes, the thing its sibling
  just fixed;
- the conversion has a shipped precedent in the same predicate's own consumer set:
  `wikilinkExtraction.bodyOf` was moved onto `matchFrontmatterBlock` by #4461 and needs no change
  here — it inherits both shapes for free, which is the whole point of a single predicate.

Issue #4452 lists "scope creeps into unifying `extractBodyContent`'s twin regex" as a risk to be
avoided *unless the requirement explicitly says otherwise*. This requirement says otherwise, for
the reason above, and locks the inclusion with its own axis plus a mutant that reverts
`extractBodyContent` to the twin regex.

## Non-goals (deliberately NOT part of this requirement)

- **Normalising a file's line endings.** Decision 1 above: the block is replaced, the file keeps
  its style. A lone-CR file stays a lone-CR file after a property write.
- **Preserving a run of BOMs verbatim on write — the ONE intended asymmetry.** Decision 2 rewrites
  `N>1` to exactly one U+FEFF while decision 1 normalises nothing. The two are deliberately
  different because the inputs are different in kind: a line-ending style is a legitimate authoring
  choice, a stacked byte-order mark is damage. Named here so the asymmetry is a recorded decision
  rather than an inconsistency someone later "fixes" in either direction.
- **A block that opens `---` and never closes.** Unchanged, and still `c05a3565`'s named non-goal:
  indistinguishable from a note whose body starts with a horizontal rule.
- **The plugin's own adapter diagnostics — #4440.** `ObsidianVaultAdapter`'s `#4440` diagnostic
  half is a separate work item on a separate surface and no plugin source file is touched here.
  ⛤ But the plugin's READ tolerance is not separable, and this requirement does not pretend it is:
  the plugin's three sites go through the same core helper since `1dfbd427`, so they gain both
  shapes by construction. The plugin axis **C4** of `1dfbd427`, which pins lone-CR and a doubled
  BOM as unrecognised, is therefore flipped in the same change — a control that asserts the old
  limit cannot survive the limit being lifted.
- **The remaining LF-only predicates elsewhere in the repo** (`FrontmatterService.FRONTMATTER_REGEX`,
  `PropertyCleanupService`, `RenameToUidService`, `NodeFsAdapter`, `CandidateShaclValidator` —
  census in `frontmatterBlock.ts`'s own header). They are not consumers of this predicate; two of
  them are live parity gaps with their own work items. Not widened, not claimed.
