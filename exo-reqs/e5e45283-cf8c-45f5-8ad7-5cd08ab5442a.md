## Зачем

Инцидент 2026-09-26 08:53 диагностировали неверно: вердикт брали у `gh api rate_limit`, а он
слеп — отдаёт `used=0 remaining=5000` при фактических 379 и 2468 (ходит OAuth-токеном приложения
и считает не тот пул). Единственный источник истины об остатке — заголовки `x-ratelimit-*`
**самого** ответа GitHub.

Сегодня эти заголовки читаются **только на пути отказа**, и это проверено по всем четырём
носителям на `origin/main`:

| носитель | где читает | на успехе |
|---|---|---|
| `packages/cli/src/services/RestPushService.ts:185` | `enrichRateLimitError` перед `throw` | нет |
| `packages/obsidian-plugin/src/infrastructure/adapters/GitHubRestClient.ts:511` | `enrichRateLimitError` перед `throw` | нет |
| `packages/cli/src/services/BootstrapAssetSpaceService.ts:229-230` | внутри `if (!response.ok)` → `403` | нет |
| `packages/core/src/services/sync/conditionalRequestCache.ts`, `.../github/restCommit.ts` | только докстринги | кода нет |

⇒ остаток квоты виден ровно тогда, когда его уже израсходовали. Пока прогоны идут нормально,
расход невидим — то есть предупредить об исчерпании нечем, и следующий инцидент опять будет
диагностирован по слепому прибору.

Вторая половина того же пробела — асимметрия между командами: `restCalls` уже считается
(`SyncPhaseTimer`) и печатается в `exosync sync` (`formatRepoTimings` построчно +
`formatTimingsLine` агрегатом), а `exosync-parity` свои числа не печатает вовсе — при том что
он дороже: 83 запроса на 21 монтирование (vault-tbank), ≈210 на 37 (vault-exodev).

Третья — числа живут только в stdout прогона. Постфактум сопоставить «сколько потратил кто и
когда» нечем.

## Сценарии

### Сценарий 1 — остаток квоты читается на УСПЕШНОМ ответе

```gherkin
Given GitHub ответил 2xx на любой REST-запрос ExoSync
  And ответ несёт заголовки x-ratelimit-limit / x-ratelimit-remaining / x-ratelimit-used / x-ratelimit-reset
When прогон завершается
Then сводка прогона печатает limit, remaining и момент сброса из ПОСЛЕДНЕГО успешного ответа
  And значения взяты из заголовков ответа, а не из отдельного запроса к /rate_limit
```

### Сценарий 2 — `exosync-parity` печатает свои числа

```gherkin
Given запущен exosync-parity по любому vault
When прогон завершается
Then он печатает restCalls и остаток квоты той же строкой, что и exosync sync
```

### Сценарий 3 — журнал прогонов

```gherkin
Given любой прогон exosync sync или exosync-parity завершился
When он завершился — успехом ИЛИ отказом
Then в журнал дописана одна строка: момент, команда, vault, restCalls, limit, remaining, исход
  And журнал переживает прогон (постфактум-диагностика возможна без повторного запуска)
```

### Сценарий 4 (negative) — заголовков нет

```gherkin
Given ответ GitHub не несёт ни одного заголовка x-ratelimit-*
When прогон завершается
Then сводка печатает остаток как «n/a»
  And прогон НЕ падает и НЕ делает дополнительного запроса ради числа
```

⛔ Сценарий 4 несущий: он запирает то, что диагностика остаётся **наблюдателем** и не начинает
сама тратить квоту, ради измерения которой заведена.

## Non-goals

- Pre-flight по остатку (притормозить прогон, если remaining мал) — это #3974, отдельная единица.
- Разделение бюджетов через installation-токен GitHub App — #4411, отдельная единица.
- Изменение поведения `withRateLimitBackoff`: реактивный backoff уже отгружен и работает;
  требование только ЧИТАЕТ и ПЕЧАТАЕТ, решения о паузах не меняет.
- Мобильный плагин: требование про CLI-вывод и журнал. Паритет по чтению заголовков на успехе
  сохраняется тем, что чтение живёт в общем core-транспорте, а не в CLI.

## Как проверяется

Revert-verify по каждой гарантии отдельно:

1. Снять чтение заголовков на успешном пути ⇒ ось «сводка печатает remaining» краснеет.
2. Снять вызов печати в `exosync-parity` ⇒ ось «parity печатает restCalls» краснеет (ось обязана
   драйвить настоящую точку входа команды, а не звать форматтер напрямую).
3. Снять запись в журнал ⇒ ось «после прогона в журнале на одну строку больше» краснеет.
4. Подать ответ без заголовков ⇒ печатается «n/a», дополнительных запросов ноль.
