## Job story

When a homoiconic command's `exocmd__Grounding_inputSchema` declares an `assetRef` field whose `targetClassUid` is an ABSTRACT or PARENT class (the live case: `set-parent` / `set-blocker` groundings whose target properties `ems__Effort_parent` / `ems__Effort_blocker` range over `ems__Effort`, an abstract class with zero direct instances), I want the plugin's reference-picker candidate resolver to collect the instances of that class AND of every class that reaches it through the `exo__Class_superClass` chain (Task ∪ Project ∪ Action ∪ … for `ems__Effort`), so that the picker offers the real efforts to link instead of an empty (dead) picker — and a `targetClassUid` naming a class outside the hierarchy still yields nothing.

## Context

- Source: ticket `8df9e6eb-d441-4707-89f1-0301e1ff5a52` (parent techbacklog `bbac67ce`), founder decision 2026-09-16 (interview 18:42, question 2: "buttons with a drop-down list" for set-parent / set-blocker). Sibling req `c4adae42` (Active, PR #4244) made `format: asset-reference` project as `assetRef` and explicitly left the subclass-aware resolver + `targetClassUid` data as a follow-up ("Declaring `targetClassUid` (and a subclass-aware candidate resolver for Task ∪ Project) is a data/product decision, not this requirement").
- Mechanism measured on `origin/main` `66592ea2` (v16.240.0): the ONLY builder of picker candidates for command forms is `findAssetRefCandidates(app, classUid)` (`packages/obsidian-plugin/src/presentation/utils/assetRefCandidates.ts`), wired by `DynamicFormModal` (production default `candidatesResolver`) which `ObsidianCommandPromptAdapter.promptInputSchema` opens from `CommandExecutionFlow.run`; the same function serves `PropertyEditorModal.resolveCandidates(rangeClassUid)` (relations picker, range-scoped). It matches an asset iff one of its `exo__Instance_class` refs equals the class UID or the class file's `exo__Asset_label` — exact class only, no `exo__Class_superClass` walk. `DynamicForm` puts `ReferencePicker` in picker mode when candidates exist OR `targetClassUid` is declared, so a declared `targetClassUid` with 0 candidates is a picker that can never be filled.
- Live hierarchy (vault-exodev, exoas-public/ems): `ems__Effort` = `086f71fa-dd30-4284-90cf-e609f2a6c461` (superClass `ems__AreaAware`); `ems__Task` `1b20a8f0` → Effort; `ems__Project` `7db5eeff` → [Effort, `ems__ParentEffort` `17c5cf45` → Effort]; `ems__Action` `6a99d2ca` → Effort; `ems__Meeting` `1b0a5e34` → Task; `ems__TaskPrototype` `df7e579d` → [Task, …]. `ems__Effort_parent` (`6528ecfa`) and `ems__Effort_blocker` (`d9a56a56`) both have range `ems__Effort`. No asset is a direct `ems__Effort` instance, so today `targetClassUid = 086f71fa` would resolve to 0 candidates.
- Existing hierarchy walkers are all upward or store-based (`GroundingExecutor.classRefReachesPrototype`, CLI `EffortStatusResolver`, `ClassHierarchyResolvingStore`, `RequiredPropertyResolver`); the only downward (descendant) walk over frontmatter is `PropertiesLabelPatch.resolvePropertyClassUids` (UID-only, private). None is reusable by the picker as-is, so the descendant closure is extracted into a pure core helper.
- Why a NEW requirement: nothing on `origin/main` locks subsumption in the candidate resolver — the existing `assetRefCandidates.test.ts` axes assert exact-class matching only; the change adds behaviour (subclass instances become candidates) rather than restoring a specified one; `c4adae42` names it a non-goal.

## Scenarios

### Scenario A — core: transitive subclass closure of a target class
Given class definitions with `exo__Class_superClass` edges `Task → Effort`, `Project → [Effort, ParentEffort]`, `ParentEffort → Effort`, `Meeting → Task`, `Area → AreaAware` (Area is NOT under Effort)
When the subsumed-class keys of `Effort` (given by UID) are resolved (`resolveSubsumedClassKeys` in `@kitelev/exocortex-core`)
Then the set contains the UID and `exo__Asset_label` of Effort, Task, Project, ParentEffort and Meeting (transitive, multi-parent)
And it does NOT contain Area / AreaAware (a sibling or ancestor of the target is not subsumed).

### Scenario B — core: dual-IRI tolerance and safety
Given a subclass whose `exo__Class_superClass` names the parent in label form (`[[ems__Effort]]`) or piped form (`[[<uid>|ems__Effort]]`), and a hierarchy containing a cycle outside the target (`X → Y`, `Y → X`)
When the keys are resolved
Then the label-form / piped-form subclass is included, the cycle terminates, and resolving a target that no definition declares still returns the target's own key (exact-class matching is preserved).

### Scenario C — plugin resolver: subclass instances are candidates, foreign classes are not
Given a metadata cache holding the class files of Scenario A and these instances: a Task (`[[<Task uid>]]`), a Project (`[[<Project uid>]]`), a Meeting (`[[<Meeting uid>]]`), a symbolic-form Task (`[[ems__Task]]`) and an Area
When `findAssetRefCandidates(app, <Effort uid>)` runs
Then it returns the Task, Project, Meeting and symbolic-form Task as `{uid, label}` sorted by label, and NOT the Area
And `findAssetRefCandidates(app, <Area uid>)` returns only the Area (exact-class behaviour unchanged — the existing T1 axes stay green).

### Scenario D — production wiring: the form prompted by the engine receives the subsumed candidates
Given the REAL `ObsidianCommandPromptAdapter` over a fake `App` whose metadata cache carries the class files + one Task and one Project, and the `set-parent` input schema as `CommandResolver` projects it (`parent: assetRef`, `targetClassUid = <Effort uid>`)
When `promptInputSchema` opens the REAL `DynamicFormModal` (production `candidatesResolver`, no injection)
Then the `DynamicForm` element rendered for the modal receives `candidates.parent` = the Task and the Project.

### Scenario E — consumer control: the picker lists the subsumed candidates
Given a `DynamicForm` with an `assetRef` field `parent` (`targetClassUid` declared) and candidates = a Task and a Project
When the form renders
Then the field is the ARIA combobox (not the plain text input) and typing the Project's label offers it as an option that commits `"[[<Project uid>]]"`.

## Non-goals

- `targetClassUid` is still NOT derived from the property's range for non-required fields (`c4adae42` non-goal stands); the data-side declaration (`targetClassUid = 086f71fa-…` on `18f12de2` set-parent and `2b0b381d` set-blocker in exoas-exocmd) is a separate data commit made ONLY after this resolver is released, so the field never goes dead.
- No filtering of prototype / template subclasses (`ems__TaskPrototype` is a declared subclass of `ems__Task` and its instances are offered like any other subclass instance) — excluding them would be a product rule on top of the declared hierarchy, not this requirement.
- No change to `ReferencePicker`, `DynamicForm` semantics (picker mode / text fallback), `RequiredPropertyResolver`, the CLI surface (`apply set-parent --input parent=<uid>` unchanged) or any exoas-exocmd binding.
- `PropertyEditorModal.resolveCandidates` (relations picker) consumes the same resolver and therefore also becomes subsumption-aware; it gets no separate axis here — the consumer is unchanged, the resolver's contract (Scenario C) covers it.
