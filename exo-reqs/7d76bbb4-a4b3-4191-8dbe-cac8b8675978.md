## Job story

When any frontmatter writer that goes through the shared YAML escaper (`create`, `set-property`, `property_set`, `property_append`, `apply rename-to-uid`) receives a label / alias / property value carrying a Unicode non-character (U+FFFE, U+FFFF) or a lone surrogate half (a truncated astral character such as an emoji cut by a code-unit `slice`), I want the value written as a double-quoted YAML scalar with the unit `\uNNNN`-escaped, so that the frontmatter stays readable by js-yaml and the value reads back byte-for-byte — instead of the whole frontmatter becoming unreadable (non-characters) or the half being silently replaced by U+FFFD on the way to disk (lone surrogates).

## Context

- Ticket `65ea50c4` (tech backlog `bbac67ce`; found by the review of PR kitelev/exocortex#4261, ticket `71f1ca37`). Sibling of `389d4e14` (C0/DEL/C1 control characters, `\xNN` form, Active) — that req is scoped to the control class in its label, covers and Gherkin (`YAML_CONTROL_CHARS` extended from C0+DEL to C0+DEL+C1), so this class, which is neither "control" nor expressible as `\xNN`, gets its own requirement rather than an amendment.
- Mechanism (`packages/core/src/utilities/yamlScalar.ts` @ `39080e3b`): `needsYamlQuoting` tests only `YAML_CONTROL_CHARS` (`:45`, `:157`); `quoteYamlString` escapes only `< 0x20` and `0x7f–0x9f` (`:187`). Everything else is emitted bare.
- Measured on js-yaml **5.3.0** (the version `packages/core` resolves; `PATTERN_NON_PRINTABLE`, `dist/js-yaml.cjs.js:1812`, applied by `checkPrintable` to plain scalars): outside C0/DEL/C1 the reader rejects **U+FFFE, U+FFFF**, a **high surrogate D800–DBFF not followed by a low DC00–DFFF**, and a **low surrogate DC00–DFFF not preceded by a high** — a plain scalar carrying one throws `the stream contains non-printable characters` and the whole frontmatter is unreadable at rc 0 of the writer. Inside `"…"` the raw unit loads (as with C1), and js-yaml reads `\uD83D` / `\uFFFE` back as the same code unit — the form its own `dump` emits.
- On disk (Node `fs.writeFileSync`, UTF-8): a raw lone surrogate is encoded as `EF BF BD` (U+FFFD) — readable but lossy; U+FFFE is encoded as `EF BF BE` — unreadable. The `\uNNNN` form is pure ASCII on disk and round-trips the original JS string.
- Printable to the reader and therefore unchanged (no churn): U+FFFD, a valid surrogate pair (any astral character, e.g. emoji), a BOM inside a value.

## Statement (Gherkin)

```gherkin
Feature: the shared YAML escaper quotes and \uNNNN-escapes js-yaml's non-printable positions outside the control class

  Scenario: a value with a non-character is written quoted and round-trips
    Given a string value containing U+FFFE or U+FFFF
    When serializeYamlScalar (and every writer that calls needsYamlQuoting / quoteYamlString) emits it in a `key: value` mapping
    Then the emitted scalar is a complete double-quoted YAML scalar
    And js-yaml (YAML11 schema) loads the mapping without throwing
    And the loaded value equals the original string byte-for-byte

  Scenario: a value with a lone surrogate half is written quoted and round-trips, wherever the half sits
    Given a string value containing a high surrogate not followed by a low one, or a low surrogate not preceded by a high one (in the middle, at the start or at the end of the value)
    When serializeYamlScalar emits it
    Then the emitted scalar is a complete double-quoted YAML scalar that js-yaml loads without throwing
    And the loaded value equals the original string byte-for-byte, the lone half included

  Scenario: the unit is emitted in the \uNNNN escape form, not raw
    Given the string "a" + U+FFFE + "b" (or "a" + U+D83D + "b")
    When quoteYamlString emits it
    Then the output is exactly "a\uFFFEb" (or "a\uD83Db") — backslash, u and four upper-case hex digits inside the quotes
    And no raw non-character or lone surrogate unit is present in the emitted text

  Scenario: a valid surrogate pair is never split
    Given a string containing a valid surrogate pair next to a lone half
    When quoteYamlString emits it
    Then the pair is emitted raw as one astral character and only the lone half is escaped

  Scenario: the escaped form survives a UTF-8 file write faithfully
    Given a value containing a lone high surrogate
    When the emitted `key: value` line is written to a UTF-8 file and read back
    Then the file contains no U+FFFD replacement character and js-yaml loads the original value, the lone half included
    (a bare write of the same value would have stored U+FFFD instead — the pre-change on-disk behaviour, named here as the behavioural change)

  Scenario: printable values keep their existing on-disk form (pair, no churn)
    Given a value containing U+FFFD, a valid surrogate pair, U+10FFFF or a BOM inside the value
    When serializeYamlScalar emits it
    Then the output is the bare value, byte-identical to the pre-change output, and loads without throwing
```

## Non-goals

- Not changing the control class (C0 / DEL / C1 and its `\xNN` form) — req `389d4e14` governs it, untouched.
- Not touching the YAML11 reader (`parseYamlFrontmatter`), `decodeYamlQuotedScalar` (delegates to `yaml.load`, which already reads `\uNNNN` — it gets a regression axis, not a change) or the Obsidian metadataCache parser.
- Not re-quoting or repairing values already on disk (a U+FFFD that a past bare write produced stays U+FFFD); only values written after this change are affected.
- Not replacing lone surrogates by U+FFFD in the escaper (a data mutation in the serializer) — the escape is expressible and faithful.
- `RenameToUidService` inline-aliases parsing (req `2f642d6c`), `ShapeLoader` / `ShaclLiteValidator` (req `b0ad1160`) are out of scope.
