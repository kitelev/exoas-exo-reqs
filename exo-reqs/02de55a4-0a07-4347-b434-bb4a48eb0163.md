## Job story

Когда мне нужно **сменить один класс** в `exo__Instance_class` ассета — перетипировать
property-определение `exo__ObjectProperty` → `exo__DatatypeProperty`, заменить один
статус-класс другим, снять устаревший маркер, оставив остальные, — я хочу
**санкционированный путь**, который меняет ровно названный элемент списка и не трогает
соседние; а не выбирать между «заменить весь список» (теряя со-классы) и «дописать»
(оставляя два противоречащих класса).

## Замер: почему существующих примитивов НЕ хватает

Перечислены **исполнением** 2026-09-20 (11 типов grounding в TBox `exoas-exocmd`):

| примитив | что делает со списком | годится? |
|---|---|---|
| `property_set` | заменяет значение **целиком** | ⛔ разрушает со-значения |
| `property_delete` | `removeProperty` — снимает свойство **целиком** | ⛔ то же |
| `property_append` | добавляет, сохраняя существующие (`ac0cf4ce`) | ⛔ оставляет оба класса |
| `sparql_update` | объявлен, **не реализован** — `"sparql_update grounding not yet implemented"` | ⛔ |
| `service_call` | произвольное, но новый сервис = тот же объём кода | — |

⇒ **точечного обмена элемента в multi-value списке нет ни одного.**

Популяция, ради которой это несущественно-мелкое различие важно: **103 из 644**
property-определений трёх каноничных vault (**15 %**) несут ДВА и более класса —
`ems__Effort_status` = ObjectProperty + `exo__NonInheritableProperty`,
`concept__Concept_definition` = ObjectProperty + `exo__DeprecatedProperty`,
шесть `pmbok__*` — по три. Wholesale-замена стёрла бы у них второй класс **молча**.

⛤ Гвард CLI на этот путь не распространяется, и это **задокументированный механизм, а не
лазейка**: `guardedRouteFor` живёт в command-слое (`set-property` / `remove-property`),
а `GroundingExecutor` его не консультирует — ровно так уже работает отгруженный
`property_append` для того же `exo__Instance_class` (ассет `ac0cf4ce`, проверено
исполнением 2026-08-28). Требование делает это свойство **несущим**, а не побочным.

## Scenarios

### Сценарий 1 — со-значения сохраняются (несущий)

```gherkin
Given ассет, у которого exo__Instance_class = [exo__ObjectProperty, exo__NonInheritableProperty]
When исполняется grounding типа property_replace с from = exo__ObjectProperty
                                                  и to = exo__DatatypeProperty
Then exo__Instance_class = [exo__DatatypeProperty, exo__NonInheritableProperty]
 And порядок остальных элементов не меняется
```

### Сценарий 2 — паритет с wholesale на списке из одного

```gherkin
Given ассет, у которого exo__Instance_class = [exo__ObjectProperty]
When исполняется тот же property_replace
Then exo__Instance_class = [exo__DatatypeProperty]
 And результат побайтно совпадает с тем, что дал бы property_set
```

### Сценарий 3 — отсутствующее `from` есть ОТКАЗ, а не дописывание

```gherkin
Given ассет, у которого exo__Instance_class НЕ содержит значения from
When исполняется property_replace
Then исполнение завершается неуспехом с сообщением, называющим и property, и искомое from
 And файл остаётся байт-идентичным
```

⛤ Без этого сценария `property_replace` вырождается в `property_append` на любом промахе —
то есть молча производит ровно то состояние (два противоречащих класса), против которого
требование и написано.

### Сценарий 4 — гвард CLI не применяется к grounding-пути

```gherkin
Given targetProperty = exo__Instance_class (guarded в command-слое CLI)
When исполняется property_replace через apply <команда>
Then операция выполняется
 And set-property на то же свойство по-прежнему отказывает fail-loud
```

### Сценарий 5 — `to` уже в списке: идемпотентность без дубля

```gherkin
Given exo__Instance_class = [A, B]
When исполняется property_replace с from = A, to = B
Then exo__Instance_class = [B]
 And значение B не задваивается
```

## Non-goals

- ⛔ Команда vault-уровня и её биндинг к property-определениям — **отдельная единица**
  (этот req даёт примитив движка; без команды он не достижим пользователю).
- ⛔ Починка самого носителя `ems__AlcoholicDrinkSession_drink` (#4305) — она следствие,
  а не предмет.
- ⛔ Реализация `sparql_update` — соседний незакрытый тип, к этому требованию не относится.
- ⛔ Расширение на не-списочные свойства: у скаляра «заменить элемент» тождественно
  равно `property_set`, отдельного смысла нет.

## Verification surface

Оси `@req` на `GroundingExecutor` (Unit) + прогон реального `apply` на временном vault
(Integration). ⛤ Каждый сценарий обязан иметь мутанта, краснящего **ровно** его; сценарий 3
и сценарий 5 — разные гварды, поэтому разные мутанты (§A8 integration-test-revert-verify).

⚠ Новый предикат grounding читается **ДВУМЯ** загрузчиками — `CommandResolver.loadGroundingDefinition`
(продовый путь плагина и CLI) и `GroundingFrontmatterParser` (BDD) — и правка одного из них
оставляет фичу мёртвой в проде при зелёном наборе (`multi-parser-predicate-migration`).
Ось на паритет загрузчиков обязательна.
