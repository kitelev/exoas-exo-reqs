# req(exo): W3C-prefixed labels emit canonical vocabulary IRIs, not exocortex.my ad-hoc IRIs

## Job Story

**When** I open the vault asset that defines a W3C vocabulary term (e.g. the `exo__Class` whose label is `rdfs__subClassOf`),
**I want** the graph to describe it under the same IRI that the engine already uses when that term appears as a predicate (`http://www.w3.org/2000/01/rdf-schema#subClassOf`),
**so that** a query about that term reaches BOTH its 319 usages and its definition, instead of silently splitting them across two IRIs that never join.

## Gherkin

```gherkin
Feature: canonical IRIs for external W3C vocabulary prefixes

  Background:
    Given the engine already holds canonical Namespace constants for rdf, rdfs, owl and xsd
    And RDFVocabularyMapper already emits predicates under those canonical IRIs

  Scenario: an rdfs-prefixed label emits the canonical RDFS IRI
    Given a vault asset whose exo__Asset_label is "rdfs__subClassOf"
    When the converter derives the symbolic IRI for that label
    Then the emitted IRI is "http://www.w3.org/2000/01/rdf-schema#subClassOf"
    And it is NOT "https://exocortex.my/ontology/rdfs#subClassOf"
    And it is byte-identical to the IRI the engine already uses for that predicate

  Scenario: the shacl prefix resolves to the canonical SHACL namespace
    Given a vault asset whose exo__Asset_label is "sh__severity"
    When the converter derives the symbolic IRI for that label
    Then the emitted IRI is "http://www.w3.org/ns/shacl#severity"

  Scenario Outline: every registered W3C prefix resolves canonically
    When Namespace.forPrefix is asked for "<prefix>"
    Then it returns the canonical namespace whose IRI is "<iri>"

    Examples:
      | prefix | iri                                           |
      | rdf    | http://www.w3.org/1999/02/22-rdf-syntax-ns#   |
      | rdfs   | http://www.w3.org/2000/01/rdf-schema#         |
      | owl    | http://www.w3.org/2002/07/owl#                |
      | xsd    | http://www.w3.org/2001/XMLSchema#             |
      | sh     | http://www.w3.org/ns/shacl#                   |

  Scenario: exocortex.my prefixes are unchanged (backward compatibility)
    Given a vault asset whose exo__Asset_label is "ems__Task"
    When the converter derives the symbolic IRI for that label
    Then the emitted IRI is still "https://exocortex.my/ontology/ems#Task"

  Scenario: an unknown prefix still falls back to the ad-hoc convention
    Given a frontmatter key "aiKnow__Memory_aboutConcept"
    When Namespace.fromPropertyKey parses it
    Then the namespace IRI is "https://exocortex.my/ontology/aiKnow#"
    And no code change is required to introduce a further user namespace
```

## Acceptance

- `Namespace.forPrefix("rdfs")` returns the canonical `Namespace.RDFS` singleton (reference equality), not a freshly constructed ad-hoc namespace.
- A new `Namespace.SHACL` constant exists with IRI `http://www.w3.org/ns/shacl#` and prefix `sh`.
- The full `packages/core` suite stays green — measured on the probe: **374/374 suites, 8599 tests**, zero regressions attributable to the change.
- Revert-verify: removing the W3C prefixes from `KNOWN_NAMESPACES` reddens the canonical-emission scenarios and leaves the exocortex.my backward-compatibility scenario green (non-vacuity: the delta is the W3C registration, not namespace resolution as a whole).

## Non-goals

- Deriving namespace bases from `exo__Ontology_url` at emission time (see `covers` — the data does not exist yet and the change is disproportionate today).
- Splitting `exoas-w3c-aggregated` into per-vocabulary ontologies. That is vault DATA and is tracked separately; this requirement is the engine half that makes such a split meaningful.
- Adding vocabularies with zero vault presence (e.g. `skos`, `dc`, `foaf`). `ShaclLiteValidator` already exempts them from range checks; registering them here without a single asset would be hardcoding ahead of need.
