# req(exo): каноничный YAML-ключ — один источник в core, которым пользуются ВСЕ писатели frontmatter

## Job Story

Когда я пишу свойство `exo__Asset_aliases` любым путём — CLI-командой, гомоиконичным grounding'ом или при создании ассета — я хочу, чтобы оно легло под тем ключом, который Obsidian и RDF-конвертер действительно читают (`aliases:`), а не под литеральным `exo__Asset_aliases:`. Сегодня это зависит от того, каким из четырёх писателей значение прошло: два канонизируют ключ, два — нет. Результат первых двух работает, результат вторых — мёртвый ключ, который Obsidian игнорирует, а конвертер не связывает с `exo:Asset_aliases`.

## Statement (Gherkin)

```gherkin
Given грануляция ключей объявлена в core как UNPREFIXED_ASSET_FIELDS
When писатель frontmatter проходит через примитивы записи core
    (FrontmatterService.updateProperty / removeProperty / createFrontmatter,
     MetadataHelpers.buildFileContent)
Then физический ключ определяет ОДНА функция канонизации, экспортируемая из core,
     а не решение на стороне вызывающего
And в пакете cli не остаётся собственной копии этого правила
And примитив матчит ключ ТОЛЬКО с начала строки, поэтому канонизация (которая
    делает искомый ключ КОРОЧЕ) не задевает соседнее свойство, чьё имя
    оканчивается тем же словом

Given grounding с targetProperty exo__Asset_aliases
When шаг property_set исполняется
Then значение записывается под ключом aliases
And к нему применяется строковая семантика (STRING_SCALAR_PROPERTIES), потому что поиск идёт по каноничному ключу
And scalar-образный алиас вида 2026-01-15 переживает round-trip строкой, а не становится Date

Given создание ассета командой create
When передан --property exo__Asset_aliases=X
Then команда ОТКАЗЫВАЕТ с указанием выделенного флага --aliases
And ассет не создаётся с литеральным ключом exo__Asset_aliases
# Канонизация одна отправила бы значение в skip-лист create (там уже есть aliases,
# потому что create формирует алиасы сам из label + --aliases) — то есть значение
# пропало бы МОЛЧА. Отказ выбран сознательно: он симметричен тому, как set-property
# отклоняет guarded-свойства, и ничего не теряет без ведома пользователя.

Given set-property и remove-property
When они мутируют любое свойство
Then их наблюдаемое поведение байт-в-байт прежнее
# они уже канонизируют; меняется только МЕСТО, откуда импортируется функция.
```

## Verification

**Revert-verify — ось на КАЖДОГО писателя, и это и есть доказательство единого источника.** `@req:<этот-uid>` — интеграционные тесты гоняют РЕАЛЬНЫЕ пути записи (`setPropertyCommand`, `removePropertyCommand`, `GroundingExecutor.executeStep` с `property_set`, `createCommand`) над временным vault и читают файл обратно **продовым YAML-парсером**.

Нейтрализация общей функции канонизации в core обязана покраснеть **у всех четырёх** осей. Именно «у всех четырёх» отличает выполненное требование от точечной правки двух call-site: если после нейтрализации краснеют только два, значит источник по-прежнему не один и правило снова размножено.

Негативные контролы (обязаны остаться зелёными): свойство БЕЗ префикса `exo__Asset_` (канонизация — тождество); свойство с префиксом, чьё поле НЕ входит в `UNPREFIXED_ASSET_FIELDS` (`exo__Asset_isDefinedBy` → ключ не меняется). Они доказывают, что канонизация не начала переписывать ключи всем подряд.

## Scope — что это требование НЕ утверждает (уточнено 2026-08-03 по раунду-2 ревью)

⛔ Первая редакция пункта 1 говорила «**любой** писатель frontmatter». Это было
неправдой, и формулировка исправлена, а не оставлена как намерение: ревью
перечислило ~17 продовых писателей, которые собирают frontmatter **мимо**
примитивов и потому канонизацию не увидят. Оставить универсальный квантор значило
бы, что следующий читатель примет его за установленный инвариант и пропустит
проверку.

Известные обходы (трекаются на `ems__Bug` `43e41c8f`, не закрываются здесь):

- `ObsidianVaultAdapter.updateFrontmatter` — **единственный, кто ещё способен
  СОЗДАТЬ** мёртвый ключ: он применяет `normalizeIRI` и останавливается на шаг
  раньше канонизации, поэтому полный IRI из редактора свойств лэйаута
  превращается в литеральный `exo__Asset_aliases:`.
- `PropertyUpdateService`, `AtomicFrontmatterService`, `FileSystemVaultAdapter`,
  `StructuredMerger` (ExoSync), `prototype-subtree-instantiator`,
  `RenameToUidService` — переносят/сохраняют уже существующие ключи либо пишут
  фиксированные имена, то есть новых мёртвых ключей не порождают.

Также вне скоупа: `removeProperty` не применяет `normalizeIRI` (в отличие от
`updateProperty`), поэтому IRI-форма имени **ставится, но не удаляется**. Эта
асимметрия предшествует требованию (`origin/main` ведёт себя так же) и не
расширяется молча: добавление `normalizeIRI` превратило бы сегодняшний тихий
no-op в реальное удаление и для не-whitelisted IRI-входа.

## Homoiconicity Invariant (Q1/Q3)

Q1 = нет: под каким физическим ключом свойство лежит во frontmatter — не user-configurable семантика, а инвариант формата хранения. Q3 = «ядро обработки»: правило уже наполовину живёт в core (`UNPREFIXED_ASSET_FIELDS` объявлен в `NoteToRDFConverter.ts` и читается конвертером обратно), требование лишь переносит туда его вторую половину — применение.

## Classification note (почему новое требование, а не bug-fix и не расширение соседнего)

- `21ceea14` (Active) **явно выводит** этот случай из своего скоупа («pre-existing create-side gap of the #3944 class and out of this requirement's scope») — расширять его `@req`-покрытием значило бы противоречить его же тексту.
- `3800d995` (Active) специфицирует guard'ы и скоуп `set-property`; оно не может говорить за `create` и `GroundingExecutor` и не формулирует правило канонического ключа вообще.
- Ни одно требование не утверждает межписательский инвариант «все консультируются с одним источником» — а именно он и есть предмет. Плюс у `create` меняется наблюдаемый исход (отказ вместо молчаливой записи мёртвого ключа).

## Корень, установленный чтением origin/main

`canonicalYamlKey` определён в `packages/cli/src/commands/propertyMutationShared.ts` и импортируется **ровно двумя** файлами (`set-property.ts`, `remove-property.ts`) — в core его нет. При этом его единственная зависимость, `UNPREFIXED_ASSET_FIELDS`, **уже** живёт в core. То есть расхождение — не небрежность, а **недостижимость**: core-писатели физически не могут спросить правило, лежащее по ту сторону границы пакета. Поэтому фикс — перенос функции к её же данным, а не патч двух мест.

Замеренные проявления: `GroundingExecutor.ts:672-675` передаёт в `updateProperty` **сырой** `grounding.targetProperty` (даже не нормализованный), а флаг строковой семантики ищет по `normalizeIRI(...)` — сломаны обе половины; `GenericAssetCreationService` skip-лист содержит `"aliases"`, но не `"exo__Asset_aliases"`, поэтому префиксная форма проваливается в общую ветку записи.
