# req(exo): TBox entities display as `prefix#slug` (computed projection, RFC 78572fa9 Candidate B Phase 2)

## Job Story

When I look at a TBox class or property definition — its tab/inline title, or a wikilink to it (`[[ems__TaskPrototype]]` / `[[<uid>]]`) in another asset's body, properties panel, graph node, or a plugin table — I want it to display as its **readable symbolic projection** `ems#TaskPrototype` (the ontology's canonical prefix + the entity's slug), **computed on the fly and never stored**, so that the TBox identity is shown in its human-readable `prefix#slug` form (the same shape a query would use) instead of the raw `ems__TaskPrototype` label — and so that once the store goes uid-only (Phases 3-4) the display keeps working from the naming fields, not from a stored symbolic identity.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: TBox naming display-projection (prefix#slug), computed, never stored

  Background:
    Given the ems ontology asset carries exo__Ontology_shortName "ems"
    And the DisplayNameResolver is built with a metadataResolver that resolves
        exo__Asset_isDefinedBy -> the ontology frontmatter

  Scenario: a populated class-def displays as prefix#slug (headline)
    Given a class-def asset with exo__Asset_label "ems__TaskPrototype"
    And exo__Instance_class -> exo__Class (the Slugable-mixin metaclass)
    And exo__Slugable_slug "TaskPrototype"
    And exo__Asset_isDefinedBy -> the ems ontology
    When the DisplayNameResolver resolves its display name
    Then the result is "ems#TaskPrototype"
    # Revert-verify: projectTBoxNames OFF -> "ems__TaskPrototype" (raw label, RED). ON -> "ems#TaskPrototype" (GREEN).

  Scenario: a populated property-def displays as prefix#slug
    Given a property-def asset with exo__Asset_label "ems__Effort_status"
    And exo__Instance_class -> exo__DatatypeProperty
    And exo__Slugable_slug "Effort_status"
    And exo__Asset_isDefinedBy -> the ems ontology
    When the DisplayNameResolver resolves its display name
    Then the result is "ems#Effort_status"

  Scenario: fallback — an unpopulated class-def derives prefix+slug from the label
    Given a class-def asset with exo__Asset_label "ems__WaitingCheckTaskPrototype"
    And exo__Instance_class -> exo__Class
    And NO exo__Slugable_slug field
    And the ems ontology has NO exo__Ontology_shortName field
    When the DisplayNameResolver resolves its display name
    Then the result is "ems#WaitingCheckTaskPrototype"
    # slug derived from the label's local part; prefix derived from the label's prefix part.

  Scenario: orphan-namespace — slug present but the ontology has no shortName
    Given a class-def asset with exo__Asset_label "okr__Objective"
    And exo__Instance_class -> exo__Class
    And exo__Slugable_slug "Objective"
    And its ontology has NO exo__Ontology_shortName (an orphan-namespace prefix, RFC v4)
    When the DisplayNameResolver resolves its display name
    Then the result is "okr#Objective"
    # slug from the field; prefix derived from the label-prefix fallback.

  Scenario: a participating exo__DisplayNameSpec wins over the projection
    Given a class-def asset that ALSO has a participating exo__DisplayNameSpec for its class
    When the DisplayNameResolver resolves its display name
    Then the DisplayNameSpec template output is rendered (NOT the prefix#slug projection)
    # The projection is subordinate to an explicit author override.

  Scenario: ABox instances are byte-identical (no regression)
    Given a task instance with exo__Asset_label "Купить молоко" and exo__Instance_class -> ems__Task
    When the DisplayNameResolver resolves its display name
    Then the result is the same as before the projection existed (its label / status-spec output)
    # A non-Slugable-metaclass instance never triggers the projection.

  Scenario: revert axis — the projection is toggleable
    Given projectTBoxNames is OFF
    When the DisplayNameResolver resolves any TBox class/property def
    Then the raw exo__Asset_label is displayed (baseline)
```

## Notes

- **Design (Andrey R22 naming architecture, faithful to RFC 78572fa9 §v3 point 6 + §v4).**
  - **Where:** `DisplayNameResolver.resolve()` (packages/obsidian-plugin/src/domain/display-name/DisplayNameResolver.ts) — a new `computeTBoxNamingProjection(assetClasses, metadata): string | null` called at the top of `resolve()`. Returns the `prefix#slug` string when applicable, else `null` (→ the existing template path). All 8 native-link/tab surfaces + 3 plugin renderers route through `.resolve()`, so the single method reaches every TBox-display surface.
  - **Detection:** `exo__Instance_class` ∈ {exo__Class, exo__Property, exo__ObjectProperty, exo__DatatypeProperty, exo__URLProperty} (UID or label form), OR a non-empty `exo__Slugable_slug`.
  - **Precedence:** a participating `exo__DisplayNameSpec` (via `PrintNameRuleService.getParticipatingRules`) wins → return `null`, the normal path renders the spec.
  - **Slug:** `exo__Slugable_slug` ?? the label's local name (after the first `__`). **Prefix:** the isDefinedBy ontology's `exo__Ontology_shortName` (two-hop via `metadataResolver`) ?? the label's prefix (before the first `__`). **Compose:** `prefix ? prefix#slug : slug`.
  - **Revert axis:** `DisplayNameSettings.projectTBoxNames` (default ON via `?? true`) — the revert-verify toggle + a user escape hatch.
- **Store UNTOUCHED** — additive display only; the converter still emits symbolic (Phase 3-4 flips emission to uid-only later). Consistency with the future name-resolver: the projection reads the SAME fields (`exo__Slugable_slug`, `exo__Ontology_shortName`).
- **Data state (verify-before-assert, 2026-07-29):** remote/main HAS the Phase-1 population (`ems__TaskPrototype` slug="TaskPrototype", ems ontology shortName="ems"); vault-my is ExoSync-stale (fallback derives). The fallback chain handles both populated and unpopulated data — so the projection is correct regardless of local sync state.
