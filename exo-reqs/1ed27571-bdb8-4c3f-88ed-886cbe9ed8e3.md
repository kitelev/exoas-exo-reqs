## Зачем

ems__Bug `bcc041d8` (vault-exodev). Позиционный аргумент `exocortex query` читается как ФАЙЛ, если в нём нет `SELECT`/`CONSTRUCT`/`INSERT`/`DELETE` и такой путь существует (`loadQuery`). Если содержимое — не SPARQL, ошибка разбора цитирует прочитанное: сообщение парсера и строки контекста `SPARQLErrorEnhancer`. Так `query <путь к токену>` печатал секрет в ответ — в обход запрета Read у ботов, где файл читает CLI, а не Read-тул. Замер 2026-10-10 на синтетической канарейке, CLI 17.10.3: утечка в текстовом режиме, при `--dry-run` и `--explain`.

Обёртки четырёх закрытых ботов закрыты отдельно, в dotfiles (отказ на аргумент `query`, называющий существующий путь). Это требование — второй слой в самом CLI: он закрывает и личного бота, чья обёртка по директиве 2026-08-03 команды не проверяет.

## Поведение

```gherkin
Feature: ошибка запроса, прочитанного из файла, не печатает содержимое файла

  Background:
    Given файл F, чьё содержимое — не SPARQL и несёт уникальную строку-канарейку

  Scenario: текстовый режим
    When запускается `query F`
    Then код выхода 2
    And вывод не содержит канарейку
    And вывод называет F и тип ошибки и сообщает, что содержимое файла не показано
    And позиция ошибки (строка, столбец) не сообщается

  Scenario: JSON-режим
    When запускается `query F --output json`
    Then код выхода 2, ответ — JSON-ошибка без канарейки (ни в message, ни в context)

  Scenario: проверка синтаксиса и анализ
    When запускается `query F --dry-run` или `query F --dry-run --explain`
    Then вывод не содержит канарейку, код выхода 2

  Scenario: цифры из файла не выдаются за позицию
    Given файл с текстом вида «(4821, 9930)» и «at 7351:6624»
    When запускается `query F`, `query F --output json` или `query F --dry-run`
    Then ни одно из этих чисел не появляется в выводе

  Scenario: относительный путь
    Given рабочий каталог содержит F
    When запускается `query <имя F>`
    Then вывод не содержит канарейку

  Scenario: запрос строкой — контекст ошибки как прежде
    When запускается `query '<невалидный SPARQL с SELECT>'`
    Then вывод по-прежнему показывает контекст ошибки с текстом запроса

  Scenario: валидный запрос из файла .sparql работает как прежде
    Given файл Q.sparql с валидным SELECT
    When запускается `query Q.sparql`
    Then запрос исполняется (код 0)

  Scenario: ошибки CLI для запроса из файла сохраняют своё сообщение
    Given файл Q.sparql с валидным SELECT и несуществующий vault
    When запускается `query Q.sparql --vault <нет такого>`
    Then печатается прежнее сообщение «vault не найден»
```

## Уточнение по ревью PR #4550 (2026-10-10)

Первая редакция обещала «тип и позицию». Ревью показало, что позицию CLI извлекает регулярками из сообщения парсера, а оно цитирует окно входа: файл с «(4821, 9930)» выдавал эти числа за строку и столбец (в тексте и в `context` JSON). Без `--dry-run` позиция к тому же сдвинута внедрёнными PREFIX и не совпадает со строкой файла. Поэтому для запроса из файла позиция не сообщается; сценарий «цифры из файла» запирает это.

## Non-goals

- Правило «аргумент — путь, если он существует и без ключевых слов» не меняется; флага `--query-file` нет (форму `query <файл.sparql>` используют скрипты, поэтому выбран мягкий вариант).
- Тексты ошибок для запроса, переданного строкой, не меняются.
- Успешный ответ на запрос из файла, который разобрался как SPARQL (поле `query` в JSON, план `--explain`, `--stats`), не меняется: файл, являющийся валидным запросом, — законный вход.
- Обёртки ботов — отдельная правка в dotfiles (`bot-wrapper-security-verify.sh`, оси Q1–Q6).
