`create` resolves the target folder in two ordered attempts
(`packages/cli/src/commands/create.ts`): **priority-1** — the `exo__Asset_isDefinedBy`
ontology folder (`resolveCoLocationFolder`); **priority-2** (req `cec6af2c`, issue #3934) —
the folder holding the most sibling instances of the same class **that share the new
asset's anchor**. When both decline, the asset falls back to the inbox default `01 Inbox/`
— a folder that need not even exist on disk and that `audit co-location` skips **by design**
(an empty `isDefinedBy` is a documented skip reason).

That fail-open is correct and stays. What is wrong is that it is **mute**: `rc=0`, the JSON
on stdout is valid, SHACL is silent, and only someone who compares the printed path by eye
notices the asset left its class's canonical home.

## Why priority-2 cannot rescue the anchor-less case

With **no** `exo__Asset_isDefinedBy` at all, `newAnchor = null`, so a sibling only counts if
it has **no anchor either**. Measured on the live vault-exodev (2026-09-10): class
`inbox__ExoAssistantKnowledge` has **451** instances and **0** of them lack an anchor ⇒ the
comparison population is empty *by construction*, not "rarely non-empty". The same measurement's
canary — a vault-wide `FILTER NOT EXISTS { ?s exo:Asset_isDefinedBy ?idb }` — returns **43**
anchor-less assets, so the zero is a fact about the data, not a dead query.

## Why the placement must NOT change

Matching siblings **without** the anchor filter would have moved RFC assets to
`exoas-exoass/exoass` (**284** instances) rather than `exoas-exodev/inbox` (**128**) — a
different audience assetspace. The anchor filter exists for exactly that reason (the #3934
comment says so). The tool cannot know which of a class's several homes was meant, so
"quietly place it somewhere" would be a guess. Only one thing changes: the fail-open stops
being silent.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: the co-location fail-open is observable instead of silent

  Scenario: anchor absent + the class demonstrably has a home elsewhere -> stderr warning
    Given a vault where instances of class C live in folder F
    And F is neither the vault root nor the inbox default
    When I run `create --class C --label L` with NO exo__Asset_isDefinedBy
    Then the asset is still written into `01 Inbox/` (placement unchanged — req cec6af2c scenario 3 preserved)
    And the exit code is 0 and stdout remains a single JSON document
    And stderr names the fail-open, the inbox path, the anchor state, and F with its sibling count
    # Removing the diagnostic -> stderr silent (RED). Restoring -> warning present (GREEN).

  Scenario: a resolvable isDefinedBy stays silent
    Given a vault with an on-disk ontology file that isDefinedBy resolves to
    When I run `create --class C --property exo__Asset_isDefinedBy=[[<ontology-uid>]]`
    Then the asset is co-located in that ontology's folder
    And stderr emits no co-location warning

  Scenario: a class with no instances stays silent
    Given a vault with NO existing instances of class C
    When I run `create --class C` with no isDefinedBy
    Then the asset falls back to `01 Inbox/`
    And stderr emits no co-location warning

  Scenario: a bang-anchor whose siblings share that anchor places by neighbour and stays silent
    Given sibling instances of class C carrying the same `!`-prefixed anchor in folder F
    When I run `create --class C --property exo__Asset_isDefinedBy=[[!anchor]] --skip-wikilink-validation`
    Then the asset is written into F (priority-2, req cec6af2c)
    And stderr emits no co-location warning

  Scenario: the class's only home IS the inbox default -> silent
    Given every instance of class C already lives in `01 Inbox/`
    When I run `create --class C` with no isDefinedBy
    Then the asset falls back to `01 Inbox/`
    And stderr emits no co-location warning

  Scenario: the class's only home is the VAULT ROOT -> silent
    Given every instance of class C lies loose at the vault root
    When I run `create --class C` with no isDefinedBy
    Then the asset falls back to `01 Inbox/`
    And stderr emits no co-location warning
    # A sibling at the root is not evidence of a canonical home, so naming it
    # would be advice to move the asset nowhere. Symmetric with the inbox case.

  Scenario: isDefinedBy is set but resolves nothing -> warn, naming the anchor
    Given sibling instances of class C carrying the anchor `[[!kitelev]]` in folder F
    When I run `create --class C --property exo__Asset_isDefinedBy=[[!someoneelse]]`
    Then the asset falls back to `01 Inbox/`
    And stderr names that anchor and says no sibling shares it
    And stderr lists F with its sibling count
    # The other arm of the anchor-state wording: both priorities decline even
    # though isDefinedBy IS present, because nothing resolves it and no sibling
    # carries it.
```

## Notes

- **Sibling requirement:** `cec6af2c` (#3934) owns the *placement*; its third scenario
  explicitly requires the `01 Inbox/` fail-open. This requirement adds **observability** on
  top of it and deliberately leaves the placement byte-identical.
- **Emission condition derived from the same scan.** `scanClassNeighbours` returns both
  populations (`sameAnchor` — what decides placement; `anyAnchor` — every home of the class)
  from **one** vault pass, so the numbers printed can never drift from the numbers the
  decision used. The warning fires only when `anyAnchor` holds a folder other than the vault
  root and the inbox default — i.e. only when the class demonstrably has a home the asset
  just missed.
- **Channel:** `process.stderr` only. stdout must stay a single JSON document for the
  callers that parse it, and `rc` stays 0 — creating an anchor-less asset remains a legal
  operation. ⚠ A caller that merges the streams (`2>&1`) and parses the result now sees the
  warning ahead of the JSON; the one such caller found in the corpus survives because it
  pipes through `tail -1`.
- **Wording is part of the contract, not decoration.** The message distinguishes `absent`
  (no `exo__Asset_isDefinedBy` at all) from `empty` (the key written with an empty value,
  reachable via `--property exo__Asset_isDefinedBy=`) — saying "absent" for the latter would
  be a false statement about the asset being created. It also says "would land", because the
  placement is decided here while the file is written ~150 lines later and `--validate` can
  still refuse it — under `--dry-run` nothing is written at all.
- **Source:** ticket `3f8b640f-c690-49bd-ba9b-fbe57fc0f13f` (vault-exodev), StageSpecification
  by MemberArchitect 2026-09-10; the design (variant «a» — fix the mechanism, not the prose)
  was chosen there and is pre-approved by that stage.
