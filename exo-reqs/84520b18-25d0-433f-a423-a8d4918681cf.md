# req(exo): the CLI vault walk follows a directory symlink that leads OUT of the vault

## Job Story

When an AI session checks commands on a COPY of a vault whose `assetspaces/` is a symbolic link
to the real one, I want `resolve-buttons` (and every other reader of the CLI graph) to see the
files behind the link, because today the walk drops every symlink without a word: classes 1,
`visible` 0, `hidden` 0, rc 0, no warning — read as "nothing is bound to this asset" while the
data is intact (ticket `0a7ddb0d`; the night 04→05.10 a session drew a wrong conclusion from it).

## Mechanism (read on `origin/main` `f8233789`)

`FileSystemVaultAdapter.walkDirectory` reads a directory with `readdirSync(…, { withFileTypes: true })`
and branches on `entry.isDirectory()` / `entry.isFile()`. For a symlink's `Dirent` BOTH answer
`false`, so the entry falls through both branches. `resolve-buttons` loads the graph through this
walk in both modes (`loadVaultTriples` without cache, `CacheManager` with `--use-cache` — both
enumerate via `getAllFiles()`).

## Measurement (2026-10-13, CLI 17.14.1 = latest)

- Copy of vault-exodev whose `assetspaces` is a symlink to the original, asset `46d8c45f`,
  `resolve-buttons --json --show-hidden`: classes **1** / visible **0** / hidden **0**, rc 0.
- The original vault, same asset, same version: **2 / 19 / 20**.
- Symlinks in all 20 directories under `~/vaults/*`: **0** — the founder's own vaults are not
  affected; the defect hits sessions that verify on linked copies.

## Statement (Gherkin)

```gherkin
Given a vault whose directory entry is a symbolic link to a directory OUTSIDE the vault
When the CLI vault adapter walks it
Then the files behind the link are emitted under the LOGICAL path (through the link),
  at the link's sorted position,
  and each real directory is walked at most once — when two links of the vault reach
  overlapping trees (a diamond, a link to the parent), the files go under the FIRST by order
# This includes a vault-level link that leads into the tree another vault-level link reaches
# later (`aaa-store -> store` before `assetspaces -> store/assetspaces`; or a link inside the
# vault's own real `assetspaces/k` pointing at the store an `inbox` link reaches): the files
# are reported once, under the first link by order — the vault's author placed both links.
# "At most once" assumes the links are not replaced while the walk runs: the target is
# resolved, then read again — a link swapped in that window is not guarded against.

Given a link that lies BELOW an already-followed link
When the CLI vault adapter walks the vault
Then it is not followed, whatever its target — inside the followed tree, its ancestor, a
  sibling tree, or an unrelated directory
# Only links the walk reaches through real directories are judged. A link below a followed one
# was placed by the content of the external tree, not by the vault's author: for a linked COPY
# such a link is part of the ORIGINAL, which judges it against ITSELF — followed through the
# copy it claimed a real directory or the files of the copy's own later link under its path
# (review rounds 2 and 3). Loops inside an external tree are impossible by construction.
# ⛔ Consequence, accepted: when the original holds an outward link inside its own tree, the
# copy does not see that subtree (named in Non-goals).

Given a link whose target — as written (resolved from the link's LOGICAL folder), or as
  resolved by the filesystem — is the vault, lies inside it, or contains it
When the CLI vault adapter walks the vault
Then the link is not followed
# Without the "as written" rule a link `0-x -> assetspaces/a` next to an outward `assetspaces`
# link would take files over under ITS path; without the "contains" rule a link to a folder
# above the vault would walk everything around it and the vault itself a second time.

Given a dangling link, a self-referential link, a link to a file, or a hidden (dot-named) link
When the CLI vault adapter walks the vault
Then the entry is skipped without an exception — as before

Given a directory under a followed link that cannot be read (ENAMETOOLONG, ENOENT in a race, EIO)
When the CLI vault adapter walks the vault
Then that directory is skipped; the same failure in a directory of the vault itself still fails the walk
# Any error code is skipped there, and silently — part of the tree behind a link can go
# missing without a word (named in Non-goals).

Given a vault without links
When the CLI vault adapter walks it before and after this requirement
Then the emitted sequence is byte-identical, and the walk makes no extra stat/realpath call

Given a space declaration whose real path lies outside the vault (reached through an outward link)
When sync units of this vault are collected (`collectVaultSpecs`)
Then it is not taken as a sync unit of this vault, and the skip is named in the warnings
# A copy whose `assetspaces` is a link must not push or pull the ORIGINAL's files under its
# own (absent) watermark. The guard judges where the DECLARATION lies: a real declaration
# whose mount folder is itself a link is enumerated as before (unchanged behaviour).
```

## Non-goals

- ⛔ File symlinks — still skipped (the sanction covered directory links only).
- ⛔ The other 16 directory walks of the source tree (`ShapeLoader`, `vaultSignature`,
  `PropertyNameValidator`, …) — a separate decision; on a linked copy they stay blind behind the
  link (`validate schema`, the `query` result-cache signature, the property-name validator).
- ⛔ SET parity with `PropertyNameValidator.walk` (req `265844b7` judges ORDER of the files both
  walks enumerate; the validator does not follow the link, its scenario 2 is not violated).
- ⛔ **The vault boundary moves deliberately:** an outward link brings into the graph whatever
  `.md` lies behind it. ExoSync tarball mounts create no links, so the channel is closed in
  practice.
- ⛔ **Writing through a link is NOT guarded, and this requirement makes it reachable.** Before
  it, the graph of a linked copy was empty, so commands with preconditions (`apply`) saw
  nothing and stayed inert; now they see the graph (19 visible commands on the measured asset)
  and their writes — including paths derived from the graph, such as co-location — land in the
  LINKED target, i.e. the live vault. Commands without preconditions wrote there before too.
  Floor for sessions: build a vault copy with `cp -Rc`, not `ln -s`. A guard symmetric to the
  sync one is a separate decision.
- ⛔ macOS firmlinks (`/System/Volumes/Data/…`) are not canonicalised by `realpath` — a link
  spelled through one is judged outward. No such link exists in the vaults.
- ⛔ Other readers stay blind behind a link: besides the 16 `readdir` walks above, the
  glob-based `NodeFsAdapter.getMarkdownFiles` (used by `create`, wikilink validation,
  `ClassResolverService`) does not enter it.
- ⛔ Indexes over a linked tree: the UUID index is last-write-wins, basename/alias
  first-write-wins — a stale copy of an asset behind a link can win one of them.
- ⛔ A read failure below a followed link is skipped for any error code without a message, and
  the directory stays marked as walked: a second link straight to it (whose shorter path would
  read fine) is skipped as well.
- ⛔ **A linked copy sees LESS than the original when the original itself holds an outward link
  inside its tree** (a mount folder that is a link): through the copy that link lies below the
  followed `assetspaces` link and is not followed — silently. The live vaults hold 0 links (all
  20 directories under `~/vaults`, 13.10.2026), so copy and original agree today; that is a
  snapshot, not a property.
