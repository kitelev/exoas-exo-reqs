# req(exo): the property editor's Relations section lists inline + reified relations, creates inline relations via a range-scoped picker, and deletes a relation in place

## Job Story

When I open the property editor on an asset, I want a Relations section that shows all of
that asset's outgoing relations — both the ordinary inline (frontmatter) ones and the
ones reified into a separate `exo__Statement` asset, with a marker telling me where each
reified statement lives — and lets me add a new relation (picking a predicate and a
range-scoped target) or remove an existing one right there at the point of the relation —
so that I can manage my asset's relations without hand-editing raw frontmatter or the
statement files, and without ever seeing the same relation listed twice.

## Statement (Gherkin)

```gherkin
Scenario: the Relations section lists outgoing inline and reified relations, deduplicated
  Given an asset A whose frontmatter has inline wikilink relations
    And the triple store has exo__Statement instances where A is the subject (reified relations)
  When the property editor's Relations section builds its list
  Then it shows A's inline relations (wikilink-valued frontmatter, excluding housekeeping keys)
    And it shows A's outgoing reified relations, each with the factual "reified · <AS>" marker
    And a relation present BOTH inline and reified appears ONCE, shown as inline (inline wins)
    And a reified relation whose object is a Literal is excluded (it is a property, not a relation)
    And an inline relation carries no marker

Scenario: create a new inline relation via a range-scoped picker
  Given the Relations section's create affordance
  When I pick a predicate and a target asset
  Then the picker's candidate targets are scoped to the predicate's range (not the whole vault)
    And confirming appends the relation as an inline wikilink to A's frontmatter
    And an existing multi-value predicate keeps its other values (the new value is appended, not replacing)

Scenario: the range-scoped picker works for a SYMBOLIC range IRI (2026-09-17, ticket 7d91d13a, PR #4253)
  Given a predicate whose exo:Property_range object is the symbolic ontology IRI <ns>#<Local>
    (the form the converter emits for every class with a prefix__LocalName label — 348 of the
    350 object ranges in vault-exodev on 2026-09-17, across 33 namespaces, 26 of them outside
    FrontmatterService.IRI_PREFIX_MAP; the 2 remaining ranges are path-form obsidian://…/<uid>.md)
  When the Relations section resolves that predicate's picker candidates
  Then the range key handed to the candidate resolver is the class LABEL <ns>__<Local>
    (via the shared Namespace.fromTermIRI inverse — every registered and ad-hoc namespace)
    And the candidates are the instances of that class AND of every subclass (req 15f48fa1 closure)
    And a path-form range still resolves to the class UID, exactly as before
    And a symbolic range naming the ROOT class (exo#Asset, no superClass) reaches its definition by label

Scenario: delete a relation in place
  Given a relation row in the Relations section with a delete affordance
  When I delete an inline relation
  Then that single value is removed from A's frontmatter (sibling values of the same key are kept)
    And the key is dropped only when its last value is removed
  When I delete a reified relation
  Then its backing exo__Statement asset is deleted (verify-after-write)
    And all writes go through app.vault.modify / app.vault.delete (Desktop↔Mobile parity)

Scenario: scope boundary (Task 3.1 = list + create + delete)
  Then there is NO reify/de-reify toggle in this section (that is Task 3.2)
    And new relations are always created inline (reify-on-share is Task 3.2)
```

## Verification

**Revert-verified (component binding):** `@req:e084627c-38b7-4498-be0a-a3e07e790943` —
`packages/obsidian-plugin/tests/unit/presentation/components/RelationsSection.test.tsx`
asserts the pure relations-editor model (`relationsEditorModel.ts`) and the
`RelationsSection` React component (rendered via `@testing-library/react`, jsdom):
the unified list de-duplicates an inline+reified duplicate to a single inline row; a
reified row shows the `reified · <AS>` marker and an inline row none; a Literal-object
reified relation is excluded; create appends an inline wikilink to the multi-value
frontmatter without dropping siblings; delete-inline removes one value (keeping
siblings) and delete-reified invokes the statement-delete callback. The type-preserving
break — making `dedupeRelations` skip the dedup (return inline ∪ reified verbatim) —
turns the dedup case RED (the duplicate then appears twice); restored → GREEN.

**Gap closed 2026-09-17 (ticket `7d91d13a`, PR #4253, bug-fix under this req — no new req):**
the modal's `buildPredicateRangeMap` derived the picker key with `uidFromIri`, which slices a
symbolic range IRI to the bare local name (`Effort`) — neither UID nor label — so the picker was
EMPTY for 348 of the 350 object ranges on the live vault: this req was effectively unmet for
nearly every predicate, the gap surfaced in the IRI form (dual-IRI, `sparql-iri-form-pre-verify`).
The spec is extended above, not replaced. Axes R1–R5 in
`packages/obsidian-plugin/tests/unit/PropertyEditorModal.test.ts` (`@req:e084627c-…`) drive the
REAL `buildRelationsDeps()` over a REAL InMemoryTripleStore + fake `app.metadataCache`; mutant
driver: revert to `uidFromIri` alone → R1/R3/R4 RED, `FrontmatterService.normalizeIRI` → R4 RED,
path-form fallback broken → R2 RED.
