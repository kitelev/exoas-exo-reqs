Generic guarded CLI primitive to DELETE a frontmatter property from an existing vault asset — the delete-side counterpart of `set-property` (#3795) / `set-property --input` (#3848). Closes the recurring "I had to raw-Edit / Bash-strip a frontmatter line" dogfooding gap (empirical 2026-07-20: `/weekly-recurring-tasks` needed to remove `ems__EffortPrototype_startTime`/`_endTime` from prototypes; `set-property … value:null` errors, and a Bash strip bypasses the PreToolUse hook-coverage + SHACL floor).

**Design decision (chosen autonomously, option 2 of the issue):** a dedicated `remove-property <path>` verb, symmetric to `set-property`, over overloading `set-property --unset` (a "set" verb that deletes is confusing UX). It reuses the SAME guard denylists, the canonical-YAML-key mapping (#3944), and the mounted-TBox property-name validation as `set-property`, delegating to `FrontmatterService.removeProperty`.

## Job Story
When I audit vault assets and need to delete an obsolete non-guarded frontmatter property (e.g. a recurring-prototype's `startTime`), I want a first-class CLI verb so I don't bypass the product's hook-coverage / SHACL floor with a raw Bash strip.

```gherkin
Feature: exocortex remove-property — delete a non-guarded frontmatter property

  Scenario: delete a non-guarded scalar property
    Given a vault asset carrying a non-guarded property (e.g. ems__EffortPrototype_startTime)
    When I run `exocortex remove-property <path> --property ems__EffortPrototype_startTime`
    Then the key is removed from the frontmatter
    And exo__Asset_updatedAt is bumped
    And the file remains a valid asset (no Bash-bypass of the hook-coverage / SHACL floor)

  Scenario: refuse a state-machine / precondition-guarded property
    Given a property that has a dedicated guarded command (status / zone / parent / label / instance_class / a fact-timestamp / a plan-date / votes / the archive flag)
    When I attempt to remove it via remove-property
    Then the command REFUSES it, naming the dedicated `apply` command to use instead
    And the file is left byte-unchanged

  Scenario: refuse the immutable identity properties
    Given exo__Asset_uid or exo__Asset_updatedAt
    When I attempt to remove it via remove-property
    Then the command REFUSES it as immutable / self-managed, leaving the file unchanged

  Scenario: canonical YAML key mapping for the unprefixed-asset-field whitelist
    Given an asset with an `aliases:` list
    When I run `remove-property <path> --property exo__Asset_aliases`
    Then the canonical bare `aliases:` key is removed (not a literal `exo__Asset_aliases:` key)

  Scenario: idempotent no-op + dry-run preview
    Given a property that is absent from the asset
    When I run remove-property for it
    Then the command succeeds (no-op, key already absent) and bumps updatedAt only if a change occurred
    And `--dry-run` previews the resulting frontmatter without writing
```
