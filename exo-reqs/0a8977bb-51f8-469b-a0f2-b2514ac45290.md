# Contract

Two silent-failure modes measured on published CLI 16.230.0 against a real vault
(vault-exodev, ~1.8k assets). Neither raises; both return output that reads as data.

```
agg:bogusZzz(?n)      →  [ {}, {}, {} … ]   (no error, no aggregation at all)
agg:median(?n, ?n)    →  "33"                (2nd argument SILENTLY dropped)
```

The second is the dangerous one: it is exactly the shape a user writes for a
two-column statistic (`agg:corr(?x, ?y)`, issue #3994) and it returns a
plausible ONE-column number.

## Given/When/Then

**Scenario: an unregistered name inside the agg: namespace raises**
- Given the aggregate IRI `https://exocortex.my/ontology/agg#bogusZzz` is not in
  `BUILT_IN_AGGREGATES` and not in `CustomAggregateRegistry`
- When a query selects `(agg:bogusZzz(?n) AS ?r)`
- Then translation raises, naming the unknown local name AND listing the registered ones
- And the query does NOT return solutions

**Scenario: a function OUTSIDE the agg: namespace is untouched**
- Given an IRI in any other namespace (e.g. `ex:myFunction(?n)`)
- When it appears in a SELECT expression
- Then behaviour is unchanged (it is a normal function call, not an aggregate)

**Scenario: a wrong-arity call to a REGISTERED aggregate raises**
- Given `agg:median` is registered and single-argument
- When a query selects `(agg:median(?x, ?y) AS ?r)`
- Then translation raises, stating the aggregate takes exactly 1 argument and that
  two-column aggregates (corr/slope/intercept) are tracked by #3994
- And no value is computed from `?x` alone

**Scenario: a correct single-argument call is unaffected**
- Given `agg:median(?n)` over a populated solution set
- When executed
- Then it returns the median exactly as before this requirement

## Why this is not #3994

#3994 ADDS two-column aggregates. This requirement makes their absence **loud**.
Shipping #3994 without it leaves a partial implementation indistinguishable from a
working one; shipping this without #3994 already removes a false-data path.
