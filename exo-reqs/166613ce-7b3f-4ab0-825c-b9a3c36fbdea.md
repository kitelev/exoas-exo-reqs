# req(exo): `query --batch` and `run-query --batch` — many queries from one file, ONE graph load

## Job Story

When a pipeline script needs ~20 read queries against the same vault in one run, I want to hand the
CLI ONE file with all of them, because today every `query` call pays a full graph load: on a clone of
vault-exodev a single call with a cache hit costs 10.1–14.9 s, and the task selector makes 19 such
calls per run — 244.5 s of CLI time; the same 19 queries as one batch took 22.2–24.4 s with one load
(ticket `8ada0615` §1, §7; RFC `049bc5f1`, variant A).

## Mechanism (read on `origin/main` `bc669c7d`)

Each `query` invocation runs `loadVaultTriples` into a fresh store; with the result cache enabled it
also walks every `.md` with `stat` for the vault signature (`computeVaultSignature`). A query error
leaves through `handleSparqlError` → `process.exit`. There is no way to ask several questions over
one loaded graph.

## Statement (Gherkin)

```gherkin
Feature: query --batch and run-query --batch — many queries over one graph load

  Scenario: N queries from a file load the graph once and answer by name in file order
    Given a batch file holding a JSON array of entries {"name", "sparql"} with unique names
    When I run `query --batch <file> --vault <vault> --no-cache`
    Then the graph is loaded exactly once for the whole batch
    And stdout carries one NDJSON line {"type":"result","name",...} per entry, in the order of the file
    And the last line is {"type":"summary",...} with "graphLoads": 1 and "queries": N
    And progress and notices go to stderr, never to stdout

  Scenario: each answer equals the single query answer for the same text
    Given an entry whose text is also run as `query "<text>" --format json`
    Then a SELECT entry answers {"ok":true,"kind":"select","count","bindings"} whose bindings equal that output
    And a CONSTRUCT entry answers {"ok":true,"kind":"construct","triples"} equal to the single query's triples

  Scenario: a failing entry does not stop the batch
    Given a batch in which one entry has a syntax error and the others are valid
    Then the failing entry answers {"ok":false,"error":{"type":"syntax"}} and every other entry is answered
    And the summary line is still printed last, counting the entry in "failed"
    And the exit code is 5

  Scenario: an update request in a batch is refused, not executed
    Given an entry holding INSERT DATA or DELETE DATA
    Then it answers {"ok":false,"error":{"type":"update-rejected"}}
    And a later entry of the same batch does not see the inserted triple

  Scenario: no error quotes the content of the batch file
    Given a batch file that is not JSON, or an entry with an invalid name, an unknown field or a broken query
    Then neither the refusal nor the entry's error contains text taken from the file
      (only the error type and the entry number or field position)
    And a `run-query --batch` error carries only its type — a parameter value from the file is never echoed

  Scenario: an answer reaches the pipe before the next entry starts
    Given a reader on stdout
    Then each result line is written and confirmed before the next entry executes
    And when the reader closes the pipe the batch stops: no further entry executes and the exit code is 1

  Scenario: the vault signature for the result cache is computed at most once per batch
    Given the result cache is on
    Then the vault signature is computed once for the whole batch
    And under --no-cache it is not computed at all

  Scenario: answers from the result cache are the computed answers
    Given the same batch is run twice within the cache TTL, the vault unchanged
    Then the second run answers every entry from the cache, equal to the first run, in the same order
    And it reports "graphLoads": 0 and "queryResultCacheHits" equal to the number of entries
    And an entry is served from an answer a single `query` cached for the same text
    And a vault edit between the runs makes the answers fresh, not stale
    And a failed WRITE to the result cache keeps the computed answer (a warning with the errno on stderr)

  Scenario: malformed batches and incompatible flags are refused before the graph is loaded
    Given a batch that is not a JSON array, is empty, holds a non-object, a name outside
      ^[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$, a repeated name or an unknown field —
      or `--batch` combined with a positional query, --template, --param, --dry-run, --explain,
      --stats, --output json or --format csv|ntriples
    Then nothing is loaded and the exit code is 2
    And a missing batch file exits 3; a directory is refused; /dev/stdin and process substitution are accepted

  Scenario: a timed-out entry answers type timeout and the batch goes on
    Given an entry that exceeds --timeout while yielding to the event loop
    Then it answers {"ok":false,"error":{"type":"timeout"}} with the CLI message built from the options
    And the next entries are answered, the entry counts as failed, the exit code is 5

  Scenario: a graph load failure answers every entry
    Given the graph cannot be loaded
    Then every entry answers error type "load", the load is attempted once, the exit code is 5

  Scenario: line separators inside values cannot cut a line
    Given a value containing U+2028, U+2029 or U+0085
    Then it is written as a JSON escape, so splitting stdout on "\n" or by a splitlines()-style reader gives one line per answer

  Scenario: run-query --batch runs named queries by uid over one graph load
    Given a batch file holding entries {"name","uid","currentAsset"?,"params"?,"paramsIri"?}
    When I run `run-query --batch <file> --vault <vault>`
    Then the graph is loaded once and each entry answers the same data `run-query <uid> --format json` prints
      with the same context ("currentAsset" and "paramsIri" reach the body as IRIs)
    And an entry whose uid names no query answers error type "not-found"
    And an entry that leaves a $parameter of the body unfilled answers error type "unset-token"
    And `--batch` combined with a positional uid, --current-asset, --param, --param-iri or --output json is refused (exit 2)
```

## Output contract for consumers

- Tell lines apart by `"type"` (`result` / `summary`), never by name — an entry may be called `summary`.
- Split stdout on `"\n"` only.
- **No summary line ⇒ the batch did not finish** (killed, out of memory): the entries without an answer
  are re-run one by one (a single `query`, or a batch of one), and an external `timeout` over the batch
  is mandatory — a compute-bound query that ignores `--timeout` (bug `8fe905e9`) can take the whole
  batch down with it, where a series of single calls would lose only that query.
- Exit codes: 0 — every entry succeeded; 5 — at least one entry failed; 2 — refused before start;
  3 — no batch file; 1 — the reader closed stdout.

## Verification

Integration axes in `packages/cli/tests/integration/query-batch-8ada0615.integration.test.ts` and
`query-batch-signature-8ada0615.integration.test.ts` (51 axes; graph loads are counted by spies on the
loader, independent of the `graphLoads` field the code reports about itself); 50 mutants in four
`*-8ada0615.spec.json` specs, each reddening its expected axes. Parity on real queries: the 19 queries
of the task selector run as one batch and as 19 single calls on a clone of vault-exodev must agree
19/19 as a sequence (ticket `8ada0615` appendices В–Г).

## Non-goals

- Moving the pipeline onto batches and the "≤ 3 graph loads per selector run" target — phase 2,
  ticket `da8c7d69`.
- Cancelling a compute-bound query on timeout (bug `8fe905e9`; RFC variant B).
- ASK in `query` (ticket `3254ccba`) and the dead `--no-optimize` flag (bug `954c7dfa`): the batch
  shares the single query's execution function, so it inherits both behaviours today and both fixes
  later. Today an ASK entry answers error type "execution", as a single `query` exits 1.
- Changing the vault-signature formula so that it is taken from the loader's own file walk: the two
  walks enumerate different file sets, and a batch signature would stop matching the single-query
  signature (ticket `8ada0615` §3 Р3).
- The single `query` and `run-query <uid>` keep their behaviour unchanged (a single `query` still
  accepts INSERT DATA in memory; a single `run-query` does not refuse an unset $parameter).
