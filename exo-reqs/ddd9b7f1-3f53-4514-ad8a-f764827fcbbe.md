# req(exo): a query__TableBlock parses into the query-table kind, Layout blocks are linked block → Layout and ordered by exo__LayoutBlock_order, the Layout is selected by class label or UID, and a SELECT result carries its projection in declared order

## Job Story

When I open a daily note, I want a table of the rows of a named query (the first one: «Эпизоды
дня») drawn from a Layout I wrote as data, because today any new view of a page needs code
(RFC 9821a379 §Проблема). The core half: the block kind exists, the Layout finds its blocks and
the right notes, and the query hands the table its columns in the order the query declares.

## Statement (Gherkin)

```gherkin
Given a block asset of class query__TableBlock (by label, or by its class UID 0e865363-da38-480c-824f-e59aabec3514)
  and query__TableBlock_query = "[[<query uid>]]" or "[[<query uid>|<label>]]"
When the core parses the block
Then it is a block of kind "query-table" whose query is <query uid> — the wikilink TARGET (before "|" and "#"), not its alias
  and its row cap is query__TableBlock_limit (100 when absent; a value that is not a positive STRICT integer — "2.5", "10abc", "1e2", 0 — → 100 with a warning)
  and its empty text is query__TableBlock_emptyText ("Нет строк" when absent)

Given a block asset of class query__TableBlock without query__TableBlock_query
When the core parses the block
Then the block is rejected with a warning naming query__TableBlock_query, and the Layout repository does not index it (it is never drawn)
  and a LIST value is rejected with its own message ("must be a single wikilink"), not "required"

Given query__TableBlock_query names the query by label ("[[Эпизоды, покрывающие день]]") instead of uid
When the core parses the block
Then the block is kept and a warning says the runner finds a query only by its exo__Asset_uid
# Kept, not rejected: the plugin then shows the runner's «query not found» IN the block instead of
# a section that silently is not there.

Given exo__LayoutBlock assets that name a Layout through exo__LayoutBlock_layout — the wikilink TARGET (before "|") is the Layout's uid, file name or label; the text after "|" is ignored
When the Layout repository assembles its snapshot
Then the Layout's blocks are exactly the blocks naming it, by exo__LayoutBlock_order ascending,
  blocks without an order after the numbered ones, ties and the unordered tail by block uid ascending
  and a block naming another Layout is not among them
  and a block whose TARGET names two Layouts (a label they share) is attached to none, with a warning
  and "[[<uid of L1>|<label of L2>]]" — a block copied from L2 with its alias left behind — belongs to L1
  and an exo__LayoutBlock_order that is not a STRICT integer ("1.5", "2nd", 1.5) counts as absent, with a warning
# exo__Layout_blocks is no longer read (RFC 9821a379 decision 3; reading both forms was rejected
# at the interview). On 2026-10-24 no vault holds an exo__Layout asset — nothing to migrate.

Given an exo__Layout that no block names
When the Layout repository assembles its snapshot
Then the Layout is not in the snapshot (a warning says exo__Layout_blocks is no longer read), so the selector never picks it
  and a Layout that still carries exo__Layout_blocks is warned that the list is not read
  and isLayout() accepts the parser's Layout (blocks: []) as well as the assembled one

Given a Layout whose exo__Layout_targetClass is "[[<class uid>]]", "[[<class uid>|<label>]]" or "[[<label>]]"
  and a note whose exo__Instance_class names the same class in any of these forms
When the plugin's LayoutSelector resolves the note's Layout
Then that Layout is selected — a bare UUID on either side is resolved to the class label through the metadataCache
  and a note of another class does not get it
# Without a resolver (any caller other than the plugin's onload) a bare UUID stays a UUID —
# the pre-9821a379 behaviour, byte-identical.
# On the NOTE side "[[<uid>|<alias>]]" is decided by its ALIAS — what resolveSymbolic (named by
# RFC decision 4) does, the codebase-wide class-ref convention (#2764). Exposure 2026-10-24: 0
# (every alias in the 388 daily notes of vault-my equals the class label).

Given a SELECT named query whose projection order differs from the order its variables are bound
When NamedQueryRunner.run evaluates it
Then the SELECT envelope carries variables = the projection in the order the query declares it
  (a projected variable bound in no row is still listed; "(expr AS ?x)" is listed as x in its place)
  and for SELECT * — every variable bound in the rows, in first-seen order
  and without a store the empty envelope still carries the declared projection
```

## Non-goals

- Drawing the query-table block (provider, «индекс стабилен», cells, error isolation, the
  unset-token bypass) — the plugin ticket `058bad52` of the same RFC. Until it lands the
  renderer parses the block and draws nothing.
- PanelResolver's and ThemeResolver's own targetClass comparison (the `commandPanel` / theme
  slots, `ExocortexPlugin` layoutProvider) — unchanged: no canonicalization, no «Layout without
  blocks is not selected».
- CLI `run-query` column order — still the binding order (idea `cb16b1b9`).
- The TBox assets of the new vocabulary — phase 1 of the RFC.
