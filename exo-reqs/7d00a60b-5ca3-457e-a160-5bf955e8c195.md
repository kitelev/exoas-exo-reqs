# req(exo): a class wikilink resolves FROM DISK — a cold metadataCache no longer yields ZERO command buttons (Tier 2)

## Job Story

When Obsidian's index resets on my phone (reinstall, new device, a large re-sync), I want the
Exocortex command buttons to keep working while it re-indexes — so that I am not locked out of my
own system for as long as the re-index takes.

## Why this is not covered by an existing requirement

`NoteToRDFConverter.convertNoteFromFrontmatter` (RFC 8f93ff95, ExoSync disk-read reindex) already
decouples **Tier 1** — an asset's OWN frontmatter — from `metadataCache`, and its docstring
**explicitly defers this one**:

> «Wikilink TARGET resolution … still flows through the adapter — acceptable for Tier 1 … **Full
> disk-resolution of wikilinks is Tier 2.**»

That deferral was correct for its own goal (Layout visibility needs only the asset's own triples).
It is **not** acceptable for the command surface, and this requirement states why.

## The mechanism (measured, not inferred)

`ObsidianVaultAdapter` reads BOTH ends through the same cache — own frontmatter
(`getFileCache(...).frontmatter`, :60) and link targets (`getFirstLinkpathDest`, :161). So on a cold
cache the class reference never resolves:

1. `NoteToRDFConverter.valueToClassURI:1606` — `getFirstLinkpathDest(classRef,"")` returns `null`,
   the resolution block is skipped, and the object stays a `Literal` holding the raw wikilink text.
2. `LazyAssetGraphLoader.walkClassAndPrototypeRelations:312` — `if (!(t.object instanceof IRI)) continue`
   drops every non-IRI, so the class file is **never loaded**.
3. No class ⇒ no `rdf:type` triple ⇒ `CommandResolver.findPaletteEnabledCommands` matches nothing.

⇒ **Tier 1 without Tier 2 yields ZERO buttons, not "fewer" buttons.**

The identical literal-vs-IRI break is already documented from a DIFFERENT root — the
`dependsOn`-closure requirement (RFC 430e84f1 P3, alpha-tester incident 2026-07-27) describes the
class file being *absent from disk*. Here the file is present and merely unreachable through a cold
cache. Two roots, one break — this is a second, independent confirmation of the same mechanism.

## What actually depends on the cache (vault measurement, 2026-08-29)

Form of the `exo__Instance_class` value across all three vaults — 37 071 files, 40 656 values, read
from RAW frontmatter (SPARQL discards the alias and cannot answer this):

| form | count | share | resolution layer | needs cache? |
|---|---|---|---|---|
| `uid-bare` (double-bracket wikilink whose body is a bare uuid) | 38 317 | **94.2 %** | layer 3 — `isUUID` → `getFirstLinkpathDest` | **YES — this is what breaks** |
| `uid+alias` (uuid, pipe, then a `prefix__Name` alias) | 2 182 | 5.4 % | layer 2 — alias → `expandClassValue` | no — already works cold |
| `label-bare` (the `prefix__Name` label alone) | 157 | 0.4 % | layer 1 — direct `expandClassValue` | no — already works cold |

`valueToClassURI` has THREE layers and only the third touches the vault, so the blast radius is
exactly the `uid-bare` form. `Namespace.forPrefix` is generative (unknown prefixes still yield a
namespace), which is why layers 1-2 need no vault at all.

## Statement (Gherkin)

```gherkin
Scenario: a cold cache still yields the class type triple
  Given a vault whose metadataCache returns null for every frontmatter and every linkpath
  And an asset whose exo__Instance_class is in the `uid-bare` form (a wikilink whose body is only the class uuid)
  And that class file exists on disk with a namespace-parseable exo__Asset_label
  When the asset is converted to RDF
  Then the exo__Instance_class object is an IRI, not a Literal
  And the graph loader recursively loads the class file
  And an rdf:type triple is emitted for the asset

Scenario: the already-working forms are not disturbed
  Given the same cold vault
  When an asset carries the `uid+alias` or the `label-bare` form
  Then the class IRI is produced WITHOUT any disk or cache lookup
  And the resolution is byte-identical to the current behaviour

Scenario: mobile parity
  Given the plugin runs on iOS where Node fs is unavailable
  When the disk resolution path is exercised
  Then every read goes through vault.adapter
  And no Node-only dependency (fs / fs-extra / child_process) is reachable from it
```

## Non-functional constraint (this is what makes it viable on a phone)

The UID index must be built **from the directory listing only** — under the UID-CANON TBox invariant
a class file's name IS its uuid, so no file contents are read to build it. The CLI's battle-tested
`FileSystemVaultAdapter.buildUuidIndex` already works exactly this way (`walkDirectory` + basename
regex, zero `readFileSync`). Its expensive basename/alias index — which DOES read every file — is
built lazily on a UUID miss, and per the measurement above **it is not needed for this requirement
at all**: those forms never reach layer 3.

⛔ The CLI implementation is bound to `fs-extra` and therefore cannot be imported by the plugin. The
ALGORITHM ports; the source file does not.

## Non-goals

- Wikilink positions other than the class reference (`prototype`, Exo 0.0.3 anchors, body links).
  They flow through the same resolver and would benefit, but only the class reference gates
  `rdf:type`, and therefore the buttons. Widening the scope without its own measurement is out.
- Making Obsidian's own re-index faster. This requirement makes the plugin independent of it.
- Anything about the 0.4 % label-form legacy debt (8 distinct targets, `pmbok__*` mostly) — those
  already resolve cold, and re-canonising them is a separate data question.
