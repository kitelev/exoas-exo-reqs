# req(exo): ExoSync honors GitHub Retry-After in rate-limit backoff (RFC 6a1a6518 / A)

> Source: RFC `6a1a6518-613c-447c-a75b-9d30f4ae3008` (Approved) — ExoSync perf & rate-limit revision of the baseline RFC `4e4dc453` R6 backoff primitive. 4-agent adversarial review converged: value is sharply in A (rate-limit resilience, trigger-agnostic). This requirement is **Phase 1 / A only**.
>
> **Why it matters (incident 2026-07-27):** a 1204-file `broader→genus` sweep hit a GitHub **secondary** 403 on `POST git/trees` (at core 4994/5000 — misleading, secondary limits are invisible to `/rate_limit`). The transport discards response headers on throw, so the backoff never saw `Retry-After`; 3 blind ~1-8s retries could not survive the minutes-long secondary window → `pushed 0` → ~15 min manual recovery. This req makes the backoff **wait exactly as long as GitHub asks**, so a bulk sync re-syncs itself (`pushed N`, not `pushed 0`) within a bounded per-sync budget.
>
> **⛔ Data-loss constraint:** the enrichment MUST attach fields and preserve `.message` byte-for-byte — it must NOT replace the error with a typed one — because `isNonFastForwardError` (D16) keys off `.message`; misclassifying a 422 non-fast-forward as non-retryable would route a contended push around quarantine → silent data loss.

## Job Story

When a bulk ExoSync push hits a GitHub secondary rate-limit, I want the backoff to wait exactly as long as GitHub's `Retry-After` tells it (or at least a minute when there is no header), bounded by a global per-sync time-budget, so the sync finishes itself instead of giving up with `pushed 0` and forcing me to re-run it by hand — without ever breaking the auth / rate-limit / non-fast-forward classification the engine depends on.

## Statement (Gherkin)

```gherkin
Background:
  Given the ExoSync transport (CLI fetch and plugin Obsidian requestUrl) throws on a non-2xx response
    And withRateLimitBackoff wraps the transport once, covering reads and writes
    And three parsers classify the thrown error by its .message string:
        isRateLimitError, isAuthError, isNonFastForwardError

Scenario: a rate-limited error carries Retry-After and the backoff sleeps exactly that
  Given a transport that responds 403 with header "Retry-After: 120" and a rate-limit body
  When a request goes through the backoff decorator
  Then the thrown error carries own-property retryAfterMs = 120000
    And the decorator sleeps ~120000 ms (not a jittered exponential guess) before retrying

Scenario: absent Retry-After falls back to at least 60 seconds
  Given a transport that responds 429 with NO Retry-After / x-ratelimit headers
  When a request goes through the backoff decorator
  Then the decorator waits at least 60000 ms (the documented secondary fallback), then exponential

Scenario: the three parsers classify the enriched error identically to the bare error
  Given a bare Error and an enriched Error with the SAME .message
  When isRateLimitError / isAuthError / isNonFastForwardError run on each
  Then each parser returns the same verdict for both
    And .message is byte-for-byte identical (the transport attaches fields, never replaces the string)
    And a 422 "git/refs" non-fast-forward error stays isNonFastForwardError=true after enrichment

Scenario: case-insensitive header lookup on the plugin (iOS) transport
  Given the plugin transport whose requestUrl().headers is a Record with arbitrary casing
  When the response carries the header as "retry-after" OR as "Retry-After"
  Then both casings resolve to retryAfterMs on the thrown error

Scenario: a global per-sync time-budget warn-defers instead of stalling every repo
  Given a sync of many repos where a repo keeps rate-limiting
  When the accumulated rate-limit wait for this sync would exceed the per-sync budget
  Then the backoff rethrows the rate-limit error (warn-not-block, D12) rather than sleeping again
    And later repos fail fast (budget spent) instead of each waiting a full window
    And the budget resets at the start of each syncAll / sync
    And maxRetries defaults to at least 6
```

- **Preserve `.message` (3-parser identity):** make the enrichment mutate/replace `.message` → a `422 git/refs` error stops being `isNonFastForwardError` AND/OR a plain-403 auth error stops being `isAuthError` → **RED**; restore attach-only → all three classify identically **GREEN**.

## Design notes

- **Attach, never replace.** A shared core helper (`rateLimitHeaders`) parses the headers via a case-insensitive getter and attaches `retryAfterMs` / `rateLimitReset` / `rateLimitRemaining` as **non-enumerable** own-properties (invisible to `JSON.stringify` / `Object.keys` / telemetry, matching the codebase's `#private`-field discipline) while leaving `.message` untouched. Both transports call the same helper (no duplicated parsing across CLI/plugin — [[multi-parser-predicate-migration]]).
- **Delay priority** (GitHub secondary-limit guidance): `Retry-After` present → wait exactly that; else `rateLimitRemaining === 0` with a `rateLimitReset` → wait until reset; else ≥60s floor then exponential-with-jitter.
- **Global budget lives on the engine**, is passed into the per-request decorator, and resets on every top-level `syncAll`/`sync` (both flip the D11 single-flight guard). Exhaustion rethrows the (already-classified) rate-limit error — the message/fields are preserved, so the per-repo cycle still fails warn-not-block (D12). `maxTotalRateLimitWaitMs` is configurable (default ~5 min).
- **Trigger-agnostic:** honors whatever GitHub signals (CPU-time / content-creation / points). The exact secondary mechanism is unconfirmed and irrelevant to this fix.
