# req(exo): query --stats prints the predicate-pruning line — on a fresh run and on a result-cache hit

## Job Story

When I look at the execution statistics of a query, I want to see what share of the loaded graph the
query actually needs — the pruning mode, the number of predicates and «N of M loaded triples» — on a
fresh run and also when the answer comes from the result cache (today the cache hit prints no statistics
at all), so that the gain of on-demand loading (RFC `308a52c3` «Загрузка по запросу», Д4, phase 4) is
visible per query before the loader starts pruning (ticket `c7a94d8e`).

## Mechanism (read on `origin/main` `7db41a60`, v17.21.x)

`query --prune-report` (req `551f5dbd`) computes `pruneReport(analysis, triples)` — mode, P' and the
share in loader units (duplicates included). The text `--stats` block lives in the UPDATE, CONSTRUCT and
SELECT branches of `sparql-query.ts`; the result-cache hit prints the answer and returns before any
statistics block. The cache (`QueryResultCache`) is shared by `query` and `query --batch`.

## Statement (Gherkin)

```gherkin
Feature: query --stats — the predicate-pruning line

  Background:
    Given a vault loaded by the same loader as plain `exocortex query`

  Scenario: fresh run prints the line
    When `exocortex query "<sparql>" --stats` runs the query
    Then the «📊 Execution Statistics» block carries, after «Results returned» (SELECT), «Triples generated» (CONSTRUCT) or «Triples scanned» (UPDATE), the line
      «Predicate pruning: <mode> — needs <k> predicate(s), <N> of <M> loaded triples (<x.xx> %)»
    And mode, N, M and the share are those of `pruneReport` (the same numbers `--prune-report` prints in one run on one snapshot)
    And for a full load the mode is «full load (<all reasons>)» and k is «all K», K the number of distinct predicates of the loaded graph

  Scenario: result-cache hit prints the recorded line
    Given the answer was cached by a run with `--stats` in text output
    When the same query is run again with `--stats` and the result cache answers
    Then a statistics block is printed with the recorded line and the mark «— recorded with the cached answer» and «Query result cache: HIT»
    And the vault is not loaded for the line

  Scenario: nothing recorded
    Given the answer was cached without `--stats`, under `--output json`, by a batch, by an older CLI, after a failed analysis, or the recorded text is not one «Predicate pruning: …» line without control characters
    When the cache answers a `--stats` run
    Then the line reads «Predicate pruning: not recorded with the cached answer (rerun with --no-cache to measure)»

  Scenario: statistics never change the answer
    Then without `--stats` and under `--output json` nothing changes: no analysis, no line, no block on a hit
    And the JSON `data` of a hit and the batch records are unchanged
    And a failed analysis prints «Predicate pruning: not computed — <Error>: <message>», the answer is printed and cached, the line is not recorded
```

## Non-goals

`--stats --output json`; `run-query --stats`; `--stats` in `query --batch` (still refused); the ASK
branch (seam with ticket `3254ccba`). Until phase 3b the loader reads the whole graph, so the line says
«needs … of M loaded triples», not «loaded N».
