# req(exo): `create` / `set-property` отказывают на `exo__Asset_isDefinedBy`, чья цель резолвится, но не является `exo__Ontology`

## Job Story

Когда бот или скрипт собирает вызов `create` и подставляет в анкер **прототип** вместо онтологии,
я хочу получить отказ в момент записи — а не молча созданный ассет, который держит SHACL-baseline
целого vault красным до тех пор, пока кто-нибудь не запустит аудит.

## Контекст

Бот ExoAssistant (транскрипт `915265dc`, 2026-08-30 00:24) на запрос «создай задачу на сон по
соответствующему прототипу» подставил прототип `628bc0e5` (`ems__SessionPrototype`, метка «Сон»)
в `exo__Asset_isDefinedBy`. `create` валидирует, что wikilink **резолвится**, но объявленный
**range** свойства (`exo__Property_range` = `exo__Ontology`) не проверяет ⇒ `rc=0`. Ассет
`beb2600c` 15 дней нёс `sh:class`-violation и держал baseline `vault-my` красным; CI
`kitelev/exoas-my` не доходил до шагов imports/membership/depends.

Репро восстановлено из git-истории data-репо, а не пересказано: коммит `exoas-my@5ff28539`
(2026-08-30) записал `exo__Asset_isDefinedBy: "[[628bc0e5-…]]"`, коммит `6a5e4fce` (2026-09-14)
заменил его на `[[a2f5ac16-…]]` (`$kitelev`). На живом vault `628bc0e5` — инстанс `868c2297`
(прототип), `a2f5ac16` — инстанс `829b9b3b`, то есть самого класса `exo__Ontology`. Обе стороны
одной реальной починки и служат фикстурой осей.

⛔ Дефект **вероятностный** (LLM): остальные сессии того же бота анкер проставили верно.
Требование закрывает **поверхность записи**, а не атрибуцию писателя.

## Почему гвард на ЗАПИСИ, а не расширение существующего аудита

`audit ontology-membership` этот же класс уже детектирует — но **постфактум**: он судит то, что
**уже лежит на диске**. Предмет требования в том, чтобы запись **не состоялась**; аудит на этот
вопрос не отвечает, как бы хорош он ни был. Пятнадцать дней из §Контекст — это и есть промежуток
между «записано» и «кто-то запустил аудит».

## Почему БЕЗУСЛОВНО, а не за флагом `--validate`

Active-req `dd9ab956` вынес полную SHACL-проверку за opt-in флаг, и причина названа в нём прямо:
она стоит `convertVault` на каждый `create`. Здесь этой цены нет: `create` **уже** резолвит
`isDefinedBy`, чтобы разместить ассет (co-location), поэтому добавляется чтение frontmatter цели
плюс, изредка, один-два шага вверх по `exo__Class_superClass`. Отложенная цена не возвращается ⇒
оснований прятать проверку за флаг нет.

⛤ **Отношение к `dd9ab956` — УТОЧНЕНИЕ, а не отмена.** Его сценарий «default OFF — create is
byte-identical without the flag» сформулирован широко («a candidate that violates **a** shape»), а
запертый им случай — **datatype**-нарушение (`ems__Task_count=not-a-number`), не `sh:class` у
`isDefinedBy`. Этот req сужает квантор: `sh:class` у `exo__Asset_isDefinedBy` гейтится писателем
безусловно, **все прочие** shape-нарушения по-прежнему только под `--validate`. Клауза `dd9ab956`
не становится ложной и не снимается; её статус не меняется.

## Что НЕ отвергается (четыре fail-open формы, замерено)

Co-location объявляет четыре законные формы `isDefinedBy`, и гвард пропускает каждую. На трёх
каноничных vault они покрывают **745 живых ассетов** `[три каноничных, индекс 40 953 ассета,
2026-09-24]`: `!`-анкеры **699**, свойство отсутствует **45**, ссылка нерезолвима **1**, пустое
значение **0**. Ассетов, которые гвард отверг бы, — **0**: данные починены тикетом `b80442aa`,
то есть дефект снят с корпуса, но не с пути записи.

## Acceptance Criteria (Gherkin)

```gherkin
Scenario: create refuses an anchor that resolves to a non-ontology
  Given exo__Asset_isDefinedBy pointing at an asset whose class is not exo__Ontology
  When I run `create --class <c> --label <l> --property exo__Asset_isDefinedBy=[[<that uid>]]`
  Then the command fails fail-loud naming the target's class
  And no asset is created

Scenario: the refusal precedes the preview
  Given the same anchor and `--dry-run`
  When I run create
  Then the command refuses, prints no preview and creates nothing

Scenario: a real ontology anchor still works
  Given exo__Asset_isDefinedBy pointing at an instance of exo__Ontology
  When I run create
  Then the asset is created

Scenario: set-property refuses a repoint onto a non-ontology, on BOTH doors
  Given an existing asset
  When I repoint exo__Asset_isDefinedBy at a non-ontology via --property/--value or via --input
  Then the command fails fail-loud and the file is left byte-identical

Scenario: a subclass of exo__Ontology is accepted
  Given an anchor whose class has exo__Class_superClass = exo__Ontology
  When I run create
  Then the asset is created (subsumption, not equality)

Scenario: the four fail-open forms stay legal
  Given isDefinedBy that is absent, empty, `!`-prefixed, or unresolvable
  When I run create
  Then the asset is created (co-location's contract is unchanged)
```

## Verification

`packages/cli/tests/integration/isdefinedby-range-d8c3c86b.integration.test.ts` — production-shape:
реальные `createCommand().parseAsync` / `setPropertyCommand().parseAsync` над временным vault; оси
V1-V9. Фикстура V1/V3/V4/V9 — **реальная пара** из git-истории `exoas-my` (`5ff28539` → `6a5e4fce`).
Канарейка на живых данных: продовый CLI прогнан по **25** живым `ems__SleepSession` — принято
25/25, отвергнуто 0; тот же CLI на до-фиксном значении даёт `rc=1` и сообщение, называющее класс
цели. ⚠ Тело тикета говорило «15 SleepSession» — это снимок 2026-09-14; на 2026-09-24 их 25.

## Non-goals

- Атрибуция писателя (дефект вероятностный, LLM — см. §Контекст).
- Починка уже испорченных ассетов: на момент поставки их **0** (сделано тикетом `b80442aa`).
- Проверка **прочих** shape-нарушений на записи — остаётся за `--validate` (`dd9ab956`).
- Четыре fail-open формы co-location — остаются законными без изменений.
