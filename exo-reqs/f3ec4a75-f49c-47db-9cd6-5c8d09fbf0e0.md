## Job Story

When Obsidian is re-indexing my 8k-file vault on the phone, I want the buttons a task shows to be
the **right** ones — so that a task already in progress does not offer me "Start" again.

## Why this is not covered by the three shipped tiers

| req | conveyor | cold-cache failure it closed |
|---|---|---|
| Tier 1 (v16.235.1) | the asset's OWN frontmatter | empty store |
| `7d00a60b` (Tier 2/3) | the **class** position (`exo__Instance_class`) | zero buttons, then file-IRI instead of symbolic |
| `c3072a80` | `classIsPrototype` (does not go through the vault adapter) | the ordinary button set instead of the prototype one |

None of them reaches a wikilink standing in a **value** position. `7d00a60b` names "other wikilink
positions" in its own Non-goals, and its warm-up loop is explicitly keyed on `exo__Instance_class`.

## The mechanism (measured, not inferred)

The #2782 enum-substitution block resolves a value target like this:

```ts
const basenameClassIRI = this.expandClassValue(targetFile.basename);  // UID-CANON: basename is a uuid, so null
if (basenameClassIRI) { ... }
const targetFm = this.vault.getFrontmatter(targetFile);               // COLD: null
if (targetFm) { /* label -> symbolic */ }                             // never runs
// falls through to the file-IRI / dual-storage branch
```

Under UID-CANON the basename carries no namespace, so `exo__Asset_label` is the **only** source of
the symbolic IRI — exactly the shape Tier 3 fixed one call-site earlier. The block's own comment says
it "mirrors valueToClassURI's Issue #2745 lookup", so the two are known to be the same lookup.

**Reproduced**, not deduced (throwaway jest over the real converter, one cold target):

```
WARM objects: ["https://exocortex.my/ontology/ems#EffortStatusDoing"]
COLD objects: ["obsidian://vault/assetspaces/kitelev/exoas-public/ems/<uuid>.md"]
```

## Why this tier is WORSE than the ones already closed

Tiers 1-3 removed buttons. This one **adds** them. The starter-kit preconditions are existential —
the block's own comment spells it out: "ASK is existential — any non-matching binding (file IRI or
UUID literal) makes the FILTER pass and the gate returns TRUE". So a file-IRI does not merely fail
to match the status; it makes `FILTER(?s != ...)` **pass**, and the gate opens on an asset it was
written to close.

## Exposure (measured on vault-my, 8531 uid-named assets)

- 1057 uid-named files carry a namespace-parseable `exo__Asset_label` — i.e. their symbolic IRI is
  reachable **only** through that label.
- **3088 value-position wikilinks in 2189 files (26 % of the vault)** point at one of them, excluding
  `exo__Instance_class` (already closed).
- Top predicate: `ems__Effort_status` — **735** — precisely what the starter-kit ASK gates read.

## Cost of the generalisation

Warm-up is skipped whenever the cache is warm (`getFrontmatter` wins first), so a warm session pays
**zero** extra reads. On a cold cache the ceiling is the number of distinct uid-form wikilink targets
in one asset's frontmatter: mean **3.69**, median 3, p90 5, p99 9, max 27 (measured over 9054 assets).

## Non-goals

- Re-index speed. This makes the plugin correct **while** Obsidian re-indexes; it does not shorten it.
- `classIsPrototype` — owned by `c3072a80`.
- Wikilinks in the note **body** (`exo:Asset_bodyLink`), and label-form / uid+alias references, which
  resolve from their own text and need no lookup.
- The CommandManager path, blocked by Obsidian's synchronous `checkCallback` contract (see `c3072a80`).

## Acceptance

Given a cold `metadataCache` and an asset whose `ems__Effort_status` is a uid-form wikilink to a
uid-named status whose label is `ems__EffortStatusDoing`,
When the converter builds that asset's triples,
Then the `ems__Effort_status` object is the SYMBOLIC IRI ending `ems#EffortStatusDoing`,
And it is NOT an `obsidian://vault/` file-IRI,
And a warm cache produces the byte-identical object (no behaviour change when nothing is cold).
