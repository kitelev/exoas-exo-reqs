# req(exo): CLI vault walk is deterministic BY CONSTRUCTION, not by filesystem

## Job Story

When the CLI resolves a duplicated property label — which definition "wins" — I want the answer
to be the same on my Mac and on a Linux CI runner, because today it is the same only by accident.
`PropertyNameValidator.collect()` sorts directory entries byte-wise **explicitly** (ticket
`8185c9dd`, review #4282 NIT-2, pinned by mutant `M12_sort_reversed` → `Q4/S7/W7` under req
`21ceea14`), while `FileSystemVaultAdapter.walkDirectory()` — the walk that **hydrates the CLI
triple store** (`loadVaultTriples` → `getAllFiles()` → `NoteToRDFConverter.convertVault`) — does
not sort at all and takes `fs.readdirSync` order as given.

The store's consumers read "first" from that hydration order: `InMemoryTripleStore.matchP`
iterates `pso.get(predicateKey)`, a `Map`, i.e. **insertion order**. Two production consumers
depend on it — `createTripleStoreDeclaredRanges` (first-wins, ticket `534a7a46`) and
`createTripleStoreClassPropertyResolver` (`seen.has(propertyKey)` dedup, req `07509cf9`).

## Measurement that motivates this (2026-09-22, ticket `193147b4`, `origin/main` `8453778a`)

- Both walks reproduced verbatim and run on three live mounts: **34 526 / 9 661 / 7 687** `.md`,
  same-set canary green, **0 order differences** on all three.
- ⛔ The control that changes the reading: files created in deliberately REVERSE byte order
  (`zz yy mm bb aa`) came back from `readdirSync` as `aa bb mm yy zz` — **APFS keeps directory
  entries sorted by name**, so the unsorted walk agrees with the sorted one *because of the
  filesystem*, not because of the code. On ext4 (CI runners, Linux users) `readdir` returns
  hash order. ⛔ **Not measured on ext4** — stated, not assumed.
- Duplicate property labels today: **0 / 0 / 0** (735 / 531 / 513 definitions) ⇒ the defect is
  LATENT: nothing observable is broken, and the first duplicate makes "first" non-deterministic
  in two places at once.

## Statement (Gherkin)

```gherkin
Given a vault directory whose entries the filesystem returns in an order that is NOT byte order
When the CLI vault adapter walks it
Then the emitted file sequence is byte-ordered per directory, depth-first
# The axis stubs `fs.readdirSync` so it is RED on any filesystem, including one that
# already sorts — otherwise the axis would be vacuous exactly where the defect lives.

Given one and the same directory tree
When PropertyNameValidator.walk and FileSystemVaultAdapter.walkDirectory both enumerate it
Then the two sequences are IDENTICAL
# The parity that "first-wins" silently assumes today. A mutant on EITHER side must redden it.

Given the vault the CLI already reads today (an APFS mount)
When the adapter walks it before and after this change
Then the emitted sequence is unchanged
# Zero-regression on the filesystem where the two orders already agreed.
```

## Non-goals

- ⛔ `NodeFsAdapter.getMarkdownFiles()` is **not** unified with this walk, and the difference is
  MEASURED rather than assumed: it sorts **full relative paths** (`relativePaths.sort()`, #4272),
  which is a different order from per-directory DFS whenever a directory name is a prefix of a
  file name. Probed on this tree: per-directory gives `a/b.md a-c.md a-d/e.md a.md`, full-path
  gives `a-c.md a-d/e.md a.md a/b.md`. This requirement adopts the comparator of the walk it is
  the structural twin of (`PropertyNameValidator.walk`), and NAMES the third order rather than
  inventing a fourth. Reconciling the two is a separate decision.
- ⛔ ext4 behaviour is not claimed, only that the guarantee no longer depends on the filesystem.
- ⛔ No change to who wins among duplicates (still first in walk order) and no change to the
  plugin path (Obsidian supplies its own file list).

## Verification

- cli unit — the adapter over a stubbed `fs.readdirSync` that returns reverse-byte order; the
  walk must emit byte order. Mutant "drop the sort" ⇒ RED.
- cli unit — parity: one tree, both walks, identical sequences. Mutant on either comparator ⇒ RED.
- revert-verify — one mutant per guard, `expect` filled from the driver's printed lists.
