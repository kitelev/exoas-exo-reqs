## Контекст

Композитная команда (`exocmd__GroundingTypeComposite`) умеет **действовать над** ассетом,
созданным предыдущим шагом (флаг `exocmd__Grounding_targetsCreatedInstance`, req
`b00acde4-e796-4bb0-8136-8bac8ca9cf9e`), но **не умеет вставить его как значение** свойства
другого ассета. Проброс односторонний: путь созданного живёт в локальной переменной
`lastCreatedPath` внутри `GroundingExecutor.executeComposite` и используется только как
**цель** шага; `ResolverContext`, из которого питаются токены подстановки, строится в
`executeCreateInstance` и этой переменной не видит.

Замер слоёв (`origin/main` = `ec47137c`, реплей 2026-09-24) — способность отсутствует во
**всех** механизмах записи значения, а не в одном сломанном:

| слой | почему не закрывает |
|---|---|
| PropertyDefault + `exocmd__SubstitutionToken` | **20 [registry: `registerResolver` call-sites, `packages/*/src`]** реализаций и **17 [whitelist: `KNOWN_SUBSTITUTION_RESOLVER_IDS`, `CommandResolver.ts`]** разрешённых к употреблению из vault (`target`, `targetFolder`, `targetProperty`, `targetRefProperty`, `targetClassSelf`, `groundingTargetClass`, `userInput`, `userInputLabel`, `labelAsArray`, `randomUUIDv4`, семейство дат) — **ни один** не даёт созданный ассет. Два множества меряют разное: реестр держит реализации, whitelist разрешает токен в данных; поэтому новый резолвер требует записи в **оба** (без whitelist `CommandResolver` даёт warn и откат к wikilink-форме) |
| `exocmd__Grounding_inheritanceRule` | читает frontmatter **click-target** (`targetFm`), созданного не видит |
| `exocmd__Grounding_targetsCreatedInstance` | меняет **ЦЕЛЬ** шага, а не **ЗНАЧЕНИЕ**; req `b00acde4` явно фиксирует, что `targetIRI` остаётся click-target — «the just-created asset is not yet indexed in the store» |
| `body_template` | пишет **тело** созданного ассета, а не свойство другого ассета |
| литеральное значение в Grounding | статично по построению |

Вскрыто дог-фудингом (RFC `85fa0652-58f7-412d-8490-eb4c9a29e973`, команда «Правим» механизма
аудита соглашений): шаг 5 цепочки — создать связь «последняя сверка» и указать в ней на
запись, созданную шагом 4, — неисполним. Любая **реификация внутри одной команды** упирается
в то же самое.

## Acceptance criteria (BDD)

```gherkin
Feature: composite grounding — the asset created by an earlier step as a property VALUE

  Scenario: a later create_instance step links to the asset created earlier
    Given a composite grounding with steps:
      | 1 | create_instance (creates asset A, returns openPath) |
      | 2 | create_instance (creates asset B) whose PropertyDefault entry
            carries a SubstitutionToken with resolver-id `createdInstance` |
    When the composite executes against a click-target file
    Then asset B's frontmatter holds the wikilink of asset A
    And the value form is `"[[<bare-uid-of-A>]]"` — the same strip-canon form `$target` emits

  Scenario: negative control — no create_instance ran before the token
    Given a composite grounding whose FIRST step is a create_instance
          carrying a `createdInstance` PropertyDefault entry
    When the composite executes
    Then the resolver returns null and the PropertyDefault entry is SKIPPED
    And that property is absent from the created asset's frontmatter
    And the click-target is NOT substituted in its place

  Scenario: a nested composite inherits the parent's most-recently-created asset
    Given a composite whose step 1 is create_instance (asset A)
          and whose step 2 is a NESTED composite containing a create_instance
          with a `createdInstance` PropertyDefault entry
    When the outer composite executes
    Then the asset created inside the nested composite holds asset A's wikilink

  Scenario: the parser emits an execute-time marker, not a wikilink fallback
    Given a SubstitutionToken asset declaring resolver `createdInstance`
    When CommandResolver resolves the Grounding's PropertyDefaults
    Then the emitted value is the execute-time substitution marker
    And no "unknown resolver-id" warning is logged
```

## Non-goals (осознанные границы, выведенные из механизма)

- **Парный id для body-шаблонов НЕ вводится.** Реестр резолверов общий
  (`TemplateBodyResolver` берёт функции тем же `getResolver`), поэтому отдельного словаря не
  нужно; но `executeBodyTemplate` строит свой `ResolverContext` из `{userInput, targetIRI,
  targetFilePath}` и нового поля не несёт ⇒ `$createdInstance` в теле шаблона остаётся
  **видимым литералом** (`TemplateBodyResolver`: `null`/`""` оставляют полный маркер — «a
  visible unresolved token the user can fix beats a silently-deleted one»). Это штатное
  поведение «контекст отсутствует», такое же, как у `$target` вне контекста. Расширение на
  body — отдельная единица работы: у `body_template` шага `targetFilePath` УЖЕ равен пути
  последнего созданного, поэтому там токен означал бы ссылку на самого себя, и полезный
  сценарий требует различать «последний» и «предпоследний» созданный.
- `targetIRI` шага НЕ перенацеливается: `$target` продолжает резолвиться в click-target
  (клаузы req `b00acde4` остаются в силе, supersede не требуется).
- Созданный ассет не индексируется в triple store внутри того же вызова — резолвер работает
  от **пути**, а не от запроса к графу.

## Revert-verify

Через реальный `GroundingExecutor.executeComposite` (production-shape: настоящие шаги
`create_instance`, in-memory fs, read-after-write):

- **GREEN (с фиксом):** frontmatter второго созданного ассета содержит `[[<uid первого>]]`.
- **RED (без фикса):** нейтрализация ЛЮБОГО из уровней протяжки
  (`executeComposite` → `executeStep` → `execute` → `executeCreateInstance` → `ResolverContext`)
  делает сценарий 1 красным — по одному мутанту на уровень, иначе проводка не покрыта.
- Негативный контроль остаётся зелёным при снятии фикса (свойство отсутствует в обоих
  состояниях) — поэтому он запирается **своим** мутантом: подмена `null` на форму `$target`
  обязана его покрасить.
