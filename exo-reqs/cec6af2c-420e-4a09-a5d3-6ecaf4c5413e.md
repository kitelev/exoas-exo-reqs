# req(exo): `create` co-locates by class-neighbour when isDefinedBy gives no folder (#3934)

## Job Story

When I run `exocortex create --class inbox__ExoAssistantKnowledge` (or `aiKnow__MemoryFeedback`) with a bang-anchor `exo__Asset_isDefinedBy: [[!kitelev]]` (or `[[!aiKnow]]`), I want the new asset placed next to the existing sibling instances of that class (the folder where they already live), so that RFC/aiKnow assets land in their canonical folder through the product's own create path — instead of the `01 Inbox/` fallback that forces me to raw-`Write` past the product and breaks the co-location invariant + dogfooding.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: `create` co-locates a new asset by class-neighbour when isDefinedBy resolves no folder

  Scenario: bang-anchor isDefinedBy + existing sibling instances -> neighbour folder (not inbox)
    Given a vault where instances of class C already live in folder F
    And F is NOT the ontology folder of a resolvable isDefinedBy anchor
    When I run `create --class C --property exo__Asset_isDefinedBy=[[!kitelev]]`
    Then the new asset is written into F
    And the asset is NOT written into `01 Inbox/`
    # Reverting the class-neighbour fallback -> the asset lands in `01 Inbox/` (RED). Restoring -> lands in F (GREEN).

  Scenario: resolvable isDefinedBy still wins (priority 1 unchanged)
    Given a vault with an on-disk ontology file that isDefinedBy resolves to
    When I run `create --class C --property exo__Asset_isDefinedBy=[[<ontology-uid>]]`
    Then the new asset is placed in the ontology's folder (existing behavior, unaffected)

  Scenario: fail-open when neither isDefinedBy nor class-neighbour resolves
    Given a vault with NO existing instances of class C
    And a bang-anchor / empty / unresolvable isDefinedBy
    When I run `create --class C`
    Then the new asset falls back to `01 Inbox/` (fail-open preserved)

  Scenario: class-neighbour matches any wikilink form of exo__Instance_class
    Given sibling instances that reference class C by bare `[[uid]]`, alias `[[uid|label]]`, or label `[[label]]`
    And exo__Instance_class may be a YAML list (multi-valued)
    When the neighbour scan runs
    Then instances are matched by extractAssetReference(class-ref) == C's UID OR C's short-name label
```

## Notes

- **Source design:** GitHub issue #3934 + Andrey's design comment (2026-07-25): co-location by ontology/class, NOT a `--folder` flag. The product enforces the co-location invariant automatically.
- **Implementation point:** `packages/cli/src/executors/folderRepairHelpers.ts` (new `resolveNeighbourFolderByClass` helper, sibling to `resolveCoLocationFolder`) + `packages/cli/src/commands/create.ts` (call the fallback when the isDefinedBy co-location resolves to the inbox default). CLI-only; `packages/core` untouched.
- **Binding:** production-shape integration test (REAL `createCommand()` end-to-end against a temp fixture vault, mirroring `create-co-location.integration.test.ts`) — revert-verified RED (drop the class-neighbour fallback -> lands in `01 Inbox/`) / GREEN (restore -> lands in the neighbour folder). CI-gated suite under `packages/cli/tests/integration/` (auto-picked-up by `test-coverage-cli`).
