## Job story

When any frontmatter writer that goes through the shared YAML escaper (`create`, `set-property`, `property_set`, `property_append`, `apply rename-to-uid`) receives a label / alias / property value that carries a C1 control character (U+0080–U+009F — the range a copy-paste from a Windows-1252 document or a terminal paste can smuggle in), I want the value written as a double-quoted YAML scalar with the character escaped as `\xNN`, so the file stays readable by the YAML11 reader (`parseYamlFrontmatter`) and the value round-trips byte-for-byte; and I want every value WITHOUT such a character to keep exactly the on-disk form it has today (no quote churn).

## Context

- Ticket `71f1ca37` (tech backlog `bbac67ce`; review observations of PR kitelev/exocortex#4256). Sibling of `2f642d6c` (rename-to-uid writers through the shared escaper — its Non-goals explicitly leave "which characters `needsYamlQuoting` treats as significant" untouched) and `21ceea14` (per-property quoting flag). The C0 half of this class shipped with #3750 LOW-4 without a requirement; this req owns the C1 half.
- Mechanism (`packages/core/src/utilities/yamlScalar.ts` @ `9bbb11c0`): `YAML_CONTROL_CHARS = /[U+0000–U+001F, U+007F]/` (C0 + DEL) — a C1 character neither triggers quoting in `needsYamlQuoting` nor is escaped by `quoteYamlString` (only `code < 0x20 || code === 0x7f` gets `\xNN`).
- Measured on js-yaml **5.3.0** (`packages/core`, `require.resolve` from the consumer), schema `YAML11_SCHEMA` (the production read path, `parseYamlFrontmatter.ts:84`): a plain scalar carrying U+0080 or U+0081–U+0084 or U+0086–U+009F (**31 of 32**) throws `the stream contains non-printable characters` — the whole frontmatter becomes unreadable at rc 0 of the writer; **U+0085 (NEL) is the exception** — YAML 1.1 lists it as printable, the plain scalar loads with the character intact. Inside `"…"` every C1 loads, both raw and as `\xNN` (32/32 round-trip). ⛔ The ticket's table had the two rows inverted ("U+0085 throws, U+0080 reads") — corrected by this measurement; same defect class, same fix.
- Not a semantic change for any other property class: the quoting is keyed on the character, not on the property, and the `\xNN` form is what #3750 already emits for C0.

## Statement (Gherkin)

```gherkin
Feature: the shared YAML escaper quotes and \xNN-escapes C1 control characters

  Scenario: a value with a C1 control character is written quoted and round-trips
    Given a string value containing U+0080, U+008D or U+009F
    When serializeYamlScalar (and every writer that calls needsYamlQuoting / quoteYamlString) emits it in a `key: value` mapping
    Then the emitted scalar is a complete double-quoted YAML scalar
    And js-yaml (YAML11 schema) loads the mapping without throwing
    And the loaded value equals the original string byte-for-byte

  Scenario: the C1 character is emitted in the \xNN escape form, not raw
    Given the string "a" + U+0080 + "b"
    When quoteYamlString emits it
    Then the output is exactly "a\x80b" (the six characters backslash, x, 8, 0 inside the quotes), with the escape upper-cased for A–F
    And no raw C1 byte is present in the emitted text

  Scenario: NEL (U+0085) is quoted too, as the same class (control)
    Given a string value containing U+0085
    When serializeYamlScalar emits it
    Then it is quoted and escaped as "\x85" and loads back byte-for-byte
    (NEL is readable bare under YAML 1.1 — the quoting is uniform across C1, not a fix for NEL specifically)

  Scenario: values without a control character keep their existing on-disk form (pair, no churn)
    Given a plain ASCII value such as "Plain Task Label" or a non-ASCII printable value such as "Ünïcödé — тест"
    When serializeYamlScalar emits it
    Then the output is the bare value, byte-identical to the pre-change output
```

## Non-goals

- Not changing what `needsYamlQuoting` does for scalar-shaped strings (`123`, `true`, `2026-01-15`, datetime) — #3750 MEDIUM-3 and req `21ceea14` govern that; datetime-shaped labels stay unquoted deliberately (0 live carriers across the three vaults, 2026-09-18).
- Not touching the YAML11 reader (`parseYamlFrontmatter`) or the Obsidian metadataCache parser; `yes`/`no`/`on`/`off` are strings under YAML11 on js-yaml 5.3.0 and are not quoted.
- Not re-quoting existing values on disk; only values written after this change are affected.
- The inline-flow `aliases: […]` parsing fix in `RenameToUidService` is a bug-fix under req `2f642d6c` (its own Y11/Y11b axes), not this req.
