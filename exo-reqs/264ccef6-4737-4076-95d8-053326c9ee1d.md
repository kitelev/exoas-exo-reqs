# req(exo): `exocortex-cli mcp` — MCP-MVP stdio server (create_asset / create_effort + inline-SHACL)

## Job Story

When an AI agent creates a vault asset, I want it to call a **structured MCP tool** instead of composing a shell command line, so that the asset's label, body and property values — which routinely contain `$`, backticks, `()`, quotes and newlines — reach the creation pipeline **byte-identically**, without any shell interpolation, word-splitting or `--body-file` temp-file workaround.

**The gap this closes.** The dogfood-canonical creation path today is `exocortex-cli create` / `apply`, invoked through a **shell**. Shell quoting is the single most-recurring mechanical failure class in this environment (word-splitting of multi-word variables, `$`/backtick command substitution inside `-m`/`--label` arguments, `()` parse errors, glob expansion of unquoted `?`/`*`). Every one of those is a *transport* defect, not a defect of the creation pipeline. An MCP server removes the transport: the client hands over a JSON object, the server builds an **argv array** and executes the CLI with `execFile` (no shell), so no character in any value can be reinterpreted.

**What this requirement is NOT.** It does not replace the CLI, does not change any existing command, and does not make MCP the mandatory path (RFC `7c7859d1` alternative D — "MCP as the only path" — was explicitly rejected as a first step and kept long-term). It is the *optional MVP* (`W6`) of that long-term direction: the smallest server that proves the value.

## Design (verified against `origin/main` before writing)

1. **Vehicle = a new `mcp` subcommand of the existing CLI**, not a new npm package. It reuses the existing publish pipeline, version and dependency tree; extraction into its own package later is mechanical. `mcp` is a **transport entry-point**, not a domain verb — it does not count against the RFC's "22 → 18 → 17 domain-command surface" metric.
2. **Zero new runtime dependencies.** The MCP subset needed (`initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`) is a small, well-specified JSON-RPC 2.0 dialogue over newline-delimited JSON on stdio. Hand-rolling it keeps a *published* package's supply-chain unchanged — proportionate for a task marked optional. Adopting the official SDK is a follow-up once the value is proven.
3. **Tools shell out to the CLI via `execFile` (argv array, no shell), they do not re-implement it.** Every guarantee the creation path already has — co-location by `exo__Asset_isDefinedBy`, dangling-wikilink VALUE rejection, unknown-property-NAME rejection (req `40a9a81b`), SHACL-lite conformance (req `dd9ab956`), canonical property ordering — is inherited unchanged, and no existing command file is modified. This is what makes the change purely additive.
4. **`create_asset` wraps `create`**, whose success output is already exactly one `{uuid,path,label}` JSON line on stdout (all diagnostics on stderr). **`create_effort` wraps `apply <cmd> <target> --json --yes`** — the *homoiconic* effort-creation path (RFC alternative E: create-effort is already homoiconic) — whose `--json` envelope is `{command,target,created:[{uuid,path,label}]}`.
5. **inline-SHACL is ON by default for `create_asset`** (`validate: true` unless the caller opts out). The CLI keeps `--validate` opt-in because a full vault conversion per create is a real cost for interactive use; the MCP surface is the *agent* surface, where landing a non-conformant asset is the expensive outcome. Overridable per call.
6. **A failing CLI invocation is an MCP tool error, never a crash** — non-zero exit becomes `isError: true` carrying the CLI's own stderr diagnostic and exit code, so the agent gets the actionable message (`Unknown property … Did you mean …`, SHACL violation, dangling wikilink) rather than an opaque failure.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: exocortex-cli mcp — stdio MCP server for structured asset creation

  Background:
    Given the CLI is started as `exocortex-cli mcp`
      And it speaks newline-delimited JSON-RPC 2.0 over stdin/stdout

  Scenario: initialize handshake advertises the tools capability
    When the client sends an `initialize` request
    Then the reply carries a protocolVersion, a `tools` capability and serverInfo naming the CLI

  Scenario: tools/list advertises exactly the two MVP tools
    When the client sends `tools/list`
    Then the result contains `create_asset` and `create_effort`
      And each tool carries a JSON Schema declaring its required inputs

  Scenario: create_asset routes through the existing `create` pipeline as ARGV
    When the client calls `create_asset` with a vault, a class, a label and properties
    Then the CLI is invoked with `create` and each value as its OWN argv element
      And the tool result is the `{uuid,path,label}` JSON that `create` emits

  Scenario: shell-metacharacter payloads survive verbatim (the reason this server exists)
    When the client calls `create_asset` with a label and body containing `$`, a backtick, `$&`, `()` and a newline
    Then each of those values reaches the CLI as a single argv element, byte-identical
      And no shell interpolation, word-splitting or glob expansion occurs

  Scenario: inline-SHACL is on by default and is overridable
    When the client calls `create_asset` without specifying `validate`
    Then the CLI invocation includes `--validate`
     But when the client passes `validate: false`
    Then the CLI invocation omits `--validate`

  Scenario: create_effort routes through the homoiconic apply path
    When the client calls `create_effort` with a command slug and a target path
    Then the CLI is invoked as `apply <command> <target> --json --yes`
      And the tool result is the `{command,target,created:[...]}` envelope

  Scenario: a failing CLI invocation becomes a tool error, not a crash
    When the wrapped CLI exits non-zero
    Then the tool result has `isError: true`
      And its text carries the CLI's stderr diagnostic and the exit code

  Scenario: an unknown tool name is a tool error, not a protocol error
    When the client calls a tool that does not exist
    Then the reply has `isError: true` and names the unknown tool

  Scenario: an unsupported JSON-RPC method returns method-not-found
    When the client sends a method the server does not implement
    Then the reply is a JSON-RPC error with code -32601

  Scenario: notifications are not answered
    When the client sends `notifications/initialized`
    Then the server writes nothing to stdout
```

## Out of scope (documented, not silently dropped)

- Adopting `@modelcontextprotocol/sdk` (deliberately deferred — see design point 2).
- MCP `resources` / `prompts` capabilities; only `tools` is advertised.
- Read/query tools (`query`, `find`) — the RFC's read-axis cluster is `W5`, deferred.
- Making MCP the mandatory creation path — that is the `W8` hard-hook, gated on the `W7` metric.
