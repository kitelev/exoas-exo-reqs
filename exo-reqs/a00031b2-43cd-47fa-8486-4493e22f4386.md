# req(exo): `cleanEmptyProperties` leaves every SURVIVING value byte-identical — `String.replace` must not read the file's own frontmatter as a replacement pattern

## Job Story

When I run the one command whose whole job is to repair my asset, I want every value it
does **not** remove to come out byte-identical — so that a price (`cost $100`) or a quoted regex in
a label does not silently rewrite my frontmatter, duplicate my keys and resurrect the very empty
property the repair had just deleted.

## Statement (Gherkin)

```gherkin
Given an asset whose frontmatter carries `ems__Effort_result: cost $& ref` and one empty property
When `cleanEmptyProperties` runs (the `clean-properties` service_call / `apply clean-properties`)
Then the surviving value is BYTE-IDENTICAL (`cost $& ref`)
And the empty property is still removed
And the frontmatter still parses to exactly the expected keys (no duplicate key, no stray `---`)
And the note BODY is byte-identical

Given the same asset with `ems__Effort_result: cost $100` — an ordinary money value
When `cleanEmptyProperties` runs
Then the surviving value is BYTE-IDENTICAL (`$1` must NOT expand to the captured frontmatter)

Given values carrying `` $` ``, `$'`, `$$` and `$1`
When `cleanEmptyProperties` runs
Then each surviving value is BYTE-IDENTICAL

Given an asset with no `$` anywhere
When `cleanEmptyProperties` runs
Then every empty form (`""`, a bare key, `null`, `[]`, `{}`, an all-empty list) is still removed
and every real value is kept (control — the repair itself must not regress)

Given a mutant restoring the string replacement
When the matrix runs
Then the `$&` axis reddens
```

req, упоминающих `PropertyCleanupService` / `clean-properties`, и ни один не говорит о **сохранности
переживших значений**:

## ЗАМЕР ПОВЕДЕНИЯ — origin/main `cbff7ef5`, 2026-10-03 (сделан ДО формулировки)

Прогон через настоящий `PropertyCleanupService.cleanEmptyProperties` (jest, реальный vault-стаб),
вход — `exo__Asset_label: Keeper` + `ems__Effort_result: <значение>` + пустой `ems__Effort_area:` +
тело `body text`; байты прочитаны обратно:

| значение | что осталось в значении | байты | пустой ключ удалён? |
|---|---|---|---|
| `cost $& ref` | `cost ` + **ВЕСЬ заматченный блок** + ` ref` | 93 → **155** | ⛔ **НЕТ** (воскрешён) |
| `cost $1 ref` | `cost ` + **группа захвата 1** (исходный frontmatter) | 93 → 147 | ⛔ НЕТ |
| ⛔ `cost $100` | `cost ` + frontmatter, затем `00` дописано к ключу ⇒ `ems__Effort_area:00` | 91 → 143 | ⛔ НЕТ |
| `` cost $` ref `` | `cost  ref` — `` $` `` (всё ДО матча = пусто) молча удалён | 93 → 73 | да |
| `cost $' ref` | `cost ` + **всё ПОСЛЕ матча** (тело заметки) | 93 → 84 | да |
| `cost $$100` | `cost $100` — значение молча изменено | 92 → 73 | да |
| `plain value` (контроль) | `plain value` | 93 → 75 | да |

Пример выдачи для `$&` (дословно, с диска):

```
---

ems__Effort_result: cost ---
exo__Asset_label: Keeper
ems__Effort_result: cost $& ref
ems__Effort_area:
--- ref
---

```

⇒ два `exo__Asset_label`, ВОСКРЕШЁННЫЙ `ems__Effort_area:` (то, что ремонт только что удалил),
висячий `--- ref` и два закрывающих `---`. Ремонт не просто портит значение — он **отменяет свою
собственную работу** и ломает структуру.

⛤ **Три факта сверх формулировки issue:**

1. ⛔ **`$1` ЗДЕСЬ РАСКРЫВАЕТСЯ, и поэтому ОБЫЧНАЯ ДЕНЕЖНАЯ СУММА разрушает ассет.**
   `frontmatterRegex = /^---\n([\s\S]*?)\n---/` **имеет группу захвата**, так что `$1`..`$9`
   подставляют её. Floor правила `string-replace-dollar-corruption` («фикстура обязана нести `$&`,
   а `$1` на паттерне БЕЗ групп остаётся литералом ⇒ ось на `$1` вакуумна») к ЭТОМУ сайту не
   применим — проверено замером, а не унаследовано. Значит экспозиция не экзотическая: страдает
   `$100`, `$1000`, `$2 500`.
2. **Ремонт отменяет себя** — у форм `$&` / `$1` / `$100` пустой ключ остаётся в файле, то есть
   команда рапортует успех, ничего не вылечив.
3. **`$'` затягивает в значение ТЕЛО заметки** — потеря не ограничена frontmatter.

⛤ Ось на `$&` остаётся первичной (она переживёт рефакторинг, снимающий группу захвата), ось на
`$100` — реалистичной.

## Границы фикса

**Function-replacer:** `content.replace(frontmatterRegex, () => \`---\n${cleaned}\n---\`)`.

- ✅ Возвращаемое функцией значение вставляется **дословно**, без интерпретации `$` — ровно floor
  правила `string-replace-dollar-corruption`.
- ⛤ **Splice-by-index не нужен, и это выведено из механизма:** регексп `^`-якорный и НЕ глобальный
  ⇒ матч ровно один и начинается с индекса 0, поэтому риска «заменить ДРУГОЕ вхождение» нет. Единственная
  опасность была в интерпретации `$`, и её функция снимает целиком — при диффе в один токен.
- ⛔ **Второй `.replace`-сайт того же файла НЕ меняется и это проверено:**
  `item.replace(/^\s+- /, "")` (строка 77) имеет **константный** второй аргумент `""`, то есть
  data-bearing строкой не является. Мандат issue «мутант на КАЖДЫЙ `.replace`-сайт» исполняется
  мутантом **на этот сайт тоже** (подстановка `"$&"` вместо `""` оставляет префикс `- ` ⇒ пустой
  список перестаёт считаться пустым) — он краснит контрольную ось ремонта.
- ⛔ **Экранирование `$` в строке (`replacement.replace(/\$/g, "$$$$")`) отвергнуто:** оно решает ту
  же задачу менее читаемо и оставляет будущему редактору возможность снять экранирование, не заметив
  зависимости.

## Non-goals

1. **Ремонт уже повреждённых ассетов не входит.** Предмет req — чтобы ремонт БОЛЬШЕ не портил;
   поиск и лечение файлов, уже пострадавших от прошлых запусков, — отдельная работа (на 2026-10-03
   таких не обнаружено: все 169 — экспонированные, не повреждённые).
2. **Логика определения пустоты (`isEmptyValue`) не меняется** — её семантика предмет req `f05caada`
   и решения фаундера #4274.
3. **Другие `String.replace`-сайты репозитория не ревизуются** этим req (у правила
   `string-replace-dollar-corruption` уже есть прецедент #3800 на `repair-frontmatter`); sweep —
   отдельный тикет, если понадобится.
4. **`createUpdatePropertyService` / не-скалярное значение** — issue #4527, свой req и свой PR
   (другой класс: порча при ЗАПИСИ, не при РЕМОНТЕ).
