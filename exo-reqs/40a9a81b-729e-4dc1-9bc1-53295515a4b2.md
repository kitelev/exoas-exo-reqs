# req(exo): `create` rejects unknown property NAMES against the mounted TBox (RFC 430e84f1)

## Job Story

When an LLM agent (or a human) runs `exocortex create --class <C> --property <prefix__Name>=<value>` and misspells the property NAME (`ems__Effort_parentEffort` instead of `ems__Effort_parent`), I want `create` to REJECT it with a fuzzy suggestion and a machine-readable structured error — instead of silently writing a dead property that no query/layout/graph-relation reads — so that a hallucinated property name is a structurally-impossible outcome of the `create` CLI path, not a silent data-corruption the user discovers weeks later.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: exocortex-cli create validates property NAMES against the mounted TBox

  Background:
    Given a mounted vault whose TBox defines the property `ems__Effort_parent`
      And the vault has property definitions (a non-empty mounted property-name set)

  Scenario: unknown-prefix property is rejected (fail-silent -> fail-loud)
    When I run `create --class ems__Task --property "nonExisting__Prop=x"`
    Then the command exits with a non-zero code
      And no asset file is created
      And the error message contains "Unknown property"

  Scenario: a real (known) property passes with no false-positive
    When I run `create --class ems__Task --property "ems__Effort_parent=[[<valid-uid>]]"`
    Then the command exits 0
      And the asset is created with `ems__Effort_parent`

  Scenario: known-prefix + misspelled name is rejected with a fuzzy suggestion
    When I run `create --class ems__Task --property "ems__Effort_parentEffort=[[<valid-uid>]]"`
    Then the command exits with a non-zero code
      And the error message contains "ems__Effort_parent"

  Scenario: the structured error form is machine-readable for an LLM consumer
    When property-name validation rejects a key
    Then the thrown error carries a structured `{ unknown, suggestions }` form
      (unknown = the rejected key; suggestions = the closest known names)

  Scenario: bare Obsidian-native YAML keys are skipped (not TBox properties)
    When I run `create` with a bare key such as `aliases` or `tags`
    Then property-name validation does not reject it

  Scenario: partial profile — a valid property of a MOUNTED class passes
    Given a partial profile that mounts only a subset of the TBox
      And that subset defines `ems__Effort_parent`
    When I run `create --class ems__Task --property "ems__Effort_parent=[[<valid-uid>]]"`
    Then the command exits 0 (an unmounted namespace does not false-reject this valid property)

  Scenario: degenerate mount — no property definitions -> validation is skipped (fail-open)
    Given a vault with ZERO mounted property definitions
    When I run `create --property "anything__Prop=x"`
    Then property-name validation is skipped (it does not reject in a degenerate/unmounted TBox)

  Scenario: no bot-accessible escape-hatch
    Then `create` exposes NO `--allow-unknown-property` (or equivalent) flag
```

## Revert-verify

Production-shape integration test (real `createCommand()` over a temp fixture vault WITH property definitions, so the name-set is non-empty). Reverting the property-name validation call in `create.ts` (type-preserving Edit-break) makes the `nonExisting__Prop` / `ems__Effort_parentEffort` scenarios PASS the create (exit 0) -> those assertions go RED; the no-false-positive + skip + degenerate-fail-open negative-controls stay GREEN in both states, proving non-vacuity. Restoring makes all GREEN.
