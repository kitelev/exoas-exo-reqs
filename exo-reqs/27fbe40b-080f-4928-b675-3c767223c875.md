## Job story

When a frontmatter write goes through the object-shaped port (`IVaultAdapter.updateFrontmatter` → `FrontmatterService.applyPatch`, i.e. the plugin's `ObsidianVaultAdapter` over Obsidian's `processFrontMatter` object and the CLI's `FileSystemVaultAdapter` over its parsed YAML block), I want an IRI-normalised reference value to be stored as the BARE wikilink `[[x]]` and serialised by the CLI adapter to the same byte-form the text path (`FrontmatterService.updateProperty`) writes — `key: "[[x]]"`, double-quoted — so that the two write paths of one chokepoint no longer produce two disk shapes for one value; and I want the CLI adapter's re-serialisation to be `$`-safe and free of the dead `quoteStyle` option.

## Context

- Source: ticket `73b16cc4-c805-46b6-8f10-b0e1b7a85cfa` (parent techbacklog `bbac67ce`), three observations of PR kitelev/exocortex#4243's review (LOW) that req `2a020489` (Active) explicitly named and deferred: §Non-goals "Known discrepancy, named not fixed … Axes A7/C7/H5 assert `toContain("[[…]]")` until the follow-up decides the object-path form" and "The CLI adapter's YAML serialisation (`yaml.dump` …; its `quoteStyle: "double"` option is not a js-yaml option — the real one is `quotingType` — so it is ignored, pre-existing) … unchanged".
- Mechanism measured on `origin/main` (v16.240.0): `FrontmatterService.normalizeIRIValue` returns `"[[x]]"` WITH quotes (a ready YAML scalar for the text path; `updateProperty` inserts it verbatim into the block). `applyPatch` calls the same function and stores the quoted string as the object value; `FileSystemVaultAdapter.replaceFrontmatter` then `yaml.dump`s it → on disk `ems__Effort_status: '"[[ems__EffortStatusDoing]]"'` (double wrap); the plugin hands the quoted string to `processFrontMatter`, which serialises it as a string containing quotes. Graph readers strip quotes (`removeQuotes`), so the graph is correct and only the byte-shape differs.
- `quoteStyle: "double"` (FileSystemVaultAdapter.replaceFrontmatter, AtomicFrontmatterService.serializeFile) is not a js-yaml option: measured `yaml.dump` output is byte-identical with and without it (single quotes); `quotingType: '"'` is the real option and yields double quotes. Live corpus (vault-exodev, 32 103 assets): 232 144 double-quoted scalars (163 675 wikilinks) vs 244 single-quoted (86 wikilinks) — double quotes are the vault convention; the CLI dumper is the outlier.
- `replaceFrontmatter` builds the new block with `content.replace(regex, string)` — a `$&` / `$1` / `` $` `` / `$'` / `$$` inside any dumped value is re-interpreted as a replacement pattern (class #3748 / #3795; `updateProperty` already uses a function replacer). Production callers of the CLI object path today: 0 (`git grep updateFrontmatter packages/cli/src` — only the adapter); `AtomicFrontmatterService` is used by `ClaimService` / `SpawnService`; the plugin object path has ONE production caller (`LayoutService.handleCellEdit`).
- Why a NEW requirement (sibling, not an extension of `2a020489`): `2a020489` §Non-goals deliberately scopes the object-path form and the CLI serialisation OUT and defers the decision; its Scenario H reads the value as `"[[ems__EffortStatusDoing]]"` — the text-path scalar form — and the bound axes assert `toContain`. This requirement DECIDES the form; the corresponding clauses of `2a020489` get an in-place `SUPERSEDED by <this uid>` marker (its other clauses stay valid, req stays Active).

## Scenarios

### Scenario A — object path stores the BARE wikilink; text path unchanged
Given a patch value `obsidian://vault/x/ems__EffortStatusDoing.md` (or an ontology IRI `https://exocortex.my/ontology/exo#Asset`)
When `FrontmatterService.applyPatch(target, patch)` runs
Then `target.ems__Effort_status` is exactly `[[ems__EffortStatusDoing]]` (and `[[exo__Asset]]`) — no surrounding quotes in the string value
And `FrontmatterService.updateProperty(content, key, sameValue)` still emits the line `ems__Effort_status: "[[ems__EffortStatusDoing]]"` (the text path's scalar form is not changed).

### Scenario B — CLI adapter: byte-parity with the text path
Given a CLI vault file and `FileSystemVaultAdapter.updateFrontmatter` writing the obsidian:// value under an IRI-form key
When the file is re-read from disk
Then it contains the line `ems__Effort_status: "[[ems__EffortStatusDoing]]"` — byte-identical to the line `FrontmatterService.updateProperty` writes for the same key and value — and never `'"[[…]]"'` / `'[[…]]'`.

### Scenario C — CLI adapter: values that need quoting are double-quoted (`quotingType: '"'`, the dead `quoteStyle` removed)
Given a patch with a value js-yaml must quote (`has: colon`, a timestamp-looking string)
When it is written through `FileSystemVaultAdapter.updateFrontmatter` or `atomicUpdateFrontmatter`
Then the dumped block uses double quotes (`key: "has: colon"`), matching the corpus convention; plain values stay unquoted.

### Scenario D — CLI adapter: `$`-safe block replacement
Given a patch value carrying replacement-pattern tokens (`cost $& and $1 and $$ and `$'` `)
When `FileSystemVaultAdapter.updateFrontmatter` re-serialises the block
Then the value survives byte-identically on disk and the body is untouched (a string replacer would splice the matched block / capture groups into the value).

### Scenario E — plugin adapter: the object handed to `processFrontMatter` carries the bare wikilink
Given `ObsidianVaultAdapter.updateFrontmatter` with the obsidian:// value under an IRI-form key
When the processor runs on the live object
Then `live.ems__Effort_status` is exactly `[[ems__EffortStatusDoing]]` (Obsidian's own serialiser quotes it on disk; the adapter no longer pre-quotes).

## Non-goals

- The text path (`updateProperty` / `removeProperty` / `serializeValue`) is unchanged; the `"[[x]]"` scalar it emits is the same byte-form Scenario B now guarantees for the object path.
- No change to what values the plugin's Obsidian serialiser produces on disk (that is Obsidian's), to `RenameToUidService` (its private text rewrite), to `LayoutService.handleCellEdit`'s payload, to the 15 in-memory test adapters, or to the graph readers (`removeQuotes` stays; both old and new disk shapes keep reading correctly).
- The UNPREFIXED reverse write (PR #4241 review LOW-3) stays a `2a020489` non-goal.
- Existing `'…'`-quoted values on disk are not migrated.
