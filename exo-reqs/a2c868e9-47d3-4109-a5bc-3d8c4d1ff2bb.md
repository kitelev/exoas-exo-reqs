## Context

`mergeInheritanceRules` merged the Universal Default Template's rule list with the
grounding-local one through a `Map<string, InheritanceRuleResolved>` keyed by
`targetPropertyName`. Two independent defects followed from that single key:

1. **A grounding could express at most one rule per property.** Building the map
   overwrote earlier entries, and `usedFromGrounding` (keyed by the same name)
   made the second loop drop the remainder. With a universal rule present for the
   same property, every grounding rule but the last was lost silently.
2. **A property carrying several universal rules emitted the override twice.**
   The first loop pushed the override once per shadowed universal rule.

Neither is expressible as a conflict: unlike `PropertyDefaultResolved` (which
carries only `{propertyName, value}` and where name-keyed dedup is correct),
`InheritanceRuleResolved` carries `targetClassCondition` / `targetClassExclusion`
/ `priority`, so several rules for one property are distinct conditional rules.

## Scenario: a grounding declares two conditional rules for one property

Given the Universal Default Template declares an InheritanceRule for `ems__Effort_parent`
And a grounding declares TWO InheritanceRules for that SAME `ems__Effort_parent`,
  one conditioned on `ems__Project` and one on `ems__Task`
When the resolver merges the universal and grounding rule lists
Then BOTH grounding rules survive the merge, in authoring order
And the universal rule for that property is shadowed
And applying the grounding to an `ems__Task` target writes `ems__Effort_parent`
  from the Task-conditioned rule
And applying it to an `ems__Project` target writes it from the Project-conditioned rule

## Scenario: several universal rules for one overridden property emit the override once

Given the Universal Default Template declares TWO InheritanceRules for `ems__Effort_parent`
And a grounding declares its own rule for `ems__Effort_parent`
When the resolver merges the two lists
Then the grounding rule appears in the merged list EXACTLY ONCE
And no universal rule for that property appears in the merged list

## Scenario: production shadowing semantics are unchanged

Given the Universal Default Template declares 01f570c9 (parent, condition ems__Project)
  and 65acce2f (parent, condition ems__Task)
And a grounding declares 43731bae (parent, condition ems__Project)
When the resolver merges the lists
Then the merged list carries 43731bae and NEITHER universal parent rule
So the six groundings that declare 43731bae behave byte-identically

## Non-goals

- **Keying the override by the `(targetPropertyName, targetClassCondition)` PAIR is
  explicitly NOT done.** Measured on the live vault: six groundings declare 43731bae
  (parent / ems__Project) while the template declares both 01f570c9 (parent /
  ems__Project) and 65acce2f (parent / ems__Task). Pair-keying would un-shadow the
  Task rule for all six and introduce the Create-Task-to-Task parent binding that
  active req `2821fdf0-bf65-4afe-96cd-59da980ffe84` section 7 explicitly rules out.
  The grounding-level override therefore stays keyed by property NAME.
- Production vault data is not changed by this requirement.
- `mergePropertyDefaults` is not touched: name-keyed dedup is correct there.

## Notes

Ticket `c3de23a8-9751-4dbe-8ab7-2e7053b14e88`. The ticket's first suggested form
("deduplicate by the pair") is the one ruled out above; its second ("do not
deduplicate grounding rules against each other, keeping the Universal override by
targetPropertyName") is what ships.

Section 6 of req `2821fdf0` states "a grounding can express at most one rule per
property" as the engine constraint that forced the Task rule onto the template.
That half of the sentence stops being true here; the other half (a grounding rule
shadows every universal rule for the same property) stays true by design.
