# req(exo): a printed property declares WHICH name of the referenced asset it prints

## Job Story

When a `exo__DisplayNameSpec` prints an object-property whose target has BOTH an
`exo__Asset_label` and a spec composing a different string — a `period__Quarter` labelled
«Q4-25» whose own spec renders «Q4-2025» — I want the spec's author to be able to say WHICH of
the two the part prints, instead of the engine always choosing the label. Requirement
`0f992e88` (issue #4303) made the composed name reachable only where the label is ABSENT;
this one makes it *declarable* where the label is present.

The alternative is what #4303 documented and the founder rejected on measurement: printing the
composed name by default whenever the target has a spec changed 597 rendered names across the
three canonical vaults and fixed none of the symptom.

## Statement (Gherkin)

```gherkin
# --- the new declaration ---

Scenario: a part declaring DisplayName prints the composed name over the label
  Given a period__Quarter instance with exo__Asset_label "Q4-25"
    And a exo__DisplayNameSpec for period__Quarter composing "Q4-2025"
    And a tbank__Review whose spec prints that quarter through a part carrying
        exo__PrintedProperty_valueSource = exo__PrintedPropertyValueSourceDisplayName
  When the review's displayName is resolved
  Then it reads "ОС Q4-2025"

Scenario: the value is keyed by UID as well as by label (dual-IRI)
  Given the same part written as [[<uid of the DisplayName individual>]] without an alias
  When the review's displayName is resolved
  Then it reads "ОС Q4-2025"
# A vault authors class/enum references BOTH ways; a reader that understands only one form
# is a silent non-match, which is the dual-IRI floor this codebase already carries.

# --- the three controls ---

Scenario: a part with NO declaration is byte-identical to today
  Given the part carries no exo__PrintedProperty_valueSource
  When the review's displayName is resolved
  Then it reads "ОС Q4-25" — the label, exactly as requirement 0f992e88 leaves it

Scenario: declaring Label explicitly is the same as not declaring it
  Given the part carries exo__PrintedProperty_valueSource = exo__PrintedPropertyValueSourceLabel
  When the review's displayName is resolved
  Then it reads "ОС Q4-25"

Scenario: an unrecognised value does not change the printed name
  Given the part carries a value that is neither enum individual
  When the review's displayName is resolved
  Then it reads "ОС Q4-25"
# Fail-open, as the sibling exo__PrintedProperty_format already is: a naming engine must not
# fail or blank a name because a declaration was mistyped.

# --- the declaration is a PREFERENCE, not a guarantee ---

Scenario: DisplayName falls back to the label when nothing composes
  Given a part declaring DisplayName
    And the target has a label but NO spec composing its name
  When the referring asset's displayName is resolved
  Then it reads the target's label
# The order becomes: composed name (when asked for and available) → label → linkpath. The
# bounds of 0f992e88 — depth cap, re-entry set, containment, provenance gate — are unchanged
# and apply to this hop too.

Scenario: the authored alias still wins over everything
  Given the reference is authored as [[<uid>|Q-четвёртый]] on a part declaring DisplayName
  When the referring asset's displayName is resolved
  Then it reads "ОС Q-четвёртый"
```

## Verification

- core unit — the compile side (`PrintNameRuleService`): the declaration is resolved from BOTH
  identity forms and compiled into the part's placeholder; absent/unknown declaration compiles
  byte-identically to today.
- core unit — the render side (`DisplayNameTemplateEngine` + `DisplayNameResolver`): the
  declared source is honoured, the fallback chain holds, and the bounds of `0f992e88` still
  apply.
- core integration — a production-shape fixture vault driven through the real
  `PrintNameRuleService.initialize()` → `resolveWithProvenance()` pipeline, covering the
  scenarios above.
- CLI integration — the same behaviour through `resolve-display-name` over a temp vault on disk.
- revert-verify — one mutant per guard of the diff, each reddening its own axis.
- live-corpus delta — the whole-vault sweep: 0 changed names, because no live part declares the
  new property until an author adds one.
