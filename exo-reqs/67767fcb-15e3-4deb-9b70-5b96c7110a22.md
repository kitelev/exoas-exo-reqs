# req(exo): both SHACL-lite shape loaders accept a property definition typed by ANY descendant of exo__Property — the class set is walked from the declared exo__Class_superClass hierarchy, transitively, with a cycle guard, and the two loaders agree

## Job Story

When I declare a property with `create --class DatatypeProperty` (or the vault carries a def typed `exo__StringProperty`, `exo__TimestampProperty`, `exo__NonInheritableProperty`, … — 291/220/200 of the 696/492/468 live property definitions [vault-exodev / vault-my / vault-tbank] on 2026-09-19 name NO class from the pair `exo__Property` / `exo__ObjectProperty`), I want `validate schema --shapes-mode`, `create --validate`, the plugin on-save pass (all `ShapeLoader.loadFromRDFGraph`) and `create`'s cardinality-aware serialization (`ShapeLoader.loadFromVaultFS`) to build that definition's shape — `sh:datatype`, `sh:minCount`, `sh:maxCount`, `sh:class` — exactly as they do for a def typed `exo__Property`, so that a declared range or cardinality is enforced regardless of which subclass of `exo__Property` the author (or `create`) picked, and so that the next subclass added to the TBox is covered without another code change.

Sibling of req `b0ad1160` (ticket a9b55ead / PR #4266), whose Non-goals read: «Property definitions typed ONLY `exo__DatatypeProperty` … are invisible to BOTH shape loaders (they match `exo__Property` / `exo__ObjectProperty` only, no superClass walk) — separate ticket». That ticket is `84bb4d08`; this requirement is its specification. ORCH decision 2026-09-19 (plan-gate, verbatim): «plan-ok — кандидат (1) walk по Class_superClass в ОБОИХ загрузчиках, данные не править».

## Statement (Gherkin)

```gherkin
Feature: property definitions typed by a subclass of exo__Property are loaded by both shape loaders

  Scenario: the RDF-graph loader walks the declared class hierarchy down from exo:Property
    Given a property definition whose only rdf:type is exo:DatatypeProperty, with a domain and range "xsd:integer"
    And the graph declares exo:DatatypeProperty exo:Class_superClass exo:Property (as NoteToRDFConverter emits it for the exoas-exo class file)
    When the ShapeRegistry is built with ShapeLoader.loadFromRDFGraph
    Then the definition's shape is registered with range ["http://www.w3.org/2001/XMLSchema#integer"]
    And the walk is transitive: a def typed exo:StringProperty is registered when StringProperty ⊑ DatatypeProperty ⊑ Property is declared
    And the RDFS twin edge rdfs:subClassOf is walked too, and a parent written as the class FILE IRI resolves through that file's label
    And a def typed exo:Property or exo:ObjectProperty keeps loading with no hierarchy edge at all (the previous behaviour, verbatim)

  Scenario: the class set is derived from the graph, never hard-coded, and never over-includes
    Given the same DatatypeProperty-only definition but NO edge from exo:DatatypeProperty to exo:Property in the graph
    Then no shape is registered for it
    And a definition typed by a class outside the exo:Property hierarchy (ems:Task ⊑ exo:Asset) never yields a shape

  Scenario: a cycle in the declared hierarchy terminates
    Given exo:Property ⊑ exo:XProperty and exo:XProperty ⊑ exo:Property are both declared
    Then a def typed exo:XProperty is registered and the loader returns
    And an unrelated cycle exo:ACycle ⊑ exo:BCycle ⊑ exo:ACycle registers nothing and the loader returns

  Scenario: the filesystem loader accepts the same definitions through the class files on disk
    Given a vault tree with a def whose exo__Instance_class is the pure-UID wikilink of exo__DatatypeProperty
    And UID-named class files exo__DatatypeProperty (exo__Class_superClass → exo__Property's UID) and exo__Property
    When the ShapeRegistry is built with ShapeLoader.loadFromVaultFS
    Then the definition's shape is registered with its range, cardinality and minCount
    And the legacy label form [[exo__DatatypeProperty]] resolves through a label-named class file declaring [[exo__Property]]
    And the uid|alias form and a two-level chain resolve, with the class files scanned AFTER the definition (order-independent)
    And a def typed by a class outside the hierarchy, or a DatatypeProperty def whose class file is absent, registers nothing
    And [[exo__Property]] / [[<its uid>]] / [[exo__ObjectProperty]] keep loading with no class file at all

  Scenario: loader parity
    Given the SAME three files (a DatatypeProperty-only def and its two class files)
    When the registry is built via NoteToRDFConverter + loadFromRDFGraph and via loadFromVaultFS
    Then the two shapes are deep-equal (propertyIRI, domain, range, cardinality, minCount, severity)

  Scenario: the shape gates through the production pipeline
    Given a fixture vault with a def ems__Task_rank typed only [[ae56ca4c-…]] (exo__DatatypeProperty), range "xsd:integer", and its tbox/ class-file chain
    When runShapesValidation (the validate schema --shapes-mode / create --validate / plugin path) runs over the converter's triples
    Then an asset with ems__Task_rank: 3 has no violation
    And an asset with ems__Task_rank: 3.5 has an sh:datatype violation (actualValue "3.5", expectedRange …#integer) — silent before this requirement
```

## Non-goals (measured 2026-09-19, ticket 84bb4d08 plan-gate)

- The data the walk now exposes — live [vault-exodev / vault-my / vault-tbank] `validate schema --shapes-mode` goes 9/0/0 → 36/64/33: `setting__SettingKey_datatype` minCount ×23 (`exo__SettingKey ⊑ setting__SettingKey`, instances carry the `exo__`-namespaced twin), `ems__Reminder_chatId` unquoted number under `xsd:string` ×26/×6, `lit__Conspect_sourceUrl` string-tag under `xsd:anyURI` ×2/×7/×2, `ems__WorkflowState_timestampOnEnter` maxCount ×2, `agr__Norm_acceptedOn` minCount ×6 — data / TBox / validator-policy follow-ups, not corrected here.
- The validator's lexical table (`literalConformsToDatatype`, req b0ad1160) — in particular `xsd:anyURI` under a string tag (separate follow-up under the same founder rule).
- `loadFromVaultFS` resolution of pure-UID `exo__Property_domain` wikilinks (it registers 66/26/32 of 696/492/468 live defs for that reason) and its verbatim handling of a quoted `exo__Property_minCount: "1"` — pre-existing, separate.
- `exoas-ci` `cli_version` (pinned 16.238.0): data-repo CI does not pick this up until bumped.
