# req(exo): CLI `query` names the files the loader skipped instead of silently reporting an empty vault

## Job Story

When I run `exocortex query` against a vault where an asset violates the #2997 loader
invariant, I want the command to tell me that a file was dropped and why, so that
"0 results" is distinguishable from "the file you care about was never loaded" —
instead of paying a diagnostic cycle reading `NoteToRDFConverter` to find out.

## Statement (Gherkin)

```gherkin
Scenario: the default load path names the skipped file in JSON
  Given a vault whose only asset declares exo__Instance_class WITHOUT exo__Asset_uid
    (an invariant violation per issue #2997 Phase 2 / RFC 0810aad3)
  When I run `query "SELECT ?s ?l WHERE { ?s exo:Asset_label ?l }" --output json`
    on the DEFAULT load path (no --use-cache, i.e. a full parse)
  Then the response meta carries skippedCount = 1
  And meta.skippedFiles[0].path is that file's vault-relative path
  And meta.skippedFiles[0].reason names exo__Asset_uid

Scenario: the default load path names it in text mode too, on stderr
  Given the same vault
  When I run the same query in the default text mode
  Then stderr carries a block naming the skipped file and its reason,
    in the same shape `index` already prints (parity by citation, not analogy)
  And stdout keeps carrying the result document

Scenario: a clean vault says nothing
  Given a vault in which every asset is well-formed
  When I run the query on the default load path
  Then meta carries neither skippedFiles nor skippedCount
  And stderr stays silent about skipped files

Scenario: the cache path claims only what its format can tell
  Given --use-cache is passed (the opt-in path the bot loop uses)
  When the load is served from the cache (hit / delta / rebuild)
  Then no per-file skipped list is claimed — the cache format does not
    distinguish a skipped file from a genuinely empty one
  And at most ONE stderr line reports the COUNT of files that produced no
    triples, worded so that it names both populations
  And that line asserts nothing about the reasons and nothing about all of
    them being invariant-skips
  And that line names the ROUTE to the per-file reasons — a run without
    --use-cache, or `index`
  And meta carries no skippedFiles
```

## Non-goals

- ⛔ The #2997 loader invariant itself is NOT touched (it is the subject of RFC 0810aad3
  and is accepted).
- ⛔ The cache FORMAT is not changed. Making `--use-cache` name the skipped files per-file
  requires storing the reason in `triples.json` — a separate ticket, named as variant (в)
  in the Step-0 fork below and deliberately not taken here.
- ⛔ `sparql-exo003.integration.test.ts` and its self-skip are the subject of ticket
  2716d6c7 and are not touched.
- ⛔ Only `query` prints. The other six `loadVaultTriples` consumers (`apply`, `classes`,
  `resolve-buttons`, `run-query`, `validate-schema`, `CandidateShaclValidator`) receive the
  new field and ignore it; giving each its own surface is a separate decision per command
  (`apply --json` and `resolve-buttons --json` must keep stdout a single document).

## Step-0 fork, named aloud

Three variants were on the table (the orchestrator required them named):

- **(а)** surface on the full parse; on the cache branch print `zeroTriplePaths` under its
  own name with the caveat "skipped + genuinely empty".
- **(б)** widen the `loadVaultTriples` return with `skippedFiles`, moving its full-parse
  branch from `convertVault` to `convertVaultWithValidation`; leave the cache branch alone.
- **(в)** change the cache format — a separate ticket.

Taken: **(б) as the core + a minimal (а)** — one stderr line carrying the COUNT on the
cache branch, without a per-file list. Reason (б) is the core: the default load path of
`query` — and of all seven `loadVaultTriples` consumers — is the FULL PARSE
(`--use-cache` is an opt-in flag with no default, sparql-query.ts:242; `options.useCache ??
false` at sparql-query.ts:377, apply.ts:659, classes.ts:84, resolve-buttons.ts:275 and :453,
run-query.ts:118, CandidateShaclValidator.ts:155, and `Boolean(options.useCache)` feeding the
`useCache` parameter of validate-schema.ts:144 at :1207 and :1445). The count-only line keeps the
opt-in path from being mute while claiming nothing the cache format cannot support.

## Why a new requirement and not conformance with an active one

Active P0 req `fe50da38` covers the loader: its Gherkin says "When I convert the vault via
NoteToRDFConverter.convertVaultWithValidation / Then every malformed asset is reported in
skippedFiles". That promise is about the CONVERTER's return value, and it is kept today —
`skippedFiles` is populated. What is absent is any promise about a COMMAND's output; the
convertVault signature drops the field one layer above the converter. So this is new
user-facing behaviour, not a gap in an existing spec.
