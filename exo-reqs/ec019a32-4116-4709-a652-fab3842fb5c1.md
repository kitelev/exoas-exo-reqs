# req(exo): naming-capability TBox layer (RFC 78572fa9 Candidate B Phase 1 — additive foundation)

## Job Story

When the exo ontology eventually stores class/property identity by uid and computes the readable `prefix#LocalName` on the fly, I need a **stable local name** (`slug`) on every class/property and a **canonical prefix** (`shortName`) on every ontology to compute that projection from — so I want the TBox to declare the naming-capability layer **additively and reversibly first** (a metaclass mixin + two property-defs), changing **no** existing behavior, so the later display-projection and uid-only-store phases have a schema to build on without a big-bang migration.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: exo naming-capability TBox layer (Candidate B Phase 1, additive foundation)

  Scenario: exo__Class subsumes exo__Slugable (metaclass-level slug mixin)
    Given the exo TBox declares exo__Slugable (a metaclass, instance_class exo__Class)
    And exo__Slugable_slug (DatatypeProperty, domain exo__Slugable) is declared
    And the exo__Class metaclass carries exo__Class_superClass -> exo__Slugable
    When the class-hierarchy subsumption is walked from exo__Class
    Then exo__Class subsumes exo__Slugable (every class-def transitively carries the slug capability)
    # Revert-verify: remove the exo__Class -> exo__Slugable link -> subsumption no longer reaches exo__Slugable -> RED

  Scenario: exo__Property subsumes exo__Slugable
    Given the exo__Property metaclass carries exo__Class_superClass -> exo__Slugable
    When subsumption is walked from exo__Property
    Then exo__Property subsumes exo__Slugable (every property-def transitively carries the slug capability)

  Scenario: exo__Ontology declares exo__Ontology_shortName (canonical prefix field)
    Given exo__Ontology_shortName (DatatypeProperty, domain exo__Ontology, cardinality Single) is declared
    Then an exo__Ontology instance MAY additively carry a shortName (canonical prefix) — no instance is required to yet

  Scenario: additive / reversible / no-regression (nothing reads the fields yet)
    Given the naming-capability layer is added and NO slug/shortName values are populated
    Then SHACL `validate schema --shapes-mode` (cache cleared) violations <= baseline
    And existing exo__Class_superClass consumers (ClassHierarchy, audit ontology-membership, RequiredPropertyResolver) behave unchanged
    And no class-def / property-def observable behavior changes (slug/shortName are unread until Phase 2)
```

## Notes

- **⛤ WHY the metaclass mixin (not plain properties) — Andrey vision decision 2026-07-29:** the `exo__Slugable` metaclass realized via a reified `exo__Class_superClass` link is deliberate — it is an **Interface Segregation Principle** capability-interface (the slug capability is a segregated mixin, attached only where wanted, NOT forced onto the universal `exo__Asset`). Crucially it is an **EXTENSION mechanism** (analogous to C#/Kotlin extension methods): users can extend even FIXED domain models later by adding a reified `exo__Class_superClass` link to `exo__Slugable` (or any future capability metaclass) — mixing a new capability into an existing class **without modifying that class**. This extensibility is the first-class design value, and it justifies accepting the small in-memory RDFS materialization cost. That cost is also NOT load-bearing: the shipped query-time class-hierarchy resolver (req 9fddda62, Phase 0, v16.198.0) already resolves `Class_superClass*` walks lazily, so `RDFSInferenceEngine` materialization can be disabled later and the mixin still resolves at query-time — the metaclass-mixin approach is robust either way.
