## Контекст

Три функции читают **один** словарь `ems__Effort_status`, каждая по-своему:

| функция | файл | стратегия | **выход** |
|---|---|---|---|
| `resolveStatusFromFrontmatter` | `core/services/GroundingExecutor.ts` | UID-таблица | symbolic либо `null` |
| `getStatusLabel` | `plugin/domain/property-editor/PropertySchemas.ts` | UID-таблица | человекочитаемый label |
| `resolveStatusLabel` | `core/domain/display-name/hostFunctions.ts` | vault-lookup | symbolic либо сырой таргет |

⛤ **Выходы у них РАЗНЫЕ**, и это не дефект: две дают symbolic, третья — label для UI. Значит «одна функция вместо трёх» невозможна буквально; общей может быть только **нормализация к symbolic**, а интерпретация результата остаётся за каждым.

## Что действительно дублируется

Две **UID-таблицы** содержат одни и те же 6 UID (`STATUS_UID_BY_ENUM` и `FALLBACK_EFFORT_STATUS_VALUES`), различаясь лишь формой записи. Обе пришлось править вручную 2026-08-13, когда `ToDo` и `Analysis` были удалены из `exoas-public` — обе цитируют req `fcbde537`. Дрейф уже случался.

⛤ **Держателей на самом деле ЧЕТЫРЕ, а не три.** `EFFORT_STATUS_OPTIONS` (`core/domain/constants/EffortStatusOptions.ts`) зеркалит тот же словарь в **symbolic**-форме для UI-дропдауна. Он не парсер (write-side), поэтому в это требование не входит — но следующая правка словаря обязана посетить и его.

## Требование

1. Канон UID↔enum живёт **в одном месте** — `core/domain/constants/`, рядом с прецедентами (`WorkflowClassUids`, `GroundingTypeUIDs`). Обе таблицы **выводятся** из него.
2. Нормализация сырого значения `ems__Effort_status` к symbolic-форме — **одна функция**; три потребителя зовут её и добавляют только своё.
3. Каждое расхождение либо сохранено, либо **решено явно** — не унаследовано молча.

⛔ Импортировать `services/` в `domain/` нельзя (инверсия слоёв) — отсюда извлечение, а не прямая ссылка.

## Решения по известным расхождениям

| вход | было | решение |
|---|---|---|
| `["[[a]]","[[b]]"]` (мультизначный) | GE → `null` (громко), hostFn → `""` | нормализатор возвращает `null`; **интерпретация остаётся за потребителем** — для перехода это отказ, для отображения «неизвестно» |
| `ems__EffortStatusDone <uuid>` | GE **отвергает**, двое других принимают | **принимать** — форма документирована как реально возникающая после части переходов; отказ на легальной форме был дефектом |

⛤ Второе — поведенческое изменение `GroundingExecutor`, и оно строго в сторону терпимости: переход, который раньше отказывал на валидном значении, теперь состоится.

## Gherkin

```gherkin
Feature: one normaliser for one vocabulary

  Scenario: every legal wikilink form yields the same symbolic status
    Given a status written as [[<uid>]], [[<uid>|label]], [[ems__EffortStatusDone]]
      or [[ems__EffortStatusDone <uuid>]]
    Then the normaliser returns ems__EffortStatusDone for all of them

  Scenario: a multi-element list is not guessed
    Given a status written as a two-element list
    Then the normaliser returns null
    And each caller decides what that means for it

  Scenario: the UID table has ONE source
    Then the workflow table and the property-editor table are derived from it
    And a status added in one place appears in both without a second edit

  Scenario: each caller keeps its own output shape
    Then the workflow reader still yields a symbolic status or null
    And the property editor still yields a human label
    And the display matcher still falls back to the vault lookup
```

## ⛤ Ось, без которой набор был бы вакуумным

Оси на отдельные формы значения проходят и у трёх независимых реализаций — они и сегодня по большей части согласны. Различает **только** ось на ИСТОЧНИК: добавь статус в канон и проверь, что обе выведенные таблицы его увидели. Мутант — вернуть литеральную таблицу одному из потребителей.
