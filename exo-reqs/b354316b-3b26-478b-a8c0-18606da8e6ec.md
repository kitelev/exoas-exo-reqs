## Контекст

`CommandResolver.resolvePropertyDefaultValue` имеет **пять** мест, возвращающих
`"[[<uid>]]"` вместо подставленного значения. Три из них — штатные (значение и
есть ссылка). Две — **аварийные откаты**, при которых созданный ассет получает
ссылку на сам токен подстановки там, где должно стоять подставленное значение:

| строка | условие | лечится |
|---|---|---|
| `!valueSubject` | ассета токена нет в store (cold-start race / pruned vault) | перезапуском |
| `!isSubstitutionToken` | класс токена не зарезолвился | перезапуском |

Обе **молчали**. Две соседние аварийные ветки (`dispatchSubstitutionToken`:
нет `_resolver`, resolver-id вне whitelist) пишут `warn` — то есть асимметрия
не намеренная, а исторический пропуск.

Наблюдаемая цена молчания: у шести ассетов в живом vault `exo__Asset_label`
равен `[[ecd68426-…]]` (= токен `$userInputLabel`), а введённое пользователем
значение лежит в `aliases`. Порча **кластеризуется по сессии** (два случая
2026-08-17 в 23 секундах друг от друга) — определение команды кэшируется, и
один холодный старт травит все создания этой сессии. Ни одной строки в логе;
класс был недиагностируем, и корень пришлось сужать исключением, а не замером.

⛔ Это требование **не чинит** порчу — оно делает следующий случай
самоназывающимся. Собственно fail-loud (отказать вместо записи ссылки в label)
— отдельная работа: он меняет поведение команд и требует своей оценки.

## Gherkin

```gherkin
Feature: аварийный откат подстановки токена оставляет след в логе

  Scenario: ассета токена нет в store (cold-start race)
    Given grounding с PropertyDefault, чей value ref указывает на UID, отсутствующий в store
    When CommandResolver разрешает значение этого PropertyDefault
    Then он возвращает wikilink-форму "[[<uid>]]"
    And logger.warn вызван ровно один раз
    And сообщение содержит uid значения, имя свойства и uid grounding'а

  Scenario: значение — обычный ассет, не токен подстановки
    Given grounding с PropertyDefault, чей value ref указывает на существующий НЕ-токен
    When CommandResolver разрешает значение этого PropertyDefault
    Then он возвращает wikilink-форму "[[<uid>]]"
    And logger.warn НЕ вызван
    And logger.debug вызван ровно один раз

  Scenario: предупреждение звучит ОДИН раз на пару (grounding, значение)
    Given grounding, чей PropertyDefault ссылается на отсутствующий в store UID
    When CommandResolver разрешает его, затем кэш инвалидируется, и разрешает снова
    Then logger.warn вызван РОВНО один раз суммарно

  Scenario: штатная подстановка молчит
    Given grounding с PropertyDefault, чей value ref указывает на валидный SubstitutionToken
    When CommandResolver разрешает значение этого PropertyDefault
    Then ни logger.warn, ни logger.debug не вызваны для отката
```

⛤ Дедуп — не косметика: `warn` маршрутизируется в **пользовательский тост**
Obsidian (`notice: true`) и в файл лога, а ветка перевычисляется на каждом
рендере кнопок (`invalidateCache()` фаерит на каждое сохранение `.md`). Без
дедупа одна висячая ссылка давала бы тост при каждом рендере; в репозитории
есть прецедент этого класса — #3186, ~6 МБ лога за двое суток.

⛔ Множество намеренно **не** сбрасывается в `invalidateCache()`: он фаерит на
каждое сохранение, и сброс там вернул бы ровно тот шторм, который дедуп
предотвращает. Починка самой ссылки гасит предупреждение **по построению** —
ветка перестаёт исполняться.

⛤ Сообщение содержит только **наблюдаемое** («ассета нет в store»). Причины —
cold-start race, размонтированное пространство, обычная битая ссылка — живут в
комментарии кода, а не в тосте, который выдал бы одну из них за установленную.

⛤ Второй сценарий — про **уровень**, а не только про факт: не-токен есть
частый штатный путь (любое `assetRef`-поле), поэтому `warn` там превратился бы
в шум и обесценил первый сценарий. Разделение `warn` / `debug` — несущее.
