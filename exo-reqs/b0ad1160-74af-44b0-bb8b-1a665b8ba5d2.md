# req(exo): validate schema --shapes-mode enforces sh:datatype for a CURIE-literal range xsd:<local> — the RDF-graph shape loader resolves it like the FS loader, and a converter-tagged YAML scalar conforms by its lexical form

## Job Story

When I declare a property's value type as `exo__Property_range: xsd:integer` (or `xsd:gYear`, `xsd:boolean`) — the form `create --class DatatypeProperty` writes and 100 % of live datatype ranges use — I want `validate schema --shapes-mode` (and everything sharing its pipeline: `create --validate`, the plugin's on-save SHACL pass) to actually check values against that type, judging a YAML number by what I wrote (`7` is an integer, `7.5` is not, `1987` is a year) rather than by the `xsd:decimal` tag our converter puts on every number, so that a wrong value is reported and a right one is not.

Founder decision 2026-09-18 (ticket a9b55ead, AskUserQuestion, verbatim): «Объявленный range — валидатор принимает число, если его запись подходит под тип» — the declared range is the source of truth where the datatype tag is a converter artefact.

## Statement (Gherkin)

```gherkin
Feature: sh:datatype reaches CURIE-literal ranges and judges converter-tagged scalars by lexical form

  Scenario: the RDF-graph shape loader resolves a CURIE-literal datatype range
    Given a property definition whose exo__Property_range is the plain literal "xsd:integer"
    When the ShapeRegistry is built from the RDF graph (ShapeLoader.loadFromRDFGraph — the path
      validate schema --shapes-mode, create --validate and the plugin on-save pass use)
    Then the shape's range is ["http://www.w3.org/2001/XMLSchema#integer"]
    And ShapeLoader.loadFromVaultFS built from the SAME frontmatter yields the SAME range (loader parity)
    And a full-IRI literal range "http://www.w3.org/2001/XMLSchema#integer" still resolves as before
    And a literal that is neither a CURIE nor an IRI (e.g. "integer") is still dropped (range undefined)

  Scenario: a YAML number under an integer / gYear range conforms by lexical form
    Given pmi__Principle_number is declared with range xsd:integer
    And an asset carries `pmi__Principle_number: 7` (NoteToRDFConverter tags it xsd:decimal)
    When I run `validate schema --shapes-mode` over the vault
    Then no sh:datatype violation is reported for that asset
    And `pmi__Principle_number: 7.5` IS reported as an sh:datatype violation (actualValue "7.5", expectedRange …#integer)
    And `pmi__Model_originYear: 1987` under range xsd:gYear is NOT a violation
    And `pmi__Model_originYear: 2026-05` under range xsd:gYear IS a violation

  Scenario: strict tag equality is kept wherever the tag is NOT a converter artefact
    Given the same shapes
    Then a quoted "10" (tagged xsd:string) under range xsd:integer IS an sh:datatype violation
    And a number (tagged xsd:decimal) under range xsd:string IS a violation
    And a number under a datatype outside the lexical table (xsd:anyURI) IS a violation (number tag: unchanged by the 2026-09-19 amendment)
    And the Exocortex ad-hoc range form https://exocortex.my/ontology/xsd#integer is judged by the same table

  Scenario: a YAML string under range xsd:anyURI is judged as an absolute IRI (amendment 2026-09-19, ticket e55b0a07)
    Given a property declared with range xsd:anyURI (lit__Conspect_sourceUrl)
    Then a plain literal `https://example.com/video/1` (tagged xsd:string — the converter's tag for every YAML string) conforms
    And the plain literals `not a uri`, `https://x.com/a b` and ` https://x.com` (whitespace) ARE sh:datatype violations
    And the same URL carrying a NON-converter tag (xsd:token) under xsd:anyURI IS a violation (strict tag equality — the relaxation is keyed on the xsd:string tag)
    And the plain literal `/relative/path` IS a violation (absolute IRI required — IRI.isValidIRI; deliberately stricter than XSD 1.1 §3.3.17)
    And a number-tagged `7` under xsd:anyURI IS still a violation (the relaxation applies to the string tag only)

  Scenario: a YAML boolean under range xsd:boolean
    Given a property declared with range xsd:boolean
    Then a plain literal `true` (the converter's form of a YAML boolean) conforms
    And the plain literal `yes` is a violation
```

## Amendment 2026-09-19 (ticket e55b0a07, ORCH mandate — derived from founder rule 6c, not a new founder fork)

Range `xsd:anyURI` was unreachable by construction: NoteToRDFConverter tags every YAML string `xsd:string`, and this requirement kept strict tag equality for anyURI, so every `lit__Conspect_sourceUrl` value (2/7/2 [vault-exodev/my/tbank], all absolute https URLs) was an sh:datatype violation once #4271 made the def visible. Under rule 6c («объявленный range — источник истины, тег — артефакт конвертера») the string tag is the same converter artefact as the number tag ⇒ a string whose lexical form is a valid absolute IRI (`IRI.isValidIRI`, the one IRI notion in core) conforms. Non-ASCII IRIs conform; whitespace, empty, relative references and schemes outside the core allowlist are violations — stricter than the XSD 1.1 letter (any string), deliberately. Number-tagged literals under anyURI are unchanged (V6/I4). Live expectation: 11/7/2 → 9/0/0 (remaining 9 = exoas-flow, Non-goals).

## Non-goals (measured 2026-09-18, ticket a9b55ead)

- Property definitions typed ONLY `exo__DatatypeProperty` (88/29/25 of 134/48/44 CURIE-range defs [vault-exodev/my/tbank]) are invisible to BOTH shape loaders (they match `exo__Property` / `exo__ObjectProperty` only, no superClass walk) — separate ticket.
- `exoas-flow` `flow__StatusModel_boardStatus` / `_statusProperty`: typed `exo__ObjectProperty` with range `xsd:string`, values promoted to IRIs by the converter → 9 genuine violations in vault-exodev (2 nodes); a data / declaration question, separate ticket.
- YAML dates (`2026-01-01` → Date → tagged xsd:dateTime) under range `xsd:date`; the converter's `xsd:decimal` emission itself (converter ↔ RDFSerializer asymmetry); the wording of the IRI-under-datatype-range message (reported as sh:class today).
