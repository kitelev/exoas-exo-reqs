# req(exo): `create-batch` — create many assets from one JSON file in one invocation

Source: GitHub issue kitelev/exocortex#4347 (bulk/batch create).

## Job Story

When I digitise a large structured source through the CLI — the motivating case is a 300-exercise coaching book, about 6,500 assets — I want to hand the whole set to ONE `create-batch` call and get every asset created with exactly the guarantees `create` gives one at a time, so the job takes minutes instead of the 30+ hours that 6,500 separate `create` calls cost on the working vault, and a mistake in the generated input is refused as a whole instead of leaving half a tree behind.

## Why the process boundary is NOT the cost (measured 2026-09-25, CLI 16.254.2, vault-exodev, 34,935 `.md` files)

| measurement | value |
|---|---|
| `npx … --version` (process start) | 0.73 s |
| `create --dry-run` with a resolvable `exo__Asset_isDefinedBy` | 16.7-22.9 s |
| `create --dry-run` without an anchor (neighbour scan) | 29.1 s |
| reads of EACH vault file by ONE `create` (`-r` counter over `fs.readFile` cb + `fs.promises.readFile` + `readFileSync`, run on `node <dist>` directly) | 4 (34,930 files) / 5 (5 files) |

The cost is vault-wide scans repeated inside every `create` (class index, TBox property walk, shape load, anchor/neighbour resolution through an adapter that caches nothing), not `npx`. A loop of `create` calls inside one process would therefore read the vault 4×N times and save almost nothing. The load-bearing property of this requirement is that **the scans are done once per invocation, not once per item**.

## Statement (Gherkin)

```gherkin
Scenario: a batch creates every item in one invocation
  Given a vault and a JSON file holding an array of items, each with "class" and "label"
  When I run `cli create-batch <file> --vault <vault>`
  Then every item is written as a vault asset
  And stdout is ONE JSON document: an array of {uuid, path, label}, one entry per item, in input order
  And the command exits only after stdout and stderr are flushed, so a reader on a pipe receives the whole document
  And the exit code is 0

Scenario: each item goes through the SAME pipeline as `create`
  Given an item and the equivalent `create` flags (class→--class, label→--label, aliases→--aliases,
        properties key→value / key→[v1,v2] → repeated --property (a number or boolean as its JavaScript text),
        body→--body-file, status "X"→--status X, status false→--no-status, createdBy→--created-by)
  When both are run against the same vault
  Then the two files are byte-identical apart from exo__Asset_uid, the filename and the timestamps
  And every refusal `create` makes (empty label, comma-joined alias, self-managed key via properties,
      unknown property NAME, dangling wikilink VALUE, body that copies a frontmatter block,
      --status on a non-status-bearing class, status+explicit ems__Effort_status, isDefinedBy that is not an ontology)
      is made for the item too

Scenario: all-or-nothing
  Given a batch in which item 2 and item 5 are invalid and the rest are valid
  When I run `cli create-batch`
  Then NO file is written
  And stderr names EVERY failing item by 0-based index and label (items 2 AND 5, not only the first) —
      its shape, uid and anchor problems and its first planning failure
  And the exit code is 2

Scenario: an item links to another item of the same batch through a caller-supplied uid
  Given item A carries "uid": "<uuid-A>" and item B has property "ems__Effort_parent": "[[<uuid-A>]]"
  When I run `cli create-batch`
  Then A is written as <uuid-A>.md with exo__Asset_uid <uuid-A>
  And B passes wikilink validation although <uuid-A> did not exist before the call

Scenario: a caller-supplied uid is refused when it cannot be the new asset's identity
  Given an item whose "uid" is not a canonical UUID, OR repeats another item's uid, OR is already the uid of an
        asset in the vault — by filename OR by frontmatter exo__Asset_uid (label-named assets such as pn__DailyNote)
  When I run `cli create-batch`
  Then the batch is refused (all-or-nothing) and the item is named
  And running the SAME file twice is refused on the second run instead of creating duplicates, WHEN its items carry uids
      (an item without "uid" gets a fresh uid every run and is created again)

Scenario: an isDefinedBy anchor must exist on disk
  Given item A carries "uid": "<uuid-A>" and item B has "exo__Asset_isDefinedBy": "[[<uuid-A>]]"
  When I run `cli create-batch`
  Then B is refused, naming item A — the range guard and co-location read the anchor's file, which does not exist yet

Scenario: vault scans are not repeated per item
  Given a batch of 20 items
  When I run `cli create-batch`
  Then each vault-scanning service (class resolver, property-name validator, effort-status resolver, shape load)
       is instantiated/run once for the invocation, exactly as for a batch of 1
  And the vault is listed, and each file's frontmatter read from disk, no more often than for a batch of 2 —
      also when every item carries a different anchor
  And linking the 20 items to 20 DIFFERENT existing assets by UUID does not walk the vault once per link
      (UUID lookups are answered from one in-memory filename index; a label-form link target, or a target that is
      not UID-named, is resolved once per distinct target)

Scenario: dry run
  When I run `cli create-batch <file> --dry-run`
  Then every item is planned and validated, NO file is written
  And stdout carries the planned {uuid, path, label} array — an item that supplies no "uid" gets one generated
      for this run, so its uuid and path differ from a later real run
  And stderr previews each item's exact bytes

Scenario: malformed input is refused by name
  Given a file that is not a JSON array, OR an empty array, OR an item without "class" or "label",
        OR an item carrying a key outside {class, label, uid, aliases, properties, body, status, createdBy},
        OR a property number that is an integer beyond 2^53 (a JSON double has already lost its digits)
  When I run `cli create-batch`
  Then nothing is written, the offending item/key is named and the exit code is 2

Scenario: input a generator plausibly emits is accepted
  Given an item whose optional keys are null (Python None), OR a document starting with a UTF-8 BOM
  Then null means "absent" and the BOM is ignored
  And `-` reads stdin to its end with no time limit; a terminal on stdin is refused instead of waited on
```

## Input format

`<file>` is a path, or `-` for stdin. The document is a JSON array; each item:

| key | required | meaning (= the `create` flag) |
|---|---|---|
| `class` | yes | `--class` (short name or UUID) |
| `label` | yes | `--label` |
| `uid` | no | caller-supplied identity (canonical lower-case UUID); omitted → generated, as `create` does |
| `aliases` | no | array of strings → `--aliases` |
| `properties` | no | object; a string / number / boolean value → one `--property k=v` (a number as JavaScript prints it: `1.0` → `1`), an array value → the same key repeated (multi-value); an integer beyond 2^53 is refused |
| `body` | no | string, taken VERBATIM (no `\n` escape expansion — same rule as `--body-file`) |
| `status` | no | string → `--status <name>`; `false` → `--no-status` |
| `createdBy` | no | `--created-by` for this item; falls back to the batch-wide `--created-by`, then to the `create` default |

Batch-wide flags: `--vault`, `--dry-run`, `--timezone`, `--skip-wikilink-validation`, `--created-by`, `--yes` (no-op, for symmetry).

## Non-goals (v1)

- `--validate` (per-candidate SHACL-lite), `--use-cache`, `--write-through` are not offered: the SHACL candidate validator loads the whole vault per candidate, so it needs its own design. Commander refuses the unknown flag (fail-loud); run `validate schema --shapes-mode` after the batch.
- Updating existing assets — `create-batch` only creates.
- The filesystem is not transactional: all-or-nothing covers VALIDATION. An I/O failure during the write phase stops the remaining writes, names the items already written and exits 5.
- Plugin/UI surface: `create-batch` is a transport optimisation of the existing per-asset `create` capability, which the plugin already offers per asset; it adds no new user capability to mirror.
- MCP `create_asset` batching — separate work.

## Approval note

Design decisions (separate `create-batch` verb over `create --batch`; caller-supplied `uid` over a placeholder mini-syntax; all-or-nothing over best-effort) were put to the founder on 2026-09-25; the founder answered with an explicit autonomy mandate for the session ("принимай все решения от моего лица по своим рекомендациям"). The requirement is approved under that mandate, on the recommended options.

**Amended 2026-09-25, before merge, after review round 1** (`code-reviewer`, verdict BLOCK, every finding reproduced):
clauses that claimed more than the code did were narrowed to what it does — the dry-run mapping for items without
`uid`, re-run safety only for items that carry `uid`, the vault-listing claim now names what is looked up per distinct
target — and guarantees were added where the code was fixed: stdout/stderr flushed before exit (a 2,000-item dry run
reached a pipe as 65,536 of 328,892 bytes), an in-batch isDefinedBy anchor refused, the vault uid check extended to
frontmatter uids, UUID link targets answered from one filename index, unsafe integers refused, `null`/BOM accepted,
stdin read without a time limit.
