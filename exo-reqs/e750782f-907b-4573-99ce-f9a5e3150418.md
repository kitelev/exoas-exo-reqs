# req(exo): the skos prefix emits the W3C SKOS namespace (http://www.w3.org/2004/02/skos/core#)

## Job Story

**When** I record that my author's term is the same as (or close to) a neutral concept on the comparison desk,
**I want** the mapping predicate `skos__exactMatch` (and the four other SKOS mapping properties) to be the W3C term `http://www.w3.org/2004/02/skos/core#exactMatch`,
**so that** a query written against the standard SKOS vocabulary finds my mappings, and the words "W3C SKOS" are true of them.

## Gherkin

```gherkin
Feature: the skos prefix resolves to the canonical W3C SKOS namespace

  Background:
    Given the engine registers external W3C vocabularies in Namespace.KNOWN_NAMESPACES (req aceaa2cc)
    And the founder decided on 2026-10-10 (RFC 14217015, decision №6) that SKOS terms use the W3C address

  Scenario: a skos-prefixed label emits the W3C SKOS IRI
    Given a vault asset whose exo__Asset_label is "skos__exactMatch"
    When the converter derives the symbolic IRI for that label
    Then the emitted IRI is "http://www.w3.org/2004/02/skos/core#exactMatch"
    And it is NOT "https://exocortex.my/ontology/skos#exactMatch"

  Scenario: an instance of the skos__Concept stub class carries the W3C class IRI
    Given a class asset labelled "skos__Concept" and an instance whose exo__Instance_class links to it by UID
    When the vault is converted
    Then the instance's exo__Instance_class object is "http://www.w3.org/2004/02/skos/core#Concept"

  Scenario: a reified mapping statement materialises a triple under the W3C predicate
    Given an exo__Statement whose exo__Statement_predicate links by UID to the property asset "skos__exactMatch"
    When the vault is converted
    Then a triple <subject> <http://www.w3.org/2004/02/skos/core#exactMatch> <object> exists
    And a SPARQL query using PREFIX skos: <http://www.w3.org/2004/02/skos/core#> finds it
    And the same query with PREFIX skos: <https://exocortex.my/ontology/skos#> returns 0 rows

  Scenario: Namespace.forPrefix returns the canonical singleton
    When Namespace.forPrefix is asked for "skos"
    Then it returns Namespace.SKOS whose IRI is "http://www.w3.org/2004/02/skos/core#"

  Scenario: the inverse reads the W3C SKOS IRI back
    When symbolicIriToPropertyKey reads "http://www.w3.org/2004/02/skos/core#exactMatch"
    Then it returns "skos__exactMatch"

  Scenario: the CLI SHACL validator derives skos subClassOf edges under the same IRI
    Given an instance of concept__Concept, a class edge concept__Concept ⊂ skos__Concept, and a property skos__exactMatch whose range is skos__Concept
    When validate schema --shapes-mode checks a mapping from that instance to another concept__Concept
    Then there is no sh:class violation on http://www.w3.org/2004/02/skos/core#exactMatch
    And a mapping to an instance that is NOT a concept raises exactly one such violation

  Scenario: a CLI triple cache written before this change is rebuilt
    Given a .exocortex/cache/triples.json of the previous format (formatVersion 4) that carries the ad-hoc skos IRI for unchanged files
    When the CLI loads the cache
    Then the cache is invalid and rebuilt, and the W3C SKOS IRI reaches the caller
```

## Acceptance

- `Namespace.forPrefix("skos")` returns the canonical `Namespace.SKOS` singleton (reference equality).
- The CLI `NAMESPACE_PREFIX_MAP` maps `skos__` to the W3C base, so `labelToOntologyIRI("skos__Concept")` equals the IRI the converter emits.
- `CACHE_FORMAT_VERSION` is raised so caches of the previous format are rebuilt once.
- Revert-verify: removing `Namespace.SKOS` from `KNOWN_NAMESPACES` reddens the emission scenarios; removing the `skos__` entry from the CLI map reddens the SHACL scenario; setting the cache version back reddens the cache scenario.

- Registering `dc`, `dcterms`, `foaf`, `schema` — no vault presence.
- Moving the `skos__Concept` / `skos__ConceptScheme` stubs between assetspaces — that is vault data (leaf 6d3d7dd2), not engine.
