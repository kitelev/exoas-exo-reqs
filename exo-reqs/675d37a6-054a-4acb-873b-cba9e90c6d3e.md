## Job story

When an e2e shard launches Obsidian several times in a row (one launch per spec, `workers: 1`, one CDP port) and Obsidian renders the "Trust author and enable plugins" dialog AFTER the launcher's single visibility probe, I want the launcher to notice and click that late dialog while it is still waiting for the exocortex plugin, so that the vault never spends the whole plugin wait in Restricted Mode and the shard does not fail on a 30 s `pluginLoaded` timeout that a bare rerun would make green.

## Context

- Source: ticket `be9e9b46-4427-4b41-9add-43cce49f6037` (parent techbacklog `bbac67ce`). Two red attempts of `e2e-shard (6)` on unrelated PRs (runs `35078685737` @e45771e1, `35097784476` @d0211d9b), both green on rerun; in both the SECOND launch of the shard (`daily-note-tasks.spec.ts`, right after the SIGKILL of launch №1) logged `Trust dialog not present` at `App object found after 0 polls`, then 0 renderer console lines and `exocortex plugin did not load within 30000ms. Loaded plugins: [none]` — i.e. the community-plugin layer never started (Restricted Mode), not "slowly". In 40 green launches of 10 `main` runs `Plugin ready after` was 9–33 ms.
- Mechanism (`packages/obsidian-plugin/tests/e2e/utils/obsidian-launcher.ts`, `handleTrustDialog`): the trust button is probed ONCE with `locator(...).isVisible({ timeout: 10000 })`. In `playwright-core@1.62.1` that option is `@deprecated This option is ignored … does not wait for the element to become visible and returns immediately` (`types/types.d.ts:15868-15875`); at runtime the client sends `channel.isVisible(…, kNoTimeout)` and the server's `isVisibleInternal` takes a single `callOnSelector` snapshot. The probe therefore fires at the moment `window.app` appears; a dialog rendered after that moment is never clicked, stays on screen, and the vault remains untrusted for the entire plugin wait.
- Secondary: when the 30 s plugin wait plus cleanup plus retry overflow the spec's 60 s `beforeAll` budget, Playwright runs `afterAll` → `launcher.close()` nulls `this.window` while the retry's wait loop is still polling → `TypeError: Cannot read properties of null (reading 'evaluate')` — a misleading second failure. And `close()` leaves its 10 s `setTimeout` armed after the process has already terminated, printing `termination timeout (continuing anyway)` after `terminated` — log noise that reads as a race.
- Prior practice: PR kitelev/exocortex#4160 (the plugin-wait move into the launcher) shipped as e2e-infra without a requirement. This requirement follows the `req(testsys)` precedent `7af848cd` (a test-system invariant bound to a jest unit axis) so the launcher guarantee is owned by the active-gate.

## Statement (Gherkin)

```gherkin
Feature: ObsidianLauncher clicks a trust dialog that renders after the initial probe

  Background:
    Given ObsidianLauncher.launchAttempt has found window.app and run the initial trust probe (handleTrustDialog)
    And the launcher is inside waitForPluginReady polling `app.plugins.plugins.exocortex` every 500 ms with a 30 s ceiling

  Scenario: a trust dialog that appears during the plugin wait is clicked and the wait completes
    Given the exocortex plugin is not loaded on poll 1 and the trust button is not visible on poll 1
    When on poll 2 the trust button "Trust author and enable plugins" becomes visible
    Then the launcher clicks it exactly once and logs that the trust dialog appeared late
    And the wait resolves as soon as a later poll reports the plugin loaded
    And the launcher does NOT fail with "exocortex plugin did not load within 30000ms"

  Scenario: no trust dialog — behaviour unchanged (control)
    Given the trust button is never visible during the plugin wait
    When the plugin becomes loaded on poll 2
    Then the launcher resolves after 2 polls and never calls click

  Scenario: the initial probe is instantaneous by contract and still clicks a dialog that is already visible
    Given the trust button is already visible when handleTrustDialog runs
    When handleTrustDialog probes it with a bare isVisible() (no deprecated timeout option)
    Then it clicks the button once and waits for the dialog to be hidden
    And when the button is not visible it clicks nothing

  Scenario: the window is closed underneath the plugin wait (afterAll → close() during a retry)
    Given the plugin is not loaded on poll 1
    When close() nulls the launcher window before poll 2
    Then waitForPluginReady rejects with an explicit "window closed during plugin wait" error
    And NOT with TypeError "Cannot read properties of null (reading 'evaluate')"

  Scenario: close() disarms its termination timeout once the Electron process has terminated
    Given close() has sent SIGKILL and the process is gone on the first 100 ms check
    When 10 s pass after close() resolved
    Then "termination timeout (continuing anyway)" is NOT logged

  Scenario: close() still gives up after 10 s when the process does not terminate (control)
    Given the Electron process keeps answering `process.kill(pid, 0)`
    When 10 s pass
    Then close() logs "termination timeout (continuing anyway)" and resolves
```

## Non-goals

- Not changing the specs, the shard assignments, `playwright-e2e.config.ts` timeouts (`test.setTimeout`) or CI workflow.
- Not fixing why Obsidian sometimes does not persist trust between consecutive launches (race between SIGKILL in `close()` and Obsidian's config write — not provable from logs); the launcher must tolerate a late dialog regardless.
- Not a claim that one green shard-6 run proves the flake gone: the flake is probabilistic; the proof is the unit axes + mutants above.
