# req(exo): query --batch --prune-oracle — the double-run oracle of on-demand loading

## Job Story

When the analyzer's P' is about to decide which triples a CLI call loads, I want every query a
pipeline actually sends to be answered twice over the SAME graph snapshot — over the full graph and over
the graph cut to P' — and the two answers compared, so that a cut which silently changes an answer is
caught as a defect of the mechanism long before on-demand loading becomes the default (RFC `308a52c3`
«Загрузка по запросу», §Д3; ticket `2588fa84`).

## Mechanism (read on `origin/main` `bb2ef2dc`)

There is no "answer with the cut" path in the CLI: the analyzer (`analyzeParsedQuery`,
`computeSubPropertyIndex`, req `f5db994b`) is exported from core and called by nobody; the loader by P'
is phase 3b. `query --batch` (req `166613ce`) loads the graph once per file and answers its entries as
NDJSON through the shared `buildAlgebra` / `executeAlgebra`. The reference semantics of the cut is the
loaded triples (explicit and inferred layer) filtered by P' in their original order — the set the
analyzer's axes and fuzzers proved answers over.

## Statement (Gherkin)

```gherkin
Feature: query --batch <file> --prune-oracle — full answer versus cut answer, per entry

  Background:
    Given a batch file in the query --batch format
    And the CLI is called as `exocortex query --batch <file> --prune-oracle`

  Scenario: the flag is a diagnostic mode of --batch only
    When --prune-oracle is given without --batch
    Then the call is refused before any graph load
    When it is given with --batch
    Then the oracle runs instead of the plain batch, and --timeout and --use-cache reach its runs and its load

  Scenario: both runs read one snapshot and never the result cache
    Then the graph is loaded once for the whole file
    And for every entry the full run and the cut run execute over that one loaded graph
    And the query result cache is neither read nor written (a warmed entry for the same text still executes)

  Scenario: the cut and the comparison
    Given the analyzer's verdict for the entry is "prune" with predicate set P'
    When the cut store holds the loaded triples whose predicate is in P', in their original order
    Then the entry's verdict compares the canonical full answer with the canonical cut answer
    And a canonical row is the sorted pairs (variable, term) where a term keeps every part that tells answers
      apart: a literal's value, datatype, language and direction; an IRI; a blank node; a bare JS value;
      all three positions of a CONSTRUCT triple
    And the verdict is "equal" (same rows in the same order), "order-only" (same multiset, other order) or
      "diverged" (with the number of rows only in the full answer and only in the cut answer)
    And the reference answer and any re-run are computed over the FULL graph, never over the cut

  Scenario: what is not judged
    When the full answer is computed again and differs from the first full answer in any way, order included
    Then the entry is "unstable" and is not judged (NOW(), exo:age_days, any nondeterminism of the engine)
    And a re-run that fails (timeout or error) makes the entry "unstable", never "failed"
    When the cut run times out
    Then the entry is "cut-timeout": not judged, not diverged
    When the cut run throws any other error while the full run answered
    Then the entry is "diverged" (the cut changed the outcome)
    When the analyzer refuses to prune
    Then the entry is "full-load": the query is still executed once over the full graph, so a query the
      product cannot run (DESCRIBE) is a failed entry
    When the entry is an UPDATE
    Then it is refused before any analysis, as query --batch refuses it

  Scenario: the oracle is not vacuous — skeleton canaries
    Given an entry whose P' holds skeleton predicates (class bridge; sub-properties and their declarations)
    When the cut is repeated without each skeleton part
    Then a canary that changes the multiset (or fails with a non-timeout error) while the full answer is
      stable is "detected" and counted per part
    And a canary never removes a predicate the query itself names
    And a canary that changes only the order, times out, or comes with an unstable full answer is not "detected"

  Scenario: exit code and summary
    Then the summary is the last NDJSON line (type summary, oracle true) and counts every entry once,
      judged entries and non-empty judged entries separately
    And the exit code is OPERATION_FAILED (5) when any entry diverged or failed, and 0 when none did
      (an error writing the output stream fails the call as in query --batch)
    And "order-only" alone does not fail the call

  Scenario: nothing private leaves the oracle
    Then no bound value, no digest of an answer and no predicate IRI is printed — cardinalities only
      (rows, cut triples, size of P', counts of sources)

  Scenario: memory stays bounded
    Then one cut store is kept: entries in a row with the same P' reuse it, a different P' replaces it,
      canary stores are not kept

  Scenario: nothing outside the flag changes
    Then the oracle module is loaded by a dynamic import only under the flag
    And query and query --batch without --prune-oracle give the same output as before
```

  0 diverged, and every skeleton canary fires at least once on the supplement.

## Non-goals

- The loader by P' (phase 3b, `f9fc7589`) — the oracle's cut is the reference it must reproduce; the
  same comparator takes the loader as the second source of the cut.
- `query --prune-report` and the cut-share threshold (phase 1b).
- ASK — the CLI `query` does not execute ASK at all (bug `3254ccba`).
- Making "order-only" red — the RFC judges after canonicalising order; proposed for phase 3b.
- `--no-optimize` reaching the oracle through the command — the flag is dead in the whole product
  (bug `954c7dfa`); the oracle passes `options.noOptimize` as query --batch does.
- Cancelling an expired run — `Promise.race` without cancellation is engine work (bug `8fe905e9`).

## Amendments before Active (2026-11-14, independent review of the implementation, round 1)

Verdict WARNING: 0 CRITICAL, 1 HIGH, 2 MEDIUM, 6 LOW. The reviewer re-measured the matrices (57 of 57 exact,
control 0), the 60 axes and the harness (29 of 29, 30 mutants exact). No finding gives a false green on the
shipped code; each is a clause the axes do not pin, so a later change of the module could break it under
green CI. The specification locked this diff (appendices by sha256, counts of axes and mutants in its
acceptance), so the findings went to the board as bugs instead of extending the diff:

- Not pinned by an axis (bug `0352b657`): the bare JS value of a BIND or an aggregate in the canonical row
  (HIGH — a mutant dropping it passes all 60 axes; 32 of 138 live corpus entries use BIND); the per-entry
  scope of the stability memory (MEDIUM); the exit code when an entry failed without any divergence; a
  literal's direction; a blank node; the cut taken from the SAME loaded graph and from both the explicit and
  the inferred layer. The statement keeps these clauses: the shipped code satisfies them (read and probed),
  only their lock is missing.
- A graph load failure is typed `execution` on every entry instead of `load` as query --batch types it
  (bug `d4ae38ed`) — not a clause of this statement, a parity gap of the error type.
- Wording fixed here: an UPDATE is refused before the analysis (it was listed under the analyzer's refusal);
  the exit-code clause no longer says "0 otherwise" (an output-stream error fails the call).
