# req(exo): SPARQL BIND extends the group prefix at its position — a later pattern joins with the bound value

## Job Story

When I write `BIND(<value> AS ?p)` before a triple pattern that reads `?p` (a constant predicate chosen by a BIND, or an IRI computed from an earlier pattern), I want that pattern to join with the bound value — exactly as the same predicate written literally does — so that the query returns the matching triples (2), not every triple of the store (147 576), and so that BIND means in Exocortex what it means in any SPARQL 1.1 engine.

## Context

- kitelev/exocortex#4551 (found by the review of RFC `14217015`, finding 30; decision №6 «чинить движок»; queued task P1.5 `c223e6ef`).
- Defect: `PatternTranslator.translateWhere` collected every `bind` of a group and wrapped the join of all the other patterns in `Extend` afterwards — the BIND's position was lost. `--explain` of `{ BIND(P AS ?p) ?s ?p ?o }` was `Extend(?p = P)(BGP[?s ?p ?o])`: the BGP ran with `?p` free (full scan), the Extend overwrote `?p` in every row afterwards.
- SPARQL 1.1 §18.2.2.4 (translation of a group graph pattern): `BIND(expr AS ?v)` gives `G := Extend(G, ?v, expr)` over the patterns that PRECEDE it; the following patterns are joined with that result; the FILTERs of the group are collected and applied to the whole group at the end.
- Same class as the MINUS defect fixed earlier in the same method (bucketing the patterns by type lost their scope in the group).
- The bind join (`QueryExecutor.executeJoin`) substituted the shared variables into the subject and object of the right-hand triples but never into the predicate, so even a correctly placed BIND made the joined pattern scan every triple per left solution.

## Statement (Gherkin)

```gherkin
Scenario: a constant BIND before a pattern restricts that pattern
  Given a store where predicate P occurs in exactly 2 triples among many others
  When "SELECT (COUNT(*) AS ?n) WHERE { BIND(P AS ?p) ?s ?p ?o }" runs
  Then ?n is 2 — the same as for "?s P ?o"

Scenario: a computed BIND between two patterns joins with the later pattern
  Given properties Q1 and Q2 whose labels are "prefix__Local" and whose super-property is S
  When "{ ?q exo:Property_superProperty S . ?q exo:Asset_label ?l .
          BIND(IRI(CONCAT(<ontology base>, REPLACE(STR(?l), '__', '#'))) AS ?p)
          ?s ?p ?o }" runs
  Then only the triples whose predicate is Q1 or Q2 are returned

Scenario: a BIND reads only the variables bound before it
  Given "{ BIND(STR(?x) AS ?y) ?s exo:Asset_label ?x }"
  Then ?y is unbound in every solution (SPARQL 1.1: ?x is not yet bound at the BIND)
  And "{ ?s exo:Asset_label ?x BIND(STR(?x) AS ?y) }" binds ?y in every solution

Scenario: a FILTER stays group-scoped
  Given "{ FILTER(?y = 'a') ?s exo:Asset_label ?x BIND(STR(?x) AS ?y) }"
  Then the FILTER sees ?y — it is applied to the whole group, after the BIND

Scenario: a predicate bound by an earlier operator is looked up, as stored
  When the join substitutes a left solution into the right-hand pattern and the shared variable is that pattern's predicate
  Then the store is asked for the triples of that predicate (an index lookup, not a scan of every triple)
  And the predicate is matched as stored, without sub-property widening (req 8a0ed10b),
      exactly as a predicate bound by an earlier triple of the same BGP
```

## Compatibility (corpus sweep before the change, 2026-10-12)

Positional semantics changes the result of two kinds of BIND only: (F) its output variable is read by a LATER pattern of the group — the defect being fixed; (B) one of its inputs is bound only by a LATER pattern — the hoisting used to compute it, the standard leaves it unbound. Every SPARQL text containing BIND was parsed with the engine's own parser and every BIND classified by its group position:

- three canonical vaults (frontmatter + fenced and inline query texts of 63 967 notes): 159 BINDs in 39 parseable queries — F 0, B 0; 13 texts are prose fragments, read by hand — none is F or B;
- `exocortex-starter-kit` invariants: 5 BINDs, all at the end of the group; engine sources: 1 (`ClassHierarchyResolver`, after its pattern); named-query harness specs in `~/dotfiles/scripts`: 6 specs, they mutate the same queries;
- classifier canaries: the two queries of #4551 → F, `{ BIND(STR(?x) AS ?s) … ?x }` → B.

Decision (by mandate, the founder may revisit): the standard semantics, no compatibility hoisting — there is nothing to protect in the stored corpus, and a hoist for "inputs bound later" would give one query two meanings.

## Non-goals

- Rejecting a BIND that rebinds a variable already in scope (a syntax-level error in SPARQL 1.1) — unchanged.
- `Extend` built for SELECT expressions (`AlgebraTranslator`) — unchanged.
- Property-path predicates are not substituted by the join.
