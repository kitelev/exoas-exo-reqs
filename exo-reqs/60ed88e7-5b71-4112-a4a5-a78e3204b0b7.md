# req(exo): SPARQL BIND extends the group prefix at its position — a later pattern joins with the bound value

## Job Story

When I write `BIND(<value> AS ?p)` before a triple pattern that reads `?p` (a constant predicate chosen by a BIND, or an IRI computed from an earlier pattern), I want that pattern to join with the bound IRI — exactly as the same predicate written literally does — so that the query returns the matching triples (2), not every triple of the store (147 576), and so that BIND means in Exocortex what it means in any SPARQL 1.1 engine.

## Context

- kitelev/exocortex#4551 (found by the review of RFC `14217015`, finding 30; decision №6 «чинить движок»; queued task P1.5 `c223e6ef`).
- Defect: `PatternTranslator.translateWhere` collected every `bind` of a group and wrapped the join of all the other patterns in `Extend` afterwards — the BIND's position was lost. `--explain` of `{ BIND(P AS ?p) ?s ?p ?o }` was `Extend(?p = P)(BGP[?s ?p ?o])`: the BGP ran with `?p` free (full scan), the Extend overwrote `?p` in every row afterwards.
- SPARQL 1.1 §18.2.2.4 (translation of a group graph pattern): `BIND(expr AS ?v)` gives `G := Extend(G, ?v, expr)` over the patterns that PRECEDE it; the following patterns are joined with that result; the FILTERs of the group are collected and applied to the whole group at the end.
- Same class as the MINUS defect fixed earlier in the same method (bucketing the patterns by type lost their scope in the group).
- The bind join (`QueryExecutor.executeJoin`) substituted the shared variables into the subject and object of the right-hand triples but never into the predicate, so even a correctly placed BIND made the joined pattern scan every triple per left solution.

## Statement (Gherkin)

```gherkin
Scenario: a constant BIND before a pattern restricts that pattern
  Given a store where predicate P occurs in exactly 2 triples among many others
  When "SELECT (COUNT(*) AS ?n) WHERE { BIND(P AS ?p) ?s ?p ?o }" runs
  Then ?n is 2 — the same as for "?s P ?o"

Scenario: a computed BIND between two patterns joins with the later pattern
  Given properties Q1 and Q2 whose labels are "prefix__Local" and whose super-property is S
  # a "prefix__Local" label is emitted as the predicate IRI itself, so STR(?l) is that IRI
  When "{ ?q exo:Property_superProperty S . ?q exo:Asset_label ?l .
          BIND(IRI(STR(?l)) AS ?p)
          ?s ?p ?o }" runs
  Then only the triples whose predicate is Q1 or Q2 are returned
  And IRI()/URI() build an IRI from a string, so BIND(IRI(CONCAT(…)) AS ?p) restricts the later pattern too
  # The issue's literal form REPLACE(STR(?l), "__", "#") over such a label builds a non-existent IRI:
  # after the fix it returns 0 rows (it scanned every triple before) — use IRI(STR(?l)).

Scenario: a BIND reads only the variables bound before it
  Given "{ BIND(STR(?x) AS ?y) ?s exo:Asset_label ?x }"
  Then ?y is unbound in every solution (SPARQL 1.1: ?x is not yet bound at the BIND)
  And "{ ?s exo:Asset_label ?x BIND(STR(?x) AS ?y) }" binds ?y in every solution

Scenario: a BIND in the middle of a group keeps a group FILTER on a shared variable working
  Given "{ ?s exo:Asset_label ?l BIND(STR(?l) AS ?y) ?s ?p ?o FILTER(<f>) }"
  And <f> compares a shared variable with a constant (?s = <iri>, CONTAINS(STR(?s), …), ?s != <iri>)
      or reads a shared AND a right-only variable (?s != ?o, STR(?s) != STR(?o), isIRI(?s) && BOUND(?o))
  Then it returns the same rows as the group without the BIND
  # round 2: a FILTER is pushed into the right operand of a join only when NONE of its
  # variables is bound on the left — a bind join substitutes into the filter expression;
  # round 3: "its variables" are the ones read ANYWHERE in the expression (arithmetic,
  # function calls, IN), and a FILTER with EXISTS is never pushed
  # review of PR #4557: without the Extend branch in the optimizer's variable collection the FILTER
  # was pushed into the right operand alone and every row was dropped

Scenario: a BIND does not capture a variable a subquery does not project
  Given "{ BIND(P AS ?p) { SELECT ?s WHERE { ?s ?p ?o } } }"
  Then the subquery's ?p is its own variable — every triple is counted
  And when the subquery projects ?p, the bound value restricts it
  And in a JOIN a LIMIT/OFFSET subquery takes no outer value — it is evaluated on its own, then joined,
      and it runs once, not once per left solution

Scenario: EXISTS and LATERAL over a LIMIT subquery stay correlated
  Given "{ ?x a C FILTER EXISTS { SELECT ?x WHERE { ?x V ?o } LIMIT 1 } }"
  Then the outer solution is substituted before the slice (SPARQL 1.1 §18.6) — every ?x with a V is kept,
      NOT EXISTS keeps the others, and IF(EXISTS …) is evaluated per row
  And a LATERAL over a nested LIMIT subquery returns the top-N of each outer row

Scenario: a FILTER reading a BIND variable anywhere in its expression is not pushed away from it
  Given "{ BIND(48 AS ?window) ?s exo:Asset_uid ?t FILTER(STRLEN(?t) <= <e>) }"
  And <e> reads ?window inside arithmetic (?window * 1), a cast (xsd:integer(?window)) or IN
  Then it returns the same rows as FILTER(STRLEN(?t) <= ?window)
  And a FILTER with NOT EXISTS after a BIND returns the same rows as with the BIND last

Scenario: a FILTER stays group-scoped
  Given "{ FILTER(?y = 'a') ?s exo:Asset_label ?x BIND(STR(?x) AS ?y) }"
  Then the FILTER sees ?y — it is applied to the whole group, after the BIND

Scenario: a predicate bound by an earlier operator is looked up, as stored
  When the join substitutes a left solution into the right-hand pattern and the shared variable is that pattern's predicate
  Then the store is asked for the triples of that predicate (an index lookup, not a scan of every triple)
  And the predicate is matched as stored, without sub-property widening (req 8a0ed10b),
      exactly as a predicate bound by an earlier triple of the same BGP
```

## Compatibility (corpus sweep before the change, 2026-10-12)

Positional semantics changes the result of two kinds of BIND: (F) its output variable is read by a LATER pattern of the group — the defect being fixed; (B) one of its inputs is bound only by a LATER pattern — the hoisting used to compute it, the standard leaves it unbound. Every SPARQL text containing BIND was parsed with the engine's own parser and every BIND classified by its group position:

- three canonical vaults (frontmatter + fenced and inline query texts of 63 967 notes): 159 BINDs in 39 parseable queries — F 0, B 0; 13 texts are prose fragments, read by hand — none is F or B;
- `exocortex-starter-kit` invariants: 5 BINDs, all at the end of the group; engine sources: 1 (`ClassHierarchyResolver`, after its pattern); named-query harness specs in `~/dotfiles/scripts`: 6 specs, they mutate the same queries;
- classifier canaries: the two queries of #4551 → F, `{ BIND(STR(?x) AS ?s) … ?x }` → B.

Besides BIND, the change alters queries WITHOUT a BIND in three ways (review rounds 2–3): a subquery in a join no longer takes an outer value for a variable it does not project (`?s exo:Asset_label ?x . { SELECT ?s WHERE { ?s ?p ?x } }`); a LIMIT/OFFSET subquery in a JOIN takes no outer value (EXISTS and LATERAL still substitute before the slice — round 3); a LATERAL subquery now correlates on a PREDICATE variable too (the join substitutes it). The first two follow SPARQL 1.1 §18.5 (the operands of a join are evaluated independently); the third extends the existing LATERAL substitution to the predicate position, after the SPARQL 1.2 draft rather than the 1.1 standard. The stored corpus A/B (44 BIND queries) did not measure these.

Decision (by mandate, the founder may revisit): the standard semantics, no compatibility hoisting — there is nothing to protect in the stored corpus, and a hoist for "inputs bound later" would give one query two meanings.

## Non-goals
- A LITERAL or numeric value bound by BIND (`BIND("x" AS ?l) ?s exo:Asset_label ?l`, `BIND(3 AS ?n) ?s :score ?n`) still does not join with a later pattern: BIND puts a JS primitive, not an RDF term, into the solution (the root of the open bug `37c80e59`). Before this change such a query returned every row with the value overwritten; after it, 0 rows (an OPTIONAL after such a BIND keeps the row with the optional variables unbound). Only an IRI-valued BIND joins (a constant IRI, IRI()/URI(), or a variable already holding an IRI).
- A bound IRI substituted into a FILTER expression is an unsupported expression node, and the row is silently dropped — bug `4e3ce943`, older than this change. This change does not open a new route into it: the optimizer pushes a FILTER into the right operand of a join only when none of the variables it reads — anywhere in the expression (round 3) — is bound on the left, and never pushes a FILTER with EXISTS; this also closes the old no-BIND form `?s exo:Asset_label ?l . FILTER(?s != ?o) ?s ?p ?o`. The old forms with a subquery or VALUES on the left of a shared filter, and an OPTIONAL one, are unchanged.
- The UUID-index filter rewrite (`optimizeAsync` / `optimizeWithSubjects`, no production callers) still loses the constraint in a group WITHOUT a BIND when the filtered variable is also bound by an operand the injection does not enter (a subquery, a UNION) — older than this change; a group WITH a BIND takes the VALUES join (round 3).
- Rejecting a BIND that rebinds a variable already in scope (a syntax-level error in SPARQL 1.1) — unchanged.
- `Extend` built for SELECT expressions (`AlgebraTranslator`) — unchanged.
- Property-path predicates are not substituted by the join.
