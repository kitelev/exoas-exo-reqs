# req(exo): loadFromVaultFS resolves a pure-UID domain/range wikilink through a uid → symbolic-label index collected in the SAME single scanDir pass

## Job Story

When I run `exocortex-cli create` against a vault whose property definitions are written in the post-RFC-004 canonical form (`exo__Property_domain: "[[ae56ca4c-…]]"`, a bare UID with no alias), I want the SHACL-lite shape of those definitions to be loaded, so that the cardinality-aware property emission shipped in #3179 actually engages on the properties whose domains are written canonically — instead of silently falling back to the scalar default because the shape was dropped.

## Context — the defect, measured

`ShapeLoader.registerCandidate` resolves each `exo__Property_domain` value through `wikilinkToIRI`. For a bare-UID ref the chain is: `labelToIRI` → `Namespace.fromPropertyKey(<uid>)` → null (a UUID is not `<prefix>__<Local>`), then `datatypeRangeToIRI` → null (not `http(s)`/`xsd:`), then the `sh:` prefix → no match. The value resolves to null, `domain` ends up empty, and `if (domain.length === 0) return;` drops the whole definition — with no message.

Measured on `origin/main` 5f14cc2f (2026-09-20), by instrumenting the shipped loader itself (`scanDir` + `propertyClassKeysFromEdges` + `wikilinkToIRI`, no re-implementation):

- property definitions typed as a descendant of `exo__Property`: **697 / 492 / 468** `[vault-exodev/my/tbank]`
- of those, definitions whose domain resolves today: **67 / 27 / 33**; **dropped: 630 / 465 / 435**
- registry size: **66 / 26 / 32**
- domain value forms: pure-UID **632 / 465 / 435**, `uid|alias` 63 / 23 / 29, label-form 4 / 4 / 4. The arithmetic closes: resolved = `uid|alias` + label (63+4=67, 23+4=27, 29+4=33) — i.e. **every** pure-UID domain fails.
- cross-checked with a second, independent instrument (SPARQL, `--no-cache`, vault-my): subjects carrying `exo:Property_domain` = **492**, identical to the FS probe's 492.

The graph loader is NOT affected: `loadFromRDFGraph` already canonicalizes a bare-UID domain AND range through `resolveClassIRI` + the `buildUidClassIndex` UID index (issue #3523). So the two loaders disagree exactly on the canonical form, and `validate schema --shapes-mode` (which goes through `loadFromRDFGraph`) shows nothing.

Blast radius: the single `src` consumer of `loadFromVaultFS` is `packages/cli/src/commands/create.ts:604`.

## Design — why the index is collected in the EXISTING pass

`loadFromVaultFS` already walks the whole tree once (`scanDir` → `collectFile` reads every `.md`'s frontmatter). The uid → label index is therefore collected **in that same pass**; the number of files read is unchanged (I/O delta = 0 files), and the only cost is a Map of ~1688 / 1120 / 1088 entries.

This is deliberately NOT the approach rejected in **PR #3138** (branch `fix/shapeloader-uid-range`, commit cc893f67, closed by Andrey 2026-05-17): that one added a literal *second* walk — "two-pass scan in `loadFromVaultFS`: Pass 1 — `buildUidLabelMap`: walks vault" — and was refused as "Pass 1 (double vault scan) approach is too invasive: breaks performance-tests + cascades to e2e + test-bdd via timing". What #3138 rejected is the **second traversal**, not UID resolution as such. The replacement named in that closure ("Will reimplement using `loadFromRDFGraph` in validate-schema.ts") has since been implemented — `validate-schema.ts:962` runs on the graph — which leaves exactly one consumer of the FS loader, `create.ts`, and `create` has no triple store on its path at all (zero occurrences of `tripleStore` / `NoteToRDFConverter` / `VaultRDFIndexer` in that file; the CacheManager there is lazily imported precisely so the default `create` path does not pay a graph load).

## Scenarios

```gherkin
Feature: pure-UID domain/range resolution in the filesystem shape loader

  Background:
    Given a vault scanned by ShapeLoader.loadFromVaultFS
    And a class file named "<uid>.md" whose exo__Asset_label is a single token of the form <prefix>__<Local>

  Scenario: a definition whose domain is a bare-UID wikilink registers its shape
    Given a property definition whose exo__Property_domain is "[[<uid>]]"
    And that <uid> is the class file's exo__Asset_uid
    When the registry is loaded
    Then the definition is registered
    And its domain is the canonical ontology IRI of that class label
    And its range, cardinality and minCount are the ones its frontmatter declares

  Scenario: the UID half is used when the alias half does not parse
    Given a property definition whose exo__Property_domain is "[[<uid>|Some Human Label]]"
    When the registry is loaded
    Then the domain resolves through the <uid> half

  Scenario: registration waits for the index to be complete
    Given the class file is visited AFTER the definition in scan order
    When the registry is loaded
    Then the definition is still registered
    # this is what makes the single-pass design correct: candidates are registered
    # after the pass, never during it

  Scenario: range resolves through the same fallback, so the loaders agree
    Given a property definition whose exo__Property_range is "[[<uid>]]" of a class file
    When the registry is loaded
    Then shape.range is the canonical ontology IRI of that class label
    And loadFromRDFGraph over the SAME files yields a deep-equal shape for both domain and range

  Scenario: nothing that resolves today changes
    Given a domain written in label form "[[ems__Task]]", or as "xsd:integer", or as a full http IRI
    When the registry is loaded
    Then it resolves exactly as before
    # the index is consulted only AFTER every pre-existing branch has failed

  Scenario: an unresolvable UID stays unresolved
    Given a domain "[[<uid>]]" whose target has a multi-word label such as "concept__Definition (DEPRECATED)"
    Or whose <uid> names no file in the vault
    When the registry is loaded
    Then that domain value is not resolved
    # multi-word labels are excluded by the SAME filter buildUidClassIndex uses on the
    # graph side — parity, not a gap
```

## Non-goals

- The `loadFromRDFGraph` semantics are not touched; parity is proved by an axis over the same files, not by rewriting both loaders.
- The data the newly-loaded shapes expose (any SHACL findings, any property whose declared cardinality or range turns out to be wrong) is a data question, not this requirement's — `validate schema --shapes-mode` runs through the graph loader and is unaffected by this change.
- A quoted `exo__Property_minCount: "1"` is still parsed verbatim by the FS frontmatter parser (pre-existing, unchanged here).
- Property definitions whose class-file chain is absent from the scanned tree stay unknown by design.
