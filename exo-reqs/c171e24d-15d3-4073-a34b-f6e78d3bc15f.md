A parked AssetSpace is **on the device but not active**: `apply-profile` moves its bytes to `.exocortex/parked/<owner>/<repo>` (req `d4ccc901`). That destination is a dot-folder, so Obsidian never indexes it — `getMarkdownFiles()` does not list it and `metadataCache.getFirstLinkpathDest` cannot resolve into it. Consequently every wikilink pointing at a parked asset falls through `BodyLinkPatch.ts` / `PropertiesLinkPatch.ts` at their `if (!file) return` seam and Obsidian renders its native unresolved form: **a raw UID, dimmed, no preview**. The cost of the missing placeholder is therefore not cosmetic — it is an unreadable string inside running prose.

This requirement supplies the honest render: the link either resolves, or it says *"I am on this device, just not active"*. It works identically for a frontmatter link and a prose link, which is what makes it the answer to "there should be no broken links at all" — reification cannot fix prose by construction (it would have to delete the link from the readable text; of the 5158 boundary-crossing edges measured on this device, 1030 are prose).

**Why the asset's own label and not the AssetSpace's name.** A link is an identity reference: the reader wants to know WHAT was linked. A placeholder reading `⏸ Concepts` answers "where it lives" and destroys the sentence the moment a paragraph carries two such links (`… helps ⏸ Concepts through ⏸ Concepts in ⏸ Concepts`). The measured distribution supports the same choice from the other side: 622 of 1240 efforts are affected, median **1** link, mean 1.6 — so the typical case is one link in a paragraph, and the label keeps that paragraph meaningful while costing only the click-through.

**⛔ Why the AssetSpace name must NOT be a tooltip.** A touch device generates no hover. Putting the name in `title`/`aria-label` would make it unreachable exactly on the iPhone that parking exists for. The one channel a phone has is the **tap**, so the name travels with the activate action.

**Why the miss carries as much weight as the hit.** If the lookup answered "parked" for anything it could not find, the placeholder would swallow genuinely broken links and "no broken links" would be satisfied by pretending. The lookup is therefore positive-evidence-only: it reports a hit ONLY for a basename actually present under the parked root.

**Why the check reads the adapter.** The asymmetry between `getMarkdownFiles()` (index, blind to dot-folders) and `vault.adapter` (plain filesystem port) is the entire mechanism, not an implementation detail. The plugin already depends on that asymmetry in production: `OperationsLogReader` reads `.exocortex/switch-journal.jsonl` through the adapter to power the Settings journal panel.

## Job Story
When I open a note that links to something I parked, I want the link to name the thing it points at and offer to bring it back, so that taking an AssetSpace off this device never turns my own notes into rows of raw UUIDs.

```gherkin
Feature: a link into a parked AssetSpace renders as a placeholder

  Background:
    Given an AssetSpace was parked, so its files live under .exocortex/parked/<owner>/<repo>
    And Obsidian does not index that dot-folder

  Scenario: the placeholder carries the linked asset's own label
    Given a note links to a parked asset whose exo__Asset_label is "МОЧИ"
    When the link is rendered
    Then the link text is the asset's label followed by a pause glyph
    And the parked AssetSpace holding it is recorded on the element for the action
    And the AssetSpace name appears in NEITHER the link text NOR any tooltip

  Scenario: the tap opens activation instead of Obsidian's create-missing-note
    Given a rendered placeholder
    When it is tapped
    Then the default create-missing-note behaviour is prevented
    And the activate action receives the parked hit, so it can name the AssetSpace

  Scenario: NEGATIVE CONTROL — a link to an asset that exists nowhere stays broken
    Given a note links to a UID that is present neither in the vault nor under the parked root
    When the link is rendered
    Then the link is left exactly as Obsidian rendered it
    And no placeholder text, class or AssetSpace attribute is added

  Scenario: NEGATIVE CONTROL — a failed lookup is not evidence of parking
    Given the adapter read fails
    When the link is rendered
    Then the link is left exactly as Obsidian rendered it

  Scenario: both render channels
    Given one note carries a parked link in its frontmatter and another in its body prose
    When each is rendered
    Then both show the placeholder
    And removing the placeholder call from either channel leaves the OTHER channel still working

  Scenario: the check reads the dot-folder through the adapter
    Given the parked asset is invisible to getMarkdownFiles and to metadataCache
    When the parked lookup runs
    Then it still finds the asset
    And it skips a nested dot-folder such as the parked repo's own .git

  Scenario: an asset brought back by apply-profile stops reading as parked
    Given a parked asset that currently renders as a placeholder
    When an apply flow finishes and the parked directory index is invalidated
    Then the next lookup no longer reports it as parked
```

## Notes

- **Activation reuses the ONE existing path.** The action opens the existing `Apply profile` flow (`ProfileCommands.invokeApplyProfile`), which owns the transition table (req `d4ccc901`), the TS-floor assertion and the crash-recovery journal. No private unpark logic is introduced — the placeholder never moves a byte itself.
- **Cost.** One directory walk of `.exocortex/parked` per index lifetime, shared by every unresolved link on the page, plus exactly **one** file read per hit (the asset's own frontmatter, for its label). The walk skips nested dot-folders, so a parked repo's `.git` is never traversed. The index is invalidated only after an apply flow — the one thing that parks or unparks a mount — so it is never rebuilt from a `metadataCache` event, the documented cause of an indexing storm and iPhone Jetsam.
- **Unwired is byte-identical.** The placeholder reaches the patches through an OPTIONAL plugin field; absent, both channels behave exactly as before, which is what makes the zero-regression claim structural rather than argued.
- **Label reading is deliberately not a YAML parse.** The label is read from the single-line scalar form that `exocortex-cli create` and `apply set-label` both write; an unreadable or multi-line value degrades to `null` and the caller falls back to the file's basename. A parked asset is read only to be NAMED, so no write-capable frontmatter machinery is reachable from this path.
- **Binding class.** `unit`: the core lookup is bound by its own suite (positive, both negative controls, dot-folder skip, invalidate, single-walk), and the two render channels are bound through their REAL entry points (`BodyLinkPatch.enable()` / `PropertiesLinkPatch.enable()`) over a jsdom DOM — so the wiring being present in the production path is locked independently of the placeholder doing its job.
