# req(exo): a YAML number enters the graph with ONE tag whichever path it takes — whole → xsd:integer, fractional → xsd:decimal on both the frontmatter and the JSON-LD path; the validator judges the xsd:integer tag by the lexical table; the triple-cache format is bumped

## Job Story

When I write `ems__Task_weight: 3` in a note and the same asset also arrives as a JSON-LD document with `"…Task_weight": 3`, I want both to become the same literal (`"3"^^xsd:integer`) so that `datatype(?o)`, `sameTerm` and every consumer that keys on the tag see ONE number, not a converter artefact (`"3"^^xsd:decimal`) next to a parser fact (`"3"^^xsd:integer`) — and I want `validate schema --shapes-mode` to keep judging that number by its lexical form under an integer-family / decimal / float / double / gYear range, exactly as it did for the decimal tag (req b0ad1160), so that the tag change produces no new violation on the live vaults.

Sibling of req `b0ad1160` (ticket a9b55ead / PR #4266), whose Non-goals read: «the converter's `xsd:decimal` emission itself (converter ↔ RDFSerializer asymmetry)». Ticket `d5ad5217` (follow-up (iii) of a9b55ead) put the three candidates to the founder; decision 2026-09-19 (verbatim): «Паритет: целое → xsd:integer, дробное → xsd:decimal в обоих путях (Recommended)».

## Statement (Gherkin)

```gherkin
Feature: one tag for one number on both graph entry paths

  Scenario: a whole YAML number is tagged xsd:integer and matches the JSON-LD parser
    Given a note whose frontmatter carries `ems__Task_weight: 3` (a YAML number)
    When NoteToRDFConverter converts the note
    Then the object literal is "3"^^xsd:integer
    And RDFSerializer.parse of a JSON-LD document with the native number 3 for the same predicate yields a literal with the SAME datatype
    And 0, -7, 166774905 and 1e3 are tagged xsd:integer on both paths

  Scenario: a fractional number keeps xsd:decimal on both paths (the branch the change must not touch)
    Given `ems__Task_weight: 3.5`
    Then the converter emits "3.5"^^xsd:decimal
    And the JSON-LD parser emits the same datatype for the native number 3.5
    And 0.5 and -0.25 are tagged xsd:decimal on both paths

  Scenario: a quoted number is not a number
    Given `ems__Task_weight: "3"`
    Then the converter emits a plain string literal "3" (no numeric tag)

  Scenario: the validator judges the xsd:integer tag by the lexical table
    Given a property definition with range xsd:gYear and an asset carrying `pmi__Model_originYear: 1987`
    When validate schema --shapes-mode runs over the converter's triples ("1987"^^xsd:integer)
    Then there is NO sh:datatype violation (three-digit 987 IS a violation)
    And "20"^^xsd:integer under range xsd:decimal conforms (integer ⊂ decimal — the b5a670e8 case)
    And "7"^^xsd:integer conforms under xsd:long / int / short / byte / float / double, "0" under nonNegativeInteger, "7" under positiveInteger, "-3" under negativeInteger and nonPositiveInteger
    And "-1" under nonNegativeInteger / unsigned*, "0" under positiveInteger and "3" under negativeInteger / nonPositiveInteger ARE violations
    And "7"^^xsd:integer under range xsd:string and under xsd:anyURI ARE violations (strict outside the table)
    And the xsd:decimal tag keeps its own judgement: "7.5"^^xsd:decimal under xsd:integer still violates, "7"^^xsd:decimal still conforms

  Scenario: the production pipeline (validate schema --shapes-mode / create --validate / plugin on-save) is unchanged in outcome
    Given the shacl-integration fixture vault with a def ems__Task_hours (range xsd:decimal) and an asset ems__Task_hours: 20, ems__Task_weight: 7
    When runShapesValidation runs over NoteToRDFConverter triples
    Then the asset has no violation, asset-d (10 under xsd:integer, 1987 under xsd:gYear) still has none
    And the golden report is byte-identical (10.5 and 3.5 are still reported as xsd:decimal; no whole number is reported)

  Scenario: a warm pre-parity triple cache is rebuilt, not served
    Given a vault cached by CacheManager under formatVersion 2 with "3"^^xsd:decimal for an unchanged file
    When loadOrBuild (or loadVaultTriples with useCache) runs with the current CLI
    Then isCacheValid is false, the mode is "rebuild", the caller receives "3"^^xsd:integer and the rewritten cache carries formatVersion 3
```

## Non-goals (measured 2026-09-19, ticket d5ad5217 plan-gate on aaadac12)

- The 26/6 [vault-my / vault-tbank] `bot__Reminder_chatId` number-under-`xsd:string` violations (ticket d72aba19) — pre-existing; only the tag named in their message changes (decimal → integer).
- Which YAML scalars are numbers (js-yaml typing), YAML dates (`Date` → xsd:dateTime), booleans — untouched.
- The plugin's index: it has no persisted triple cache (0 hits for formatVersion|CACHE_VERSION|schemaVersion in packages/obsidian-plugin/src), so desktop/mobile re-convert on load and get the new tag with no migration.
- The CLI query-result cache (`~/.exocortex/cache/query-results`, TTL 300 s + vault-signature invalidation): a cached row may name the old tag for at most one TTL after the upgrade — no bump needed.
- Vault data: `b5a670e8` (`pmbok__ChangeRequest_*` whole numbers under range xsd:decimal) and `pmi__Model_originYear` (range xsd:gYear) are NOT edited — they conform under the integer tag through the lexical table, as measured (0/0/0 delta).
