# req(exo): registerCandidate strips the surrounding quotes from `exo__Asset_label`

## Job Story

When I run `exocortex-cli create` against a vault where some property definitions
write `exo__Asset_label` as a **quoted** YAML scalar (`exo__Asset_label: "ems__Effort_lockedBy"`),
I want those definitions to load their SHACL-lite shape like every other definition,
so that the cardinality-aware property emission shipped in #3179 engages on them too —
instead of silently falling back to the scalar default because the shape was never
registered.

## Context — the defect, measured

`ShapeLoader.parseFrontmatter` is a deliberately naive YAML reader: it keeps a value
**verbatim**, quotes included. Every other consumer in the file therefore strips the
surrounding quotes itself — the identical predicate `replace(/^["']|["']$/g, "")`
appears **five** times: `collectFile` twice (the class-edge child keys, `:612` / `:616`),
`indexUidLabel` twice (`:655` / `:663`) and `extractWikilinkRef` once (`:829`).

`registerCandidate` does not:

```ts
const labelRaw = fm["exo__Asset_label"];
if (typeof labelRaw === "string" && labelRaw.trim().length > 0) {
  label = labelRaw.trim();          // quotes are NOT stripped
}
```

so for a quoted scalar the label comes out as `"ems__Effort_lockedBy"` (quotes included),
`labelToIRI` → `Namespace.fromPropertyKey` returns `null` (a leading `"` is not
`<prefix>__<Local>`), and the function returns at `if (!propertyIRI) return;` — **before**
the domain is parsed at all. The definition is dropped with no message.

Reproduced by fixture on `origin/main` `2fdabf1c` (2026-09-20), three definitions in one
temp vault, identical except for the label form:

| `exo__Asset_label` | shape registered |
|---|---|
| `flow__Stage_plain` (bare) | **yes**, domain `[ems#Task]` |
| `"flow__Stage_quoted"` (double) | **no** |
| `'flow__Stage_single'` (single) | **no** |

The bare case is the probe's own canary: if it did not register, the fixture — not the
defect — would explain the zero.

Radius, measured by a raw frontmatter scan (SPARQL is blind here by construction: the
engine normalises quotes away, so the RAW YAML form cannot be expressed as a graph query;
the scan mirrors `ShapeLoader.parseFrontmatter` so it counts what the loader itself sees):

- property definitions carrying a non-empty `exo__Property_domain` whose `exo__Asset_label`
  is a quoted scalar that WOULD parse as `<prefix>__<Local>` without the quotes:
  **15 / 15 / 15** `[vault-exodev/my/tbank]` — the same 15 names in all three vaults,
  because they live in shared assetspaces:
  `ems__Effort_lockExpires`, `ems__Effort_lockedBy`, `ems__QuarterlyObjective_quarter`,
  `ems__YearlyObjective_year`, `exo__Event_timestamp`,
  `exo__FunctionSignature_inputArguments`, `exo__FunctionSignature_outputType`,
  `exocmd__Command_paletteEnabled`, `exocmd__Command_paletteId`,
  `exocmd__Grounding_linkBackProperty`, `find__Alias_sparql`, `inbox__Capability_system`,
  `kf__InterdisciplinaryField_discipline`, `lit__Content_source`, `vault__Folder_vault`.
- a WIDER predicate — any file with a quoted symbolic label, with or without a domain —
  gives **29 / 20 / 20**. That number measures a different subject (enums, classes and
  prototypes carry no `exo__Property_domain`, so they never reach `ShapeRegistry` under
  any state of this defect) and is recorded here only so a later reader who counts FILES
  rather than DEFINITIONS knows why their number is larger.

The graph loader is **not** affected: Obsidian's YAML parser strips the quotes before the
frontmatter ever reaches `NoteToRDFConverter`, so `loadFromRDFGraph` has always seen
`ems__Effort_lockedBy`. The defect is therefore one-sided, and this requirement RESTORES
loader parity rather than introducing a divergence.

## Scenarios

```gherkin
Feature: a property definition whose label is a quoted scalar registers its shape

  Background:
    Given a vault scanned by ShapeLoader.loadFromVaultFS
    And a property definition typed as a descendant of exo__Property
    And its exo__Property_domain resolves to a class IRI

  Scenario: double-quoted label
    Given its exo__Asset_label is written as "flow__Stage_order"
    When the vault is loaded
    Then the registry contains a shape whose propertyIRI is
         https://exocortex.my/ontology/flow#Stage_order
    And that shape carries the same domain, range and cardinality it would carry
        had the label been written bare

  Scenario: single-quoted label
    Given its exo__Asset_label is written as 'flow__Stage_order'
    When the vault is loaded
    Then the shape registers identically — the stripped character class covers
         BOTH the double quote and the apostrophe

  Scenario: an unquoted label is unchanged
    Given its exo__Asset_label is written bare as flow__Stage_order
    When the vault is loaded
    Then the shape is byte-identical to what the previous implementation produced

  Scenario: the filename fallback is untouched
    Given the definition carries no exo__Asset_label at all
    And its filename stem is flow__Stage_order
    When the vault is loaded
    Then the shape still registers through the basename branch — a filename cannot
         carry surrounding quotes, so that branch is deliberately left alone

  Scenario: stripping quotes does not widen admission
    Given its exo__Asset_label is written as "Some Human Label"
    When the vault is loaded
    Then no shape is registered — removing the quotes leaves a multi-word label,
         which Namespace.fromPropertyKey rejects exactly as the graph side does

  Scenario: loader parity
    Given the same files are loaded through loadFromRDFGraph and through loadFromVaultFS
    And the definition's label is a quoted scalar
    Then both loaders yield a deep-equal shape
```

## Design — the predicate is copied, not re-derived

The fix applies the predicate that the file already uses, copied verbatim from `:655`:

```ts
label = labelRaw.trim().replace(/^["']|["']$/g, "");
```

Two literal character classes (`["']` at each anchored end), the alternation `|` OUTSIDE
the class between the two anchored halves, and the `g` flag — each of the four is
behaviour-bearing and each carries a mutant.

**A shared `stripQuotes` helper is deliberately NOT extracted.** All five existing
call sites already carry an identical form (read verbatim, 2026-09-20), so consolidating
them would surface no divergence; it would only widen this change's radius to five
foreign call sites and make the behavioural delta unverifiable name-by-name — exactly the
reason ticket `32d44596` gave for not fixing the quoted label inside PR #4293. Extracting
the helper would also make the contract of those five sites this requirement's
responsibility (the mirror obligation in `multi-parser-predicate-migration`).

## Not governed

- `exo__Property_minCount: "1"` — `parseInt` still reads the raw value, so a quoted
  count yields `NaN`. Pre-existing, already acknowledged in the repo's own test comment
  ("the FS parser keeps a quoted \"1\" verbatim — separate gap"); a separate ticket.
- `loadFromRDFGraph` semantics — untouched; parity is proved by an axis over the same
  files, not by editing both loaders.
- `validate schema --shapes-mode` — unaffected, because that path runs on
  `loadFromRDFGraph` (`validate-schema.ts:962` on `2fdabf1c`, the only `ShapeLoader.*`
  call in that file). Two traces that could suggest otherwise were resolved by quoting
  them, not by summarising:
  - `docs/explanation/CROSS_RUNTIME_PARITY.md` — on `2fdabf1c` the "Shape loading" cell
    reads `ShapeLoader.loadFromRDFGraph` in **both** rows (CLI row `:11`, Plugin row `:12`,
    quoted cell-by-cell). The doc DID drift earlier — it named `loadFromVaultFS` for the
    CLI row — and that drift was closed by the predecessor in PR #4293 (`efc88f84`,
    `git log -S` on the cell). Nothing left to fix here. A third mention at `:36` belongs
    to a different table (§Known Differences) that contrasts the two LOADERS as mechanisms
    and does not assign either to `--shapes-mode`.
  - the `loadFromVaultFS` mock in `packages/cli/tests/unit/commands/validate-schema.test.ts:16`
    is legacy from PR #3057 and inert — the only `--shapes-mode` reference in that file
    asserts option registration, and the mock does not even expose `loadFromRDFGraph`,
    which the production path calls.
- A definition whose domain names a multi-word class label stays unresolved — the same
  admission filter the graph side applies, i.e. parity, not a gap.
