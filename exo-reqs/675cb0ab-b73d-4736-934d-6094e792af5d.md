# req(exo): the plugin / apply write path types a scalar by the declared range

## Job Story

When I create an asset by pressing a button in Obsidian — or by running the same
homoiconic command through `cli apply` — I want a scalar to land in the frontmatter
with the YAML type the property's **declared** `exo__Property_range` calls for, exactly
as `cli create` has landed it since ticket `2227d660`. Today the two paths disagree: a
negative chat id written from the button becomes `"-1003912427125"` (an `xsd:string`
literal under an `xsd:integer` range — a `sh:datatype` violation by founder rule 6c),
while the same property written by `cli create` lands bare. One property then carries
two types depending on which surface touched it last, which is the CLI/UI parity debt
#3417 in its plainest form.

## Statement (Gherkin)

```gherkin
# --- the create_instance path (FrontmatterService.createFrontmatter) ---

Given a mounted property definition with exo__Property_range: xsd:integer
  And a create_instance grounding that writes that property the value -1003912427125
When the grounding is executed with the declared-range port wired
Then the created frontmatter carries the value BARE
  And a YAML parse yields the number -1003912427125

Given a mounted property definition with exo__Property_range: xsd:string
  And a create_instance grounding that writes that property the value 42
When the grounding is executed with the declared-range port wired
Then the created frontmatter carries the value QUOTED
  And a YAML parse yields the string "42"

Given a property for which NO definition declares a range
When the same grounding is executed with the port wired
Then the created frontmatter is BYTE-IDENTICAL to the output without the port
# This is the control: it must stay green under every mutant of this change.

Given the declared-range port is NOT supplied (tests, headless runners, any
  caller that has no triple store)
When a create_instance grounding is executed
Then the created frontmatter is BYTE-IDENTICAL to the pre-change output
# Fail-open by construction: absence of a TBox source never fails a create.

# --- the key derivation (the 78-per-cent hole) ---

Given a mounted property definition in a namespace ABSENT from
  FrontmatterService.IRI_PREFIX_MAP (flow, pmi, person, team, bot, exodev)
  And its exo__Property_range is xsd:integer
When a grounding addresses that property by its full symbolic IRI
Then the range IS resolved and the scalar is typed by it
# An axis written on ems or exo would be GREEN under BOTH derivations
# (normalizeIRI and fromTermIRI) and is therefore vacuous against this defect:
# the fixture MUST use an out-of-map namespace. The paired mutant swaps the
# derivation back to normalizeIRI and must redden THIS axis while leaving the
# in-map (ems) axis green — addressability shown, not asserted.

# --- the property_set path (GroundingExecutor.executePropertySet) ---

Given a mounted property definition with a typing range
  And a property_set grounding that writes a canonical scalar to it
When the grounding is executed with the port wired
Then the value is typed by the declaration
# SYNTHETIC BY NECESSITY: 0 of the 48 live groundings target a ranged
# property, so this scenario cannot be exercised on live data today.

Given a property_set grounding whose target property has NO declared range
  And the value is a deliberate YAML flow array ["[[ems__Task]]"]
  Or a pre-quoted wikilink "[[<uid>]]"
When the grounding is executed with the port wired
Then the value is written VERBATIM, exactly as before this change
# The gate scalarTypingForRange(range) !== undefined is what makes this true;
# its own mutant must redden THIS scenario and not the typing ones.
```

## Verification

- core unit — `FrontmatterService` threading (scalar and array items, an unmapped
  key, the supplied-key map) and `GroundingExecutor` port plumbing.
- core integration — `create_instance` end to end through a real grounding on a
  UID-canon TBox fixture: negative integer bare, number under `xsd:string` quoted,
  rangeless property byte-identical, port absent byte-identical, out-of-map
  namespace resolved.
- core integration — `executePropertySet`: typed with a range, verbatim without
  one (flow array and pre-quoted wikilink).
- revert-verify — one mutant per guard of the diff, enumerated from
  `git diff -U0` (integration-test-revert-verify §A8), including a mutant on the
  `scalarTypingForRange(range) !== undefined` gate and the paired
  `normalizeIRI`-instead-of-`iriToObsidianName` mutant described above.
- neighbour specs run on this tree (§A96) — the nine `.spec.json` whose subject is
  one of this diff's files or their direct collaborators, with the flip shown by
  BOTH halves (my axes stop reddening under their mutants; their own axes still
  redden under them).
- `validate schema --shapes-mode` on a vault copy, delta against a baseline taken
  before the change.
