# req(exo): CLI can relabel an asset while KEEPING the previous label as an alias (set-label-keep-alias)

**Job story.** When I rename an asset whose old name is a legitimate synonym (a concept, a person, a project renamed but still searched for under its old name), I want an explicit opt-in relabel that keeps the previous label in `aliases`, so the old name stays findable — while the default `set-label` keeps replacing the mirror (req `f7790000-3779-4bbb-8bbb-000000000002`, unchanged).

**Origin.** Ticket `eb603ba7`; founder decision 2026-09-26 (post-window interview): «opt-in, в НОВОМ соседнем req, дефолт set-label не меняется».

⛔ **Surface differs from the option as worded in the interview, and why.** The option read `set-label --input '{"label":"…","keepAlias":true}'`. The grounding engine has no conditional steps — no `exocmd__Grounding_*` property runs a step only when an input key is set (measured: the property set read by `GroundingExecutor` on origin/main) — so a `keepAlias` input on the SAME composite would need new engine semantics. The same end-state (opt-in, default untouched) is reached by composing existing steps into a SEPARATE command, with zero engine code. The option's cost line did not check the engine; this is the correction.

## Scenarios

```gherkin
Scenario: the previous label is kept as an alias
  Given an asset with exo__Asset_label "Old Label" and aliases ["Old Label"]
  When I run `apply set-label-keep-alias <asset> --input '{"label":"New Label"}'`
  Then exo__Asset_label becomes "New Label"
  And aliases equals ["Old Label", "New Label"] in that order
  And exo__Asset_updatedAt is bumped

Scenario: other aliases are preserved
  Given an asset with exo__Asset_label "Old Label" and aliases ["Old Label", "Some Synonym"]
  When I run `apply set-label-keep-alias <asset> --input '{"label":"New Label"}'`
  Then aliases equals ["Old Label", "Some Synonym", "New Label"]

Scenario: the previous label is added even when it was not mirrored yet
  Given an asset with exo__Asset_label "Old Label" and aliases ["Some Synonym"]
  When I run `apply set-label-keep-alias <asset> --input '{"label":"New Label"}'`
  Then aliases equals ["Some Synonym", "Old Label", "New Label"]

Scenario: relabelling to the same label duplicates nothing
  Given an asset with exo__Asset_label "Same" and aliases ["Same"]
  When I run `apply set-label-keep-alias <asset> --input '{"label":"Same"}'`
  Then aliases equals ["Same"]

Scenario: a label that needs YAML quoting keeps the file parseable
  Given an asset with exo__Asset_label "Old Label" and aliases ["Old Label"]
  When I run `apply set-label-keep-alias <asset> --input '{"label":"Meeting: Q3 \"review\""}'`
  Then the frontmatter parses under a real YAML parser
  And aliases deep-equals ["Old Label", "Meeting: Q3 \"review\""]

Scenario: the default set-label is unchanged
  Given the same asset
  When I run `apply set-label <asset> --input '{"label":"New Label"}'`
  Then aliases equals ["New Label"] (req f7790000-3779-4bbb-8bbb-000000000002 still holds)
```

## Mechanism (vault data only, exoas-exocmd)

New command `set-label-keep-alias` (CLI-only, no class binding — like `set-label`) → new composite grounding with the steps, in order:
1. `a85668fa` — property_append `aliases` = `$target.exo__Asset_label` (the label BEFORE the change; read fresh from disk at the step);
2. `f79e2d7d` — property_set `exo__Asset_label` = `$input.label`;
3. `b36996d5` — property_append `aliases` = `$input.label`;
4. `49e00287` — bump `exo__Asset_updatedAt`.

Deduplication and escaping come from `property_append` (set-based dedup on decoded values; `quoteYamlString`). Step 1 must precede step 2: after the label is overwritten, `$target.exo__Asset_label` would read the NEW label.

## Non-goals

- No `keepAlias` input on `set-label`; no engine conditional steps (a separate engine feature if ever wanted).
- No UI button (mirrors `set-label`, which is CLI-only).
