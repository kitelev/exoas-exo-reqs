A `--no-status` opt-out flag for `exocortex create`, complementing the #3849 default-status injection. A recurring/template prototype (e.g. `ems__TaskPrototype`, `ems__ActionPrototype`) is a template, not a live effort — it should carry no `ems__Effort_status`. Since #3849 auto-injects Backlog for every status-bearing class on create, there was previously no way to opt out except a raw Bash strip of the frontmatter line (bypassing the PreToolUse hook-coverage + SHACL floor). `--no-status` closes that gap declaratively.

## Job Story

When I create a recurring-task prototype via `exocortex create --class ems__TaskPrototype …`, I want to opt out of the auto-injected Backlog status, so the prototype matches its status-less siblings without a manual frontmatter strip.

## Acceptance Criteria (Gherkin)

```gherkin
Scenario: --no-status suppresses the default status on a status-bearing class
  Given a status-bearing class (an ems__Effort subclass, e.g. a *Prototype)
  When I run `create --class <that-class> --no-status`
  Then the written frontmatter has NO ems__Effort_status property

Scenario: without --no-status the #3849 default is unchanged (backward-compat)
  Given a status-bearing class (ems__Task)
  When I run `create --class ems__Task` (no --no-status, no --status)
  Then the written frontmatter has ems__Effort_status = Backlog

Scenario: --no-status conflicts with an explicit status property
  Given a status-bearing class
  When I run `create --class <that-class> --no-status --property ems__Effort_status=[[…]]`
  Then the command fails fail-loud with an ambiguity error and writes nothing
```

Empirical: 2026-07-20, `/weekly-recurring-tasks` created a recurring prototype whose auto-injected `ems__Effort_status: Backlog` had to be Bash-stripped (issue #3928).
