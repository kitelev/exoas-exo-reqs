# req(exo): a reified statement whose class is a SUBCLASS of exo__Statement materializes its logical edge

## Job Story

When I record an author's thesis as an asset whose ONLY class is `exoization__Thesis` (declared `exo__Class_superClass` → `exo__Statement`) with `exo__Statement_subject / _predicate / _object`, I want the indexer to emit the logical edge `<subject> <predicate> <object>` exactly as it does for a plain `exo__Statement`, so that `?a <link> ?b` finds the thesis — without giving the thesis a second class.

## Context

- RFC `14217015` (Approved 2026-10-10), decision №7: «Тезис» (`exoization__Thesis`) ⊂ `exo__Statement`, one class per thesis; the engine learns to expand SUBCLASSES of `exo__Statement` into a triple. AC1c of the RFC.
- Before: `NoteToRDFConverter.convertLegacyNote` materialized the edge (EKA D5) only when one of the asset's classes resolved to EXACTLY `exo#Statement` (`classNode.value === statementClassIRI`). A subclass gave no edge.
- Second consumer of the same predicate: the plugin `VaultRDFIndexer` routed a reified statement to a full refresh (its materialized edge has a non-file subject that the subject-scoped incremental purge cannot evict) by `<file> rdf:type exo#Statement` — a subclass instance is typed by its own class, so its old edge would stay stale after an edit.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: subclasses of exo__Statement expand into a triple at index time

  Background:
    Given a class Thesis whose frontmatter declares exo__Class_superClass -> exo__Statement
    And a link predicate L and two concepts A and B

  Scenario: S1 — a thesis with the single class Thesis gives the edge
    Given an asset T with exo__Instance_class -> Thesis only
    And T carries exo__Statement_subject A, _predicate L, _object B
    When T is indexed by NoteToRDFConverter
    Then the triple <A> <L> <B> is emitted
    And SPARQL "SELECT ?a ?b WHERE { ?a <L> ?b }" over the store returns (A, B)

  Scenario: S2 — a TRANSITIVE subclass gives the edge
    Given SubThesis -> Thesis -> exo__Statement (exo__Class_superClass)
    And an asset with the single class SubThesis and the three statement slots
    Then the edge <A> <L> <B> is emitted

  Scenario: S3 — a class that is NOT a subclass of exo__Statement gives NO edge (negative)
    Given a class Note -> exo__Asset
    And an asset with the single class Note carrying the three statement slots
    Then no triple with predicate L is emitted
    And the raw exo__Statement_subject/_predicate/_object triples are still emitted

  Scenario: S4 — a cycle in the class hierarchy terminates without an edge
    Given CycA -> CycB -> CycA (neither reaches exo__Statement)
    And an asset with the single class CycA carrying the three statement slots
    Then indexing completes and no edge is emitted

  Scenario: S5 — the walk is bounded in depth
    Given an acyclic chain of more than 16 superclass hops before exo__Statement
    Then no edge is emitted and a warning names the asset

  Scenario: S6 — a cold class cache is read through the disk fallback
    Given the adapter's getFrontmatter returns null for the class files
    And getFrontmatterWithFallback returns their frontmatter
    Then the edge <A> <L> <B> is emitted

  Scenario: S7 — exactly exo__Statement keeps its edge in every class-emission mode
    Given an asset whose class is the bare-UID wikilink of the exo__Statement class file
    When the converter emits exo__Instance_class as the class file IRI (emitInstanceClassAsUid on)
    Then the edge <A> <L> <B> is still emitted

  Scenario: S8 — the plugin re-index purges a subclass statement's stale edge
    Given the plugin store holds a Thesis asset with edge <A> <L> <B> and the file's exo:Statement_subject triple
    When the asset is edited to object C and updateFile runs
    Then the old edge <A> <L> <B> is gone and <A> <L> <C> is present
    And an ordinary note edit still takes the incremental path (no full refresh)
```

## Non-goals

- The walk reads `exo__Class_superClass` from CLASS FILE frontmatter only. A class that becomes a subclass of `exo__Statement` only through another reified `exo__Statement` (an adapter bridge) is NOT recognised: the converter is per-file and that bridge may be indexed later. `rdfs__subClassOf` is not walked (no carrier in the vaults).
- Editing a class file's `exo__Class_superClass` does not re-index its instances; the instance gives (or stops giving) the edge on its next index.
- Frontmatter consumers of `exo__Class_superClass` named in RFC §Q3 (`visibility/helpers.ts`, `ClassSubsumption.ts`, `PrintNameRuleService.ts`) are untouched.

## Cost

The walk runs ONLY for an asset that carries all three resolved statement slots AND has no class resolving to exactly `exo#Statement`. Live population (2026-10-11, `query --no-cache`, `?s exo:Statement_subject ?x`): vault-exodev 146 carriers, vault-my 68 — every one typed exactly `exo#Statement`, i.e. the walk runs on 0 of them today.
