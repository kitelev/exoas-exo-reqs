Parking an AssetSpace — moving its mount out of `assetspaces/<owner>/<repo>` and into `.exocortex/parked/<owner>/<repo>` — must be **inert for ExoSync**: the parked AssetSpace must not be enumerated as a sync unit, so its deletion set is never computed and `push` never deletes its files on the remote.

This requirement makes that safety property **executable**. Today it holds implicitly — both collectors gate `commit()` on a platform-specific existence check of the **derived** mount path — but nothing locks it. A refactor that moves the check, widens it to "a copy exists anywhere", or drops it on one of the two call-sites would silently turn parking into a remote-wide deletion, and every other device would receive that deletion on its next pull.

**Why two checks and not one.** Enumeration is two independent functions in two packages, using two different existence primitives — `node:fs existsSync` in the CLI, `app.vault.adapter.exists` in the plugin — around one shared platform-free classification core (`packages/core/src/services/sync/spaceSpecCore.ts`). That core deliberately leaves the existence step to the caller, *between* `offer()` and `commit()`. A green check on one call-site therefore says nothing about the other, and the guard must be locked on each separately.

## Job Story
When I park an AssetSpace to take it off this device, I want ExoSync to behave as if that AssetSpace had never been declared here — not as if its files had been deleted — so that my next `push` cannot wipe it on the remote for every other device.

```gherkin
Feature: parking is invisible to sync-unit enumeration

  Background:
    Given an AssetSpace declaration carrying exo__AssetSpace_source = https://github.com/<owner>/<repo>
    And its mount path is DERIVED by AssetSpacePathDeriver as assetspaces/<owner>/<repo>

  Scenario: CLI — a parked AssetSpace is not enumerated
    Given the derived mount path assetspaces/<owner>/<repo> does not exist in the vault
    But a full copy of that mount sits under .exocortex/parked/<owner>/<repo>
    When collectVaultSpecs walks the vault
    Then no sync-unit spec is produced for that repo
    And therefore no deletion set is ever computed for it

  Scenario: plugin — a parked AssetSpace is not enumerated
    Given the same vault shape read through the Obsidian DataAdapter
    When collectSyncRepoSpecs walks the vault
    Then no sync-unit spec is produced for that repo
    And the parked copy is not reported as mounted-but-undeclared either

  Scenario: negative control — a materialized AssetSpace is still enumerated
    Given the derived mount path assetspaces/<owner>/<repo> DOES exist
    When either collector walks the vault
    Then a sync-unit spec IS produced for that repo
    And its localPath equals the derived path
```

## Notes

- The existence check is the **only** platform-specific step of enumeration. `classifySpaceDeclaration` computes `localPath` via `derivePath(source)` and never reads a stored path, so the fixtures declare only `exo__AssetSpace_source`; a hand-written `localPath` would keep the tests green against a dead deriver.
- The plugin's FINDING-3 "mounted-but-undeclared" reporter (`enumerateMountFolders`) walks only `assetspaces/`, so a parked copy produces no false warning either. That is asserted in the same plugin check.
- `SpaceSpecAccumulator.offer()` registers a `repoKey` as seen even when the caller's existence check later refuses to `commit()` — so a parked AssetSpace cannot be resurrected by a second declaration of the same repo.
- Binding classes: `integration` is carried by the CLI check (a real temp vault on the real node fs, running the real exported collector with no test doubles); `unit` is carried by the plugin check (the production-shape `InMemoryAdapter` stands in for the platform boundary).
- Out of scope: `apply-profile`'s handling of a parked state, `reconcileToLocal`, and the fate of `SwitchCacheLayer` — those belong to the sibling task T3b, which depends on this guard as a proven property.
