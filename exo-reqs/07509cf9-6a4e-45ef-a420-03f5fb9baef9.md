## Зачем

Резолвер объявленных свойств класса сегодня в движке есть ровно один — `createTripleStoreRequiredPropertyResolver`, и он якорён на `exo__Property_minCount`, то есть отвечает на вопрос «какие свойства класса **обязательны**». Вопрос «какие свойства у класса **объявлены**» движок не отвечает ничем.

Замер живого графа `[vault-exodev, --no-cache]` показывает, насколько это разные вопросы:

| | значение |
|---|---|
| свойств с `exo__Property_domain` | **735** |
| свойств с `exo__Property_minCount` | **44** (все `> 0`) |
| доля, видимая существующим резолвером | **6 %** |
| свойств цепочки `ems__Task` (Task 6 + Effort 38 + Asset 28) | **72** |
| **из них с `minCount`** | **0** |

Канарейка (§A40, конъюнкт проверен отдельно): доменов, несущих `minCount`-свойства, — **23**; `ems#Task` среди них нет ⇒ ноль есть факт о данных, а не мёртвый запрос.

⇒ снятие фильтра `minCount > 0` у существующего резолвера **не даёт ничего**: все 44 и так `> 0`. Нужен второй якорь.

Потребитель — property-editor (тикет `2c592498`): сегодня он показывает **2** редактируемых поля у любого класса и **0** опций в дропдауне связей, потому что питается мёртвым слоем. Проводка редактора — отдельная работа (PR-B); это требование поставляет только движок.

## Что поставляется

Экспортируемая фабрика в `packages/core`, симметричная существующей, но якорённая на `exo__Property_domain`. Аддитивно: существующий `createTripleStoreRequiredPropertyResolver` и его три прод-потребителя не изменяются.

Переиспользуется целиком, новых механизмов не вводится: транзитивный обход предков по `exo__Class_superClass`, дуал-IRI-ключ класса (`classKeyOf`, оба написания — uid и label), ленивое точечное разрешение твинов, вывод типа поля из `exo__Property_range`, чтение метки парой `exo__Asset_label` + `rdfs:label` (у метки вида `prefix__Name` конвертер эмитит IRI, и Literal-only-фильтр её бы уронил).

Дополнительно к полям существующего контракта отдаётся признак обязательности, выведенный из `exo__Property_minCount > 0`, — чтобы потребитель мог отличить обязательное поле от необязательного, не делая второго прохода.

## Границы (Non-goals)

- Проводка property-editor — **вне** этого требования (PR-B, тикет `2c592498`).
- Группировка / сворачивание унаследованных полей в UI — продуктовое решение фаундера, вне объёма.
- Ретайр мёртвого слоя `PropertySchemaResolver` / `EnumValueResolver` / `ClassHierarchyResolver` — тикет `bd752a24`.
- Поведение существующего `createTripleStoreRequiredPropertyResolver` не меняется ни в одном сценарии.

## Сценарии

```gherkin
Feature: резолвер ОБЪЯВЛЕННЫХ свойств класса, якорённый на exo__Property_domain

  Scenario: свойства, объявленные на самом классе
    Given граф, где свойство P объявляет exo__Property_domain = класс C
    When резолвер вызван с UID класса C
    Then в результате есть поле с ключом, равным метке свойства P

  Scenario: свойства, унаследованные по цепочке exo__Class_superClass
    Given класс C объявляет exo__Class_superClass = класс B, а B — класс A
    And свойство P объявляет exo__Property_domain = класс A
    When резолвер вызван с UID класса C
    Then в результате есть поле свойства P

  Scenario: свойство БЕЗ minCount попадает в выдачу
    Given свойство P объявляет exo__Property_domain = класс C и НЕ объявляет exo__Property_minCount
    When резолвер вызван с UID класса C
    Then в результате есть поле свойства P
    And его признак обязательности равен false

  Scenario: обязательность выводится из minCount
    Given свойство P объявляет exo__Property_domain = класс C и exo__Property_minCount = 1
    When резолвер вызван с UID класса C
    Then признак обязательности поля P равен true

  Scenario: класс без объявленных свойств
    Given класс C, на который не указывает ни один exo__Property_domain
    When резолвер вызван с UID класса C
    Then результат — пустой список

  Scenario: ссылка на класс приходит в ЛЮБОЙ из двух IRI-форм
    Given свойство P объявляет exo__Property_domain символической формой класса C
    When резолвер вызван с bare-UID класса C
    Then в результате есть поле свойства P

  Scenario: тип поля выводится из range, и объектный range несёт класс пикера
    Given свойство P объявляет exo__Property_range = класс R
    When резолвер вызван с классом, к домену которого относится P
    Then тип поля P — ссылочный
    And поле несёт ключ класса R для пикера кандидатов

  Scenario: существующий резолвер обязательных свойств НЕ меняется
    Given тот же граф
    When вызван существующий резолвер обязательных свойств
    Then его выдача та же, что до этого изменения
```

## Проверяемость

Оси через **прод-загрузчик** (`loadVaultTriples`) на собственной файловой фикстуре — тот же путь, которым граф собирается в проде, а не ручной набор триплов. Каждый сценарий получает свою ось; каждая ось — своего мутанта, краснящего ровно её.
