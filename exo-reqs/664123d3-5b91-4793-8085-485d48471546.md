Generic CLI primitive to overwrite the markdown BODY of an existing vault asset — the body-rewrite counterpart of `set-property` (#3795, frontmatter mutation) / `create --body-file` (#3744, body on a NEW asset). Closes the recurring "I had to backup -> rm -> Write to rewrite an asset's body" dogfooding gap (empirical 2026-07-26, KSD RFC v1->v3 session): body-rewrite went around the product via a raw Write, which is fragile and — since the 2026-07-26 dogfood-cli-mutation hardening — requires an audited sentinel window for CLI-creatable instance classes.

## Job Story

When I need to rewrite the body of an existing task/RFC/concept asset, I want a `exocortex set-body <path> --body-file <new.md>` command that swaps the body and bumps updatedAt while validating the new wikilinks, so I never fall back to a raw backup -> rm -> Write that bypasses the product's hook-coverage.

## Acceptance Criteria (Gherkin)

```gherkin
Scenario: set-body overwrites the body, preserves frontmatter, bumps updatedAt
  Given an existing vault asset with frontmatter + an old body
  When I run `set-body <path> --body-file <new.md>`
  Then the asset's body is replaced by the new content
  And the frontmatter block is unchanged except exo__Asset_updatedAt is bumped

Scenario: a valid [[uuid]] wikilink in the new body is accepted
  Given a new body containing [[<existing-uuid>]]
  When I run set-body
  Then the write succeeds

Scenario: an invalid wikilink in the new body is rejected, file unchanged
  Given a new body containing [[<nonexistent-uuid>]]
  When I run set-body
  Then the command fails fail-loud and the file is left byte-unchanged

Scenario: set-body refuses a non-asset
  Given a markdown file with no exo__Asset_uid
  When I run set-body on it
  Then the command fails fail-loud (only existing assets are mutated)
```

Empirical: 2026-07-26 KSD RFC session — a v1->v3 body rewrite of an `inbox__ExoAssistantKnowledge` asset needed a `backup -> rm -> Write` with a dogfood-cli-mutation sentinel window (issue #3943).
