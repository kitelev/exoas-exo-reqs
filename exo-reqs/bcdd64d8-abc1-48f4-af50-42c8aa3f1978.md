# req(exo): loadFromVaultFS strips the surrounding quotes from exo__Property_minCount before parsing it — and a PARITY GUARD holds every shape field agreeing between the two loaders across quoting forms

## Job Story

When I declare a required property and write its `exo__Property_minCount` as a **quoted** YAML scalar (`"1"` — the form 11 live definitions across `exoas-exo`, `exoas-exocmd` and `exoas-tbank` already use), I want `ShapeLoader.loadFromVaultFS` to build the same shape it builds for a bare `1`, so that a declared obligation does not depend on how the author quoted the number; and I want that agreement **enforced for every field of the shape**, not re-discovered one field at a time — this is the **third** ticket on the same `loadFromVaultFS` / `loadFromRDFGraph` seam (6n: `exo__Asset_label`, req `78c46697`; 6o: pure-UID `exo__Property_domain`/`_range`, req `94b302e0`; this one: `exo__Property_minCount`).

Sibling of req `67767fcb`, whose Non-goals clause reads verbatim: «`loadFromVaultFS` resolution of pure-UID `exo__Property_domain` wikilinks … **and its verbatim handling of a quoted `exo__Property_minCount: "1"` — pre-existing, separate**». The first half of that sentence was superseded by req `94b302e0` (2026-09-20); this requirement is the specification of the **second half**. Ticket `15003314`.

## Measured premise (sha `7b558a735168b92ff5ddb464326ff442e169a249`, jest over `src`)

`ShapeLoader.parseFrontmatter` is the FS loader's OWN YAML-ish parser and it keeps a value **verbatim** (`result[key] = kvMatch[2].trim()`, no quote strip), so `registerCandidate` hands `parseInt` a string that still carries the quotes:

| in the file | FS loader `minCount` | GRAPH loader `minCount` |
|---|---|---|
| `1` | **1** | 1 |
| `"1"` | **undefined** | **1** |
| `'1'` | **undefined** | — |
| `" 1 "` | **undefined** | — |
| `2` | 2 | — |

`parseInt('"1"', 10)` = `NaN` → `minCount` drops to `undefined`. The definition still **registers** (`defined=true`) — the shape exists, the obligation silently does not. The graph loader is unaffected because the engine hands it an already-parsed literal (YAML stripped the quotes before `NoteToRDFConverter`), which is exactly why the two loaders disagree on the SAME bytes.

**Effect if a consumer read it** (same input, the two shapes fed to the real validator): FS-built shape → `0` `sh:minCount` violations, GRAPH-built shape → `1`.

**The repository already knew**, in its own test comment — `packages/core/tests/services/ShapeLoader.test.ts:1167`:
> `// unquoted, as `create --class DatatypeProperty` writes it (the FS parser keeps a quoted "1" verbatim — separate gap)`

## Scope of the guard — measured, not assumed

Every shape field × three quoting forms through **both** loaders on the same bytes (18 combinations, sha `7b558a73`):

| field | `bare` | `"…"` | `'…'` |
|---|---|---|---|
| **`minCount`** | same | **DIFF** | **DIFF** |
| `range` (`xsd:` CURIE) | same | same | same |
| `cardinality` (wikilink) | same | same | same |
| `severity` | same | same | same |
| `exo__Asset_label` | same | same | same |
| `domain` (label wikilink) | same | same | same |

**2 of 18 diverge, and both are `minCount`.** The predicate «quotes do not matter» holds for every sibling field because each either strips explicitly (`label` via `.replace(/^["']|["']$/g, "")` — req `78c46697`; `domain`/`range` via `extractWikilinkRef`) or is quote-insensitive by construction (`cardinality`/`severity` match by `.includes`). `minCount` is the only field parsed as a **number from the string edges**, and therefore the only one that breaks.

⛤ **The 18 combinations are the CONFIRMATION; the load-bearing ground is the structural asymmetry above** — it says why no further diverging form will appear, which a sample never can.

⚠ **And the honest answer to «why a guard over six fields when only one diverges»:** the other five are quote-insensitive **by accident of how they are parsed**, not by any declared contract — `severityFromValue` and `cardinalityFromLabel` happen to match by `.includes`, `domain`/`range` happen to run through an extractor that strips. Nothing states that they must keep doing so. This guard is therefore not a duplicate of an existing protection: it is the **first explicit one**.

|---|---|---|---|---|---|

| vault-my | 9618 | 300 | **24** | 15 | **9** |

Arithmetic closes in all three. Independently re-measured by the orchestrator: identical (44/24/27, 9/9/11).

⛤ **9/9/11 counts MOUNTS, not definitions** — the carriers live in shared assetspaces mounted into several vaults. **Unique definitions: 11** — `exo__Setting_key`, `exo__Setting_value`, `exo__AssetSpace_source`, `setting__Setting_key`, `setting__Setting_value`, `setting__SettingKey_datatype`, `exocmd__AnyPrecondition_preconditions`, `exocmd__NotPrecondition_precondition`, `exocmd__AllPrecondition_preconditions` (`exoas-exo` / `exoas-exocmd`) + 2 in `exoas-tbank/tbank-tbox`.

## The defect is REAL but LATENT IN ITS CONSEQUENCES — stated, not glossed

Enumerated by consumer, not inferred (`git grep '\.minCount' origin/main -- packages/*/src`):

- The **only** reader of `Shape.minCount` is `ShaclLiteValidator.ts:355` (`:363` is the same site's message).
- Every validation path takes its shapes from **`loadFromRDFGraph`**: `validate-schema.ts:962` (CLI `validate schema --shapes-mode`), `ExocortexPlugin.ts:2915` (plugin on-save), `CandidateShaclValidator` (`create --validate`).
- The **only** production caller of `loadFromVaultFS` is `create.ts:623`, and the repository's own docstring (`CandidateShaclValidator.ts:67-70`) says the registry `create` loads is used *«only for cardinality-aware property serialization (#3099/#3179), **never for validation**»* — and cardinality-aware emission reads `Shape.cardinality`, not `minCount`.

⇒ **today nothing reads `minCount` out of the FS registry.** There is no CLI-vs-plugin validation divergence on the 11 live definitions: both sides go through the graph loader. What this requirement fixes is the **loader parity invariant** — a declared invariant of this codebase (`docs/explanation/CROSS_RUNTIME_PARITY.md`, axes P1/B6 of `ShapeLoader.test.ts`) — before the next consumer of the FS registry inherits a silently wrong shape.

## Non-goals (measured 2026-09-20, ticket `15003314` plan-gate)

- **`RequiredPropertyResolver.ts:192-202` — the THIRD implementation of reading `exo__Property_minCount`** (its own `parseInt(t.object.value, 10)`, straight off the triple store, feeding the required form fields of create-instance via `CommandExecutionFlow:100`). It sits on the graph path, where the quotes are already gone, so it does **not** carry this defect; and it does not go through `ShapeLoader`, so the parity guard of this requirement structurally cannot reach it. Covered here only by a control axis asserting it agrees on both written forms. Consolidating the three readers is a separate ticket, in the same shape as `6572f3f3` (three implementations of the IRI↔prefix inverse).
- **The data behind the 11 quoted definitions is not rewritten.** The fix is in the reader, not in the vault: the written form stays legal, which is the whole point of the parity invariant.
- `parseFrontmatter` itself is untouched — stripping quotes there would change the parser's contract for every consumer (`label`, `domain`, `range` already strip downstream), which is a migration, not a shape fix.
- The behaviour of `loadFromRDFGraph` is untouched; parity is proved by an axis over the same files, not by rewriting both loaders.
