# Job Story

Когда я отгружаю фичу, меняющую **отображаемое имя** ассета (спека `exo__DisplayNameSpec`, `omitLabel`, TBox-проекция), я хочу спросить у CLI «как этот ассет будет называться», чтобы проверить результат в CI, в автономной петле и с чужой машины — а не только глазами в Obsidian.

# Контекст

Движок displayName жил **только** в плагине (`packages/obsidian-plugin/src/domain/display-name/`), поэтому составленное имя было недоступно снаружи Obsidian. Замер 2026-08-15: grep по всему дереву `--help` (корень + 8 подкоманд) на `displayname|display-name|printname|print-name` → **0 вхождений**. Есть `resolve-buttons` (оракул видимости кнопок) и `resolve` (uuid→путь); оракула имени не было.

Это дыра в инварианте **UI/CLI Parity (#3417)**. Она стала осязаемой после отгрузки `exocmd__Grounding_omitLabel` (v16.219.0): ассеты `ems__Action` создаются **без** `exo__Asset_label`, имя составляется спекой `f39ece43` на рендере — и единственные способы его проверить это (а) глазами в Obsidian, (б) jest-харнесс плагина. Ни один не доступен ни CI, ни петле, ни человеку без установленного плагина.

## Замер связанности (проведён до формулировки требования)

| Файл | Строк | Зависел от `obsidian` |
|---|---|---|
| `DisplayNameResolver.ts` | 388 | нет |
| `DisplayNameTemplateEngine.ts` | 623 | нет |
| `keyPathResolver.ts` | 87 | нет |
| `PrintNameRuleService.ts` | 773 | **да** — `TFile`, `App` |

Контакт с Obsidian API — **три** вызова: `vault.getMarkdownFiles()`, `metadataCache.getFileCache(file)?.frontmatter`, `metadataCache.getFirstLinkpathDest(linkpath, "")`.

⛤ **Три вызова схлопываются в ДВА метода порта**, потому что сканер не использует файловый объект ни для чего, кроме получения frontmatter: `collectDisplayNameSpec`/`collectDisplayNamePart` принимают только frontmatter, а `sourceFile` правила берётся из `exo__Asset_uid` самой спеки, не из пути. Хендл возвращать некому — значит и порту он не нужен:

```
listFrontmatter(): Iterable<Record<string, unknown>>
resolveLinkpathFrontmatter(linkpath: string): Record<string, unknown> | null
```

У `packages/core` зависимости от `obsidian` нет; `PrintNameRuleService` конструировался в **одном** месте (`ExocortexPlugin.ts:549`); у CLI все три операции уже есть (`FileSystemVaultAdapter.getAllFiles` / `getFrontmatter` / `getFirstLinkpathDest` — зеркало тех же трёх вызовов).

⛤ Импортёров движка на `origin/main` — **30** (14 в `src`, 16 в тестах), это выше cascade-cap. Обычный re-export их бы не спас: тесты конструируют `new PrintNameRuleService(app)`. Поэтому шим `PrintNameRuleService` — **подкласс, принимающий `App`** и оборачивающий его в порт; он и есть адаптерная граница плагина.

# Scenarios

## Scenario 1: оракул печатает составленное имя
Given vault со спекой `exo__DisplayNameSpec` для класса `C` и инстансом `A` этого класса
  And у `A` **нет** `exo__Asset_label`
When я выполняю `exocortex resolve-display-name <путь-к-A> --vault <V>`
Then на stdout печатается имя, составленное спекой
  And код возврата 0

## Scenario 2: единственный источник истины
Given движок displayName перенесён в `packages/core` за двухметодный порт
When плагин и CLI резолвят имя одного и того же ассета
Then оба проходят через **одну и ту же** реализацию в core
  And правка спеки в vault меняет вывод обоих без изменения кода
  And naming-путь CLI **не резолвит** ссылку по frontmatter-алиасу, потому что `metadataCache.getFirstLinkpathDest` этого не делает — иначе CLI разрешил бы ссылку, недоступную плагину, и составил бы **другое** имя

## Scenario 3: происхождение имени различимо
Given ассет, чей класс покрыт спекой, и ассет, чей класс не покрыт
When я выполняю `resolve-display-name <путь> --json`
Then вывод содержит `displayName` и `source`
  And `source` **сообщается движком** (`resolveWithProvenance`), а не выводится сравнением имени с лейблом
  And спека, составляющая имя, в точности равное имени файла, всё равно даёт `source: spec` — иначе главный диагностический сигнал («видно голый UID ⇒ спеки нет») **инвертировался бы** ровно там, где он важен

## Scenario 4: нулевая регрессия поверхностей плагина
Given 30 файлов импортируют движок по прежним путям `@plugin/domain/display-name/...`
When движок перенесён в core и на прежних путях оставлены re-export-шимы
Then ни один импортёр не изменён
  And 10 сьютов движка (181 тест) проходят без правок

## Scenario 5: отсутствующая цель — громкий отказ
Given путь, которого в vault нет
When я выполняю `resolve-display-name <этот-путь>`
Then команда завершается ненулевым кодом с внятным сообщением
  And ничего не пишет в vault

# Non-goals

- ⛔ **Не** хранить составленное имя. Оно вычисляется на каждый вызов — ровно как сегодня на каждый рендер.
- ⛔ **Не** менять семантику отображения. Перенос обязан быть поведенчески нейтральным; любое расхождение вывода — дефект переноса, а не улучшение.
- ⛔ **Не** трогать импорты 30 потребителей. Шимы — часть требования, а не деталь реализации.
- **Host-функции в CLI не регистрируются.** Их предикаты платформенные, движок fail-closed ⇒ спека, называющая незарегистрированную функцию, просто не участвует: CLI **недоотчитывает** такую спеку, но не выдумывает. Выведение host-функций в CLI — отдельная работа.
- Гейт в CI на основе этого верба — отдельная работа (сначала оракул, потом его потребители).

# Известные границы

- **Alias-резолюция** отключена только на naming-пути. Остальные потребители `FileSystemVaultAdapter` сохраняют прежнее поведение (флаг `allowAliasFallback` по умолчанию `true`).
- **`.md`-ретрай** в обоих адаптерах сейчас no-op: и `FileSystemVaultAdapter.getFirstLinkpathDest`, и мок Obsidian в тестах сами дописывают суффикс. Оставлен ради паритета с исходным кодом движка; в живом Obsidian он рабочий.
- Каждый вызов верба заново обходит vault (сканирование спек + построение индексов). Для одиночной проверки это приемлемо; для гейта, вызываемого на ассет, понадобится batch-режим.
