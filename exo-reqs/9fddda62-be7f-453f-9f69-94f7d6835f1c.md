# req(exo): query-time class-hierarchy resolver (RFC 78572fa9 Candidate B Phase 0 — replaces A2)

## Job Story

When I write a vault-declared pure-SPARQL query or `exocmd__Precondition_sparqlAsk` that walks the class hierarchy — `?s exo:Instance_class ?c . ?c exo:Class_superClass* <X>` (or `exo:Class_superClass+`) — I want it to return the transitively-classified instances for the ~99.8% of assets whose `exo__Instance_class` object is the symbolic class IRI, **resolved at query-time (match-time) with zero store growth**, so that homoiconic vault-declared logic gates on "is a (subclass of) X" natively — without a TS host-function, a `STRENDS(STR(?c),"…")` naming hack, **and without materializing inferred ancestor triples into the store** (the abandoned-A2 failure mode).

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: query-time class-hierarchy resolution (resolving-store decorator, Approach A)

  Scenario: transitive hierarchy walk resolves at match-time for symbolic-form instances (CQ1)
    Given a fixture vault where class C1 has exo__Class_superClass -> C2, C2 -> C3
    And instance A has exo__Instance_class -> C1 (emitted as the SYMBOLIC class IRI)
    And the store is built by NoteToRDFConverter (no inference materialization)
    When the ClassHierarchyResolvingStore is enabled and I run
      SELECT ?s WHERE { ?s exo:Instance_class ?c . ?c exo:Class_superClass* <C3-symbolic> }
    Then A is returned
    # Revert-verify: resolver OFF -> A is NOT returned (RED, only the zero-length seed). Resolver ON -> returned (GREEN).

  Scenario: file-IRI-form instances heal too (symmetric bridge)
    Given instance B has exo__Instance_class -> C1 emitted as the FILE-IRI form
    When the resolver is enabled and I run the same C3 walk
    Then B is returned (the walk crosses the first symbolic ancestor hop instead of truncating there)

  Scenario: ZERO store growth (the anti-A2 guarantee)
    Given the same fixture vault
    When the store is built and the resolver-enabled query runs
    Then no inferred / ancestor Instance_class triple is added to the store
    And the store triple-count is identical whether the resolver is enabled or disabled
    # The resolution is per-match, discarded after the query — RDFSInferenceEngine is never fed and never activates.

  Scenario: predicate-scoped — non-hierarchy queries are byte-identical
    Given a query that does NOT reference exo__Class_superClass / rdfs:subClassOf
    When it runs with the resolver enabled vs disabled
    Then the result set is identical (the decorator is a pure pass-through for non-hierarchy predicates)

  Scenario: both surfaces resolve (ASK precondition + SELECT)
    Given a vault-declared ASK precondition `ASK { <$target> exo:Instance_class/exo:Class_superClass* <X> }`
    And a SELECT analytics/CLI query over the same hierarchy
    When each runs through ExoQLQueryExecutor with the resolver enabled
    Then both gate/return correctly for symbolic-form instances
    # PreconditionEvaluator and CLI/plugin construct the same ExoQLQueryExecutor+store -> one mechanism fixes both.

  Scenario: cycle-safe walk
    Given a malformed class-def with a Class_superClass cycle (A superClass B, B superClass A)
    When the resolver-enabled transitive walk runs
    Then it terminates (the existing visited-set / MAX_DEPTH guard in PropertyPathExecutor holds across the bridge)

  Scenario: no consumer regression
    Given the resolver is enabled by default
    Then CommandResolver.getClassAncestorsWithDepth (its own file-IRI TS bridge) and RequiredPropertyResolver behave unchanged
    And the full plugin + CLI suite remains green
    And SHACL `validate schema --shapes-mode` (cache cleared) violations <= baseline
```

## Notes

- **Design (Andrey R22-decided, 2026-07-29): Approach A — resolving-store decorator.**
  - New `ClassHierarchyResolvingStore implements ITripleStore`, injected **once** at the top of the `ExoQLQueryExecutor` constructor so every sub-executor (`BGPExecutor` → `PropertyPathExecutor`, `GraphExecutor`, `FilterExecutor`) inherits the wrapped store.
  - **Pass-through** for every predicate except `exo__Class_superClass` / `rdfs:subClassOf` (a cheap early-out check on the hot `match` path).
  - **Memoized `symbolic → file-IRI` class index** built lazily on first hierarchy-match, O(number of classes ≈ hundreds), cached per store-instance until reindex. Reuses the established bridge logic (`CommandResolver.getClassAncestorsWithDepth` / `resolveClassFileIRI` / `findUidByLabel`; `iriToObsidianName` for the symbolic↔label derivation).
  - **Symmetric** (resolves either form at any node) → heals both the 9424 symbolic-form and the 18 file-IRI-form instances.
  - **Config toggle** `resolveClassHierarchy` (default ON when shipped) = the revert-verify axis (OFF → baseline).
- **Engine facts verified on origin/main @ 2119c77d (verify-before-assert):** the seam bites at `PropertyPathExecutor.evaluatePathItem` (`match(symbolic-node, Class_superClass, undefined)` → empty); both `?c Class_superClass* <X>` and `?s Instance_class ?c` route through the single `ITripleStore.match`; `ExoQLQueryExecutor` is constructed at 9 sites (`PreconditionEvaluator` ×2 ASK, CLI `find`/`sparql-query`/`validate-schema`, plugin `SPARQLQueryService`, `CommandResolver`, exoql); `RDFSInferenceEngine.materialize` reads `Class_superClass` on ANY subject → **not touched** because the resolver writes nothing to the store.
- **Binding:** production-shape integration test — build the real store from a fixture vault via `NoteToRDFConverter`, assert CQ1 through the resolver. Revert-verified RED (resolver OFF) / GREEN (resolver ON). CI-gated suite (the full `packages/core/jest.config.js` config picks it up automatically). ASK-side verified through the `PreconditionEvaluator.executeAsk` path, not `cli query` (which is SELECT-only).
