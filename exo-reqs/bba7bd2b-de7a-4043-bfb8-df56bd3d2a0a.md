# Job Story

Когда обязательная проверка `requirements-trace` докладывает «✅ Active-gate OK — N active requirement(s)», я хочу быть уверен, что **весь** корпус до неё доехал, — чтобы исчезновение целого модуля требований не проходило зелёным только потому, что уцелевшие модули дали правдоподобное N.

# Контекст

Требование `99e06488-2da6-48fe-bd64-30c1e20bca0f` (отгружено PR #4065, v16.221.0) закрыло **половину** инварианта «корпус действительно приехал»: оно ловит **тотальную** потерю (`activeTotal === 0`). Оставшаяся половина — **частичная** потеря — по-прежнему бесшумна, а она вероятнее: `git clone` пустого либо переименованного репозитория возвращает 0, поэтому шаг клонирования не падает.

## Замер (исполнением, на голове PR #4065)

| корпус | reqCount | activeTotal | inputIntegrityViolation | блокирующий гейт |
|---|---|---|---|---|
| оба ассетспейса | 172 | 161 | `null` | exit 0 — верно |
| **`exoas-ems-reqs` отсутствует целиком** | **163** | **154** | `null` | ⛔ **exit 0**, «✅ Active-gate OK — 154 active requirement(s), all bound.» |

Девять требований — целый модуль — выпали из-под контроля без единого сигнала.

Собственный замер этой сессии (`exoas-exo-reqs` 166 файлов → 164 требования, `exoas-ems-reqs` 10 → 9) подтверждает распределение: потеря `exoas-ems-reqs` уносит **весь** ems-модуль, оставляя 95 % корпуса на месте.

## Вторая дорога к той же тишине

`packages/req-audit/src/assets.ts` — `catch { continue; }` плюс `extractFrontmatter → {}` на невалидном YAML: ассет со сломанным frontmatter **молча выпадает** из корпуса, а потребитель отличить «требования нет» от «требование сломано» не может. Порог `activeTotal === 0` замечает это, только если счёт дойдёт до нуля.

# Statement (Gherkin)

## Сценарий 1 — объявленный ассетспейс, не давший ни одного требования, отвергается

    Given корпус требований объявляет ассетспейсы exoas-exo-reqs и exoas-ems-reqs
      And на входе аудита нет ни одного требования из exoas-ems-reqs
      And уцелевшие ассетспейсы дали непустой набор активных требований
     When блокирующий шаг Active-requirement gate читает отчёт
     Then шаг падает с ненулевым кодом
      And его сообщение называет причиной сломанный ВХОД гейта, а не отсутствие находок

## Сценарий 2 — отказ называет виновника поимённо

    Given объявленный ассетспейс не дал ни одного требования
     When гейт отказывает
     Then текст отказа содержит имя этого ассетспейса
      And перечисляет оба возможных корня — не доехавший клон и переставший распознаваться предикат

## Сценарий 3 — полный корпус проходит байт-в-байт как раньше

    Given каждый объявленный ассетспейс дал хотя бы одно требование
      And все активные требования несут верификационную привязку
     When блокирующий шаг читает отчёт
     Then шаг выходит с кодом 0
      And печатает прежнюю строку «Active-gate OK» с числом активных требований

## Сценарий 4 — ассет, который не удалось прочитать или разобрать, отвергается, а не пропускается

    Given под корнем корпуса лежит markdown-ассет с frontmatter-блоком, который не разбирается
     When аудит собирает корпус
     Then этот ассет попадает в отчёт как отброшенный, с путём и причиной
      And блокирующий гейт отказывает, называя его сломанным, а не отсутствующим

## Сценарий 5 — объявленный перечень совпадает с тем, что клонирует CI

    Given блокирующий гейт опирается на объявленный перечень ассетспейсов
     When перечень сверяется с шагом клонирования в .github/workflows/ci.yml
     Then множества имён совпадают

## Сценарий 6 — размер входа рапортуется рядом с числом находок

    Given аудит собрал корпус
     When он выводит отчёт
     Then отчёт содержит разбивку по ассетспейсам с числом требований и активных требований в каждом
      And объявленный, но не приехавший ассетспейс присутствует в разбивке с нулём

# Non-goals

- ⛔ **Не вводить ratchet-порог по числу** (`activeTotal < сохранённая базовая линия ⇒ отказ`). Он строго сильнее — единственный, кто ловит усадку **внутри** уцелевшего ассетспейса, — но требует хранить число в репозитории и бампать его на каждом законном переводе требования в `Deprecated`, то есть заводит собственный источник ложной красноты. Ровно тот размен, который `99e06488` уже взвесил и отклонил для нуля.
- ⚠ **Названный остаточный пробел (сознательный, не молчаливый):** порог «каждый объявленный ассетспейс дал ≥1» **не** ловит частичную усадку внутри уцелевшего ассетспейса (удалили 9 требований из 164 — гейт зелен). Закрывается только ratchet'ом выше; отложено намеренно.
- ⛔ Не менять условие `activeViolations.length > 0` — существующий инвариант остаётся байт-в-байт.
- ⛔ Не менять поле `clean` и код возврата самого аудита — семантика `--gate soft|hard` не затрагивается; порог потребляет только блокирующий CI-шаг.
- ⛔ Не менять шаг клонирования в `ci.yml` и не переносить требования. Требование — страховка на случай, если клон когда-нибудь перестанет приезжать.

# Approval

Полномочие: задача `62bf75e7-1a04-4e66-bfb2-abf13da5bca7` (проект `bae1af09` «Виртуальная команда разработки — движок конвейера», санкция фаундера получена) **называет пространство решений дословно** — три кандидата фикса с разбором размена — и явно делегирует выбор исполнителю («Решение по кандидатам не принято — оно твоё»). Выбран кандидат 1 (пол на объявленный ассетспейс) в усиленной форме плюс кандидат 3 (громкий отказ на неразобранном ассете); кандидат 2 (ratchet) отклонён с причиной — см. Non-goals. Approve в рамках стандартной ALP-делегации (`/feature-sdd` Step 2, строка «Names the design ⇒ design pre-approved by whoever queued it»), без расширения области.

**Почему пол объявляется, а не выводится из содержимого каталога.** Буквальная формулировка кандидата 1 («каждый верхнеуровневый каталог под `--reqs` даёт ≥1 требование») **не ловит измеренный сценарий**: там каталог отсутствовал целиком, а отсутствующий каталог не перечисляется. Перечень, выведенный из наблюдаемого входа, не может обнаружить пропажу члена этого перечня — по построению. Поэтому ожидаемый набор **объявлен** в коде, а расхождение объявленного перечня с шагом клонирования `ci.yml` закрыто отдельным сценарием (5).
