## Job story

When an `exosync pull` (or any editor) rewrites a TBox-form asset — an `exo__SettingKey*` definition whose `setting__SettingKey_datatype` changed, a class whose description was edited — WITHOUT changing what its referrers derive from it, I want the next `--use-cache` command to refresh the persistent triple cache incrementally (re-parse that file, keep the inferred layer) instead of paying a full vault parse, and I want a reader that DOES have to rebuild to keep the inferred layer the previous cache carried, so that a Telegram-bot turn after such a pull costs the price of a delta (≈3–6 s) instead of two full parses (reader rebuild ≈17–25 s + the engine's compensating `index --force` ≈17–20 s).

## Context

- Source: GitHub `kitelev/exocortex#4277` (mirror `ems__Task 0ecf6f39`). Sibling of #4263 (req `42812747`, Active — per-file manifest + delta) and #4272 (req `5ab3d237`, Active — explicit/inferred boundary); the write-through of #4264 (req `cb707868`, Active) reuses the same `planDelta`.
- Measured 2026-09-19 on a `clonefile` copy of `vault-bot-kitelev` (16 687 files, `@kitelev/exocortex-cli` built from origin/main `789f1f55`, `/usr/bin/time -l` + an `fs.readFile*` counter preloaded into the built CLI): after `index --force` (19.95 s wall, 21 185 inferred triples, `inferenceEnabled:true`) a plain `query --use-cache` hit costs 4.06 s wall / 2 file reads; touching ONE `exo__SettingKey*` file (only `setting__SettingKey_datatype` changed, label + alias byte-identical) turns the next `query --use-cache` into a full REBUILD: 18.14 s wall, `Loaded 270840 triples in 17317ms`, 169 559 file reads, and the persisted cache comes back with `inferenceEnabled:false, inferredCount:0` (it had `true / 21185`). The live bot then issues `index --force` (17–20 s) to get the layer back — two full parses per such turn; over one day 37 turns / 362 hits / 5 in-turn full parses.
- Mechanism A (`packages/cli/src/cache/CacheManager.ts`, `planDelta`, origin/main `:775-796`): every added/modified file whose `exo__Asset_label` matches `TBOX_FORM` returns `rebuildReason: "TBox-form asset changed"`; `entryHasTBoxLabel(previous)` → `"asset lost its TBox-form label"`; `frontmatterHasTBoxFormAlias || entryHasTBoxFormAlias` → `"TBox-form alias"`. All three probes answer "is it TBox-form?" (a boolean), never "did the referrer-visible value change?".
- What a referrer actually derives from a TBox-form TARGET (`NoteToRDFConverter`, origin/main): (1) `valueToRDFObject` for a `⟦<uid>⟧` link emits the SYMBOLIC IRI expanded from the target's `exo__Asset_label`; (2) the same branch calls `emitTypeTripleForEnumInstance(labelIRI, target)`, which reads the target's FIRST `exo__Instance_class` value through `valueToClassURI` and pushes `<labelIRI> rdf:type <class>` + `<labelIRI> exo:Instance_class <class>` INTO THE REFERRER'S triples; (3) a `⟦prefix__Name⟧` link resolves through the target's `aliases` index (alias present → target file-IRI, absent → symbolic IRI). The converter reads nothing else from a target (Exo 0.0.3 anchors aside — out of scope, unchanged). So the referrer-visible PROJECTION of a TBox-form asset is exactly: its own `exo:Asset_label` object, its own TBox-form `exo:Asset_aliases` objects (as a set) and its own `exo:Instance_class` objects (in order) — all three are already present in the asset's cached triples, and all three are re-derived by re-parsing the asset itself. ⛔ Comparing label + alias only (the issue's technical note) would let a class change on a TBox-form target leave every `⟦uid⟧` referrer's type triples stale — the `Instance_class` term is part of the projection because byte-identity with a full parse is the criterion.
- Mechanism B (`rebuild()` `:552-565` → `buildInternal` `:1073` `inferenceEnabled: false`): a reader's rebuild always writes a layer-less cache, even when the cache it replaces had `inferenceEnabled: true`. `materializeInferredTriples` (shared with the delta path and with `index`) already exists; the cost of materialising on the copy is ≈3 s (PR #4270 matrix: delta 5.5 s with inference vs 2.9 s without) against a second full parse of 17–20 s.

## Statement (Gherkin)

```gherkin
Feature: CLI persistent triple cache — delta on an unchanged-projection TBox-form asset; a reader's rebuild inherits the inferred layer (#4277)

  Background:
    Given a format-3 cache built by CacheManager from the vault's current state (per-file entries, #4263)
    And the referrer-visible PROJECTION of a file is the triples it emits for its OWN subject under
      exo:Asset_label, exo:Asset_aliases (TBox-form values only, as a set) and exo:Instance_class (in order)
      — the three things NoteToRDFConverter reads from a link target (symbolic label IRI,
      emitTypeTripleForEnumInstance's Instance_class[0], the alias index)

  Scenario: AC1 — a modified TBox-form asset whose projection is unchanged is a DELTA
    Given a cached entry for a file whose label (or alias) has the TBox form prefix__Name and whose entry carries its triples
    When the file is modified and re-parsing it yields the SAME projection (same label object, same TBox-form alias set,
      same Instance_class objects in the same order) — e.g. only setting__SettingKey_datatype or the body changed
    And loadOrBuild() is called
    Then mode === "delta" and only that file (plus the ordinary referrer rules of #4263) is re-parsed
    And the inferred layer is re-materialised iff inferenceInputsChanged says so (kept verbatim otherwise)
    And the explicit triples are identical, as a multiset, to a full parse of the same tree
    And refreshAfterWrite() (write-through, #4264) on the same change returns mode "delta", not "skipped"

  Scenario: AC2 — every change that alters the projection, or that has no readable projection, still REBUILDS
    When a modified file's label VALUE changed (exo__A → exo__B), or it gained / lost a TBox-form label,
      or its TBox-form alias set changed, or its exo__Instance_class objects changed,
      or a TBox-form file was ADDED or REMOVED, or its basename has the TBox form,
      or its cached entry carries no triples (converter-skipped — the projection cannot be read back)
    Then loadOrBuild() performs the full rebuild exactly as today, with today's rebuildReason strings
      ("TBox-form asset changed: <path>", "asset lost its TBox-form label: <path>", "TBox-form alias: <path>",
      "TBox-form asset removed/added/file changed/file removed: <path>")
    And refreshAfterWrite() on such a change is "skipped" with the same reason, as today

  Scenario: AC3 — a reader's rebuild inherits the inferred layer of the cache it replaces
    Given a readable cache whose metadata.inferenceEnabled is true
    When loadOrBuild() decides to rebuild (a rebuild-class diff, a failed walk, an over-threshold diff)
    Then the new cache is persisted with inferenceEnabled: true and a freshly materialised layer
      (materializeInferredTriples over the explicit set — the same engines index runs; inferredCount > 0 when the vault infers anything)
    And the returned triples are explicit + inferred, explicitCount === the explicit count (the #4272 boundary)
    And given NO readable cache, a legacy / corrupt cache, or inferenceEnabled: false
    Then the rebuild stays layer-less exactly as today (inferenceEnabled: false, explicitCount === triples.length)
    And `index` (buildCacheWithValidation, --no-inference) is unchanged: it still builds layer-less and persists its own layer via saveInferredTriples

  Scenario: AC4 — measured on a copy of vault-bot-kitelev with the built dist
    Given `index --force` on the copy and ONE exo__SettingKey* file touched (setting__SettingKey_datatype changed, label + alias untouched)
    When `query --use-cache` runs (/usr/bin/time -l, fs.readFile counter)
    Then it reports the incremental refresh (delta), no full parse, and the cache keeps inferenceEnabled: true
    And the before/after numbers (wall, CPU, reads) are recorded in the PR body — never asserted in jest

  Scenario: AC5 — byte-identity of the commands
    Given the trap fixture (TBox-form label, TBox-form alias, duplicate label, case-different alias, a ⟦prefix__Name⟧ referrer, a ⟦uid⟧ referrer) and the live-size copy
    Then the delta triples equal a full parse (multiset), and apply / create / resolve-buttons stdout is byte-identical before and after, with and without --use-cache
```

## Relation to the sibling requirements

- `42812747` (#4263) AC5 says "a modified, added or removed file has (or had) a TBox-form label → full rebuild" and AC6 "absent / corrupt / legacy / over-threshold → full rebuild exactly as before". This requirement NARROWS AC5's "modified" case (unchanged projection → delta) and ADDS the layer to AC6's warm rebuild; on activation both clauses receive an in-place `SUPERSEDED by 1117f9fe (2026-09-19)` marker — the sibling stays Active, its other clauses and its `@req` axes (A5 label rename, A11, A12, A16) remain true and bound.
- `cb707868` (#4264) AC6 defers to "the mutation #4263 classifies as rebuild-only"; that set is the narrowed one above — the axis fixture that used a status change on a TBox-form task now exercises a label rename (a rebuild-class change under both classifications).

## Non-goals

- Legacy label-NAMED files (`prefix__Name.md` basename form) keep the unconditional rebuild — UID-canon vaults have none; out of scope.
- The cache format (3), `--use-cache` / `--write-through` semantics, `DELTA_REBUILD_RATIO`, `index --no-inference` are untouched; cache-load cost is #4267.
- Exo 0.0.3 anchor targets are not part of the projection (pre-existing #4263 behaviour).
