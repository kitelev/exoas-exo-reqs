# req(exo): index-cost visibility — the transitive `dependsOn` CLOSURE cost, surfaced in both mount pickers

## Job Story

When I am about to change what my vault mounts — applying a profile, or removing a knowledge pack — I want to see **how many files that decision actually costs**, counted over the whole `exo__AssetSpace_dependsOn` **closure** and not just the AssetSpace I clicked, so that I can tell at a glance whether "mount less" will help me at all — instead of discovering after the fact that one leaf AssetSpace drags in almost the entire vault.

## Why the CLOSURE, not the AssetSpace (P0 falsification, 2026-08-02)

The parent project's falsification gate (`8b8466bb`, task P0) measured this on the real vaults and concluded **mount-less through profiles does NOT materially help**: the active profile already resolves to **100 % of vault-my (8 738 / 8 738)**, **100 % of vault-tbank**, **99.4 % of vault-exodev**. The limiter is *not* the always-mounted floor (`{exo}` = 300 files = 3.4 %) — it is the transitive `dependsOn` closure: mounting the personal `exoas-my` (3 763 files) *forces* another 4 862, so the "minimal profile that still has my data" saves **58 files (0.7 %)**.

P0's explicit recommendation for this task was therefore: **keep P1, re-scope it — show the cost of the CLOSURE, because that is precisely what explains why "turn the extra ones off" does not work.** This requirement implements that re-scope. Showing an AssetSpace's own size *alone* would actively mislead (it is the number that makes mount-less look promising); the closure figure is the honest one.

**Deliberately NOT shown: an estimated index time in ms.** P0 established that index time is strictly linear in file count (`index_ms = 0.677 × files + 181`, R² = 0.9995; an independent parse-proxy gave R² = 0.996) — but the *constant* is device-specific (desktop ≠ iPhone) while the *ratio* is stable. A file count is therefore the honest, device-independent weight; a millisecond figure would be a fabricated constant baked into TS.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: Index-cost visibility in the mount pickers

  Background:
    Given each AssetSpace descriptor may declare `exo__AssetSpace_dependsOn`
    And a per-AssetSpace file count is derived at runtime from `vault.adapter`
      # runtime-derived exactly like `exo__AssetSpace_materialized` — never persisted to frontmatter

  Scenario: AC1 — the Apply-profile picker shows a profile's CLOSURE cost before applying
    Given a profile whose `exo__Profile_includes` names one leaf AssetSpace "my"
    And "my" transitively dependsOn "shared-private", which dependsOn "public", which dependsOn "exo"
    And the file counts are my=3, shared-private=5, public=2, exo=1
    When the picker builds that profile's row
    Then the row reports 11 files over 4 AssetSpaces
    And the figure is the closure total, NOT the 3 files of "my" alone
    And nothing is mounted, unmounted or otherwise mutated by computing it

  Scenario: AC2 — the AssetSpace list shows each pack's OWN size and its closure cost
    Given the "Remove knowledge pack" list contains "public" (2 files) which dependsOn "exo" (1 file)
    When the picker builds that AssetSpace's row
    Then the row reports the AssetSpace's own 2 files
    And it also reports the 3-file cost of its closure, so removing it reads honestly

  Scenario: AC3 — the count is derived mobile-safely, with no Node fs
    Given the plugin is running on iOS where `node:fs` does not exist
    When the per-AssetSpace file counts are derived
    Then only `vault.adapter.exists` and `vault.adapter.list` are used
    And no `node:fs`/`fs/promises` call is reachable from the counting path

  Scenario: an unmounted closure member makes the figure an explicit LOWER BOUND
    Given a profile's closure contains "exocmd", which is not materialized and therefore not countable
    When the picker builds that profile's row
    Then the reported total is marked as a lower bound
    And the number of uncounted AssetSpaces is stated, so the gap is never silently absorbed

  Scenario: zero-regression — with no counts available the pickers render exactly as before
    Given the file-count derivation was skipped or failed
    When either picker builds its rows
    Then no cost text is produced at all
    And every row is byte-identical to the pre-feature rendering
```

## Mechanism

**One render point serves both surfaces.** The `Remove knowledge pack` picker already maps `UnmountableAssetSpace → ProfileChoice` and reuses `ProfileFuzzyModal`, so AC1 and AC2 are satisfied by a single optional `ProfileChoice.indexCost` field rendered once in `ProfileFuzzyModal.renderSuggestion`.

1. **Pure domain** — `packages/obsidian-plugin/src/domain/profile/indexCost.ts` (sibling of the existing `closureGap.ts`):
   - `computeClosureIndexCost(roots, allInfos, fileCountByUid) → IndexCost` — builds the `dependsOn` map from the scanned `AssetSpaceInfo[]`, expands `roots` through the **shared** `transitiveDependsOnClosure` (core `AssetSpaceDependsOn.ts` — the same helper `ProfileApplyManager.resolveDeclaredAndEffective` and `CliProfileResolver` use), and sums the known counts. Reports `{files, closureSize, countedAssetSpaces, uncountedAssetSpaces}`.
   - `formatIndexCost(cost) → string | null` — returns `null` when nothing is known (that null is what makes the zero-regression scenario structural rather than argued).
2. **Mobile-safe counting** — a public `ProfileApplyManager.getIndexCostInputs()` returning `{infos, fileCountByUid}`, counting each materialized AssetSpace folder with the manager's existing `vault.adapter`-based recursive walk (the same one `applyProfile` already relies on). Session-cached and best-effort: any failure yields an empty map, i.e. the zero-regression path.
3. **Wiring** — the profile lister attaches the cost of each profile's declared `_includes` closure; the unmount wiring attaches each pack's own count plus its closure cost. Both are wrapped so a failure degrades to today's rendering.

**Preview-only, never the apply path.** The preview deliberately does **not** call `resolveDeclaredAndEffective`: that method asserts the TS floor and *throws* on a floor-violating profile, which would break the picker for every other row. The preview therefore expands the direct `exo__Profile_includes` through the same closure helper. `exo__Profile_imports` (RFC-deferred 0..1 MVP) is not walked — verified 2026-08-02 that **no profile in any of the three vaults uses it**; were one to, the preview would under-report, never over-report.

## Out of scope (siblings)

- Any change to what is actually mounted — this requirement is read-only visibility.
- A CLI equivalent (`resolve-deps --cost`), and any settings-tab AssetSpace table.
- Byte/disk-size weight; index-time estimates in ms (see the rationale above).
