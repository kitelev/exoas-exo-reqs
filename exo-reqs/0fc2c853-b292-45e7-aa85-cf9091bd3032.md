# req(exo): a `life__Episode` with TIMESTAMP bounds is 📍 ongoing only INSIDE the interval — the day-bounded reading stays unchanged

> Sibling of req `[[8a47ff93-4909-4b3a-89f5-4a39c15131fa]]` (the 📍 marker and the `isEpisodeOngoing` host function). That req reads **day** bounds and is left Active and unchanged for them; this req adds the **instant** bounds the class gained afterwards (`life__Episode_startTimestamp` / `life__Episode_endTimestamp`, authored interview 2026-08-07). Task `[[019c8017-25dd-4f7f-ac08-6cee060f0efa]]`.

## Job Story

When I log an episode that has a real clock time — a flight, a migraine, a meeting — I want 📍 to
be lit **while it is happening and not before or after**, so that "what am I in right now" stays a
one-glance answer instead of a marker that burns from midnight to midnight on the day of a
two-hour flight.

## Approval

Design pre-approved by the founder in the `interactive-interview` of 2026-08-07, recorded verbatim
in task `019c8017` (decisions 1-3, "залочены, не переоткрывать"). Decision 3 is this req's
statement: *«точный эпизод считается идущим только между своими таймстемпами; дневной эпизод — как
раньше (по дню)»*. `approvedBy` is deliberately empty — the authority is that recorded decision,
not a fresh human approve in the implementing session.

## Context — what already shipped, and what did not

The vault half is **done** and live in the shared `exoas-public/life`: the two properties
(`19915a87`, `6f6ea686`), the `minCount` removal on `life__Episode_start` that makes the XOR legal
(`bf82fb62`), and the two printed parts that render them with `exo__PrintedProperty_format:
DD.MM.YYYY HH:mm` (`e910fa27` order 4, `e8ded318` order 5) inside the existing period spec
`b836acf7`. So a timestamp episode **already prints its time**.

What did not ship is the predicate: `isEpisodeOngoing` reads only `life__Episode_start` /
`life__Episode_end` and truncates both to a `YYYY-MM-DD` key, so for a timestamp episode it reads
**no start at all** and returns false (fail-closed) — the marker never appears; and were the
timestamps merely truncated to their day, it would burn for the whole day. Measured 2026-10-03 in
`vault-my`: `life__Episode_start` 9 carriers, `_end` 8, `_startTimestamp` **1**, `_endTimestamp`
**0**.

## The zone reading — derived from the shipped renderer, not invented here

An authored timestamp in this vault is a **local wall clock with no zone suffix**: the canonical
writer is `DateFormatter.toLocalTimestamp` (`YYYY-MM-DDTHH:mm:ss`, no suffix — the same shape
`$nowLocal` and `exo__Asset_createdAt` carry), and the single live carrier is
`life__Episode_startTimestamp: 2026-08-10T07:00:00`.

The predicate therefore reads **the wall clock as written** and compares it against **now in local
terms** — which is exactly what the already-shipped renderer of these same two properties does.
`DisplayNameTemplateEngine.applyValueFormat` takes its components *literally* from the stored
value: UTC getters for a `Date` (a zone-less YAML timestamp is parsed as UTC, so its UTC fields ARE
the digits in the file) and a regex over an ISO string. Reading the predicate the same way makes
**the judge agree with the display**: 📍 lights at the time the user sees printed.

Consequences, stated rather than hidden:

- A value that carries an explicit zone (`…Z`, `±HH:MM`) has that zone **ignored**, exactly as the
  renderer already ignores it. Honouring it in the predicate alone would light 📍 at a time other
  than the one printed beside it — a worse outcome than a uniform reading. Latent today: the
  canonical writer emits no suffix and 1 of 1 live carriers is zone-less.
- A single source of truth for timestamp zones across the whole engine is a **separate open
  question** (the standing "RFC: единый источник TZ для штампов" task) and is explicitly a
  non-goal here. When it is decided, the renderer and this predicate must change **together** —
  which is the point of reading them the same way now.

## Acceptance Criteria (Definition of Done)

- `isEpisodeOngoing` judges a timestamp-bounded episode by its interval and a day-bounded episode
  by its day key, selected by the presence of `life__Episode_startTimestamp`.
- A production-shape component axis drives the REAL `scanVault → getTemplateForClass →
  DisplayNameResolver.resolve` over an in-memory vault carrying **both** live specs and the
  timestamp printed parts, running the REAL predicate — so the axis proves the **composition** of
  the two specs (📍 prefix + period line with time), not only the predicate in isolation.
- Unit axes cover every value form the real parsers produce, measured rather than assumed:
  `Date` (what js-yaml `YAML11_SCHEMA` hands over for an unquoted `…T07:00:00` — **measured
  2026-10-03**, correcting the task's own note that the `T` form arrives as a string), a quoted
  string, a string carrying a zone, a date-only value in a timestamp property, and malformed input.
- **Revert-verified**: each guarantee has an axis that goes RED when the production behaviour is
  neutralised and GREEN when restored, and the mutant matrix is taken by RUNNING it.
- The axes bound to req `8a47ff93` are untouched and stay GREEN — the day path is the negative
  control.
- `requirements-trace` green with the `@req:` binding on `main` before this req is flipped Active.

## Alternatives

- **Truncate the timestamps to their day and reuse the existing key.** Rejected: that is the defect
  — the marker burns all day, which is the founder's original complaint.
- **Honour an explicit zone in the predicate.** Rejected: the shipped renderer of the very same two
  properties ignores it, so the marker would light at a time other than the one printed. The zone
  question belongs to the standing single-source-of-TZ RFC, where both halves move together.
- **Extend `life__Episode_start`/`_end` to carry time instead of adding properties.** Rejected by
  the founder in the 2026-08-07 interview (decision 1) — the two formats coexist permanently, with
  day granularity remaining correct for most episodes.
- **Materialise an `ongoing: true` property.** Rejected for the same reason req 8a47ff93 rejected
  it: nothing would flip it as the clock advances.

## Метрики успеха

- Эпизод «перелёт Алматы—Новосибирск», оформленный таймстемпами, показывает 📍 только в часы
  перелёта — не весь день.
- Дневные эпизоды и все остальные классы рендерятся байт-в-байт как прежде; оси req 8a47ff93
  зелены без правки.
- 0 новых SHACL violations (правок TBox в этом req нет — слой уже отгружен).
