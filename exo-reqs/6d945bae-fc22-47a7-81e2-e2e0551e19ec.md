# req(exo): the duplicate-range report names ONLY a property the command is actually writing

## Job Story

When I run `exocortex-cli set-property` or `create` on a vault whose mounted TBox happens to contain a duplicated property definition somewhere, I want the `⚠ [PropertyNameValidator] …` diagnostic to appear only when the duplicate concerns a property **I am writing**, so that the warning stays actionable — instead of reporting every conflicting twin in the whole mounted TBox on every single write, whatever property that write touches.

## Context — the defect, measured

`PropertyNameValidator.collect()` walks the mounted vault once and, for a property label declared by two or more definitions with DIFFERENT `exo__Property_range`, emits the report through the injected `warn` channel **inside that walk**. `collect()` is cached and is reached from the very first public call of the validator — `validate(keys)`, which both writers run for the key check before anything else. So the report fires at the first cache access, for **every** conflicting duplicate in the mounted TBox, regardless of which property the command is writing.

Reproduced on `origin/main` `efc88f84` (2026-09-20) with a fixture TBox mounting a single, conflict-free definition `ems__Reminder_text` and an unrelated pair of twins `ems__Other_twin` (`xsd:integer` vs `xsd:string`), at three levels:

- `declaredRange("ems__Reminder_text")` → 1 warning, and it names `ems__Other_twin`;
- `validate(["ems__Reminder_text"])` alone → the same 1 warning;
- the REAL `setPropertyCommand()` writing `--property ems__Reminder_text --value hello` → stderr carries `⚠ [PropertyNameValidator] property ems__Other_twin is declared more than once …` while the write itself lands (`WROTE=true`).

Live exposure, measured the same day with the PRODUCT collector over each canonical vault: conflicting duplicates **0 / 0 / 0** `[vault-exodev/my/tbank]` with the canary alive (known property names **717 / 509 / 492**, declared ranges **481 / 285 / 287**). The defect is therefore **latent**: the axes below are built on a fixture, not on live data.

## Design — why the emission moves to the ACCESS point

`collect()` cannot filter by the addressed name: it is cached, so after the first call its loop never runs again. A name filter inside it would report for the FIRST caller's name only and be silent for every later one, on the same validator instance. The only place that knows which name is being addressed is the public accessor.

So `collect()` becomes pure data collection — it records the conflicts it finds in the cached set, keyed by property name, with the message text unchanged — and `declaredRange(name)` emits the recorded message for THAT name, under a per-instance latch so that repeated addressing of the same name still yields exactly one line.

`declaredRanges()` (the plural form) hands the WHOLE map to `GenericAssetCreationService`; it does not itself address a name, because the service resolves per supplied key inside. It therefore stays silent unless the caller names what it addresses: it takes an optional `addressed` argument, and `create` passes the very same key set it already passes to `validate()`, held in ONE local variable so that "the same set" is a property of the construction rather than a coincidence of two expressions.

## Scenarios

```gherkin
Given a mounted TBox in which the property ems__Other_twin is declared twice with DIFFERENT exo__Property_range
And the property ems__Reminder_text is declared exactly once
When I run set-property (or create) writing ONLY ems__Reminder_text
Then the command succeeds
And NO ⚠ [PropertyNameValidator] line naming ems__Other_twin is written to stderr

Given the same mounted TBox
When I run set-property (or create) writing ems__Other_twin itself
Then EXACTLY ONE ⚠ [PropertyNameValidator] property ems__Other_twin … line is written to stderr
And the value is still typed by the FIRST definition in byte-ordered path walk

Given the same mounted TBox
When a command writes TWO properties and only the SECOND of them has conflicting definitions
Then exactly one line is written, and it names the SECOND property
# the emission follows the ADDRESSED name, not the first cache access

Given the same mounted TBox
When the same property name is addressed twice on one validator instance
Then still exactly ONE line is written
# the per-instance latch; collect() is cached and must not re-report

Given the same mounted TBox
When declaredRanges() is called WITHOUT naming any addressed property
Then no line is written at all, and the returned map is still complete
# a bulk hand-off claims no addressing

Given the same mounted TBox and NO warn channel injected
When any property is addressed, conflicting or not
Then nothing is printed and nothing is thrown
# the default channel stays a no-op — the DELIVERY mechanism is not changed, only the SCOPE of emission
```

## Non-goals (named, not silent)

- The `warn` channel default (a no-op) and its wiring to stderr in `create` / `set-property` are unchanged — this requirement narrows WHERE the report is emitted, never HOW it is delivered.
- First-wins resolution, byte-ordered walk, the "identical twins are silent" rule and the message TEXT are unchanged, byte for byte.
- `isUnknownName` / `remove-property` keep the default no-op channel and are untouched.
- The quoted-label defect that drops 15 definitions per vault before their domain is parsed (ticket `efe993e1`) is a separate pre-existing defect and is deliberately not fixed here.

## Relation to req 21ceea14

Requirement `21ceea14` stays **Active**; only one of its clauses is narrowed in place with a `SUPERSEDED by <this requirement> (2026-09-20)` marker. The clause it supersedes is its scenario "When either command **collects** the declared ranges … ONE ⚠ [PropertyNameValidator] … line is written to stderr" — collection is replaced by ADDRESSING as the trigger. Every other clause of `21ceea14` (declared-range typing, the reader oracle, supplied-key lookup, first-wins, identical-twin silence) is untouched and remains in force.
