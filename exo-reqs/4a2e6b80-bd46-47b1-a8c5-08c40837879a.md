# Job Story

Когда спека именования обходит путь вроде `exo__Asset_prototype.exo__Instance_class`, я хочу, чтобы каждый сегмент читался **только как собственное поле** ассета, — чтобы имя, которое видит пользователь, нельзя было получить из `Object.prototype`, а не из его данных.

# Контекст

`resolveKeyPath` — общий обходчик путей за **каждым** dot-path матчером (`exo__DisplayNameSpec_matchPath`) и **каждым** плейсхолдером вида `{{a.b}}`. Сегменты пути приходят **из frontmatter пользователя**, а обход индексирует обычный объект: `obj[part]`. Значит сегмент, названный именем члена `Object.prototype`, читается с прототипа.

Замер (исполнением, не рассуждением) на `origin/main`:

| выражение | результат |
|---|---|
| `resolveKeyPath({a:{b:1}}, "a.b")` | `1` — норма |
| `resolveKeyPath({a:{}}, "a.toString")` | **функция** |
| `resolveKeyPath({a:{real:1}}, "a.constructor")` | **функция** |

⛤ Дыра **достижима без всякого резолвера** — обычный вложенный объект уже её открывает. Она не внесена req `5cd9fffe`; тот лишь добавил одну дополнительную точку входа (адаптер стал отдавать `{}` вместо `null` для файла без frontmatter), и ревью PR #4052 это измерило отдельно.

## Почему отдельным требованием, а не внутри #4052

Близнец этой дыры — реестр host-функций (`matcherSatisfied` индексировался тем же способом) — закрыт в #4052, потому что тот PR отгружал тест, утверждающий fail-closed. Соблазн был закрыть и второй «раз уж тот же класс». Ревью возразило по существу, и возражение сильнее:

- реестр трогает host-функции — **2 спеки из 35**;
- `resolveKeyPath` стоит за **каждым** dot-path и **каждым** шаблонным плейсхолдером, на всех поверхностях, для всех ассетов.

Класс тот же, **радиус — нет**, и я аргументировал только первое. Отдельное требование даёт этому изменению собственную поверхность ревью вместо четвёртого концерна на PR, уже несущем три.

# Scenarios

## Scenario 1: обычный путь не меняется
Given метаданные `{a: {b: "value"}}`
When резолвится путь `a.b`
Then возвращается `"value"`

## Scenario 2: прототипное имя не читается
Given метаданные `{a: {}}`
When резолвится путь `a.toString`
Then возвращается `undefined`, а не функция

## Scenario 3: то же для `constructor` на НЕпустом объекте
Given метаданные `{a: {real: 1}}`
When резолвится путь `a.constructor`
Then возвращается `undefined`

## Scenario 4: индексы и `length` массива продолжают работать
Given метаданные `{a: ["x", "y"]}`
When резолвятся пути `a.1` и `a.length`
Then возвращаются `"y"` и `2` — это **собственные** свойства массива

## Scenario 5: обе точки входа закрыты независимо
Given обход достигает сегмента двумя разными путями — через hop по wikilink (резолвер вернул объект) и по обычному вложенному объекту
When сегмент назван именем из `Object.prototype`
Then **каждый** путь возвращает `undefined`
  And ось на один путь **не** покрывает второй

## Scenario 6: односоставный `matchKey` читается так же, как сегмент обхода
Given спека, чей `exo__DisplayNameSpec_matchPath` — **односоставный** (без точки), например `ems__Effort_status`
When `matcherSatisfied` читает это поле у метаданных, где такой ключ лежит **в цепочке прототипов**, а не собственный
Then матчер **не** срабатывает — плоское чтение обязано быть own-only, как и каждый сегмент обхода
  And ось на уровне хелпера этого **не** доказывает: она зелена и при откате проводки, поэтому ось обязана быть **call-site**

# Non-goals

- ⛔ **Не** менять семантику обычных путей: обход собственных полей обязан остаться байт-в-байт.
- ⛔ **Не** трогать реестр host-функций — он уже закрыт req `5cd9fffe`.
- Унификация реестров (issue #4054) — отдельная работа.

# Известные границы

- Изменение **видимо** для спеки, чей `matchPath` содержит сегмент с именем члена `Object.prototype`. Таких спек в живых vault нет (35 спек, ни одной), но формально это изменение поведения, а не рефакторинг.
- `ownProperty` возвращает `undefined` и для сегмента над не-объектом; прежний код в этой ветке и так возвращал `undefined`, поэтому расхождения нет.
