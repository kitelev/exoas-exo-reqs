# req(exo): Instance_class object-position uid-only emission (behind a default-OFF flag) + query-time symbolic-name resolution — RFC 78572fa9 Phase 3 stage-1

> The FIRST of the staged per-predicate emission flip (§v6 F1). This stage adds the **capability** (default-OFF) + generalizes the query-time resolver to cover the `Instance_class` object position + proves coverage by production-shape revert-verify (F5). It does **not** flip default-ON (that + the TS-consumer migration is a separate bounded stage — F4 "merge safely, prove, then flip on").

## Job story

**When** the Exocortex store eventually holds an asset's `exo__Instance_class` as the class **file-IRI** (uid) instead of the readable symbolic IRI — the single-uid-identity end-state,
**I want** a vault-declared pure-SPARQL query written by the readable name (`$target exo:Instance_class exo:Class`) to keep matching with **zero rewrite**,
**so that** identity stays uid (computed-not-stored) while every existing precondition / Competency Query / analytics keeps working.

## Acceptance criteria (Gherkin)

```gherkin
Feature: Instance_class object-position uid-only emission behind a default-OFF flag,
         with a query-time symbolic-name resolver (RFC 78572fa9 Phase 3 stage-1)

  Background:
    Given NoteToRDFConverter emits an asset's exo__Instance_class object as the SYMBOLIC
          class IRI today (the ~99.8% real-vault shape)
    And a default-OFF emission-flip flag (emitInstanceClassAsUid) covers ONLY the
          Instance_class object position this stage (F1 staged)

  Scenario: Flag OFF is byte-identical (safe merge — F4)
    Given the emission-flip flag is OFF (the default, production)
    When the converter emits any exo__Instance_class object
    Then it emits the SYMBOLIC class IRI exactly as before (byte-identical)
    And every existing pure-SPARQL precondition / query / analytics keeps working unchanged

  Scenario: Flag ON emits the class file-IRI (uid) for a resolved class ref
    Given the emission-flip flag is ON
    When an asset's exo__Instance_class references a RESOLVED class-def file
    Then the converter emits that class's FILE-IRI (uid), not the symbolic IRI
    And an unresolved prefix__Local class ref (no class-def in the store) still emits
          symbolic (no synthesizable uid), so a mixed store is possible

  Scenario: Query-time resolver bridges a symbolic Instance_class object to uid (F3)
    Given the store holds file-IRI Instance_class objects (flip ON)
    And the query-time name-resolver (generalized ClassHierarchyResolvingStore, default ON
          in ExoQLQueryExecutor) covers the Instance_class object position
    When a vault query asks "$target exo:Instance_class <symbolic-class-IRI>" (direct
          membership by the readable name)
    Then the resolver resolves the symbolic prefix#Local to the class file-IRI at
          match-time and the query MATCHES
    And it also matches any residual symbolic-form entries (mixed store) — the union of
          both forms — so the result is complete
    And an ambiguous prefix (two class-defs sharing a symbolic form) raises an error with
          a disambiguation hint rather than silently resolving to one

  Scenario: Resolver is a byte-identical pass-through when the object is not symbolic
    Given the query-time resolver is ON
    When a query references exo__Instance_class with a variable object, or a file-IRI
          object, or the store holds symbolic objects (flag OFF)
    Then the result set is identical whether the resolver is ON or OFF (predicate- and
          object-shape-scoped, zero store growth)

  Scenario: Proof — production-shape revert-verify over the real store (F5)
    Given the store is built by the REAL NoteToRDFConverter with the flip ON
          (Instance_class objects = file-IRI)
    And representative direct-membership queries matching Instance_class — including the
          shipped "$target exo:Instance_class exo:Class" is-a-class-def precondition shape
    When the resolver's Instance_class coverage is ON
    Then the queries resolve (GREEN)
    But when the resolver is OFF (baseline / revert-verify axis)
    Then the queries return nothing (RED) because the store holds file-IRI while the query
          used the symbolic form
    So the resolver empirically covers the flip (no fixture rewrite)
```

## Design notes

- **Emission flip site:** `NoteToRDFConverter.valueToRDFObject` — the resolved-class-ref branches (basename/label → symbolic) are gated on `emitInstanceClassAsUid && predicate === exo__Instance_class` to return the already-computed `fileIRI` instead. Unresolved-ref branches keep symbolic (no uid).
- **Resolver generalization:** `ClassHierarchyResolvingStore` gains an Instance_class object-position bridge (union of the direct symbolic-form match + the bridged file-IRI match, rewriting the object back to the queried symbolic form). Its `symbolic→file-IRI` index is broadened from hierarchy-edge subjects to all TBox class labels so metaclasses (`exo__Class`) resolve; collisions are detected → ambiguous lookup throws with a hint.
- **Revert axis (F5):** the `resolveClassHierarchy` config toggle on `ExoQLQueryExecutor` (resolver ON = GREEN, OFF = RED), the same axis the shipped Phase-0 resolver test uses.
- **Binding class:** Integration (production-shape store built by the real converter + the real executor / PreconditionEvaluator path).
