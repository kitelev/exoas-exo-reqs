## Job story

When a homoiconic command's `exocmd__Grounding_inputSchema` declares a field as `{ "type": "string", "format": "asset-reference" }` (the JSON-Schema way of saying "this string is a reference to a vault asset" — the shape the `set-parent` / `link-to-parent` groundings use), I want the engine's loader to project that field as an `assetRef` form field, so that the plugin's dynamic form renders the reusable reference picker (`ReferencePicker`, committing `[[uid]]`) whenever candidates are available and degrades to the plain text input otherwise — instead of silently treating the declared format as decoration.

## Context

- Source: ticket `efe33c5d-f8cd-4aae-b273-785aa118c55a` (parent techbacklog `bbac67ce`), found while shipping req `b06129dc` (PR kitelev/exocortex#4242, ORCH `25ec7e1d`: out of that PR's scope). Approved for implementation by ORCH `main-35699` mandate at the code-batch-2 plan-gate 2026-09-16 (decision `d64516ae`).
- Mechanism measured on `origin/main` `bd0e5b66`: `CommandResolver.loadGroundingDefinition` projects each `inputSchema.properties` entry as `type: rawType === "string" ? "text" : rawType` and never reads `format`; `targetClassUid` and `default`/`defaultValue` are propagated for any type. The plugin's `DynamicForm` renders `ReferencePicker` only for `type === "assetRef"` (`picker` = candidates present OR `targetClassUid` declared; otherwise a plain text input with the same class/testid as the `text` field); `DynamicFormModal` resolves candidates only from `targetClassUid`. `CommandExecutionFlow.run` hands the projected schema to `CommandPromptAdapter.promptInputSchema` and passes the collected values to `GroundingExecutor`, whose `property_set` path normalises `[[uid]]` / `"[[uid]]"` / bare uid to one link (req `b06129dc`).
- Live data (vault-exodev, exoas-exocmd): `18f12de2` set-parent (`parent: string + format asset-reference`), `30b9e8d8` link-to-parent (`value: string + format asset-reference`) carry the format and no `targetClassUid`; `170d1f56` / `ef896bf8` already use `type: assetRef` + `targetClassUid` (unchanged). No `exocmd__CommandBinding` targets the Set Parent / Set blocker / Link to Parent commands today (0 in vault-exodev), so the visible effect at authoring time is nil — this requirement makes the declared format mean something once a binding and/or `targetClassUid` exists.
- Why a NEW requirement: nothing on `origin/main` locks the format — removing a non-existent read reddens 0 tests; `b06129dc` specifies the executor's normalisation, not the loader's projection; the T1 `targetClassUid` propagation (project bbe40f8c) specifies `type: assetRef`, not `format`.

## Scenarios

### Scenario A — `string` + `format: asset-reference` projects as `assetRef`
Given a grounding whose `inputSchema` declares `parent: { type: "string", format: "asset-reference", title: "Parent" }`
When the command is loaded (`CommandResolver.loadCommand`)
Then the projected field is `{ name: "parent", type: "assetRef", label: "Parent", required: <per schema> }`
And an explicitly declared `targetClassUid` on that property is propagated verbatim (as it already is for any type).

### Scenario B — other formats are ignored (negative control)
Given `when: { type: "string", format: "date-time" }`
When the command is loaded
Then the field stays `type: "text"` (the loader recognises exactly one format; nothing else changes).

### Scenario C — the mapping does not widen to non-string types
Given `count: { type: "number", format: "asset-reference" }`
When the command is loaded
Then the field stays `type: "number"` (`format: asset-reference` is honoured only on `type: string`).

### Scenario D — `type: assetRef` keeps working (control)
Given `ontology: { type: "assetRef", targetClassUid: "<uid>" }`
When the command is loaded
Then the field is `type: "assetRef"` with the `targetClassUid` — unchanged from today.

### Scenario E — plugin consumer controls: picker with candidates, text fallback without
Given a projected `assetRef` field with candidates (from `targetClassUid`)
When the form renders and the user picks a candidate
Then the submitted value for the field is `[[<uid>]]` (`ReferencePicker.toReferenceWikilink`)
And given the same field with NO candidates and NO `targetClassUid`, the form renders a plain text input and submits the typed text verbatim (today's behaviour of the three groundings, preserved).

### Scenario F — the submitted reference reaches the executor in an accepted form (production-shape)
Given the REAL `CommandResolver` loads a `property_set` grounding (`targetProperty ems__Effort_parent`, `targetValueRef $input.parent`, schema `parent: string + format asset-reference`)
When `CommandExecutionFlow.run` prompts through a `CommandPromptAdapter` that (a) sees `type: "assetRef"` for `parent` in the schema it receives and (b) returns what the picker commits — `"[[<uid>]]"` — or, for the text fallback, the bare `<uid>`
Then the REAL `GroundingExecutor` over the REAL `FrontmatterService` writes `ems__Effort_parent: "[[<uid>]]"` exactly once (never `[[[[<uid>]]]]`) — req `b06129dc` on the executor side, this requirement on the loader side.

## Non-goals

- `targetClassUid` is NOT derived from the target property's range: `ReferencePicker` in picker mode refuses free text, so a declared class with 0 candidates would make the field un-enterable — deriving it silently would regress `set-parent` from "text" to "dead". Declaring `targetClassUid` (and a subclass-aware candidate resolver for Task ∪ Project) is a data/product decision, not this requirement.
- No `exocmd__CommandBinding` and no `targetClassUid` are added to the exoas-exocmd data here; the plugin (`DynamicForm`, `ReferencePicker`, `DynamicFormModal`) is not changed — Scenario E axes are consumer controls.
- The `2b0b381d` (set-blocker) grounding's `inputSchema` is written as an unquoted YAML flow mapping and reaches the loader as the literal `"[object Object]"`, so its schema is inert for a DIFFERENT reason (data defect in exoas-exocmd, present on remote too); handled in the `e98fa8a7` track with the same clone and push-gate, not here.
- The CLI surface is unchanged (`packages/cli/src` does not consume `inputSchema[].type`); `apply set-parent --input parent=<uid>` behaves as before.
