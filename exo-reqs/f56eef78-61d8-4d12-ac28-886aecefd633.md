## Job Story

When my daily note's Layout shows only some of the day's efforts — say Actions and Projects, or a "Closed today" review feed — I want to keep the legacy time-table with its columns, sorting and empty slots, because that Layout never claimed to replace it; and when I DO put a Tasks block in the Layout, I want the time-table to step aside so "Tasks" is not rendered twice.

## Statement (Gherkin)

```gherkin
Given a pn__DailyNote exo__Layout whose blocks include a daily-efforts-by-class block with partition "tasks"
When the daily note read-view renders
Then the legacy DailyTasksRenderer time-table is suppressed
And the daily navigation sections are preserved

Given a pn__DailyNote exo__Layout whose daily-efforts-by-class blocks are ALL non-"tasks" partitions (actions / projects / closed)
When the daily note read-view renders
Then the legacy DailyTasksRenderer time-table IS rendered
And the Layout's own blocks render alongside it

Given a pn__DailyNote exo__Layout carrying both an "actions" and a "tasks" daily-efforts block
When the daily note read-view renders
Then the legacy DailyTasksRenderer time-table is suppressed

Given a pn__DailyNote exo__Layout carrying no daily-efforts-by-class block at all
When the daily note read-view renders
Then the legacy DailyTasksRenderer time-table IS rendered
```

## Design note — why the gate moves to the partition, not away

Issue #3910 recorded the regression: a Layout that declared only Actions/Projects blocks still took the whole time-table away, because the suppression gate was **blind to the partition** — any `daily-efforts-by-class` block satisfied it. The measured feature-delta (issue comments 2026-08-20) showed the two feeds are **orthogonal**, not nested: the legacy table has six sortable columns, visibility toggles and empty slots; the daily-efforts block is a flat `<ul>` of `{path, title}`. So the AC "the new feed must be a SUPERSET" cannot be met by suppression at all — only by letting the two coexist wherever the Layout did not claim the Tasks territory.

Three designs were measured in the issue. This requirement formalises the third:

- **(1) Port the table into a Tasks block** — needs the item contract widened (`{path,title}` → + timestamps/status/area/votes/estimate), the partition pipeline widened, plus sorting, empty slots and column toggles moved across four files. Largest change, no user-visible gain over (3).
- **(2) Drop suppression entirely** — one line, but "Tasks" then renders twice on every Layout that has a Tasks block.
- **(3) Narrow the gate to `partition === "tasks"`** — one conjunct. No duplicate, superset **by construction**, and a Layout that declares a Tasks block keeps today's behavior byte-for-byte.

The gate is renamed `layoutHasDailyEffortsBlock` → `layoutHasDailyTasksBlock`: after the change the old name would be false for a Layout that demonstrably *has* daily-efforts blocks, and a method name that contradicts its mechanism is exactly the drift this codebase guards against.

## Relation to the two Active requirements it touches

- **req a38ac95b** (Active) — unaffected. Its `covers` requires the three class-partitioned blocks, the visibility precedence and that the day nav is "preserved — not lost"; it never required suppressing the legacy table. Its bound suppression axis uses a `partition: "tasks"` fixture, so it stays GREEN under this change (verified before implementation, not after).
- **req b2a33efc** (Active) — its `covers` carries a literal deployment note: *"activating any pn__DailyNote exo__Layout suppresses the legacy DailyTasksRenderer catch-all feed, so a live layout must carry the full block set (Actions/Tasks/Projects + Closed)"*. This requirement **supersedes that one clause**: suppression is no longer triggered by "any" Layout, and a live Layout is therefore no longer obliged to carry the full block set. The clause is amended in place with a `SUPERSEDED by f56eef78-61d8-4d12-ac28-886aecefd633` marker; every other clause of b2a33efc (the `closed` partition, the resolution/end fallback, local-tz date-match, homoiconic placement, desktop/mobile parity) stays in force untouched.

## Non-goals

- The second, independent defect measured on this issue — that 137 of 138 closed `ems__Action` carry none of the four timestamps `DailyTasksRenderer` reads, and that `isEffortClosedInDay` is never called from it — is **not** addressed here. This requirement restores the time-table; it does not change what the time-table can see.
- Porting the table's columns/sorting/slots into the block model (design 1) stays out of scope.
