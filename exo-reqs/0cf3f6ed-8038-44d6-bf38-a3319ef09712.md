# req(exo): pure-SPARQL class-hierarchy walks work for symbolic-form class instances (A2)

## Job Story

When I write a vault-declared pure-SPARQL query or `exocmd__Precondition_sparqlAsk` that walks the class hierarchy — `?s exo:Instance_class ?c . ?c exo:Class_superClass* <X>` (or `exo:Class_superClass+`) — I want it to return the transitively-classified instances for the ~99.8% of assets whose `exo__Instance_class` object is the symbolic class IRI, so that homoiconic vault-declared logic can gate on "is a (subclass of) X" natively, without a TS host-function or a `STRENDS(STR(?c),"…")` naming hack.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: symbolic-space completion of Class_superClass (A2)

  Scenario: transitive hierarchy walk is native for symbolic-form instances (CQ1)
    Given a fixture vault where class C1 has exo__Class_superClass -> C2, C2 -> C3
    And instance A has exo__Instance_class -> C1 (emitted as the symbolic class IRI)
    When the store is built by NoteToRDFConverter
    And I run SELECT ?s WHERE { ?s exo:Instance_class ?c . ?c exo:Class_superClass* <C3-symbolic> }
    Then A is returned
    # Reverting the symbolic Class_superClass emission -> A is NOT returned (RED). Restoring -> returned (GREEN).

  Scenario: additive & SHACL-safe (no-regress)
    Given the same vault
    When I run `validate schema --shapes-mode` (cache cleared) before and after the emission change
    Then the violation count after is <= the baseline before
    # A2 only widens isSubClassOf; it can never create a new sh:class violation.

  Scenario: emit once-per-class (no fan-out re-read)
    Given N assets all referencing the same symbolic class C1
    When the store is built
    Then C1's symbolic Class_superClass edges are emitted once (deduped), not per-referencing-asset

  Scenario: cycle-safe
    Given a malformed class-def with a Class_superClass cycle (A superClass B, B superClass A)
    When the store is built
    Then the symbolic-space emission does not loop (dedup + no self-edge + refuse/warn on the cycle)

  Scenario: no consumer regression
    Given the change is live
    Then CommandResolver.getClassAncestorsWithDepth (file-IRI subject) and RequiredPropertyResolver
    And the full plugin + CLI suite remain green (behavior unchanged for existing consumers)
```

## DEPRECATED (2026-07-25) — superseded by the query-time direction

Deprecated by Andrey after empirical real-vault validation of the A2 mechanism. The implementation was built, code-reviewer-APPROVED (0 CRITICAL/HIGH), and revert-verified (PR #3935), but validation revealed A2 is **not** the "inert additive groundwork" this requirement framed it as:

- `RDFSInferenceEngine` reads `exo__Class_superClass` on ANY subject and runs on the live plugin store + CLI. The symbolic edges A2 emits therefore **activate global materialization** of inferred ancestor `Instance_class` triples for the ~99.8% symbolic-form instances.
- Measured (vault-my): inferred triples 3,663 → 38,445; store 130,537 → 165,859 (**+27%**); SHACL violations 7 → 7 (**0 new**). vault-exodev: +22%, 0 new violations.
- So A2 is **safe** (0 new SHACL violations, correct RDFS) but its mechanism — **eager materialization → store grows** — is the opposite of the root-heal design principle ("store = uid only; resolve at the query boundary; keep the store minimal"; the generalized Candidate-E resolver).

**Decision:** fix Facet-1 (class-hierarchy walk) at query-time (generalize the E-bridge to walk the hierarchy at match-time), NOT via store materialization. That keeps the store minimal, unifies the resolution mechanism, and makes Candidate B coherent. A new requirement will cover the query-time hierarchy resolver when designed. PR #3935 closed; empirical method + finding recorded in RFC 78572fa9 + #3936.
