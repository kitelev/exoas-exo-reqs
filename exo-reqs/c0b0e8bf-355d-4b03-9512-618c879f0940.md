# req(exo): ExoSync makes pinned-but-not-conflicting paths visible

## Job Story

When a vault syncs push-only (a bot daemon), every incoming change the run defers is pinned, and only a pull clears those pins — so this copy falls behind the remote without anything saying so. I want `exosync quarantine list` and the sync/parity summaries to SHOW those pins and say what each one means, so a stale vault does not look like «No open conflicts ✅».

⛔ Corrected 2026-09-26 (review of kitelev/exocortex#4391, probed on the real engine): the first wording said a pin keeps a local edit out of push. It does not — push re-reads the remote diff for pinned paths and delivers a local change with remote == base at once.

## Statement (Gherkin)

```gherkin
Given a pinned path whose local copy equals the watermark base and whose remote changed or added it (a deferred incoming change)
When the quarantine resolver classifies the vault's pins
Then the path is reported as remote-pending, and it is not an open conflict

Given a pinned path whose remote equals the base and whose local copy changed
Then it is reported as local-withheld

Given a pinned path whose local copy equals the remote
Then it is reported as converged

Given a genuine 3-way conflict (base, local and remote all differ)
Then it stays in the open-conflict list and nowhere else

Given pins of a file-mode FileSpace
Then they are reported unclassified and never as conflicts

When `exosync quarantine list` runs on a vault that has such pins
Then after the conflicts (or «No open conflicts») it prints how many paths are pinned, by kind, names every local-withheld path, and names `exosync sync` as the remedy (a pull alone ships nothing)
And `--json` keeps its current shape (the open-conflict array)

When `exosync sync | push | pull` prints its Summary line and pins remain
Then the line ends with ", pinned <N> (incl. conflicts; see `exosync quarantine list`)"

When `exosync-parity` prints its summary line and quarantine-pinned discrepancies exist
Then the line carries ", <N> pinned" AFTER the parenthesised repo count — `(K repo(s) checked[, S skipped]), <N> pinned` — because the vault-quiescent-deliver daemon parses that parenthesis and must not see anything new inside it
```

## Non-goals

- Removing a pin without a pull. A pin on a deferred incoming change keeps the OLD watermark entry; unpinning it without a pull would adopt the new remote tree while the disk keeps the old copy, and the next push would send that old copy over the remote. The remedy is a pull (issue #4225 comment, 2026-09-26).
- Changing when the engine sets or clears pins.

## Why

Measured 2026-09-26 on this device: about 3 070 pins across 9 bot vaults, all but one of them local == base (a deferred incoming change or a remote add), and growing (vault-bot-messages-kitelev 360 on 09-12 → 602). ⛔ Corrected: the first wording named one live «withheld» path (vault-bot-tbank `cf879550…`); it is an open 3-way conflict (local ≠ base ≠ remote) that `quarantine list` already showed — the first measurement compared local with base only.
