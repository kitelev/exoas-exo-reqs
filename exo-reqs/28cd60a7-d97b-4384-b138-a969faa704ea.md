## Контекст

`exosync quarantine resolve` отбирает конфликт **конъюнктивным** предикатом — путь И `repoKey`
(`packages/cli/src/commands/exosync-quarantine.ts`, отбор на 210-215 на `35b45a53`), а при пустом
отборе печатал ОДНО предложение:

```
No open conflict for "<path>" — run `exosync quarantine list` to see the current set.
```

Три разных входа неразличимы, и для двух из них утверждение ЛОЖНО: `list` показывает конфликт и до,
и после. Эмпирика 2026-09-12 (`vault-my-full`, конфликт
`exoas-registry/registry/3c2fb27e-12a2-4793-a5dd-7a72c6e41def.md`) — **два промаха подряд**, оба
ровно на ФОРМЕ значений: путь должен быть repo-relative, а `repoKey` — с ветвью (`owner/repo#main`).

⛤ Цена различения — **ноль**: `conflicts` уже в руках строкой выше. Отсылка к `list` тут была
подписью, не выведенной из механизма (`decision-surface-must-derive-from-mechanism` §A9).

⛤ Образец формы уже в том же файле: ветка `matches.length > 1` перечисляет `  --repo <repoKey>`.
Паритет предъявляется ЦИТАТОЙ этой ветки и req `85630457`, а не «по аналогии».

- Три исхода отказа — три РАЗНЫХ текста, у каждого своя ось; rc=1 у всех трёх.
- ⛔ Ось на rc зовёт команду **без пайпа**: `return 1` под пайпом даёт rc последнего звена (Г3b).
- Ветка `matches.length > 1` не изменилась (регрессия прецедента #4206 / req `85630457`).

  `e85487a7` не снята; ось на существование файла И на байтовое равенство содержимому local.
