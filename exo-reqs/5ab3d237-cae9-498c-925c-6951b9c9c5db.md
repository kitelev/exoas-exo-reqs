## Job story

When the Telegram-bot engine (or any CLI consumer) runs `apply create-task-instance <prototype> --use-cache --json` against a large vault, I want the create-instance path to resolve its class label, its `exo__Asset_isDefinedBy` folder, the click-target's `targetRefProperty` second hop and a `templateRef` through an INDEX the process already holds in memory (the loaded triple store), so that a create costs the same order as `apply move-to-backlog --use-cache` (today 22–27 s vs 2.5–3 s on a quiet machine, 40–90 s vs 3 s under load — every "Начал X" turn of the assistant pays it) — without any lookup answering differently than the vault-wide frontmatter scan it replaces.

## Context

- Source: GitHub `kitelev/exocortex#4272` (mirror `ems__Task 007b7b48`). Builds on #4263 (req `42812747`, cache v2) and #4264 (req `cb707868`, `--use-cache` on apply — which explicitly leaves the create-path scans outside its scope).
- Mechanism today (origin/main `0547d51c`, verified by `git grep` + an fs-read counter preloaded into the built CLI): `apply.ts:394-460` wires `GroundingExecutor` with `createVaultFrontmatterClassLabelResolver(nodeFsAdapter)`, `createVaultFrontmatterRefToFolderResolver(nodeFsAdapter)`, `createVaultFrontmatterRefToFrontmatterResolver(nodeFsAdapter)` and a `templateLoader` on `nodeFsAdapter.findFileByUID`. Every one of them bottoms out in `NodeFsAdapter.findFilesByMetadata` (`NodeFsAdapter.ts:97-113`): `getMarkdownFiles()` (glob) + `getFileMetadata()` (read + tolerant YAML parse) for EVERY `.md` in the vault, per call. Measured on a clonefile copy of `vault-bot-kitelev` (16 664 files, cache hit): one `apply create-task-instance … --use-cache --json` = **183 317 markdown reads = 11 × 16 664** — `classRefMatchesAny` (inheritance-rule conditions) 8 scans, `resolveClassRefToUid` 1, `preResolveTargetRefs` 1, `resolveIsDefinedByFolder` 1; `apply create-execute-archive` = 150 008 reads (9 scans); `apply move-to-backlog` = 23 reads. Wall 25.2 s / user 15.0 s / sys 12.6 s / RSS 1.25 GB at LA ≈ 25 (absolute numbers inflated by load; the read count is the load-independent axis).
- The loader (`loadVaultTriples`: cache hit / delta / rebuild, or the full parse) already produces one `exo:Asset_uid` / `exo:Asset_label` / `exo:Asset_aliases` triple per frontmatter value of every converted file, keyed by the file's subject IRI (`obsidian://vault/<path>` ↔ `iriToVaultPath`). ⛔ Corrected 2026-09-19 (orchestrator review of WIP-1, CRITICAL): the earlier draft assumed the inferred layer lives in a named graph `exo:inferred` the index would not read — in the CLI it does NOT: `CacheManager.materializeTriples` returns explicit + inferred as ONE array and `apply.ts` `addAll`s it into the store's DEFAULT graph (21 186 inferred triples on vault-bot-kitelev, 4 534 of them inherited `exo:Asset_aliases`). The index is therefore built from the loader's EXPLICIT boundary (`explicitCount`) and never from the store. It is a CANDIDATE generator: each candidate's own frontmatter is re-read and judged by the scan's `matchesQuery`, so a false positive is impossible by construction; the loader also names the walked files it committed no triples for (`zeroTriplePaths`) and the adapter reads exactly those once. ⛤ Population rule (uniform since round-2 review N1, 2026-09-19): a file belongs to `zeroTriplePaths` iff the walk committed ZERO triples for it — invariant-skipped (#2997), FileSpace-excluded, or frontmatter-less alike; that is the cache entry's `triples: []` rule, and the full-parse path applies the SAME rule (`getAllFiles − committed`, via the converter's per-file commit observer) — so full parse, cache hit / delta and cold rebuild hand the index one and the same set, and the index population coincides with the scan's on every load path (locked by axis U11 across the three paths).
- Value-form seam (the reason a naive store lookup would NOT be identical — `sparql-iri-form-pre-verify` §A29): `NoteToRDFConverter.valueToRDFObject` emits a class-shaped string (`ems__Task`, `ems__EffortStatusBacklog`) as the class IRI `<https://exocortex.my/ontology/ems#Task>`, a `[[uid]]` wikilink as the target's file IRI, a number as `xsd:decimal`, an ISO date-time as `xsd:dateTime`. `NodeFsAdapter.matchesQuery` compares the RAW frontmatter value after `normalizeValue` (strip `"`, `'`, `[`, `]`, trim; arrays match on any element; no case folding). The index therefore keys each store object by the SAME normalisation applied to the value's frontmatter-side form: Literal → its lexical value; class IRI → `Namespace.fromTermIRI` → `prefix__LocalName`; vault file IRI → the target file's basename (the `[[uid]]` form — the only wikilink-form label/alias shape in the live corpus: 2 labels + 7 aliases, all bare `[[<uid>]]`).
- Determinism on duplicates: `findFilesByMetadata` returns matches in `getMarkdownFiles()` order and every consumer takes `[0]`. Measured (glob 11): that order was NOT stable — four calls in one process differed from index 36 of 16 665 — so `[0]` on a duplicated value (836 of 42 926 distinct values on the copy, none of them TBox-form labels / status-enum labels / ontology uids) was non-deterministic on main. `getMarkdownFiles()` now returns the list sorted by vault-relative path and the index orders an ambiguous result the same way: both sides deterministic and identical (a change of a behaviour that had no stable value to regress from — named in the PR).
- What the plugin does (UI/CLI parity, #3417): `ObsidianClassLabelResolver` reads `app.metadataCache` — an in-memory frontmatter index — and never scans files. The CLI equivalent of that cache IS the loaded triple store.

```gherkin

    And loadVaultTriples reports, next to the triples, the EXPLICIT boundary (`explicitCount` — the inferred layer
```

## Known limits (all measured on the vault-bot-kitelev copy: 16 664 files, 42 926 distinct key/value pairs compared scan↔index — 42 926 identical, 0 set or order divergences after the WIP-2 fixes)

Remaining false NEGATIVES, on query forms no resolver ever produces (0 such values on the corpus): the scan (glob on darwin: `nocase`) sees `*.MD` that the loader's `endsWith(".md")` does not; a label stored as an UNQUOTED date (js-yaml → `Date`) matches only its `String(Date)` rendering in the scan; a `[[uid|alias]]` label / alias matches only the literal text `uid|alias` in the scan; a `[[label]]` wikilink whose target the converter resolves CASE-INSENSITIVELY through its alias index (`[[ql]]` → the asset aliased `QL`) is keyed by the target's own names (`QL`, basename) while the scan's key is the literal `ql` (`normalizeValue` folds no case) — a lookup for `ql` finds no candidate (round-2 N4). Writes that bypass the adapter (the vault adapter's file moves inside a composite) are not folded into the index — the create path never resolves a just-moved asset. Follow-up on the loader's whole-asset skip itself (2 files on the copy, invisible to store / SPARQL / cache): kitelev/exocortex#4274.

## Non-goals (named with their numbers)

- Cache format v2 / delta semantics (#4263) and `--use-cache` / `--write-through` (#4264) are consumed, not changed.
- `create` (the bare verb) — its default path builds no triple store; its 5 scans (`create --dry-run` on the same copy: 83 333 reads = 5 × N, 9–10 s at LA ≈ 25: ClassResolverService, PropertyNameValidator, WikilinkValidator, EffortStatusResolver, ShapeLoader / co-location sibling scan) are a different mechanism (no in-process store to index) — out of scope here; the number is recorded for a follow-up.
- Inference re-materialisation: with `--use-cache` alone (the bot's mode) the create process loads `hit` and pays no inference; the whole-layer re-materialisation is paid by the NEXT process's delta (move-to-backlog 5.8 s with an `index`-built cache vs 3.1 s with `index --no-inference`, ≈ 2.7 s). Incremental materialisation for one added subject is engine work in `CacheManager` — out of scope; number recorded for a follow-up.
- `InMemoryTripleStore.addAll` from the cache (≈ 2.4 s per process) — process-per-call model, #4267.
- Semantics of `NodeFsAdapter.matchesQuery` are NOT changed: the index reproduces them; any input on which the two would differ is a defect of this requirement, not a "faster" behaviour.
