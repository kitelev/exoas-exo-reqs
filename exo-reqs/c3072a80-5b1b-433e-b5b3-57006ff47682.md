## Job Story

When Obsidian's index is cold on my phone, I want a **prototype** asset to show its **prototype**
command buttons — so that the button set I see is the correct one, not merely a non-empty one.

## Why this is not covered by req 7d00a60b

`7d00a60b` (Tier 2, shipped v16.235.0) covers the **rdf:type conveyor**: a class-position wikilink
resolves from disk, the symbolic type-IRI is emitted, and rdf:type-gated buttons render. It closed
the ZERO-buttons failure.

`classIsPrototype` is a **different visibility signal** on a **different path**. It is computed by
`resolveClassIsPrototype`, which does not go through the vault adapter at all — so Tier 2 does not
reach it, and `7d00a60b.covers` does not name it.

## The mechanism (measured, not inferred)

`resolveClassIsPrototype` reads the cache **twice**, and on a cold cache both reads fail:

1. `metadataCache.getFirstLinkpathDest(normalized, "")` -> null -> `continue`
2. `metadataCache.getFileCache(classFile).frontmatter` -> null -> `continue`

Falling through both yields `false`. Fail-safe, so the surface degrades rather than breaks: the
asset shows the **ordinary** button set instead of the prototype one.

## Evidence that the property is unspecified today

Mutant on `1bd848a6`: both copies of `resolveClassIsPrototype` reduced to `return false`.
Result: **18 suites / 275 tests, all green**. Nothing in the corpus asserts this property. The two
existing mentions of `classIsPrototype` in tests are fixture values (`classIsPrototype: false`),
not assertions about resolution.

## Scope — and where the measurement CONTRADICTS issue #4200

Issue #4200 proposed (a) de-duplicating the two copies and (b) routing both through the adapter.
Measurement refutes both halves for the second copy:

| call site | enclosing method | verdict |
|---|---|---|
| `ButtonGroupsBuilder:161` | `public async build(file)` | async context -> **full fix possible** |
| `CommandManager:124` | `private getContext(file)`, called from Obsidian `checkCallback` | **sync by platform contract** |

`checkCallback` must return a boolean synchronously — that is Obsidian's API, not our choice.
Therefore:

- **De-duplication is contra-indicated.** After this change the two copies have *different*
  contracts (one async, one sync); merging them would break the sync one.
- **A half-fix on `CommandManager` buys nothing.** Routing only step 1 through the adapter still
  dies on step 2 (`getFileCache` -> null -> `continue` -> `false`). There is no input on which
  before/after differ, so such a change would be inert — and an inert change is worse than none,
  because it looks like coverage.

Scope of this requirement is therefore **`ButtonGroupsBuilder` only** — the surface the user
actually looks at.

## Non-goals

- `CommandManager.resolveClassIsPrototype` (command palette). Blocked by the sync `checkCallback`
  contract. A future option, if it ever proves worth it: an asynchronously warmed prototype
  registry read synchronously — same shape as the uuid registry from `7d00a60b`, but populated in
  the background. Not attempted here; no measured pain justifies it yet.
- The remaining ~30 direct `metadataCache` call sites in the plugin (labels, links, properties).
  Cold-cache degradation there is cosmetic.

## Acceptance

Given a cold `metadataCache` and an asset whose class is a prototype,
when the body layout renders its command buttons,
then `classIsPrototype` is `true` — the class file is located through the vault adapter and its
frontmatter is read with the existing disk fallback.

Reverting either half (adapter routing, or disk-fallback frontmatter) must redden the axis.
