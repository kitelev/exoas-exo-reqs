# req(exo): ExoSync pull fetches changed blobs with bounded concurrency + visible progress (RFC 6a1a6518 / C)

> Source: RFC `6a1a6518-613c-447c-a75b-9d30f4ae3008` (Approved) — ExoSync perf & rate-limit revision. This requirement is **Phase 2 / C only** (concurrent pull + visible progress). Phase 1 / A (Retry-After) shipped as v16.195.0 (PR #3977), so the "solid backoff before concurrency" precondition is satisfied.
>
> **Why it matters:** a big remote delta pulls each changed blob sequentially (~0.4s each) → a minute+ of wall-clock after one "pulling remote tree…" line and nothing after → the sync **looks hung**. Bounded concurrency cuts the wall-clock; a visible `fetching-blobs done/total` tick removes the "hung" perception even before raw speed.
>
> **⛔ Determinism constraint:** the concurrent fetch MUST write results back by their `changed` index, NEVER in completion order — the consumer `matchLocalVsRemote` is order-sensitive for rename-pairs / duplicate-uid groups, so a completion-order array would silently change the pull outcome.
>
> **⛔ Atomicity constraint:** one failing blob must fail-fast the WHOLE pull with **zero partial apply** — a half-applied bulk pull is worse than a consistent status-quo.

## Job Story

When ExoSync pulls a big remote delta, I want the changed blobs fetched a few at a time (not one-by-one) with a visible growing `fetching-blobs done/total`, so the pull finishes several times faster and never looks hung — while the applied result stays byte-identical to the old sequential pull and a single blob failure aborts the whole pull cleanly instead of half-applying it.

## Statement (Gherkin)

Revert-verify axes (record in the PR body at implementation time):
- **Indexed write-back (determinism):** change the pool to `push` results in completion order → with out-of-order blob completion the captured `changes[]` reorders (reverse of `changed`) → the "in `changed` order" assertion **RED**; restore indexed write-back → **GREEN**.
- **Fail-fast (atomicity):** make the pool swallow a per-blob error and continue → collectRemoteChanges returns a partial `changes[]` → the surviving files get applied to disk → the "zero partial apply" assertion **RED**; restore fail-fast throw → **GREEN**.
- **Bounded concurrency (parallelism):** revert the pool to the sequential `for` loop → peak in-flight blob fetches = 1 → the "peak reaches the cap" assertion **RED**; restore the pool → **GREEN**.
- Progress-tick + wall-clock (local, `expectFasterThan` — skipped under CI per the perf-flake rule) + no-regression assertions GREEN both ways (non-vacuity + no-regression).

## Design notes

- **Bounded worker pool, not `Promise.all(changed.map(...))`.** A pre-sized `changeResults` array of length `changed.length`; a fixed number of workers (`BLOB_FETCH_CONCURRENCY = 6`, clamped to `changed.length`) each pull the next index atomically (single-threaded JS — `nextIdx++` is atomic), fetch its blob, and write the result at `changeResults[i]`. `await Promise.all(workers)` then, if a captured `firstError` is set, rethrow it. This is fail-fast (workers stop pulling once `firstError` is set) with **no unhandled rejection** (each worker catches its own error into `firstError`).
- **Cap 4-6** — ~20x under GitHub's 100-concurrent ceiling; a fixed module const (not a public dep — the RFC fixes it at 4-6). Safe only because Phase 1 / A shipped solid Retry-After backoff + global per-sync budget.
- **Progress tick unchanged in semantics:** still `>= BLOB_PROGRESS_MIN_TOTAL` gates it, still every `BLOB_PROGRESS_STEP` completions, `done` = a monotonic completion counter, final-tick suppressed by `done < total`. Under concurrency the counter still hits each multiple exactly once (atomic increments).
- **Metric = real Date.now(), not SyncPhaseTimer** — the timer sums per-call REST durations, which do not drop under concurrency. The speed axis is measured with a real wall-clock and asserted via the CI-skipping `expectFasterThan` helper (a hard wall-clock threshold would flake the CI gate); the CI-hard, deterministic proof of concurrency is the peak-in-flight assertion.
- **Out of scope:** the push path, the `buildWatermarkFiles` merge-base blob fetch (rare uid backfill), and RFC parts A/D/B/E/secret-scan.
