# req(exo): the homoiconic plugin-settings live-mirror is a fully bidirectional feature

> **Supersedes `5c08b7ad`** (M2.3 read-only transitional deprecation). Andrey
> reversed that decision 2026-07-27 («наоборот, полноценно внедрить эту фичу»):
> the live-mirror is a real bidirectional feature again, not a deprecated
> read-only watcher scheduled for removal.

## Job Story

When I enable homoiconic plugin settings (`settingsHomoiconizationEnabled`), I
want my settings and their vault `exo__Setting` assets to stay in continuous
two-way sync on this device — a UI toggle is auto-written into its vault asset
(so it's durable, versionable, and syncable как первоклассные vault-данные),
AND an asset edit / a cross-device synced change still flows back into the UI —
so my settings ARE homoiconic vault data, edited from either side, without me
having to remember to run «Export settings».

## Statement (Gherkin)

```gherkin
Given homoiconic settings are enabled (settingsHomoiconizationEnabled = true) so the store is constructed with outboundWriteEnabled true
When I change a registry setting in the UI (saveSettings → pushChangedFields)
Then the change is auto-written (trailing-debounced) into that field's exo__Setting vault asset
And the written asset value equals the new UI value

Given the bidirectional store is active
When a setting asset changes (a vault edit or a synced cross-device change arrives)
Then the inbound watcher still applies it to the UI (asset→UI two-way sync intact)

Given homoiconic settings are DISABLED (settingsHomoiconizationEnabled = false, the default)
When I change a setting in the UI
Then no vault asset is created or written (the whole D2 layer is skipped — default users are unaffected)

Given the bidirectional store
When the plugin's own debounced write lands and its own metadataCache echo fires
Then the echo is swallowed (a stale intermediate read never rolls a newer UI action back)
```

## Notes

- **Reverses an RFC decision.** RFC f402002b (M2.3 §6 R2) deprecated the
  live-mirror to read-only in favour of an explicit Export/Import engine, and
  its alternative D («two mechanisms») was rejected. This requirement overrides
  both per Andrey's 2026-07-27 directive: the live-mirror is fully bidirectional
  again and coexists with «Export settings».
- **Elevated-risk path** (CLAUDE.md auto-merge discipline for `VaultSettings*` —
  settings-corruption sensitive): code-reviewer + advisor round-2 before a
  manual squash-merge (no `--auto`).
- The machinery is not new/buggy — it's the same F1-F12-disciplined outbound
  path that shipped and worked before M2.3 gated it off; "implement" = enable +
  de-deprecate + prove end-to-end + document.
