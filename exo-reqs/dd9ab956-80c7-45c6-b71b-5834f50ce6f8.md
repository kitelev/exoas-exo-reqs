# req(exo): `create --validate` — opt-in pre-write SHACL-lite conformance gate (closes the last hook-gap of the CLI creation path)

## Job Story

When I create a vault asset through the CLI (`exocortex-cli create`, the dogfood-canonical creation path), I want an opt-in `--validate` flag that runs the SAME SHACL-lite conformance check the Write-path PreToolUse hook (`validate-asset.sh` → `validate schema --shapes-mode`) runs, **before** the file is written and **scoped to the new asset** — so that the CLI path can offer the same structural guarantee as the Write path instead of silently landing a non-conformant asset that only a later full-vault `validate schema --shapes-mode` would catch.

**The gap this closes.** A CLI `create` runs through Bash, so the PreToolUse Write/Edit hooks never fire. `create` already re-implements three of the four guarantees those hooks give — co-location by `exo__Asset_isDefinedBy` (#3520/#3934), dangling-wikilink VALUE rejection (`WikilinkValidator`), and unknown property NAME rejection (req `40a9a81b`, RFC 430e84f1 P1). The fourth — **SHACL-lite conformance** (`sh:minCount` required properties, `sh:class` range, `sh:datatype`, cardinality) — has no CLI counterpart: the `ShapeRegistry` loaded in `create.ts` is used only for cardinality-aware property *serialization* (#3099/#3179), never for validation. `--validate` closes it.

## Acceptance (Gherkin — executable spec)

```gherkin
Feature: exocortex-cli create --validate (opt-in pre-write SHACL-lite gate)

  Background:
    Given a mounted vault whose TBox declares SHACL-lite shapes
      And the vault contains at least one PRE-EXISTING asset that already violates a shape

  Scenario: default OFF — create is byte-identical without the flag
    When I run `create` WITHOUT `--validate` for a candidate that violates a shape
    Then the asset IS created (exit 0)
      And no SHACL validation is performed
      And stdout is the unchanged `{uuid,path,label}` JSON line

  Scenario: --validate + conformant candidate → asset created
    When I run `create --validate` for a candidate that conforms to the shapes
    Then the command exits 0
      And the asset file exists on disk
      And stdout is the unchanged `{uuid,path,label}` JSON line

  Scenario: --validate + non-conformant candidate → PRE-WRITE refusal (no file written)
    When I run `create --validate` for a candidate that violates a shape
    Then the command exits with a non-zero code
      And NO asset file is created (the gate runs BEFORE the write)
      And the error names the violated constraint and the offending property path

  Scenario: only the CANDIDATE's own violations gate
    When I run `create --validate` for a conformant candidate
     And the vault still contains the pre-existing violating asset
    Then the command exits 0
      (violations whose focus node is some OTHER asset never block a create)

  Scenario: warnings are surfaced but do not gate (open-world parity, issue #3488)
    When `--validate` produces only `sh:Warning` results for the candidate
      (an unresolvable / cross-vault / symbolic reference)
    Then the command exits 0 and the asset is created
      And the warning is reported on stderr

  Scenario: --validate composes with --dry-run
    When I run `create --dry-run --validate` for a non-conformant candidate
    Then the command exits with a non-zero code and writes no file
    And when the candidate conforms, `--dry-run --validate` exits 0 and still writes no file

  Scenario: machine-readable stdout contract is preserved
    When `create --validate` succeeds
    Then every validation message is written to stderr
      And stdout remains exactly one `{uuid,path,label}` JSON document

  Scenario: the gate is opt-in only (no implicit default-on)
    Then `create` without `--validate` never loads the vault for SHACL validation
      (the opt-in keeps the default create fast and byte-identical)
```

## Revert-verify

Production-shape CLI integration test driving the real `createCommand()` over a temp fixture vault that carries (a) real SHACL-lite shapes, (b) a PRE-EXISTING violating asset, (c) a conformant and a non-conformant candidate.

Type-preserving Edit-break of the `--validate` gate (skip the conformance check) makes the **non-conformant** scenarios pass the create (exit 0 + file on disk) → those assertions go RED. The **negative controls** — default-OFF byte-identical, conformant-candidate-passes, pre-existing-other-asset-violation-does-not-block — stay GREEN in both states, proving non-vacuity (the delta is exactly the candidate-scoped gate, not a blanket refusal). Restoring makes all GREEN.

## Design notes (verified against origin/main before writing)

- **Reuse, do not re-implement.** The gate calls the SAME exported pipeline `validate schema --shapes-mode` uses — `runShapesValidation` (graph-loaded `ShapeLoader.loadFromRDFGraph` + `TripleClassHierarchy`) + `applyLegacyExceptionFilter` + a focus-node filter — so CLI-`create` conformance is *by construction* identical to the hook's verdict, and a shapes-semantics change lands in both at once.
- **Pre-write, not write-then-rollback.** `GenericAssetCreationService.buildAsset(config)` already produces the exact bytes a real write would produce (the `--dry-run` path, `dry-run-preview-not-real-output`); the candidate is converted in-memory (`NoteToRDFConverter.convertNoteFromFrontmatter` over a synthetic `IFile`) and merged with the vault triples. Nothing is written unless the candidate conforms — strictly better than the hook, which needs a temp file in the vault.
- **Candidate-scoped by focus node.** Without the focus filter every create would fail on any vault that has pre-existing violations (vault-tbank has 7) — this is the load-bearing constraint, mirrored from the hook's temp-file filter (`filterReportToStagedFocusNodes`, #3245).

## Out of scope

- Making the gate default-ON (deliberately opt-in: a full `convertVault` per create is a real cost; the task is explicitly «опц. inline-SHACL»).
- Extending the gate to `set-property` / `apply` mutations (siblings; separate requirements).
- A `--no-validate` escape hatch (meaningless for an opt-in flag).
