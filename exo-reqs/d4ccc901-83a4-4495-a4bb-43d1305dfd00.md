`apply-profile` today knows two mount states: an AssetSpace is either **materialized** (its derived folder exists) or **absent**. Leaving the effective set therefore has exactly one outcome — the folder is deleted, and returning costs a full network re-materialisation (measured ≈2.5 s and 0.7 MB per AssetSpace, against **23 ms and 0 bytes** for a local move).

This requirement introduces the third state — **parked**: on the device, but not active. It is the state a soft-edge AssetSpace enters when a profile stops including it.

**Why the kind of the edge decides.** `exo__AssetSpace_dependsOnKind` (req `18ecf16f`) already answers "what does depending on this AssetSpace mean". A **reference** (soft) edge supplies content — unmounting it costs reachability, so keeping the bytes on the device is a pure win. A **tbox** (hard) edge supplies class and command definitions — a copy that is on disk but neither indexed nor enumerated by ExoSync is exactly the silent half-state that makes assets lose their type without any signal. Destroying it stays loud. Every unrecognised kind resolves to `tbox`, so the direction that hides files requires positive evidence.

**Why the plan must name the two differently.** The confirm-gate is the last thing the user reads before a destructive mutation. A plan that reports "N files to remove" about a park is a false statement made at the exact moment consent is given — and it is unfalsifiable afterwards, because the files are still there. Parked AssetSpaces are therefore excluded from `filesToDestroy` and `assetSpacesBeingTornDown` and carried in their own arrays.

**Why four sides and not two.** `ApplyPlan` is not an internal type — it is the confirm-gate contract, exported from the core package's public surface, with **two renderers** (`HeadlessConfirmGate` on the CLI, `ModalConfirmGate` in the plugin) and **two producers** (the CLI apply service, the plugin apply manager). A field added to the contract and rendered by neither gate leaves the approval card saying "N files to remove" while a park is what actually happens — the decision surface would stop deriving from the mechanism it describes. Each renderer therefore carries its own executable check; an existing renderer harness asserting only today's strings stays green when a new field is silently dropped, so the axis must be added, not assumed.

**Why `reconcileToLocal` is named explicitly.** It is the single production caller of `resolveEffectiveSet`, and it decides both directions: a parked AssetSpace must not be reported as `extra` (that would schedule a deletion for files the user deliberately kept) and must not be reported as `missing` (that would re-pull over the network something already on the device).

## Job Story
When I park an AssetSpace to take it off this device, I want the plan to tell me it will be *parked* rather than *removed*, and I want returning to it to be a local move rather than a re-download — so that the cheap, reversible operation is not disguised as the expensive, destructive one.

```gherkin
Feature: apply-profile distinguishes active / parked / absent

  Background:
    Given an AssetSpace whose mount path is DERIVED as assetspaces/<owner>/<repo>
    And its parked location is DERIVED as .exocortex/parked/<owner>/<repo>

  Scenario: a soft-edge AssetSpace leaving the effective set is parked, not destroyed
    Given the AssetSpace is materialized
    And its exo__AssetSpace_dependsOnKind is exo__DependencyKindReference
    When apply-profile computes a plan for a profile that omits it
    Then the transition is park
    And it appears in assetSpacesBeingParked
    And it appears in NEITHER assetSpacesBeingTornDown NOR filesToDestroy

  Scenario: a hard-edge AssetSpace leaving the effective set is destroyed
    Given the AssetSpace is materialized
    And its exo__AssetSpace_dependsOnKind is exo__DependencyKindTBox
    When apply-profile computes a plan for a profile that omits it
    Then the transition is destroy
    And it appears in assetSpacesBeingTornDown

  Scenario: an unrecognised dependency kind is destroyed, not parked
    Given the AssetSpace is materialized and its dependsOnKind is absent or unreadable
    When apply-profile computes a plan for a profile that omits it
    Then the transition is destroy

  Scenario: a parked AssetSpace re-entering the effective set is unparked, not re-pulled
    Given the AssetSpace is absent from assetspaces/ but present under .exocortex/parked/
    When apply-profile computes a plan for a profile that includes it
    Then the transition is unpark
    And no network materialisation is scheduled for it

  Scenario: an absent AssetSpace entering the effective set is materialized over the network
    Given the AssetSpace is present in neither location
    When apply-profile computes a plan for a profile that includes it
    Then the transition is materialize

  Scenario: a parked AssetSpace outside the effective set is left alone
    Given the AssetSpace is parked
    When apply-profile computes a plan for a profile that omits it
    Then the transition is none
    And no deletion is computed for it

  Scenario: unparking lands in the same state as materialising
    Given a parked AssetSpace re-enters the effective set
    When apply-profile executes
    Then its mount folder exists at the derived path
    And its .gitmodules entry is present
    And the parked copy no longer exists

  Scenario: reconcileToLocal never schedules a parked AssetSpace for removal
    Given a parked AssetSpace that the active profile does not include
    When reconcileToLocal diffs expected against materialized
    Then the AssetSpace is not reported as extra
    And no divergence is raised on its account
```

## Notes

- `.exocortex/parked/` is chosen over `.obsidian/plugins/exocortex/` because BRAT overwrites the latter on every plugin update.
- The parked root is derived, never stored: `parkedPathFor(folderName)` strips the `assetspaces/` prefix and re-roots under `.exocortex/parked/`. Tests must not hand-write the parked path, or a dead deriver would keep them green.
- Parking is already proven inert for ExoSync by req `4eca4900` (both collectors gate enumeration on the existence of the derived mount path). This requirement depends on that property and does not restate it; it adds the `reconcileToLocal` half, which that requirement explicitly left out of scope.
- The TS-floor and catalog-keep guards run before this classification, so `exoas-exo` and `exoas-registry` can never reach a park or destroy transition at all.
- Binding classes: `unit` is carried by the pure transition table and the two apply paths; `integration` is carried by the CLI end-to-end check that parks and unparks against a real temp vault on the real node filesystem.
