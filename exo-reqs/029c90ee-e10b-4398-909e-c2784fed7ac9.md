An AssetSpace repo whose branch head points at the **canonical git empty tree**
(`4b825dc642cb6eb9a060e54bf8d69288fbee4904`) is a healthy, reachable repo that simply
has no files yet. GitHub's `GET /repos/:o/:r/git/trees/4b825dc6…` answers **404** for
that SHA even when the repo exists, the branch resolves and the PAT allowlists it —
the 404 is a property of the **request**, not of reachability.

`ParityValidator` today reads that 404 through `isNotFoundError` and reports
`status: "error"` plus the warning *"repo unreachable (HTTP 404): dead AssetSpace
pointer, or the fine-grained PAT does not allowlist this repo — skipped"*. Both named
causes are false, and the operator is sent to check a dead pointer and a token scope
that are both fine. Worse, `ParityValidator` skips discrepancy counting for every
non-`checked` repo, so local files that ought to surface as `pending-local-add`
stay invisible — parity goes quiet exactly when it should be loudest.

This requirement makes the distinction **executable**: an empty tree is an empty
file list, never an error.

**Why the fix lands in `getTree`, not in a new parity status.** The originating
issue offered either shape — a dedicated status or `checked` with zero files. The
second is chosen because `ParityValidator` gates discrepancy counting on
`repo.status !== "checked"`; a new status would silence the false alarm while
leaving local files uncounted, satisfying the "must not go quiet about emptiness"
constraint in name only. `getTree` returning an empty list is also correct at the
lowest layer — an empty tree contains zero blobs by definition — so every one of
its 14 call-sites (sync engine, quarantine resolver, parity) inherits the fix
instead of parity alone. The call is short-circuited before the transport, so no
network round-trip is spent on a request whose answer is known.

## Job Story
When an AssetSpace repo is created but not yet populated, I want ExoSync parity to
count my local files as pending additions rather than declare the repo unreachable,
so that a first push is proposed instead of a false PAT/pointer alarm.

```gherkin
Feature: an empty remote tree is an empty file list, not an unreachable repo

  Background:
    Given an AssetSpace repo that exists and whose branch resolves
    And the PAT allowlists that repo

  Scenario: branch head points at the canonical empty tree
    Given the branch head commit references tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
    When getTree is asked for that tree SHA
    Then it returns an empty list of blob entries
    And no HTTP request is issued for that tree

  Scenario: parity classifies an empty repo as checked, not error
    Given the same repo and one local markdown asset under its mount
    When ParityValidator runs a round
    Then the repo status is "checked"
    And no warning mentions a dead pointer or a fine-grained PAT
    And the local asset is counted as a pending local addition

  Scenario: negative control — a genuinely unreachable repo still errors
    Given a repo whose branch does not resolve
    When ParityValidator runs a round
    Then the repo status is "error"
    And the warning still names the dead-pointer and PAT-allowlist causes
```

## Blast radius
`getTree` has 14 call-sites: `SyncEngine` (12), `ParityValidator` (2),
`QuarantineResolver` (2), plus the public re-export in `packages/core/src/index.ts`.
No `EMPTY_TREE` constant exists anywhere under `packages/` today, so the SHA is
introduced once, in `githubRepoReader.ts`, and consumed by name.

## Verification
Both halves are mandatory. A test proving only that the false alarm stopped is
indistinguishable from a test proving detection stopped: the negative control
(a repo that really is unreachable still reports `error` with the unchanged
warning) is what separates them.
