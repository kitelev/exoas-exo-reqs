# req(exo): audit ontology-membership (cohesion-side KSD ArchUnit ratchet)

> **Origin:** KSD project `531dd440` (Concept Audit & Redistribution), Phase 2
> node `bfa896a5`, RFC `2a41ef6e` v3 §Разрешения (review-panel resolutions
> F5–F10). Phase 1 is complete — the ~2340-concept redistribution is clean and
> remote-verified in all 3 vaults — so the ratchet now locks a clean state
> (on dirty data the detector would red; the gate is passed).

## Job Story

When I (or a future migration) accidentally file an asset of the wrong class
under a concept ontology — or drop a member's class, or move a non-concept asset
into a cleaned concept folder — I want CI to flag it as a membership violation
against that ontology's declared `exo__Ontology_admits` allow-list, so the
Phase-1 redistribution stays clean and the coupling-side (`audit
ontology-imports`) has its cohesion complement (the two together = the ArchUnit
fitness-function pair).

## Statement (Gherkin)

```gherkin
Given an ontology O declares exo__Ontology_admits = a non-empty allow-list of exo__Class values
And an asset A whose exo__Asset_isDefinedBy resolves to O
When I run `exocortex audit ontology-membership --vault <path>`
Then A is reported as a membership VIOLATION iff none of A's exo__Instance_class classes,
     nor any of their exo__Class_superClass ancestors, resolves to a class in O's admits allow-list
And the audit exits 1 when there is ≥1 violation, exit 0 when clean
And the skip totals (no-instance-class / unresolvable-class / no-admits ontologies) are always printed

Given an ontology O declares NO exo__Ontology_admits
When I run the membership audit
Then every asset mapped to O is SKIPPED (fail-open — no allow-list means no constraint; audit-first)
And O's members never appear as violations

Given an ontology O admits exo__Property (38277bfa)
And an asset A whose exo__Instance_class is exo__ObjectProperty (9a1cf31c, a subclass of exo__Property)
When I run the membership audit
Then A is ADMITTED via the superClass walk (exo__ObjectProperty ⊑ exo__Property), NOT a violation
     (F9: subsumption exists for TBox metaclass-mixing)

Given a concept ontology O admits exo__Ontology (829b9b3b) in its allow-list (F10)
And O's own anchor asset is an exo__Ontology instance whose exo__Asset_isDefinedBy is O itself
When I run the membership audit
Then O's anchor is admitted as a legitimate self-member, NOT a false-positive against its own gate

Given a concept ontology O admits [concept__Concept, exo__Ontology]
And a member M of O whose exo__Instance_class is ems__Task (neither admitted nor a subclass of an admitted class)
When I run the membership audit
Then M is reported as exactly one membership violation (the ratchet detects the regression)
```
