A parked AssetSpace is **frozen at the moment it was parked**. The remote keeps moving; an active mount converges on every sync, a parked one converges **never** — and today nothing tells anyone. `exosync-parity`, the one explicit "am I in sync?" probe, skips a parked AssetSpace entirely: its collector commits a candidate only when the DERIVED mount path exists (proven by req `4eca4900`), so a parked repo produces no spec, no line, and no signal. Staleness is therefore not merely unreported — it is **unbounded and invisible**.

This requirement supplies exactly the missing half: **visibility**. It deliberately introduces no new stored state. The version and the content hashes already exist and are stronger than any hand-declared field — `exosync-watermarks.local.json` holds, per repo, `lastSyncedSha` (the version), `rootTreeSha` (the tree hash) and `files[].blobSha` (per-file hashes), all derived and maintained by git. A hand-authored "version" property would be a signature next to the mechanism and would drift from it.

**Why one refs call and not a commit count.** `GET git/refs/heads/{branch}` returns the head SHA and nothing else — no date, no distance. Reporting "N commits behind" would need a second, different call per repo. The cost clause caps this check at ONE refs call per parked repo, so the verdict is the boolean fact ("this parked copy is behind, synced at `abc1234`, remote is now `def5678`") rather than a distance. That fact is what was missing; the distance is a separate, priced decision. Issue #3975 (ETag / `If-None-Match` on head reads) is orthogonal and complementary — it would make this same call cheaper, never redundant.

**Why `current` must be structurally unreachable on failure.** An empty or failed response is not evidence of freshness. The verdict is computed so that `current` requires BOTH a watermark AND a successful head read; every other path — transport error, missing watermark, malformed response — resolves to `unknown`. This is a property of the control flow, not a defensive branch that a later edit could invert.

## Job Story
When I park an AssetSpace to take it off this device, I want the sync probe to tell me how far that frozen copy has drifted from the remote, so that "kept on this device" never quietly becomes "kept on this device, months out of date".

```gherkin
Feature: a parked AssetSpace reports its staleness

  Background:
    Given an AssetSpace declaration carrying exo__AssetSpace_source = https://github.com/<owner>/<repo>
    And its mount path is DERIVED by AssetSpacePathDeriver as assetspaces/<owner>/<repo>

  Scenario: a parked AssetSpace whose remote moved reports behind
    Given the derived mount path does not exist but .exocortex/parked/<owner>/<repo> does
    And the device watermark for that repo records lastSyncedSha "aaaaaaa"
    And the remote head of that branch is "bbbbbbb"
    When the parked staleness check runs
    Then the verdict for that repo is behind
    And it reports both the last synced SHA and the remote head SHA
    And exactly ONE git/refs/heads call was made for that repo

  Scenario: a parked AssetSpace whose remote did not move reports current
    Given the same parked shape
    And the device watermark records lastSyncedSha "aaaaaaa"
    And the remote head of that branch is "aaaaaaa"
    When the parked staleness check runs
    Then the verdict for that repo is current

  Scenario: negative control — an ACTIVE AssetSpace reports no staleness verdict
    Given the derived mount path assetspaces/<owner>/<repo> DOES exist
    When the vault is enumerated
    Then that repo is a parity spec and is absent from the parked list
    And no staleness verdict is produced for it
    And no additional git/refs/heads call is made on its behalf

  Scenario: canary — an unreachable remote reports unknown, never current
    Given a parked AssetSpace with a watermark recording lastSyncedSha "aaaaaaa"
    And the git/refs/heads call fails
    When the parked staleness check runs
    Then the verdict for that repo is unknown
    And the verdict is not current

  Scenario: a parked AssetSpace never synced on this device reports unknown
    Given a parked AssetSpace with no watermark record on this device
    When the parked staleness check runs
    Then the verdict for that repo is unknown
    And no git/refs/heads call is made for that repo
```

## Notes

- **Cost.** At most one `getHeadSha` per parked repo per invocation, and zero on behalf of an active repo. The refs primitive and its budget already exist in the system: `getHeadSha` is a public core export (`packages/core/src/index.ts`), and `SyncPhaseTimer` already carries a dedicated `restHead` bucket for it. The check is driven by an explicit `exosync-parity` invocation, so it cannot be attached to a `metadataCache` event — the failure class that produced an indexing storm and iPhone Jetsam is unreachable here by construction.
- **Enumeration is additive.** The parked list is accumulated alongside the existing specs; `SpaceSpecAccumulator.commit()` is still called only for a materialized mount, so `collectVaultSpecs().specs` — and therefore the parity round, its `ok`/`vacuous` flags and the process exit code — stay byte-identical. Staleness is informational: it never changes the parity exit contract.
- **`parkedPathFor` throws on a malformed mount folder** (a deliberate fail-loud). Enumeration wraps that call so a legacy flat-path declaration degrades to "not parked" rather than aborting the whole probe.
- **Live population today is zero.** No vault on this device currently holds a parked mount (`.exocortex/parked/` is absent everywhere), so the parked branch is exercised by the tests and by future parking, not by present data. This is stated explicitly so a later reader does not mistake an empty section for a dead feature; parking itself is a shipped capability (req `d4ccc901`).
- **Binding classes:** `unit` is carried by the core verdict check (the transport and the watermark store are the injected seams, so both the failure branch and the call-count cap are directly observable); `integration` is carried by the CLI enumeration check, which runs the real exported `collectVaultSpecs` over a real temp vault on the real node fs.
- **Out of scope, deliberately:** the commit *distance* (needs a second, differently-priced call), a plugin-side surface (the core module is platform-free precisely so a plugin surface can consume it later without duplication), and any change to what parking or `apply-profile` themselves do. `exosync-parity` is a CLI-only diagnostic with no plugin counterpart, so adding a section to it introduces no Desktop↔Mobile command asymmetry.
