# req(exo): apply set-ontology writes exo__Asset_isDefinedBy as a reference, so the graph gets the asset → ontology edge

## Job Story

When I move an asset to another ontology with `set-ontology`, I want its `exo__Asset_isDefinedBy` stored as a reference to the picked ontology — the same form every other asset carries — so the graph holds a real asset → ontology edge that queries, precondition hops and audits can follow, not a string that only looks like one.

## Statement (Gherkin)

```gherkin
Given an asset in ontology A's folder with exo__Asset_isDefinedBy pointing at A
And an ontology B in its own folder
When I run `apply set-ontology <asset> --input '{"ontology":"<B uid>"}' --yes`
Then the asset's frontmatter holds exo__Asset_isDefinedBy: "[[<B uid>]]" (a wikilink, not a bare uid)
And in the graph `?asset exo:Asset_isDefinedBy ?o` binds ?o to B's file IRI (obsidian://vault/…/<B uid>.md), not to a literal
And the asset is relocated into B's folder (unchanged behaviour)
When the input is given already wrapped (`[[<B uid>]]` or `[[<B uid>|alias]]`)
Then the same single "[[<B uid>]]" reference is written (the targetValueRef normalisation of req b06129dc)
```

## Mechanism

The composite's first step `1585f1cb` («Re-anchor isDefinedBy to the picked ontology») used `exocmd__Grounding_targetValueSubstitution: $input.ontology`, which by construction writes the input as a literal value. The dynamic reference channel already exists — `targetValueRef: $input.<key>` (req b06129dc, used by set-parent `18f12de2` and set-blocker `2b0b381d`): the executor wraps the input as `"[[<ref>]]"` after normalising it. The fix is vault data only: `targetValueSubstitution` → `targetValueRef` on that step (the four value fields are mutually exclusive). No engine code changes.
