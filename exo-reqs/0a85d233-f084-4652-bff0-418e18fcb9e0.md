# req(exo): the Properties block renders a property key by its short name, and prefixes `ClassName.` only where two keys of the same block would read the same

## Job Story

When I read a note's Properties block, I want every Exocortex property key to read as a short
name (`status`, `area`, `genus`) instead of the raw predicate (`ems__Effort_status`), because the
short name is the convention I chose for `exo__Property_displayName` — and when two keys of the
same note would read the same (`status` of `ems__Effort` and `status` of `ems__Task`), I want them
told apart as `Effort.status` / `Task.status`, so a bare short name is never ambiguous
(issue #4568).

## Mechanism (read on `origin/main` `ec57bcda`)

The only renderer of property keys is `PropertiesLabelPatch`
(`packages/obsidian-plugin/src/presentation/properties/PropertiesLabelPatch.ts`, RFC-030, on by
default via `enablePropertiesLabelPatch`). It indexes property-definition assets (class descends
from `exo__Property` via `exo__Class_superClass`) by `exo__Asset_label` and renders each key of a
Properties block on its own: `exo__Property_displayName`, else the raw `exo__Asset_label`. It
never looks at the other keys of the block, so equal display names render identically.

Measured on this machine 2026-10-17 (port of the patch's own index logic over the vault files):

| vault | property defs | with displayName | displayName == label local part | displayName values shared by >1 def |
|---|---|---|---|---|
| vault-exodev | 822 | 509 | 358 | 63 (`order` ×6, `year` ×6, `status` ×4 …) |
| vault-tbank | 581 | 380 | 262 | 43 (`year` ×8, `description` ×5 …) |

So the short-name convention is already the majority, and its ambiguity is already live.

## Statement (Gherkin)

```gherkin
Given a property-definition asset indexed by its label, e.g. `ems__Effort_area`
When a Properties block shows that key and no other key of the SAME block reads the same
Then the key reads as its short name, the first non-empty of:
  | 1 | exo__Property_displayName                         |
  | 2 | exo__Property_localName                           |
  | 3 | the local part of exo__Asset_label                |

Given a label `<prefix>__<Class>_<local>`
Then its local part is everything after the class segment:
  | concept__Concept_genus                  | genus                   |
  | tbank__Task_planned_start_timestamp     | planned_start_timestamp |
  | rdfs__seeAlso (no class segment)        | seeAlso                 |
  | aliases (no prefix)                     | aliases                 |

Given two or more keys of ONE Properties block whose short names are equal
  (or a short name equal to the raw text of a key that has no property definition)
Then each such defined key reads `<ClassName>.<short name>`, where ClassName is
  exo__Class_localName of the first resolvable class in its exo__Property_domain,
  else the part of that class's label after `__` (a symbolic domain `person__Person` → `Person`),
  else the class segment of the property's own label (`ems__Effort_status` → `Effort`)

Given the prefixed text still equals another key's text of the block, or no ClassName exists
Then that key reads its raw predicate (the frontmatter key, unique in the block)

Given the colliding pair is in a different note's block
Then it does not affect this block — the context of disambiguation is one Properties block

Given a key is added to an already patched block and collides with a rendered key
Then both re-read with the prefix; when the collision disappears on the next re-render
  (metadataCache changed / resolved), they read the short name again
```

Unchanged: the native key `<input>` keeps its value (no frontmatter rename), the span still opens
the definition asset on click, keys without a property definition are not patched, the setting
`enablePropertiesLabelPatch` still turns the whole patch off.

## Deviations from the letter of the issue (named on purpose)

- **Local part of the label.** The issue says «после последнего `_`». Implemented: everything
  after the class segment. The issue's own examples hold (`concept__Concept_genus` → `genus`), and
  the failure the issue itself names — `planned_start_timestamp` read as `timestamp` — is gone
  even without `exo__Property_localName`. Measured: 4 such labels in vault-exodev
  (`exo__GraphViewFilter_excluded_uid` / `_status` / `_property` / `_archived`), which the literal
  rule would render `uid`, `status`, `property`, `archived`.
- **«Backward: старые свойства без localName продолжают рендериться как раньше».** Read together
  with the issue's numbered algorithm (step 1 ends with the label local part): a property without
  `displayName` and without `localName` now reads its label's local part instead of the raw label.
  That is a visible change for the defs without displayName (vault-exodev 313 of 822,
  vault-tbank 201 of 581 on this machine). Turning the patch off still restores raw keys.

## Non-goals

- ⛔ The TBox definitions `exo__Property_localName` (`df6acbb6`) and `exo__Class_localName`
  (`51843694`) named by the issue — data in `exoas-exo`, delivered separately. On 2026-10-17 they
  are on no local vault and not on `kitelev/exoas-exo` main; the renderer reads the frontmatter keys
  by name and works without the definitions (only authoring them through `set-property` needs them).
- ⛔ Other surfaces: layout/table column headers, CLI, the display-name engine
  (`exo__PrintedProperty`), Live Preview / Source mode (the patch is Reading Mode only).
- ⛔ Case-insensitive comparison (`Status` vs `status` are different texts).
