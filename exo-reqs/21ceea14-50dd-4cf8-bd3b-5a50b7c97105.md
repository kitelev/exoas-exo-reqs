# req(exo): set-property decides scalar quoting per property, not by a constant flag

## Job Story

When I set a date or a number on an asset with `set-property --property <k> --value <v>` — for example closing a `life__Episode` with `life__Episode_end 2026-08-09`, or reordering a display-name part with `exo__DisplayNamePart_order 3` — I want the value to land in the frontmatter with the same YAML type it would have had if `create` had written it. Today it lands quoted, so it parses as a **string** while the same property created by `create` parses as a **Date** or a **number**. One property then carries two types across the vault depending on which command touched it last, and every consumer has to accept both or silently drop half the data.

## Downstream consequence (RDF), stated deliberately

Removing the quotes changes the value's YAML type, and the RDF converter emits triples from the parsed value — so the emitted literal changes too: a date-only value goes from a plain `Literal("2026-08-09")` to `Literal("2026-08-09T00:00:00.000Z", xsd:dateTime)`, and an integer becomes `xsd:decimal`. An existing query matching such a value with a bare string (`?s <p> "2026-08-09"`) stops matching for newly-set values; `FILTER(CONTAINS(STR(?d), "2026-08-09"))` still matches. This is convergence, not novelty — `create` has always emitted these shapes — and it is the point of the requirement: one property, one type. It is recorded here so a future reader does not diagnose it as a regression.

For a few shapes the change is not merely typing — the VALUE itself is altered by the round-trip, again identically to `create`: `007` loses its zero-padding and reads back as `7`; `1.50` reads back as `1.5`; an integer past the float-safe range loses precision; and `null` / `~` make the property read as **absent** rather than as the string "null". A caller that needs such a value to survive verbatim pre-wraps it (`--input '{"property":"<k>","value":"\"007\""}'`) — an already-double-quoted scalar is passed through untouched. This is stated because "keeps its native YAML type" understates it: for these shapes the native type is reached by mutating the lexical form.

## Homoiconicity Invariant decision (Q1/Q3)

Q1 = no: how a value is serialized into YAML is not user-configurable semantics — it is the core write path of a bare CLI verb (the same Q3 "core of processing" classification the parent `set-property` requirement `3800d995` made). The rule itself is already declared in code as `STRING_SCALAR_PROPERTIES` and is shared with the `create` path; this requirement makes `set-property` **consult** that declaration instead of overriding it with a constant.

## Classification note (why a new requirement and not a bug-fix)

`3800d995` (Active) specifies `set-property` and lists both input forms, but its scenarios all use `--input` with JSON-typed values and it explicitly labels that path "(JSON-typed value)" — it never states what type a `--value` **string** should acquire. So the shell-string typing is unspecified rather than already-required, and the change is a user-visible outcome change on that path. It also introduces a rule no requirement states: the per-property asymmetry (`aliases` keeps its quoting while everything else stops). Hence a new sibling requirement rather than extending `@req:3800d995`.

## Amendment 2026-09-19 (ticket 2227d660 — the declared range types the scalar)

Founder rule 6c (2026-09-18, ticket a9b55ead) made the validator judge a literal's tag against the property's DECLARED `exo__Property_range`; decision G2 of ticket d72aba19 (2026-09-19) then declared `ems__Reminder_chatId` `xsd:integer`. A writer that types by SHAPE cannot satisfy a validator that judges by DECLARATION: the shape rule quoted every value with a leading `-` (a YAML indicator), so a GROUP chat id — negative by Telegram's convention, pinned by the bot wrappers as `create --class ems__Reminder --property ems__Reminder_chatId=<id>` — became an `xsd:string` literal under `xsd:integer` on the first new asset; and a numeric string under an `xsd:string` range became `xsd:integer`. Neither choice of range could make the shape-typing writer conform, so the writer now reads the declaration (ORCH mandate — batch6i plan-gate, 2026-09-19; not re-asked of the founder, the rule and G2 are his).

- Range source = `PropertyNameValidator` (cli): the one-pass TBox scan `create` and `set-property` already run for the key check now also keeps `exo__Property_range` per def (label-keyed, metaclass-closure-filtered, no domain filter). NOT `ShapeLoader.loadFromVaultFS`: measured on vault-my it registers 26 shapes (a UID-form `exo__Property_domain` does not resolve → the def is dropped), `ems__Reminder_chatId` among the missing, at 0.6–1.7 s per call — a separate latent defect (cardinality-aware emission #3179 is dead on a UID-canon vault), named as a follow-up.
- Injection = a third argument on the core serializer (`serializeYamlScalar(value, quoteAmbiguousScalars, declaredRange)`), so the existing four call sites stay source-compatible and any writer that later obtains a range can pass it.
- The lexical gates are deliberately NARROWER than js-yaml's resolvers (canonical integer, safe-integer, dotted decimal): the writer promises "the reader gets back the number the author wrote", and YAML 1.1 on js-yaml 5.3.0 does not keep that promise for `010` (octal 8), `1_000` (1000), `12345678901234567890` (…567000) or `1e5` (a string).
- Booleans under `xsd:string` stay bare: the converter emits a YAML boolean as a plain `"true"^^xsd:string` literal already, so quoting changes nothing in the graph and would flip the YAML-level type for YAML readers of the 233 live values in `exoas-flow`.
- Blast radius measured 2026-09-19 (SPARQL, three vaults): bare NUMBERS under an `xsd:string` range — 0 (the one scalar-looking value, `person__Person_telegramChatId`, is already quoted); numeric-range values with a leading `-` — none live (chat ids written before G2 were re-quoted by that decision's own migration).
- Out of scope, named: `FrontmatterService.createFrontmatter` (plugin / services `create_instance` — no range source at the call site; CLI↔UI parity debt, follow-up) and `GroundingExecutor.executePropertySet` (no grounding targets a datatype-range property: 0 of 51 in vault-my, 0 of 48 in vault-exodev). The `req__Requirement_label` still reads "keeps its native YAML type" — that clause now means "typed by the declared range when one is mounted; by shape otherwise", as covers[0] and covers[4] state.

## Amendment 2026-09-20 (ticket 8185c9dd — the string oracle is the reader)

"Scalar-looking" — the value the string rule (label/aliases and a declared `xsd:string` range) must quote — is redefined from a regex table to the reader itself: **a form that ANY reader of the file hands back as a non-string.** The old oracle replicated js-yaml 4's YAML 1.2-core resolvers (#3750 MEDIUM-3), but the product reads frontmatter with js-yaml 5.3.0 `YAML11_SCHEMA` (`parseYamlFrontmatterTolerant`, #4173), and the two schemas disagree in BOTH directions: YAML 1.1 coerces the sexagesimal integer (`10:30` → 630), the `yes`/`no`/`on`/`off`/`y`/`n` booleans in any case and `+.5`, which the table missed; 1.2-core coerces `1e5` / `08` / `0o17`, which YAML 1.1 reads as strings (review #4282 MEDIUM-1; ORCH plan-gate `plan-ok` 2026-09-20).

- Oracle = `typeof yaml.load("v: " + value, { schema: YAML11_SCHEMA }).v !== "string"` (a Date / number / boolean / null / nested structure, or a parse rejection → quote) **in union with** the 1.2-core table. The union is deliberate: quoting a string is lossless, so every form quoted before this amendment stays quoted (monotone — Obsidian's metadataCache reads 1.2-core), and every YAML 1.1-only form joins them. One oracle serves both paths (label/aliases and `xsd:string`); the paths differ only in the boolean exclusion below.
- The `xsd:string` boolean exclusion is narrowed to the canonical lowercase `true` / `false` (the 233 live bare values are all lowercase). `True` / `FALSE` / `yes` / `Off` are quoted: the converter would fold them to `true` / `false`, losing the author's spelling — the 2026-09-19 justification "the graph does not change" was false for them.
- ⛔ **Border change, named:** a DATETIME under string semantics (label, aliases, `xsd:string`) is now QUOTED. #3750 MEDIUM-3 kept it bare ("semantic-date format") and ticket 71f1ca37 п.2 (2026-09-18) chose to keep that as a known bound; the axis `roundTrip(datetime, true)` = Date is rewritten (R18a) to the new expectation. Under `xsd:string` a bare datetime is a Date → an `xsd:dateTime` literal under a string range — the same class of violation this requirement exists to prevent. Timestamp properties are unaffected (neither string-semantic nor `xsd:string`-ranged); live datetime-shaped labels/aliases 0 / 0 / 0.
- LOW-1 (#4282): `create` resolves a declared range by the key the caller SUPPLIED (`exo__Asset_pinned`), as `set-property` does — the two writers agree on the whitelisted bare keys by construction; a bare `aliases` / `pinned` resolves nothing in either.
- NIT-2 (#4282): `PropertyNameValidator.collect()` walks in byte order and, for a duplicated label, keeps the first def in path order; a twin with a different range is reported once through the injected warn channel (`create` / `set-property` wire it to stderr as `⚠ [PropertyNameValidator] …`). Live duplicate-label defs: 0 / 0 / 0.
- Existing vault data are NOT rewritten by this amendment; a value of these forms changes its on-disk form when it is next written by `create` / `set-property`.
