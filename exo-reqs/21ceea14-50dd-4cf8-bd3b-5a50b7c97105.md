# req(exo): set-property decides scalar quoting per property, not by a constant flag

## Job Story

When I set a date or a number on an asset with `set-property --property <k> --value <v>` — for example closing a `life__Episode` with `life__Episode_end 2026-08-09`, or reordering a display-name part with `exo__DisplayNamePart_order 3` — I want the value to land in the frontmatter with the same YAML type it would have had if `create` had written it. Today it lands quoted, so it parses as a **string** while the same property created by `create` parses as a **Date** or a **number**. One property then carries two types across the vault depending on which command touched it last, and every consumer has to accept both or silently drop half the data.

## Statement (Gherkin)

```gherkin
Given an existing asset and a NON-string-semantic property that takes a date (life__Episode_end)
When I run `cli set-property <path> --property life__Episode_end --value 2026-08-09`
Then the frontmatter line is `life__Episode_end: 2026-08-09` (bare)
And a YAML parse of the file yields a Date for that property

Given an existing asset and a NON-string-semantic property that takes an integer (exo__DisplayNamePart_order)
When I run `cli set-property <path> --property exo__DisplayNamePart_order --value 3`
Then the frontmatter line is `exo__DisplayNamePart_order: 3` (bare)
And a YAML parse of the file yields the number 3, so ordering compares numerically

Given an existing asset
When I run `cli set-property <path> --property aliases --value 2026-01-15`
Then the frontmatter value is quoted (`"2026-01-15"`)
And a YAML parse of the file yields the STRING "2026-01-15", not a Date
# exo__Asset_label is guarded by a dedicated command (apply set-label), so `aliases`
# is the reachable string-semantic property on this surface; both are in
# STRING_SCALAR_PROPERTIES and take the same branch.

Given an existing asset and a property whose value is NOT scalar-shaped
When I run `cli set-property <path> --property <k> --value "some free text"`
Then the emitted form is unchanged from before this requirement
# quoting of YAML-unsafe / wikilink / whitespace-significant values is untouched:
# only the "looks like a bool/number/date and is therefore ambiguous" branch moves.

Given an existing asset
When I run `cli set-property <path> --input '{"property":"<k>","value":3}'`
Then the emitted form is byte-identical to before this requirement (bare `3`)
# the JSON path already carried the type; this requirement does not touch it.

Given the same property and the same logical value
When I write it once with `create --property <k>=<v>` and once with `set-property --property <k> --value <v>`
Then both commands emit the same YAML form for that property
```

## Verification

**Revert-verify (integration binding, planned):** `@req:21ceea14-50dd-4cf8-bd3b-5a50b7c97105` — an integration test drives the REAL `setPropertyCommand()` against a temp fixture vault (property defs for a date property, an integer property and `aliases`), reads the written file back from disk **and parses it with the production YAML reader**, asserting (1) the date-shaped `--value` yields a `Date`, (2) the integer-shaped `--value` yields a `number`, (3) the same shaped value on `aliases` yields a `string`, (4) a free-text `--value` is emitted exactly as before, (5) the `--input` JSON path is unchanged. Reverting the per-property flag to the constant `true` makes (1) and (2) RED while (3), (4) and (5) stay GREEN — the string-semantic and unchanged-path assertions are the negative controls that prove the change is scoped to the ambiguous-scalar branch and did not simply disable quoting. Asserting the parsed TYPE (not the emitted characters) is deliberate: the defect is invisible at the character level, which is exactly how it survived until now.

## Homoiconicity Invariant decision (Q1/Q3)

Q1 = no: how a value is serialized into YAML is not user-configurable semantics — it is the core write path of a bare CLI verb (the same Q3 "core of processing" classification the parent `set-property` requirement `3800d995` made). The rule itself is already declared in code as `STRING_SCALAR_PROPERTIES` and is shared with the `create` path; this requirement makes `set-property` **consult** that declaration instead of overriding it with a constant.

## Classification note (why a new requirement and not a bug-fix)

`3800d995` (Active) specifies `set-property` and lists both input forms, but its scenarios all use `--input` with JSON-typed values and it explicitly labels that path "(JSON-typed value)" — it never states what type a `--value` **string** should acquire. So the shell-string typing is unspecified rather than already-required, and the change is a user-visible outcome change on that path. It also introduces a rule no requirement states: the per-property asymmetry (`aliases` / `exo__Asset_label` keep their quoting while everything else stops). Hence a new sibling requirement rather than extending `@req:3800d995`.
