# req(exo): set-property decides scalar quoting per property, not by a constant flag

## Job Story

When I set a date or a number on an asset with `set-property --property <k> --value <v>` — for example closing a `life__Episode` with `life__Episode_end 2026-08-09`, or reordering a display-name part with `exo__DisplayNamePart_order 3` — I want the value to land in the frontmatter with the same YAML type it would have had if `create` had written it. Today it lands quoted, so it parses as a **string** while the same property created by `create` parses as a **Date** or a **number**. One property then carries two types across the vault depending on which command touched it last, and every consumer has to accept both or silently drop half the data.

## Statement (Gherkin)

```gherkin
Given an existing asset and a NON-string-semantic property that takes a date (life__Episode_end)
When I run `cli set-property <path> --property life__Episode_end --value 2026-08-09`
Then the frontmatter value is bare (no surrounding quotes)
And a YAML parse of the file yields a Date for that property

Given an existing asset and a NON-string-semantic property that takes an integer (exo__DisplayNamePart_order)
When I run `cli set-property <path> --property exo__DisplayNamePart_order --value 3`
Then the frontmatter value is bare
And a YAML parse of the file yields the number 3, so ordering compares numerically

Given an existing asset
When I run `cli set-property <path> --property aliases --value 2026-01-15`
Then the frontmatter value is quoted
And a YAML parse of the file yields the STRING "2026-01-15", not a Date
# The lookup key is the CANONICAL frontmatter key, so `--property exo__Asset_aliases`
# takes the same branch (it is stored under the bare key `aliases`). `exo__Asset_label`
# is the other member of STRING_SCALAR_PROPERTIES but is guarded to `apply set-label`
# and never reaches this code path, so `aliases` is the only reachable member here.

Given an existing asset and a property whose value is NOT scalar-shaped
When I run `cli set-property <path> --property <k> --value "some free text"`
Then the emitted form is unchanged from before this requirement
# quoting of YAML-unsafe / wikilink / whitespace-significant values is untouched:
# only the "looks like a bool/number/date and is therefore ambiguous" branch moves.

Given an existing asset
When I run `cli set-property <path> --input '{"property":"<k>","value":3}'`
Then the emitted form is byte-identical to before this requirement (bare `3`)
# a JSON number/boolean is not a string, so the flag is never consulted for it.

Given an existing asset and a NON-string-semantic property
When I run `cli set-property <path> --input '{"property":"<k>","value":"007"}'`
Then the emitted form is bare and a YAML parse yields the number 7
# a JSON STRING shares the serializer with --value and behaves identically to it.
# This is a behaviour CHANGE on the --input path for string values, and it is
# intended: the rule is per-property, not per-input-form. A caller that needs a
# scalar-shaped value to survive as a string on such a property pre-wraps it
# (`"value": "\"007\""`), which the serializer passes through verbatim.

Given the same property and the same canonical frontmatter key and the same logical value
When I write it once with `create --property <k>=<v>` and once with `set-property --property <k> --value <v>`
Then both commands emit the same YAML form for that property
```

## Verification

**Revert-verify (integration binding):** `@req:21ceea14-50dd-4cf8-bd3b-5a50b7c97105` — an integration test drives the REAL `setPropertyCommand()` (and the REAL `createCommand()` for the parity scenario) against a temp fixture vault, reads the written file back from disk **and parses it with the production YAML reader**, asserting: (1) a date-shaped `--value` yields a `Date`; (2) an integer-shaped `--value` yields a `number`; (3) the same shaped value on `aliases` yields a `string`; (4) a free-text `--value` is emitted exactly as before; (5) an `--input` JSON **number** is unchanged; (6) `create` and `set-property` agree on the emitted form; (7) an `--input` JSON **string** behaves like `--value` and yields a `number`.

Asserting the parsed TYPE (not the emitted characters) is deliberate: the defect is invisible at the character level, which is exactly how it survived until now.

**Two independent revert axes, each with its own controls:**

- **Axis 1 — the flag.** Restoring the constant `true` reds (1), (2), (6) and (7); (3), (4) and (5) stay green. (3) is a genuine control — it proves the change did not simply disable quoting wholesale. (4) and (5) are honest unchanged-path assertions rather than discriminating controls: a free-text value is not ambiguous and a JSON number is not a string, so neither consults the flag in either state.
- **Axis 2 — the key.** Keying the lookup on the raw `--property` spelling instead of `canonicalYamlKey(property)` reds (3) alone. This proves the canonical-key decision is load-bearing: without it, `--property exo__Asset_aliases` would silently lose its quoting and reintroduce the #3750 regression.

## Downstream consequence (RDF), stated deliberately

Removing the quotes changes the value's YAML type, and the RDF converter emits triples from the parsed value — so the emitted literal changes too: a date-only value goes from a plain `Literal("2026-08-09")` to `Literal("2026-08-09T00:00:00.000Z", xsd:dateTime)`, and an integer becomes `xsd:decimal`. An existing query matching such a value with a bare string (`?s <p> "2026-08-09"`) stops matching for newly-set values; `FILTER(CONTAINS(STR(?d), "2026-08-09"))` still matches. This is convergence, not novelty — `create` has always emitted these shapes — and it is the point of the requirement: one property, one type. It is recorded here so a future reader does not diagnose it as a regression.

For a few shapes the change is not merely typing — the VALUE itself is altered by the round-trip, again identically to `create`: `007` loses its zero-padding and reads back as `7`; `1.50` reads back as `1.5`; an integer past the float-safe range loses precision; and `null` / `~` make the property read as **absent** rather than as the string "null". A caller that needs such a value to survive verbatim pre-wraps it (`--input '{"property":"<k>","value":"\"007\""}'`) — an already-double-quoted scalar is passed through untouched. This is stated because "keeps its native YAML type" understates it: for these shapes the native type is reached by mutating the lexical form.

## Homoiconicity Invariant decision (Q1/Q3)

Q1 = no: how a value is serialized into YAML is not user-configurable semantics — it is the core write path of a bare CLI verb (the same Q3 "core of processing" classification the parent `set-property` requirement `3800d995` made). The rule itself is already declared in code as `STRING_SCALAR_PROPERTIES` and is shared with the `create` path; this requirement makes `set-property` **consult** that declaration instead of overriding it with a constant.

## Classification note (why a new requirement and not a bug-fix)

`3800d995` (Active) specifies `set-property` and lists both input forms, but its scenarios all use `--input` with JSON-typed values and it explicitly labels that path "(JSON-typed value)" — it never states what type a `--value` **string** should acquire. So the shell-string typing is unspecified rather than already-required, and the change is a user-visible outcome change on that path. It also introduces a rule no requirement states: the per-property asymmetry (`aliases` keeps its quoting while everything else stops). Hence a new sibling requirement rather than extending `@req:3800d995`.
