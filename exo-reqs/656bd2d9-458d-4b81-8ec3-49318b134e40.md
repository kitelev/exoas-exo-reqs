# req(exo): `apply` enforces the command's own declared input contract

## Job Story

When I create a task with the homoiconic command — `apply create-task <project> --yes --input '{"value":"Fix the parser"}'` — and I get the input key wrong, I want the command to **refuse and name the key it wants**, so that I re-run it once. Today it succeeds: the asset is created with the label `Untitled`, my text lands in the frontmatter as an orphan property `value:`, and the engine prints a warning about an unhealthy vault while continuing anyway. Repairing that asset takes four more commands; a refusal would have taken one retry.

The contract is already declared in the graph — `create-task`'s `exocmd__Grounding_inputSchema` says `{"properties":{"label":…},"required":["label"]}` — and the sibling command `set-label` already refuses loudly on the same class of mistake (`property_set: value template references an input that was not provided (--input '{"label":...}' required)`). So the fail-loud mechanism exists in this codebase; the declared schema is simply never consulted on the CLI path.

## Statement (Gherkin)

```gherkin
Scenario: a required key with no other declared source is refused by name
Given a command whose grounding declares inputSchema {"properties":{"label":{…}},"required":["label"]}
And that grounding declares no labelTemplate, no omitLabel, no propertyDefault and no inheritanceRule for it
When I run `cli apply <cmd> <path> --yes` with no --input
Then the command refuses with a non-zero exit
And the message names the missing key in the --input '{"label":...}' form
And no asset is created

Scenario: a key the schema does not declare is refused by name
Given the same command, whose schema declares only "label"
When I run `cli apply <cmd> <path> --yes --input '{"value":"Fix the parser"}'`
Then the command refuses with a non-zero exit
And the message names "value" as not declared by the command's input schema
And the message lists the accepted keys
And no asset is created, so no orphan `value:` property is written

Scenario: the declared key is accepted and behaviour is unchanged
Given the same command
When I run `cli apply <cmd> <path> --yes --input '{"label":"Fix the parser"}'`
Then the command succeeds
And the created asset carries that label, byte-identical to the behaviour before this requirement

Scenario: a required label that a labelTemplate supplies is NOT refused
Given a command whose grounding declares required ["label"] AND a labelTemplate
When I run `cli apply <cmd> <path> --yes` with no --input
Then the command is NOT refused by the pre-flight
And the asset is created with the auto-generated label

Scenario: a required label that omitLabel deliberately drops is NOT refused
Given a command whose grounding declares required ["label"] AND omitLabel true
When I run `cli apply <cmd> <path> --yes` with no --input
Then the command is NOT refused by the pre-flight

Scenario: a required key that the schema itself defaults is NOT refused
Given a command whose schema declares a required key carrying a defaultValue
When I run `cli apply <cmd> <path> --yes` with no --input
Then the command is NOT refused by the pre-flight

Scenario: a required key that a propertyDefault or an inheritanceRule writes is NOT refused
Given a command whose grounding declares required ["ems__Effort_parent"]
And the grounding declares a propertyDefault (or an inheritanceRule) writing that same property
When I run `cli apply <cmd> <path> --yes` with no --input
Then the command is NOT refused by the pre-flight

Scenario: engine-reserved inputs are never treated as unknown
Given a command whose schema declares only "label"
When I run `cli apply <cmd> <path> --yes --input '{"label":"X","body":"text","plannedDate":"2026-09-24"}'`
Then the command is NOT refused for "body" or "plannedDate"

Scenario: a grounding with no declared schema is never refused by this check
Given a command whose grounding declares no exocmd__Grounding_inputSchema
When I run `cli apply <cmd> <path> --yes --input '{"anything":"at all"}'`
Then the pre-flight says nothing and the executor decides, exactly as before

Scenario: dry-run and the executing path return the SAME verdict
Given any of the refusal scenarios above
When I run the same invocation with --dry-run and then with --yes
Then both refuse, with the same wording and a non-zero exit

Scenario: the pre-existing value-template gate is untouched
Given a non-property_set grounding carrying a stray targetValue* that references $input.label
When findMissingInput is asked about it with an empty input
Then it still returns null, so the executor is not refused a call it would have run
```

## Non-goals

- **The plugin / UI path is not changed.** `CommandExecutionFlow` augments the declared schema at click time with the host class's required properties, so its effective contract is wider than the static one; validating the static schema there would refuse legitimate form submissions. This requirement scopes the CLI `apply` surface, where the declared schema *is* the whole contract of the call.
- **`GroundingExecutor` is not changed.** The frontmatter write at the `userInput` loop stays as it is; the refusal happens before the executor is constructed.
- **No new vault data.** All 35 groundings that declare a schema already declare `required`; nothing in `exoas-exocmd` or any other assetspace is edited by this requirement.
