# req(exo): `apply` enforces the command's own declared input contract

## Job Story

When I create a task with the homoiconic command — `apply create-task <project> --yes --input '{"value":"Fix the parser"}'` — and I get the input key wrong, I want the command to **refuse and name the key it wants**, so that I re-run it once. Today it succeeds: the asset is created with the label `Untitled`, my text lands in the frontmatter as an orphan property `value:`, and the engine prints a warning about an unhealthy vault while continuing anyway. Repairing that asset takes four more commands; a refusal would have taken one retry.

The contract is already declared in the graph — `create-task`'s `exocmd__Grounding_inputSchema` says `{"properties":{"label":…},"required":["label"]}` — and the sibling command `set-label` already refuses loudly on the same class of mistake (`property_set: value template references an input that was not provided (--input '{"label":...}' required)`). So the fail-loud mechanism exists in this codebase; the declared schema is simply never consulted on the CLI path.

## Non-goals

- **The plugin / UI path is not changed.** `CommandExecutionFlow` augments the declared schema at click time with the host class's required properties, so its effective contract is wider than the static one; validating the static schema there would refuse legitimate form submissions. This requirement scopes the CLI `apply` surface, where the declared schema *is* the whole contract of the call.
- **`GroundingExecutor` is not changed.** The frontmatter write at the `userInput` loop stays as it is; the refusal happens before the executor is constructed.
- **No new vault data.** All 35 groundings that declare a schema already declare `required`; nothing in `exoas-exocmd` or any other assetspace is edited by this requirement.
