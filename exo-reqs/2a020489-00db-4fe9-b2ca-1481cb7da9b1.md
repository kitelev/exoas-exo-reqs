## Job story

When any production vault adapter writes frontmatter through the `IVaultAdapter.updateFrontmatter` port — the plugin's `ObsidianVaultAdapter` (Obsidian `processFrontMatter`) or the CLI's `FileSystemVaultAdapter` (YAML block on disk) — I want the key dialect of the core chokepoint (`canonicalYamlKey` + `LEGACY_YAML_KEYS` drop + canonical-wins + IRI normalisation, reqs `960d7a3f` / `869561bf` / `de7131ae`) to live in ONE core function that both adapters call, so that the rule cannot drift between the two runtimes (UI/CLI parity) and the port's contract is written down once instead of being re-derived from each implementation.

## Context

- Source: ticket `5d34b55e-dfc6-4b39-8249-a403ca20b5db` (parent techbacklog `bbac67ce`), found by the review of PR kitelev/exocortex#4241 (LOW-4): after that PR the per-key rule lived TWICE — in `FrontmatterService.updateProperty` (core, text path, one property per call) and inline in `ObsidianVaultAdapter.updateFrontmatter` (plugin, object path over `processFrontMatter`). The CLI `FileSystemVaultAdapter.updateFrontmatter` applied neither the key canonicalisation nor the IRI normalisation and replaced the whole YAML block (keys the updater did not return were dropped). Approved for implementation by ORCH `main-35699` mandate at the code-batch-2 plan-gate 2026-09-16 (decision `a8939b8b`).
- Why a NEW sibling requirement (not an extension of an Active one): `de7131ae` §Non-goals explicitly excludes both `FileSystemVaultAdapter.updateFrontmatter` and any change to `FrontmatterService`; `960d7a3f` Scenario C names its writers exhaustively and the adapters are not among them. Mutant discriminator on `origin/main` `bb1f579e`: the CLI adapter has no canonicalisation to remove, so no test can redden — the CLI-parity property is not specified anywhere; the plugin half stays bound to `de7131ae` (axes A1–A5 unchanged).
- Mechanism measured on `origin/main` `bb1f579e` (2026-09-16): the port has exactly ONE production caller, `LayoutService.handleCellEdit` (`packages/obsidian-plugin/src/application/layout/LayoutService.ts:349`), which re-emits every current key next to the edited one (`{...current, [prop]: value}`); the CLI adapter has 0 callers in `packages/cli/src` and 0 in tests. `FrontmatterService` already imports `canonicalYamlKey` / `LEGACY_YAML_KEYS` from `NoteToRDFConverter` and owns `normalizeIRI` / `normalizeIRIValue`; the reverse import would be a cycle, so the shared function lives in `FrontmatterService`.

## Contract of `IVaultAdapter.updateFrontmatter` (fixed by this requirement, written in the port's JSDoc and in the helper's JSDoc)

1. **PATCH, not REPLACE.** The updater returns the keys to WRITE; every key of the live frontmatter that the updater does not return is preserved unchanged.
2. **Deletion is not expressible through this port.** `updateFrontmatter` never removes a key the caller omits; the only keys it removes are the `LEGACY_YAML_KEYS` spellings of a canonical key it has just written. Removing a property stays the job of `FrontmatterService.removeProperty` (and the CLI `remove-property` verb / `un-archive` grounding built on it).
3. **Every written key goes through the chokepoint dialect.** A patch that carries a full object (the `{...current, [prop]: value}` shape of `LayoutService.handleCellEdit`) has EACH of its keys mapped through `canonicalYamlKey(FrontmatterService.normalizeIRI(key))`, each string value through `FrontmatterService.normalizeIRIValue`, a payload carrying both spellings of one key resolved canonical-wins, and the legacy spelling(s) of each written canonical key dropped from the live frontmatter — the existing plugin behaviour since PR #4241, now a contract of the port rather than a side effect of one implementation.

The single carrier of that dialect is `FrontmatterService.applyPatch(target, patch)` (core); both production adapters call it and neither re-implements any part of it.

## Scenarios

### Scenario A — CLI adapter writes the canonical key and drops the legacy spelling
Given a file in a CLI vault whose frontmatter carries the legacy bare key `archived: true`
When `FileSystemVaultAdapter.updateFrontmatter` is called with an updater returning `{ exo__Asset_archived: false }` (and any other current keys)
Then the file on disk carries exactly ONE archive-flag key, `exo__Asset_archived: false`
And it carries NO bare `archived` key.

### Scenario B — CLI adapter upgrades a bare `archived` payload key, never writes the bare form
Given a file with no archive-flag key
When the updater returns `{ archived: true }`
Then the file carries `exo__Asset_archived: true` and NO bare `archived` key (`canonicalYamlKey("archived")` = `"exo__Asset_archived"`, the same upgrade rule as req `960d7a3f` Scenario C).

### Scenario C — CLI adapter writes the prefixed `exo__Asset_aliases` under the live `aliases:` key
Given a file with no aliases
When the updater returns `{ exo__Asset_aliases: ["x"] }`
Then the file carries `aliases: ["x"]` and NO literal `exo__Asset_aliases` key (req `869561bf` §Scope remainder, mirrored from `de7131ae` Scenario F).

### Scenario D — CLI adapter resolves a dual payload canonical-wins, in either insertion order
Given a file with no archive-flag key
When the updater returns `{ archived: true, exo__Asset_archived: false }` — or the same two entries in the opposite order
Then the file carries `exo__Asset_archived: false` only (the canonical spelling wins regardless of insertion order — the same priority as `NoteToRDFConverter` guard M1 and `MetadataHelpers.ARCHIVED_FLAG_KEYS`; a last-write-wins rule would fail one of the two orders).

### Scenario E — negative control: keys outside the canonical-key rule pass through unchanged (both adapters)
Given an updater returning `{ exo__Asset_isDefinedBy: "[[x]]", ems__Effort_status: "[[y]]", aliases: ["a"] }`
When it is written through either production adapter
Then all three keys are written under their own names with their values unchanged.

### Scenario F — PATCH semantics: keys the updater does not return are preserved (both adapters)
Given a live frontmatter `{ exo__Asset_uid: "u", exo__Asset_label: "L", ems__Effort_status: "[[s]]" }`
When the updater returns only `{ exo__Asset_label: "New" }`
Then the written frontmatter carries `exo__Asset_label: "New"` AND still carries `exo__Asset_uid: "u"` and `ems__Effort_status: "[[s]]"`
(for the CLI adapter this is a change from the previous replace-whole-block behaviour; the plugin adapter has always behaved this way because Obsidian's `processFrontMatter` hands it the live object).

### Scenario G — deletion is not expressible through the port (both adapters)
Given the same live frontmatter as Scenario F
When the updater returns an object that omits `ems__Effort_status`
Then `ems__Effort_status` is still present after the write (omission is not deletion; the only removals the port performs are the legacy spellings of a canonical key it wrote — Scenario A).

### Scenario H — IRI-form keys and values are normalised to the Obsidian dialect (both adapters)
Given an updater returning `{ "https://exocortex.my/ontology/ems#Effort_status": "obsidian://vault/x/ems__EffortStatusDoing.md" }`
When it is written through either production adapter
Then the frontmatter carries the key `ems__Effort_status` with the value `"[[ems__EffortStatusDoing]]"` (`FrontmatterService.normalizeIRI` / `normalizeIRIValue` — the same normalisation `FrontmatterService.updateProperty` applies; the plugin adapter has done this since before PR #4241 but it was not specified).

### Scenario I — one carrier: removing the helper call from ONE adapter reddens only that adapter's axes
Given the full test set
When the `FrontmatterService.applyPatch` call is replaced by a plain key copy in the plugin adapter only
Then the plugin axes for Scenarios A–D and H fail and the CLI axes stay green — and symmetrically for the CLI adapter
(evidence in the PR body: mutants M1/M2 on the two call sites, M3–M7 on the helper body reddening BOTH adapters).

### Scenario J — a block that is present but not parseable is refused, never patched over (CLI adapter; PR #4243 review MEDIUM)
Given a file whose frontmatter block exists but does not parse to a mapping (e.g. `---\nfoo: [unclosed\n---`)
When `FileSystemVaultAdapter.updateFrontmatter` is called
Then the call rejects with an error naming the file as not parseable
And the file is byte-identical before and after (patching over an unreadable block would drop every key it held — the opposite of Contract §1).
A file with NO block gets one created from the patch; an EMPTY block (`---\n\n---`) is "no keys yet", not an unreadable one.

### Scenario K — a patch value of `undefined` is "no opinion" (both adapters)
Given a live frontmatter `{ exo__Asset_label: "L", archived: true }`
When the updater returns `{ exo__Asset_label: undefined, exo__Asset_archived: undefined }`
Then `exo__Asset_label` is still `"L"` and the bare `archived` key is still present
(writing `undefined` would make the CLI's YAML dumper drop the key — a deletion Contract §2 says this path cannot express — so the key is neither written nor legacy-dropped).

## Non-goals

- Deletion of a key through `updateFrontmatter` is deliberately NOT introduced (Contract §2); callers that need removal use `FrontmatterService.removeProperty`.
- The reverse write for the UNPREFIXED direction (a literal `exo__Asset_aliases:` already on disk is not removed — `LEGACY_YAML_KEYS` has no entry for it; PR #4241 review LOW-3) is only named here, not changed: neither the chokepoint nor the adapters remove it.
- The CLI adapter's YAML serialisation (`yaml.dump` of the whole block; its `quoteStyle: "double"` option is not a js-yaml option — the real one is `quotingType` — so it is ignored, pre-existing) and the text path `FrontmatterService.updateProperty` / `removeProperty` are unchanged.
- Known discrepancy, named not fixed (PR #4243 review LOW, follow-up ticket): `normalizeIRIValue` returns the wikilink WITH surrounding quotes (a ready YAML scalar for the text path); on the object path the quotes become part of the string value, so the disk byte-shape differs from `updateProperty`'s (graph readers strip them). Axes A7/C7/H5 assert `toContain("[[…]]")` until the follow-up decides the object-path form.
- The 15 in-memory test adapters, `OracleVaultAdapter`, `LayoutService.handleCellEdit` and `NoteToRDFConverter` are unchanged; `packages/core/src/index.ts` is unchanged (`FrontmatterService` is already exported).
