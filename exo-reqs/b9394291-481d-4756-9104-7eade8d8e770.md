# req(exo): the cache path states in META how many files produced no triples, and states EXPLICITLY that the per-file list is unavailable — never an empty list

## Job Story

When I consume `query --output json` from a script or an acceptance gate, I want the response
meta to tell me — on the cache path too — that some files produced no triples and that the
per-file list is **not available on this path**, so that a machine reader gets the same signal a
human gets on stderr, and can never mistake "this path cannot tell" for "nothing was skipped".

## Why this is a NEW requirement and not an extension of `81cd5d1f`

Sibling req `81cd5d1f` (Active, P2) covers the same command, and its cache-path scenario
**requires the current behaviour**: «no per-file skipped list is claimed … And meta carries no
skippedFiles». That is the feature-sdd inverse tell — an active req that requires today's state
as a scenario scopes the change OUT, so widening it silently would rewrite an approved promise.
The review gate of PR #4343 (MEDIUM-1, 2026-09-24) reached the same conclusion independently and
filed ticket `0354c41d`.

⛤ Compatibility with `81cd5d1f` is **narrow and checked, not assumed**: its scenario forbids
`skippedFiles` specifically, not "any additional meta field". This requirement keeps
`skippedFiles` absent on the cache path; it adds two fields that say what the cache format
genuinely knows.

## Statement (Gherkin)

```gherkin
Scenario: the cache path reports the COUNT and disclaims the list
  Given a vault containing exactly one file the loader commits no triples for
  When I run `query … --use-cache --output json` and the load is served by the triple cache
  Then meta.zeroTripleCount = 1
  And meta.skippedFilesAvailable = false
  And meta carries no skippedFiles
  And meta carries no skippedCount

Scenario: the full parse marks the list as available
  Given the same vault
  When I run the same query WITHOUT --use-cache (a full parse)
  Then meta.skippedFilesAvailable = true
  And meta.skippedCount = 1
  And meta.skippedFiles has exactly 1 entry

Scenario: a clean vault says nothing at all
  Given a vault in which every asset contributes triples
  When I run the query on either path
  Then meta carries none of zeroTripleCount, skippedFilesAvailable,
    skippedCount, skippedFiles
  And the silence means "nothing to report", not "the path cannot tell"

Scenario: the disclaimer is not expressible as an empty list
  Given the cache path with one zero-triple file
  Then the response must NOT carry skippedFiles = [] nor skippedCount = 0
  Because both read as the positive claim "nothing was dropped", which the
    cache format does not support — the defect req 81cd5d1f was created to fix
```

## Non-goals

- ⛔ The cache FORMAT is not changed. Storing the per-file reason in `triples.json` is variant
  (в) of the `7a84b9f0` fork and stays a separate subject.
- ⛔ The query-RESULT cache (`options.cache !== false`, answers before the vault is read) is out
  of scope: it measured nothing, so its silence is honest. Locked by axis S8 of `81cd5d1f`.
- ⛔ Other commands sharing `loadVaultTriples` (`apply`, `resolve-buttons`, `classes`,
  `validate-schema`) are not given the fields here; per-command surfaces are a separate decision,
  as `81cd5d1f` already records.

## Verification

**Revert-verified (integration binding), PR #4442.** Control green — 13/13 in
`packages/cli/tests/integration/query-skipped-files-7a84b9f0.integration.test.ts` (10 axes of
sibling req `81cd5d1f` plus the three below). Four mutants, one per guarantee; every `expect`
derived FROM THE RUN, not from the mutant's theme:

| mutant (on `sparql-query.ts`) | axes it reddens |
|---|---|
| `MZ1` cache path claims an empty list instead of disclaiming it | `S4`, `Z1` |
| `MZ2` full parse stops marking the list as available | `Z2` |
| `MZ3` cache path emits the fields on a clean vault | `Z3` |
| `MZ4` full parse emits the fields on a clean vault | `S3`, `Z3` |

Axes: `Z1` cache path states the count and the disclaimer · `Z2` full parse marks the list
available alongside the list itself · `Z3` a clean vault carries none of the four fields, on
either path.

⛤ **`MZ3` reddened NOTHING on its first run, and the defect was in the AXIS, not the mutant.**
`Z3`'s second pass was answered from the query-RESULT cache that its own first pass had
populated, so it never reached `loaderMeta` and was vacuous — green for a reason unrelated to
the guard it claimed to lock. Fixed by adding `--no-cache` to that pass (bypasses the result
cache, keeps the triple cache); the line is load-bearing and says so in the test. This is the
axis-level counterpart of the very signature this requirement forbids: something that reads as
a claim while resting on nothing.

⛤ **A foreign spec entry was touched and is named rather than left silent.** The pre-existing
mutant `M3_select_meta_drops_the_loader_fields` now also reddens `Z1`/`Z2`, since they read the
same `loaderMeta`. Its `expect` is left UNCHANGED on purpose: `expect` is the predicate "these
axes must red", so listing another requirement's axes there would make that mutant fail the day
those axes are retired. The fact is recorded in its `_note`.

**Measured before implementing** (shipped 17.6.2, vault with one zero-triple file): full parse
`meta` carried `skippedCount: 1` + `skippedFiles`; the cache path carried `{… cacheHit: true}`
and nothing else, while stderr said `1 file(s) contributed no triples…`. That gap is the
requirement's whole subject, and it was a measurement, not an inference.

**Reach-to-user** is verified after release, not at merge: the published binary must show
`zeroTripleCount` + `skippedFilesAvailable: false` on `--use-cache --no-cache --output json`,
and the previous published version must NOT (the flip is the predecessor release, per the
`integration-test-revert-verify` floor on shipped artefacts).
