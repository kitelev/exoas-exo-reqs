## Job story

When a CLI consumer chains several `exocortex-cli` processes in one logical turn against a large vault (the Telegram-bot engine logs one user action as `apply create-task-instance` → `apply move-to-backlog` → `apply start-effort`, then `resolve-buttons --json`), I want each of those processes to opt into the persistent per-file triple cache with `--use-cache` — and a process that WRITES to the vault to hand the next process a cache that already reflects its write — so that a chain whose parse cost today is ~3 × full vault parse (12–13 s each idle, 38–83 s each under load on 16 652 files / 275 k triples) costs roughly one cache load per process, without ever evaluating a precondition on stale state.

## Context

- Source: GitHub `kitelev/exocortex#4264` (mirror `ems__Task eaa54d5c`). Builds on #4263 (req `42812747`, Active): `CacheManager` v2 with a per-file `{mtimeMs,size}` manifest, delta refresh (changed files + referrers; TBox-form / FileSpace / legacy / >50 % → full rebuild), atomic persist (tmp + rename) and the shared `loadVaultTriples(vaultPath, { useCache })` that `query` / `classes` / `run-query` / `validate-schema` already use.
- Mechanism today (origin/main `39080e3b`, verified by `git grep`): `apply.ts` ("Build triple store once for the whole batch") and `resolve-buttons.ts` ("Build the triple store from the whole vault") call `new NoteToRDFConverter(new FileSystemVaultAdapter(vault)).convertVault()` unconditionally; neither knows `--use-cache`. `create.ts` builds a triple store ONLY under `--validate` (`CandidateShaclValidator.validateCandidate` → `convertVault()`); its default path does no RDF parse at all (its cost is frontmatter/shape scans — `scanClassNeighbours`, `ShapeLoader.loadFromVaultFS`, wikilink/property-name validation — outside this requirement). The issue text's "create.ts: same full-parse pattern" is therefore corrected here: for `create` the cached load applies to `--validate`, the write-through to every real write.
- Why write-through and not "delta on the next read" alone: #4263's delta already makes the NEXT `--use-cache` process see a mutation (manifest diff → re-parse), so read-after-write is correct without write-through on a filesystem with sub-second mtime resolution. Write-through moves the delta (referrer scan + re-parse + persist) INTO the mutating process, which still holds the loaded cache in memory — the next process then pays a plain hit instead of read + diff + re-parse + re-persist. Whether that is a net win for the bot chain is decided by measurement on a copy of `vault-bot-kitelev` (three processes, each `--use-cache`, write-through on vs off; numbers + commands in the PR body), not by argument.
- Stale-precondition class (#3788): `exocmd__Precondition_sparqlAsk` is evaluated on the in-process triple store; a store loaded from a cache that does not yet contain the previous process's write answers "Precondition not satisfied" on a healthy chain. A cache that is written through with the file's NEW stamp but its OLD triples would be the worst case — a hit that is stale — so the write-through MUST re-parse, never merely re-stamp.

## Statement (Gherkin)

```gherkin
Feature: --use-cache on apply / resolve-buttons / create with write-through (#4264)

  Background:
    Given a vault indexed by CacheManager (format v2, per-file manifest) at .exocortex/cache/triples.json
    And the three commands `apply`, `resolve-inline-buttons` (alias `resolve-buttons`) and `create`

  Scenario: AC1 — the flag is opt-in and the default path is untouched
    When any of the three commands runs WITHOUT --use-cache
    Then it builds its triple store exactly as before: NoteToRDFConverter.convertVault() once, CacheManager never constructed,
      no read of .exocortex/cache/triples.json, no write to it (a vault without a cache still has none afterwards)
    And its stdout / exit code / written files are byte-identical to the pre-#4264 behaviour

  Scenario: AC2 — with --use-cache the store comes from the shared loader and the result is byte-identical
    When `apply <cmd> <target> --json` (or `--dry-run`), `resolve-buttons <target> --json` or `create --validate --dry-run` runs with --use-cache
    Then the triple store is built from loadVaultTriples(vaultPath, { useCache: true }) — mode hit / delta / rebuild —
      NOT from a direct convertVault()
    And, on a cache WITHOUT an inferred layer (one --use-cache built itself, or `index --no-inference`), the stdout document
      is byte-identical to the same command on the same vault state without the flag
      (asserted for apply create-task-instance / move-to-backlog / start-effort --json and --dry-run, resolve-buttons --json,
       and create --validate --dry-run)
    But on a cache that `index` built (inferenceEnabled: true) the flagged store ADDITIONALLY carries the inferred layer
      (RDFS Instance_class closure + prototype-chain inheritance) — exactly as `query --use-cache` already does — so a
      precondition or binding that depends on an inherited or inferred triple can differ from the no-flag full parse:
      a documented divergence, not a defect (the flagged store is the closer match to the plugin's graph), asserted by a
      command gated on an inherited property that is hidden without the flag and visible with it, and the write-through
      keeps that layer (re-materialized when an engine input changed, verbatim otherwise — #4263's gate)

  Scenario: AC3 — a mutating process writes its change through to the cache
    Given `apply` (or `create`) runs with --use-cache and a grounding EXECUTED (apply — whether or not every step of it
      succeeded, a failed composite may have landed part of its files) or an asset was written (create)
    When the command exits
    Then .exocortex/cache/triples.json contains, for every file the command added / modified / removed,
      the entry a delta refresh would produce (the file's new {mtimeMs,size} stamp AND its freshly converted triples;
      removed files have no entry; referrers of an added / removed target are re-parsed)
    And the next --use-cache process on the unchanged vault loads with mode "hit" (reparsedFiles 0), not "delta"
    And the write-through re-parses ONLY the changed files and their referrers — asserted by NoteToRDFConverter.convertNote
      call count, never by wall-clock

  Scenario: AC4 — a three-process chain never evaluates a precondition on stale state
    Given a Backlog-gated command set (create-task-instance → move-to-backlog → start-effort) on a vault with a warm cache
    When process 1 runs `apply create-task-instance <prototype> --use-cache` and creates the instance
    And process 2 (a SEPARATE invocation, fresh CacheManager) runs `apply move-to-backlog <instance> --use-cache`
    And process 3 (a SEPARATE invocation) runs `apply start-effort <instance> --use-cache`
    Then process 2's and process 3's precondition ASK sees the previous process's write (no "Precondition not satisfied")
    And the final instance file is byte-identical to the one produced by the same three commands WITHOUT --use-cache
    And a write-through that re-stamps a file WITHOUT re-parsing it (stale triples under a fresh stamp) makes this chain fail
      (the mutant the scenario exists to catch)

  Scenario: AC5 — the write-through is best-effort and never changes the command's outcome
    Given the cache cannot be persisted after the mutation (the cache file / directory is not writable, or the persist throws)
    When `apply` / `create` runs with --use-cache
    Then the vault mutation is already on disk and stays
    And the command's exit code and stdout are exactly what they would be had the persist succeeded
    And one warning line on stderr names the failed write-through
    And the next --use-cache process still sees the mutation (the manifest diff falls back to a delta / rebuild)

  Scenario: AC6 — the write-through never pays a full rebuild inside the mutating command
    Given the mutation is one that #4263 classifies as rebuild-only (a TBox-form asset changed, a FileSpace declaration
      changed, or more than half the vault changed)
    When `apply` / `create` runs with --use-cache
    Then the mutating command leaves the persisted cache as it was (no rebuild, no re-stamp)
    And the next --use-cache process detects the change through the manifest and rebuilds — correct, just not pre-paid

  Scenario: AC7 — a concurrent writer's fresher cache is never reverted
    Given process A loaded the cache (hit) and, before A's mutation, another process modified file G and persisted a refreshed cache
    When A mutates file F and writes through
    Then the persisted cache after A contains BOTH G's and F's fresh triples and stamps
    And the same holds for a concurrent writer that changed ONLY the cache file — `index` persisting the inferred layer
      (`inferenceEnabled: true` + inferred triples) or another process's delta — with no vault file touched:
      A's in-memory snapshot is trusted only while the cache file's {mtimeMs,size} stamp is the one it was read from
      (stamped before the read, and from the temp file before A's own rename); a changed stamp makes A re-read the
      cache and fold F into THAT, so index's layer and flag survive and only F is re-parsed
    And the persist is the same atomic tmp + rename as every other cache write; the remaining window is a writer
      renaming between A's stat and A's rename — the lock-free window #4263 already accepts, self-corrected by the next
      reader's manifest diff / the next `index`

  Scenario: AC8 — create's scope is the triple load under --validate plus the write-through
    When `create --validate --use-cache` runs
    Then CandidateShaclValidator builds its vault context from loadVaultTriples(vaultPath, { useCache: true })
      and the candidate verdict (violations / warnings) is identical to the no-flag run
    And `create --use-cache` (without --validate) performs no triple-store load, and after writing the asset
      writes it through to an EXISTING cache (a vault without a cache is left without one — create never builds a cache)
    And ShapeLoader.loadFromVaultFS (SHACL shapes for cardinality-aware serialization) is untouched by the flag

  Scenario: AC9 — the cache path is observable: ONE stderr line per cache phase
    When any of the three commands runs with --use-cache
    Then it prints ONE stderr line for the LOAD phase naming the mode (hit / delta with the re-parsed count / rebuild)
      wherever a triple store is loaded (apply always; resolve-buttons always; create only under --validate)
    And ONE stderr line for the WRITE-THROUGH phase (persisted N file(s) re-parsed / nothing changed / skipped: reason /
      failed: reason) only when a grounding executed (apply, dry-run and a refused precondition excluded) or an asset was
      written (create, dry-run excluded) — so the pinned counts are: apply mutating 2, apply --dry-run 1, apply with a
      refused precondition 1; resolve-buttons 1; create --validate real 2, create --validate --dry-run 1, create without
      --validate real 1 (write-through only — no load mode exists to report), create without --validate --dry-run 0
    And stdout carries nothing extra (the --json documents stay single, parseable objects)
    And without --use-cache no such line is printed
```

## Non-goals

- Making `--use-cache` the default for any command; changing the cache format v2 or the delta semantics of #4263 (its perf debt is #4267).
- The in-process triple store of a multi-target `apply` (stdin batch) is built once for the batch, as before — write-through refreshes the PERSISTED cache for the next process, not the running process's store.
- `create`'s default-path cost (frontmatter / shape scans, ~13 s on the bot vault) — not a triple-cache problem; a separate perf item.
- Consumer wiring (`poll_assistant.py` / `kitelev-exo` passing `--use-cache`, dropping the pre-turn `index --force`) — a follow-up outside this repo.
- Making the flagged and the no-flag stores identical on an `index`-built cache: the no-flag path never materializes the inferred layer (it is `index`'s product), and stripping it from the flagged path would make `apply --use-cache` see LESS than `query --use-cache` does today. Consumers that need the no-inference store use `index --no-inference` or omit the flag.
- A same-size rewrite within the filesystem's mtime resolution is invisible to the manifest (both to the delta and to the write-through diff) — not the case on APFS / ext4, named, not solved here.
