# req(exo): on the PLUGIN surface too, a frontmatter block is recognised when its fences are CRLF or a BOM precedes it

## Job Story

When the surface reading a `.md` file is the Obsidian plugin rather than the CLI — which is
the surface I actually use every day, and the only one on iPhone — I want a genuinely valid
frontmatter block to be recognised regardless of its line endings or a leading byte-order
mark, exactly as the CLI has done since req `c05a3565-7b8d-42dc-bc9f-7e71d47d9364` (#4441,
PR #4450), so that the same file produces the same triples on both surfaces instead of
silently diverging by which tool happened to read it.

## Statement (Gherkin)

```gherkin
Given a vault containing a VALID asset whose frontmatter fences are CRLF
  ("---\r\n" … "\r\n---") and a second VALID asset preceded by a single U+FEFF
When the Obsidian plugin reads either file's frontmatter — through
  ObsidianVaultAdapter.getFrontmatter (metadataCache cold, disk fallback),
  through ObsidianFileSystemAdapter.getFileMetadata, or through
  VaultRDFIndexer's post-sync disk reindex
Then every one of those paths returns the parsed mapping (today: the first two
  return null / {} and the file contributes zero triples)
And a note with NO "---" fence anywhere still returns null on all three paths
And a note whose only "---"-like text sits inside its BODY still returns null on
  all three paths — the predicate stays anchored at position 0
And the three paths decide "is a block present?" through ONE shared predicate, so
  they cannot drift apart the way the CLI's read and diagnostic paths did (#4439 review)
```

## Why this is a sibling requirement, not an amendment of `c05a3565`

`c05a3565`'s §Non-goals names this gap explicitly and assigns it to **#4453**, having
withdrawn an earlier (false) claim that it was #4440's. It also scopes it **narrower** than
the CLI half, on a measured basis: `ObsidianVaultAdapter.updateFrontmatter` writes through
Obsidian's native `app.fileManager.processFrontMatter`, not through the regex, so the
CLI's "a property write must not eat the file's BOM" constraint has no counterpart here.
All three plugin sites are read-only in their current call graph.

Making a previously-invisible **valid** asset visible is new behaviour, not conformance —
the same reasoning by which #4441 needed its own requirement rather than extending
`fe50da38`.

## Design decision this requirement records (the open question from #4453 step 2)

**Resolved: ONE shared predicate in `packages/core`, called from all three plugin sites.**

Measured, not assumed — the same predicate shape exists in **five** places today:

| # | location | shape today |
|---|---|---|
| 1 | `packages/cli/.../FileSystemVaultAdapter.matchFrontmatterBlock` | `\r?\n` + BOM skip (fixed by #4450) |
| 2 | `packages/core/.../NoteToRDFConverter.extractBodyContent` | `\r?\n` + BOM skip (fixed by #4450) |
| 3 | `packages/obsidian-plugin/.../ObsidianVaultAdapter` | LF-only |
| 4 | `packages/obsidian-plugin/.../ObsidianFileSystemAdapter` | LF-only |
| 5 | `packages/obsidian-plugin/.../VaultRDFIndexer` | LF-only regex, but the whole content is BOM-stripped and CRLF-normalised *before* matching — so it is already tolerant **by a different mechanism**, undocumented as such and pinned by nothing |

Per-package duplication would leave three plugin variants plus two more elsewhere. A core
helper takes the plugin's three to one, so the repo goes from five independent predicates to
three, and the remaining two are named work items rather than accidents.

⛔ Deliberately NOT migrated in this requirement, each with its reason:

- **#1, the CLI adapter** — `packages/cli` is outside this work item's scope, and its matcher
  additionally returns offsets into the original string for its write path. Migrating it is a
  follow-up, not a silent extension.
- **#2, `extractBodyContent`** — its pattern deliberately consumes the block *including* an
  optional trailing newline and has no capture group; expressing it through the shared helper
  changes what the body-link path receives. That path has its own requirement and deserves
  its own axes.
- **`FrontmatterService.FRONTMATTER_REGEX`** — also LF-only, and also a non-goal in
  `c05a3565` for the same reason: it is the key-dialect / text-patch carrier, not the loader's
  "is a block present?" predicate. None of the scenarios above routes through it.

## Non-goals (deliberately NOT part of this requirement)

- **Lone-CR fences** and **a doubled BOM** — the CLI's residue, work item **#4452**. Exactly
  ONE leading U+FEFF is skipped and a fence needs at least one `\n`; both residual shapes stay
  invisible on the plugin exactly as they do on the CLI, and are pinned by control axes so the
  word "one" is load-bearing rather than incidental.
- **A block that opens `---` and never closes** — indistinguishable from a body that starts
  with a horizontal rule. Behaviour unchanged.
- **The write path.** `ObsidianVaultAdapter.updateFrontmatter` →
  `app.fileManager.processFrontMatter` is Obsidian's own mechanism and does not consult the
  regex; `ObsidianFileSystemAdapter.writeFile` writes raw content with no block splicing.
  There is therefore no "does a write preserve the BOM?" clause here, unlike `c05a3565`.
- **Changing `VaultRDFIndexer`'s observable tolerance.** It is already tolerant; this
  requirement converges its *mechanism* onto the shared predicate and pins the behaviour with
  an explicit axis, so a future refactor of its normalisation cannot silently regress it. The
  parsed YAML body it hands the parser will retain `\r` where it previously received `\n` —
  named here because it is a real mechanism change, and covered by its own axis.

## Verification

Binding class **integration**: the axes drive the REAL plugin adapters and the REAL
`NoteToRDFConverter.convertVaultWithValidation`, not a mock at the `getFrontmatter` seam.
Each axis carries `@req:<this uid>` as a literal token (a template-literal tag is invisible
to `requirements-trace`'s scanner). Revert-verify with a mutant per guarantee and a control
run; the expectations are written before the run.
