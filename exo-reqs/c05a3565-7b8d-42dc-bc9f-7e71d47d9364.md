# req(exo): a frontmatter block is recognised when its fences are CRLF or a BOM precedes it — the asset is INDEXED if valid and NAMED in the skip list if malformed

## Job Story

When I index a vault whose files can originate outside this machine — a note authored on
Windows, an editor that writes CRLF, imported or synced content carrying a byte-order mark —
I want every asset with a genuinely valid frontmatter block to be indexed **whether its fences
are LF or CRLF and whether or not a single BOM precedes them**, and every asset whose block is
present-but-malformed to be named in the loader's skip list, so that "N file(s) skipped by the
vault loader" stays an exhaustive account of what the loader rejected and no valid asset
silently contributes zero triples.

⛔ **The earlier wording of the clause above said «regardless of its line endings», and that was
FALSE — withdrawn here rather than left to rot.** The predicate this requirement delivers is
`\r?\n` plus at most ONE leading U+FEFF; lone-CR fences and a doubled BOM stay invisible. Both
are named in §Non-goals and pinned by executable axes, so the gap is recorded rather than
implied. Caught by the adversarial review of the implementing PR, not by the author.

## Why this is a NEW requirement, not conformance with `fe50da38`

Active P0 req `fe50da38-4798-46e6-bb0a-b4b88596c340` (#4439) closed the
"block present but does not PARSE" branch and **explicitly scoped this one out**, naming the
issue: «Осознанно вне скоупа, каждое своим issue: … CRLF/BOM на ГРАНИЦЕ блока — #4441 (их
починка сделала бы видимыми ранее-невидимые ВАЛИДНЫЕ ассеты, то есть это новое поведение,
а не соответствие ⇒ свой req)». Widening the block predicate makes a currently-invisible
**valid** block visible — an asset that produced zero triples now produces real ones. That is
new observable behaviour, so it gets its own requirement rather than silently extending an
Active one.

`fe50da38` is NOT superseded and NOT amended: it promised nothing about CRLF/BOM, so none of
its clauses becomes false. This requirement is its sibling.

## Statement (Gherkin)

```gherkin
Scenario: A valid asset whose fences are CRLF is indexed
  Given a file whose frontmatter block opens with "---\r\n" and closes with "\r\n---\r\n"
  And its body is valid YAML carrying the required asset properties
  When the vault is converted via NoteToRDFConverter.convertVaultWithValidation
  Then that file contributes a non-zero number of triples
  And it does NOT appear in skippedFiles

Scenario: A valid asset preceded by a BOM is indexed
  Given a file whose content begins with U+FEFF immediately followed by "---\n"
  And its frontmatter body is valid YAML carrying the required asset properties
  When the vault is converted via NoteToRDFConverter.convertVaultWithValidation
  Then that file contributes a non-zero number of triples
  And it does NOT appear in skippedFiles

Scenario: A malformed CRLF-fenced asset is NAMED, not silently dropped
  Given a file whose frontmatter block opens with "---\r\n" and whose body is invalid YAML
  When the vault is converted in non-strict mode
  Then the file appears in skippedFiles with a non-empty reason
  And converting the same vault in strict mode throws

Scenario: A malformed BOM-prefixed asset is NAMED, not silently dropped
  Given a file beginning with U+FEFF whose frontmatter body is invalid YAML
  When the vault is converted in non-strict mode
  Then the file appears in skippedFiles with a non-empty reason

Scenario: The read path and the diagnostic path agree by construction
  Given any of the files above
  When getFrontmatter returns null for it
  Then getFrontmatterParseFailure answers about the SAME block the read path looked for
  And no input exists for which one sees a block and the other does not

Scenario: A property write on a BOM-prefixed file keeps the BOM and does not duplicate the block
  Given a BOM-prefixed file with a parseable frontmatter block
  When updateFrontmatter patches one unrelated property
  Then the file still begins with U+FEFF
  And the file contains exactly ONE frontmatter block, carrying the pre-existing keys plus the patch

Scenario: Control — a note with no block at all stays silent
  Given a file with no "---" fence anywhere
  When the vault is converted
  Then it contributes zero triples
  And it does NOT appear in skippedFiles

Scenario: Control — a "---" that is not a real opening fence stays silent
  Given a file whose only "---"-like text sits inside a fenced code block, never at column 0 of line 1
  When the vault is converted
  Then it contributes zero triples
  And it does NOT appear in skippedFiles
```

## Non-goals (deliberately NOT part of this requirement)

- **Lone-CR fences (`---\r…\r---`, classic pre-OS9 Mac line endings, no `\n` anywhere).** Still
  read as "no block at all" — the same silent-invisibility class, entered through a third door.
  Measured on the implementation, not assumed: `getFrontmatter` → `null` and
  `getFrontmatterParseFailure` → `null`, pinned by axis **B15**. It is not a regression (it was
  invisible before this change in exactly the same way), and it is not free to add: a property
  write on such a file PREPENDS a second block and leaves the original as body text, so the
  widening would have to be paired with a write-path decision. That makes it its own
  requirement, not a clause here. **Work item: #4452.**
- **A doubled BOM (`﻿﻿---…`).** Exactly ONE leading U+FEFF is skipped; a second still
  defeats the `^` anchor. Pinned by axis **B16**, so the word "one" in this requirement is
  load-bearing rather than incidental. **Work item: #4452** (same issue — one predicate, two residual shapes).
- **A block that opens `---` and never closes.** Indistinguishable from a note whose body
  starts with a markdown horizontal rule; deciding that ambiguity deserves its own
  requirement and its own review. Behaviour stays exactly as today.
- **The plugin half — THREE locations, and NOT #4440.** The identical LF-only regex lives in
  `ObsidianVaultAdapter.ts:136`, `ObsidianFileSystemAdapter.ts:113` and
  `infrastructure/VaultRDFIndexer.ts:547`. ⛔ **The earlier wording of this bullet said «that is
  #4440» and named only the first location — both claims were FALSE and are withdrawn here.**
  #4440 is a different defect: the plugin not implementing `getFrontmatterParseFailure`, i.e. the
  skip-list half of #4439's contract. The plugin CRLF/BOM gap was named by nobody until
  **#4453**. ⛤ Scoped narrower than the CLI half on a measured basis:
  `ObsidianVaultAdapter.updateFrontmatter` writes through Obsidian's native
  `app.fileManager.processFrontMatter`, not through the regex, so the BOM-survives-a-write
  constraint does not carry over there. Caught by the orchestrator's review of the implementing
  PR — the SECOND unbacked sentence this document shipped (see §Job Story), which is itself the
  finding: both were claims on a decision surface with no mechanism behind them.
- **`FrontmatterService.FRONTMATTER_REGEX`** (`packages/core/src/utilities/FrontmatterService.ts:65`),
  also LF-only. It is the key-dialect / text-patch carrier, not the loader's "is a block
  present?" predicate, and none of the scenarios above routes through it. Measured, not
  assumed: the loader path is `getFrontmatter → extractFrontmatter → FRONTMATTER_BLOCK`.
  Separate surface, separate decision.

## Approval

the normalised predicate (`\r?\n` on both fences, leading U+FEFF ignored for matching only),
the requirement that the read and diagnostic paths share ONE normalisation, the
BOM-survives-a-write constraint, and the two deliberately-deferred shapes (missing closing
