# req(exo): the COMMAND write channels recognise a block through the SHARED predicate — a property write REPLACES a lone-CR / N-BOM block instead of prepending a second one, and the file keeps its own line endings

## Job Story

**When** I run an ordinary command against an asset that reached my vault from outside this
machine — classic pre-OS9 Mac line endings from an old export, a second U+FEFF stacked on by a
naive "ensure a BOM" tool — **I want** `set-property` (and every `apply <cmd>` that writes a
property, and `claim`/`spawn`) to see the SAME frontmatter block the reader sees, **so that** a
one-property patch cannot turn my whole frontmatter into orphaned body text, and the read and write
halves of this system stop disagreeing about what a frontmatter block IS.

## Why this is a NEW requirement, sibling of `74419202` — not an amendment of it

Active P3 req `74419202-264e-4394-a634-0b36d47357f8` (#4452) widened the SHARED predicate
`matchFrontmatterBlock` and the write path that consumes it,
`FileSystemVaultAdapter.replaceFrontmatter`. Its §Non-goals **names**
`FrontmatterService.FRONTMATTER_REGEX` (with `PropertyCleanupService`, `RenameToUidService`,
`NodeFsAdapter`, `CandidateShaclValidator`) as out of scope, with the reason "they are not consumers
of this predicate". That clause stays true and is not being corrected — this requirement
operationalises it, exactly as `74419202` operationalised `c05a3565`'s.

What the post-release smoke of #4452 added is **which surface carries the traffic**. Measured on the
published **v17.7.13** (i.e. after #4452 shipped), in a temp vault:

| channel | predicate before this req | reached by |
|---|---|---|
| `FileSystemVaultAdapter.replaceFrontmatter` | the shared one — widened by #4452 | `IVaultAdapter.updateFrontmatter`; **no CLI `src` call site at all** — the only production caller in the repo is the plugin's `LayoutService` |
| `FrontmatterService.updateProperty` | `/^---\n([\s\S]*?)\n---/` — LF-only AND defeated by any leading BOM | `set-property`, `remove-property`, `set-body`, `repair-frontmatter`, **and every `apply <cmd>` that writes a property**: `GroundingExecutor`'s `property_set`/`property_append`/`property_replace`, the `updateProperty`/`removeProperty`/`setStatus` `service_call` factories, `ArchiveAssetService`, `StatusTimestampService`, `TaskStatusService`, `FixMissingLabelService` |
| `AtomicFrontmatterService` | `/^---\s*\r?\n…/` — LF/CRLF-only, defeated by a BOM | `ClaimService`, `SpawnService` (`claim`, `spawn`) |

So #4452's write half is correct and locked, but on the CLI it is reachable **only through the
adapter API**, never through a command a user runs. Closing that is **new observable behaviour** —
a write that used to prepend now replaces — which is a sibling requirement under this repo's
req-first SDD discipline, not an extension of `74419202`.

## Measured, not assumed

- **The defect, on the published package** (temp vault, `set-property --property smoke__marker`):
  lone-CR asset → **4** fence lines (a second block prepended, the original left as body text);
  N-BOM asset → **3** fence lines and the BOM run pushed into the body; CRLF asset → **4** fence
  lines; single-BOM asset → **3**. Only the pure-LF asset behaved. `npx @kitelev/exocortex-cli@17.7.13`.
- **The population, on the three canonical vaults** (54 818 `.md` assets, 2026-09-29): fences are
  LF in **54 812** files; lone-CR **0**, CRLF **0**, BOM **0**, trailing-whitespace opening fence
  **0**. The defect is therefore **LATENT** — it is reached by assets arriving from outside, which is
  precisely the population #4452 was written for. Stating this plainly so a later reader does not
  read the green numbers as "nothing was broken".
- **`updateProperty` is the TEXT path**: it edits ONE line and leaves every other byte alone, unlike
  `replaceFrontmatter`, which re-dumps the block through js-yaml. That property is preserved here and
  pinned by a mutant that re-dumps the whole block.

## Statement (Gherkin)

```gherkin
Scenario: A property write on a lone-CR asset replaces the block instead of prepending a second one
  Given a valid asset whose frontmatter fences use a bare "\r" and which contains no "\n" anywhere
  When one unrelated property is written via FrontmatterService.updateProperty
  Then the file still carries exactly ONE frontmatter block
  And every pre-existing key survives the write
  And the bare CRs in the body after the block are still there, unconverted

Scenario: The newly written line carries the FILE's line ending, not LF
  Given a valid asset whose frontmatter fences use a bare "\r"
  When a property that is absent is written via FrontmatterService.updateProperty
  Then the new property line is terminated by "\r"
  And the block contains no "\n" at all

Scenario: A property write on an asset with a RUN of BOMs leaves exactly one U+FEFF
  Given a valid asset preceded by two or more consecutive U+FEFF
  When one unrelated property is written via FrontmatterService.updateProperty
  Then the written file begins with exactly ONE U+FEFF followed by the block
  And every pre-existing key survives the write

Scenario: LF, CRLF and single-BOM assets keep every byte the write did not address
  Given the same asset in its LF, CRLF and single-BOM encodings
  When one property is written via FrontmatterService.updateProperty
  Then the only lines that differ from the original are the written property's own
  And no line ending foreign to the file's style appears anywhere in it

Scenario: The write stays a one-line text edit, not a re-dump
  Given an asset whose frontmatter carries a comment line, a block scalar and a flow sequence
  When one unrelated scalar property is written via FrontmatterService.updateProperty
  Then every line the write did not address is byte-identical to the original

Scenario: Removing a property from a lone-CR asset keeps the block and the file's line endings
  Given a valid asset whose frontmatter fences use a bare "\r" and which carries a removable key
  When that key is removed via FrontmatterService.removeProperty
  Then the file still carries exactly ONE frontmatter block
  And the block contains no "\n" at all
  And every other key survives

Scenario: The atomic claim/spawn channel recognises the same shapes
  Given a valid asset whose frontmatter fences use a bare "\r", and one preceded by a RUN of BOMs
  When atomicUpdateFrontmatter merges an update into each
  Then neither call returns "no-frontmatter"
  And the merged value is readable from the written file
  And the written file begins with exactly ONE U+FEFF when the original had a run

Scenario: CONTROL — a note with no fence, and a "---" that is not an opening fence
  Given a note with no frontmatter fence at all, and a note whose "---" appears only after body text
  When a property is written via FrontmatterService.updateProperty
  Then the first gains a new block ABOVE its body, which is the documented create behaviour
  And the second's original text survives in full below the newly created block
  And atomicUpdateFrontmatter returns "no-frontmatter" for both, writing nothing

Scenario: CONTROL — the pure-LF path is unchanged
  Given the LF assets the existing suites already assert on
  When they are read, patched and rewritten
  Then every observable outcome is what those suites already assert, byte for byte
```

## Decisions this requirement records EXPLICITLY

1. **The TEXT nature of `updateProperty` is PRESERVED.** It splices LINES, it does not re-dump the
   block through js-yaml. Rationale: re-dumping would cost every LF and CRLF asset its byte-identity
   — comments, key order, block scalars and flow sequences would all be rewritten by a write that
   was asked to change one property. Pinned by a mutant that replaces the splice with a re-dump: it
   must redden the byte-identity axes and nothing else.
2. **The file's EOL style is preserved, and a NEWLY INSERTED line gets the file's own EOL.** The
   block's opening fence decides which one that is. Rationale: `74419202` decision 1 already chose
   "preserve the file's style"; inserting an LF line into a CRLF block would create a MIXED block,
   i.e. a second state model for one property
   (`additive-migration-creates-two-state-models`), and the next writer would have to guess which
   ending is canonical. ⛤ "What does `updateProperty` do today for CRLF?" has no usable answer — it
   does not recognise a CRLF block at all and prepends a second one, so there is no prior behaviour
   to inherit; the rule is taken from the sibling requirement instead.
3. **BOM-run policy is the SAME as `74419202`'s: exactly ONE U+FEFF on write.** Both channels obey
   it. Rationale: the two channels must not disagree — a user whose file passed through the adapter
   and then through `set-property` must not get two different answers about his BOM. This is the one
   place normalisation is intended, and the asymmetry against decision 2 is the same one
   `74419202` §Non-goals already records: a line-ending style is an authoring choice, a stacked BOM
   is damage.
4. **`AtomicFrontmatterService` keeps re-dumping and keeps emitting LF.** It is the object path
   (parse → merge → `yaml.dump`), byte-identity was never one of its properties, and giving it an
   EOL-preservation policy would be a THIRD model. What changes is only WHICH span it recognises —
   plus the BOM, which it now preserves as one byte instead of dropping it.

## One deliberate NARROWING, named rather than discovered later

`AtomicFrontmatterService`'s old regex began `^---\s*\r?\n`, i.e. it also accepted trailing
whitespace on the OPENING fence (`--- \n`). `matchFrontmatterBlock` does not. Measured: **0**
carriers across the three canonical vaults (54 818 assets). And since the READ path
(`NoteToRDFConverter`, `FileSystemVaultAdapter`) already goes through the shared predicate, such a
file is not in the graph at all — accepting it here only let a write reach an asset nothing else
could see. The narrowing is therefore a parity fix, and it is recorded here because a silent
narrowing is indistinguishable from an oversight.

Its second, smaller narrowing: the old regex's greedy `---\s*` swallowed EVERY blank line between
the closing fence and the first body text, so `---\n\n\nbody` came back as `body` and the blank
lines were gone from the rewritten file. Only ONE line ending is consumed now. Nothing depended on
the loss; copying it forward would have been copying a defect.

## Non-goals (deliberately NOT part of this requirement)

- **`PropertyCleanupService` and `RenameToUidService`** — the two remaining LF-only write paths in
  production `src`, both reachable as `service_call` channels (`cleanProperties`, `renameToUid`).
  They are **fail-CLOSED**: their `if (!match) return content` leaves the file untouched, so the
  command silently does nothing instead of destroying data. That is a different defect class from
  the one this requirement closes, each carries its own line-splitting logic that would have to be
  made EOL-aware separately, and folding them in would put four concerns in one PR. Work item to be
  filed; named here so the gap is recorded rather than overlooked.
- **`NodeFsAdapter` and `CandidateShaclValidator`** — named non-goals of `74419202` already, with
  their own work items. Unchanged.
- **`packages/req-audit` and `packages/test-utils`** — internal tooling and test infrastructure, not
  a user-facing write channel.
- **Normalising a file's line endings.** The file keeps its style; only a run of BOMs is normalised
  (decision 3).
- **`matchFrontmatterBlock` / `replaceFrontmatter` themselves.** Closed by #4452 with 27 axes and 20
  mutants; this requirement only CONNECTS channels to them.
- **The plugin.** No plugin source file is touched. Its own write path already reaches the shared
  predicate through `replaceFrontmatter`; `ObsidianVaultAdapter`'s diagnostic half is #4440.
