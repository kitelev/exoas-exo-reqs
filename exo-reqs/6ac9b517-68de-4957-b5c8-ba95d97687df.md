# req(exo): the REMAINING packages/cli surfaces recognise a CRLF-fenced or BOM-led frontmatter block

## Job Story

When I create or index assets whose files can originate outside this machine — authored on
Windows, written by an editor that emits CRLF, imported or synced carrying a byte-order mark —
I want **every** CLI surface that asks "does this content open with a frontmatter block?" to
give the **same** answer the vault loader gives, so that a pre-write gate cannot approve a
write whose post-write triples violate SHACL, `apply` cannot fail to find an asset that
`exocortex-cli query` finds, and the vault's declared frontmatter ordering is not silently
skipped.

⛔ **Every one of these failures is in the PERMISSIVE / silent direction**, which is why none
of them surfaced on its own: a gate that says "nothing to validate" looks like a clean run, and
a resolver that drops a candidate looks like "no such asset".

## Why this is a NEW requirement, not conformance with `c05a3565`

Active P2 req `c05a3565-7b8d-42dc-bc9f-7e71d47d9364` (#4441) widened the **loader's**
predicate. Its `covers` is scoped verbatim to `FileSystemVaultAdapter.FRONTMATTER_BLOCK` plus
its three call sites and `NoteToRDFConverter.extractBodyContent` — it promises nothing about
the four surfaces above, so none of its clauses becomes false and it is neither superseded nor
amended. This requirement is its sibling.

The reasoning `c05a3565` applied to itself applies here verbatim, and is why this is not a
bug-fix under it: **making a currently-invisible VALID block visible is new observable
behaviour.** An asset that contributed nothing to a resolver now resolves; a candidate that was
waved through is now refused.

⛤ **`FileSystemVaultAdapter` itself (#4461) is deliberately NOT in this requirement's covers.**
Its migration onto the same core predicate is a pure REFACTOR: the copy it carried was
byte-identical in shape, so the observable behaviour is unchanged. Its proof is `c05a3565`'s 17
axes B1-B17 staying green **unchanged** plus a WIRING mutant — not a new clause. Classifying it
as behaviour would mint a requirement whose only honest scenario is "nothing changed".

## Statement (Gherkin)

```gherkin
Scenario: The dry-run SHACL gate reports a CRLF-fenced candidate that violates a shape
  Given a vault whose shapes give a property a range the candidate's value does not satisfy
  And a not-yet-written candidate whose frontmatter fences are CRLF
  When CandidateShaclValidator.validateCandidate is asked about it
  Then the violation is reported
  And it is NOT reported as "no frontmatter block, nothing to validate"

Scenario: The same for a BOM-led candidate
  Given the same vault
  And a not-yet-written candidate whose content begins with a single U+FEFF
  When CandidateShaclValidator.validateCandidate is asked about it
  Then the violation is reported

Scenario: Control — a VALID CRLF-fenced candidate still passes
  Given a candidate whose CRLF-fenced frontmatter satisfies every shape
  When the gate is asked about it
  Then it raises no violation for that property

Scenario: Control — a candidate with no block at all is still "nothing to validate"
  Given content with no "---" fence anywhere
  When the gate is asked about it
  Then it reports no violations and no warnings

Scenario: apply's resolvers find a CRLF-fenced asset
  Given a vault containing an asset whose frontmatter fences are CRLF
  When TripleStoreIndexedFsAdapter.findFilesByMetadata is queried by that asset's label

Scenario: apply's resolvers find a BOM-led asset
```

## Non-goals (deliberately NOT part of this requirement)

- **`FileSystemVaultAdapter` (#4461).** A refactor, not behaviour — see §Why above. It rides in
  the same PR because it is the same one-line import change and the same predicate, and its
  proof is the unchanged B1-B17 plus its own WIRING mutant.
- **Lone-CR fences and a doubled BOM.** Exactly what `c05a3565` defers to **#4452**: this
  requirement adopts core's predicate as-is and therefore inherits its residue unchanged. Making
  those visible is a founder decision about the predicate's semantics, not about which surfaces
  use it. `packages/core/src/utilities/frontmatterBlock.ts` is NOT edited here.
- **`FrontmatterService.FRONTMATTER_REGEX`** (`packages/core`) and
  **`NoteToRDFConverter.extractBodyContent`** — named non-goals in req `1dfbd427` with reasons
  (the former is the key-dialect / text-patch carrier, not the loader predicate; the latter
  consumes the trailing newline and has no capture group).
- **Converging the repo's remaining `^---…---` literals.** Measured 2026-09-29: **109**
  repo-wide, ~30 in production `src/`. The ones left in `packages/cli/src` after this change are
  all already `\r?\n`-tolerant (`repair-frontmatter`, `validate-schema`, `AtomicFrontmatterService`,
  `CliProfileResolver`, `PropertyNameValidator`, `ClaimService`, `RegistryDependencyResolver`,
  `CliApplyProfileService`); they are latent duplication, not a live gap, and converging them is
  its own work item. The ratchet this requirement installs keeps the LF-only class at zero, which
  is the half that is a live defect.
- **Exporting `bomLength` from core.** `FileSystemVaultAdapter`'s no-block INSERT branch needs
  "where does the content proper begin", and core keeps `bomLength` module-private. #4461
  sanctions either exporting it or keeping that one expression local; this work item is scoped
  out of `frontmatterBlock.ts`, so it stays local and is marked in the code as NOT a second block
  predicate. The residual convergence is a follow-up.

⛤ **The order-spec scenario was WIDENED after the review of the implementing PR, and the
first wording is recorded rather than replaced silently.** It read "Then the spec's head and
tail are loaded" — true of the implementation only for a ONE-ENTRY list. Routing this loader
onto core's predicate makes a CRLF-fenced spec visible, and `extractList`'s continuation token
was `
?`: `.` never matches a line terminator, so on CRLF it consumed nothing before the ``
and the group terminated after the FIRST item. The fix that made such a spec VISIBLE would
have made it silently WRONG — the same permissive/silent class this requirement exists to
close, entered through a fifth door. The clause now names the multi-entry case and the LF
equivalence, both of which the axes assert (`E2`, `E2b`) and a mutant discriminates
(`M_list_continuation_back_to_lf_only`). The live default order-spec asset was measured: LF on
disk today with several entries — so the defect was latent, not active.

## Verification

Binding class `integration`: every axis drives production code on a per-case temporary vault —
the real `CandidateShaclValidator` over a real converted vault, the real
`TripleStoreIndexedFsAdapter` over the real loader's triples, and one axis driving the real
`applyCommand().parseAsync([...])` end to end. No hand-injected frontmatter objects.

Axes (`packages/cli/tests/integration/cli-frontmatter-predicate-unify-4461.integration.test.ts`):
`C1`-`C4` (the SHACL gate), `D1`-`D5` (the fs adapter and `apply`), `E1`/`E1b`/`E2` (the two
ratchet sites), `E3` (the ratchet itself, with two canaries — the predicate and the corpus size).

Revert-verify evidence (RED without the fix, GREEN with it) is recorded in the implementing PR
body, per axis, as a WIRING mutant per site.

⛤ **One axis was retargeted by a measurement, not by taste, and that is recorded here because
it is the kind of thing a reader would otherwise re-derive.** The first `D3` drove a REAL
`apply` whose label-form `targetClass` pointed at a CRLF-fenced CLASS asset — and it stayed
GREEN under the LF-only mutant: a class-shaped literal is substituted to a class IRI by the
converter, so `apply` never has to ask the filesystem about it. `$isDefinedByFolder` does ask
(`findFilesByMetadata({exo__Asset_uid})` → index candidate → confirmation read), so the
CRLF-fenced asset that discriminates is the ONTOLOGY, and the observable is WHERE the instance
lands. A `getFileMetadata`-only axis would not have shown either.

## Approval

Sanctioned by the three GitHub issues that name the design verbatim — **#4459** (route
`CandidateShaclValidator` through the shared predicate and make the parity sentence true by
construction), **#4460** (route `NodeFsAdapter.extractFrontmatter` through it, with a
resolver-level and a real-`apply` axis), **#4461** (the `packages/cli` census and the ratchet
that extends beyond `adapters/`). All three were authored by the `code-reviewer` run on PR #4458
and queued by the orchestrator (`main-6260`) as this session's work item; nothing here widens
that design.

⛤ `approvedBy` names **ExoAssistant**, not the founder: the design originates in an automated
review and an orchestrator-queued task, not in a founder-authored issue. Recording it otherwise
would be a signature with nothing behind it. The two ratchet sites
(`registerOrderSpec`, `wikilinkExtraction.bodyOf`) are NOT named in any issue — they were
surfaced by the census the task text mandates ("что ещё найдёт греп сверх трёх issue — назови в
PR: чинишь или отдельный issue"), are the same predicate and the same mechanism, and are ≤3
lines each, so they are fixed here and named in the PR rather than deferred.
