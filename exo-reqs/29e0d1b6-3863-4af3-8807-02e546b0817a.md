# req(exo): `property_set` refuses an unquoted wikilink instead of writing a silent literal

## Job Story

When I set a reference-valued property through a homoiconic command from the CLI
(`apply set-ontology <target> --input '{"ontology":"[[<uid>]]"}'`), I want the engine to
**refuse** the ambiguous unquoted form and tell me the correct one — so that I never end up
with an asset that reports success while being invisible to every join on that property.

## Context — the two value-source contracts are asymmetric

`property_set` has two reference-capable value-sources, and they take the value in **opposite**
shapes:

| value-source | what the executor does | what the caller must pass |
|---|---|---|
| `targetValueSubstitution` | writes the substituted value **verbatim** | an ALREADY-quoted wikilink `"[[uid]]"` (the quotes are part of the string — exactly what the plugin's `ReferencePicker`/`toReferenceWikilink` commits) |
| `targetValueRef` | wraps the value itself (`"[[" + ref + "]]"`) | a **bare** uid |

A bare `[[uid]]` reaching the verbatim path lands in the frontmatter unquoted, where YAML reads
it as a **flow sequence**, not a string — so `NoteToRDFConverter` emits the object as a literal
and the reference is lost. Nothing fails: the command reports success and `repairFolder` (whose
resolver tolerates both shapes) even relocates the file. Two parsers disagree, and no error or
warning surfaces anywhere.

This asymmetry — not the ergonomics of any single command — is the defect. The fix is a **loud
refusal**, deliberately not normalization: accepting `[[uid]]`, `"[[uid]]"` and a bare uid alike
would fix the symptom while hiding the asymmetry that causes it.

## Scenarios

### Scenario 1 — an unquoted wikilink is refused, and nothing is written

```gherkin
Given a property_set grounding whose value-source is targetValueSubstitution "$input.ontology"
And a target property that is not a string-scalar property (e.g. exo__Asset_isDefinedBy)
When the substituted value is the bare wikilink "[[<uid>]]"
Then the step fails
And the error names the unquoted wikilink and both correct forms (quoted substitution, bare targetValueRef)
And no file is written
```

### Scenario 2 — the quoted form still writes a resolvable reference

```gherkin
Given the same grounding
When the substituted value is the quoted wikilink "\"[[<uid>]]\"" (the quotes are part of the value)
Then the step succeeds
And the frontmatter carries exo__Asset_isDefinedBy: "[[<uid>]]"
And YAML parses that value as a string, not as a sequence
```

### Scenario 3 — the sibling `targetValueRef` contract is unaffected

```gherkin
Given a property_set grounding whose value-source is targetValueRef "<uid>" (a bare uid)
When the step runs
Then it succeeds
And the frontmatter carries the quoted wikilink the executor wrapped itself
```

### Scenario 4 — non-reference values are byte-identical

```gherkin
Given a property_set grounding whose substituted value is ordinary text
When that text is a plain label, or prose that merely contains a wikilink
Then the step succeeds and writes exactly what it wrote before this requirement
```

## Non-goals

- **Normalization** of the accepted forms (see Context — it would hide the asymmetry).
- Changing `targetValueRef` / `targetValueQuery`, which already produce the quoted form.
- Any change to string-scalar properties (`exo__Asset_label`, `aliases`): they are quoted by
  `serializeYamlScalar` before the guard sees them, so they keep their current behaviour.
