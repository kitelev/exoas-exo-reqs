## Job Story

Когда ExoSync синкает несколько vault подряд, я хочу, чтобы **неизменяемые** git-объекты
(`git/commits/{sha}`, `git/trees/{sha}`, `git/blobs/{sha}`) не запрашивались по сети повторно —
потому что по данному SHA ответ не может измениться никогда, а сейчас один и тот же ассетспейс
тянется столько раз, во скольких vault он смонтирован.

## Замеренная мотивация (2026-09-26, считающий прокси через `--api-base`, не оценка)

- Холостой `exosync-parity` на 21 репозиторий = **ровно 83 запроса** (41 `refs` + 21 `commits` + 21 `trees`, 4/репо).
- При неподвижном head **42 из 83 (51 %)** — `commits` + `trees`: берутся из кэша **без сети**.
- Между vault: **35 из 81** монтирований — дубли. Дерево и блобы `exoas-public` (751 файл) тянутся
  **3 раза** за один трёхvault'овый синк.
- Живой отказ 2026-09-26 11:17: `403`, `x-ratelimit-remaining: 0`, `used: 5000`, `resource: core`
  — то есть исчерпание primary наступает в реальной работе, а не гипотетически.

## Statement (Gherkin)

```gherkin
Feature: локальный кэш неизменяемых git-объектов по SHA

  Scenario: повторный запрос того же SHA не идёт по сети
    Given ExoSync уже прочитал git-объект с SHA S и положил его в кэш
    When любой последующий синк в любом vault запрашивает тот же SHA S
    Then объект берётся из локального кэша
    And сетевой запрос по этому SHA не выполняется вовсе

  Scenario: общий ассетспейс между vault читается по сети один раз
    Given exoas-public смонтирован в трёх vault
    When три vault синкаются подряд при неподвижном head
    Then дерево и блобы exoas-public тянутся по сети только в первом vault
    And во втором и третьем restCalls по общим ассетспейсам = 1/репо (только head-проверка)

  Scenario: повреждённый кэш падает громко, а не применяет мусор
    Given в кэш-файле под известным SHA подменено содержимое
    When синк читает этот объект
    Then синк завершается ошибкой проверки целостности
    And повреждённое содержимое НЕ применяется к vault

  Scenario: кэш не растёт неограниченно
    Given размер кэша превысил заданный предел
    When добавляется новый объект
    Then вытесняются наименее недавно использованные записи
```

## Non-goals (out of scope этого требования)

- **Условные запросы (ETag / `If-None-Match`)** — отдельный механизм для **mutable** чтений
  (`git/refs`), где кэш по SHA неприменим: issue #3975. Дополняют друг друга, не заменяют.
- **Параллелизм `syncAll`** (#3911) — он повышает мгновенную ставку запросов и работает ПРОТИВ
  этой экономии; делать только ПОСЛЕ.
- **Инвалидация кэша** — не нужна by construction: объекты content-addressed.

## Приёмка (красный исход назван явно)

1. Синк трёх vault подряд ⇒ `restCalls` второго и третьего по общим ассетспейсам = 1/репо.
   ⛔ Красный: число blob-запросов на `exoas-public` во втором vault не ноль.
2. Подмена содержимого кэш-файла под известным SHA ⇒ синк падает громко.
   ⛔ Красный: мусор применён либо отказ тихий.
