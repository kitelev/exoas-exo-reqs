# req(exo): query --prune-report — what on-demand loading would load for this query

## Job Story

When on-demand loading (RFC `308a52c3` «Загрузка по запросу») is about to load only the triples a query
needs, I want any query — a single one or a whole batch a pipeline sends — to tell me which predicates it
needs (P'), why the analyzer refuses to prune when it does, and what share of the loaded triples those
predicates cover, so that the gain of the future loader is measured before it is built and its threshold
is fixed by a measurement, not a promise (ticket `dc5ed554`, phase 1b).

## Mechanism (read on `origin/main` `cde2440c`, v17.20.0)

The analyzer (`analyzeAlgebraPredicates` / `analyzeParsedQuery`, `computeSubPropertyIndex`, req `f5db994b`)
returns either `mode: "prune"` with `predicates` and their `sources`, or `mode: "full"` with named
`reasons`. Nothing in the CLI prints P': `--prune-oracle` (req `00390739`) compares answers and never
prints a predicate IRI. `query --batch` (req `166613ce`) loads the graph once per file.

## Statement (Gherkin)

```gherkin
Feature: query --prune-report — P', the full-load reasons and the share of loaded triples

  Background:
    Given a vault loaded by the same loader as plain `exocortex query` (the explicit and the inferred layer)

  Scenario: the report replaces the answer, loading is unchanged
    When `exocortex query "<sparql>" --prune-report` is run
    Then the graph is loaded in full exactly as plain query loads it
    And the query is analyzed over the translator's algebra BEFORE the optimizer
    And the query is NOT executed: the executor is never called and no answer reaches stdout
    And the query result cache is neither read nor written

  Scenario: a query the analyzer can prune
    When the query has constant predicates
    Then the report names the mode «prune»
    And lists P' sorted by IRI, each predicate with its sources (query, namespace-filter, sub-property, class-bridge)
    And prints «Triples: <cut> of <loaded> loaded (<share> %)»

  Scenario: VL-3 — a namespace filter on a variable predicate
    When the query is `?s ?p ?v FILTER(CONTAINS(STR(?p), "ontology/flow#"))` (Q_FLOW_TRIPLES of the selector)
    Then the mode is «prune by namespace filter»
    And P' is exactly the flow# predicates present in the graph, nothing else
    And a query mixing a constant predicate with such a filter is also «prune by namespace filter»

  Scenario: a full load
    When the analyzer refuses to prune (a variable predicate, a namespace filter in another group, an UPDATE, …)
    Then the mode is «full load», every reason is named (a variable with its `?`), and the share is 100 %

  Scenario: the share is in loader units
    Then the cut counts the loaded triples whose predicate is in P' — duplicates included, as the loader returns them
    And the denominator is every loaded triple of the same array
    And an empty graph gives share 0 for a prune

  Scenario: machine-readable output
    When `--output json` is given
    Then stdout is ONE JSON document with `data.type = "prune-report"` and fields
      mode, reasons, predicates[{iri, sources}], triplesCut, triplesLoaded, share

  Scenario: a batch report
    When `exocortex query --batch <file> --prune-report` is run
    Then the graph is loaded once and one NDJSON record per entry is printed in input order — the same report as a single query
    And the last line is a summary: counts per mode, the reasons, medianShare (a full load counts as 1),
      medianSharePrune (pruned entries only), the union of P' a batch would load (one full entry ⇒ full;
      overlapping entries ⇒ the union, not the sum; duplicates and skeletons counted), triplesLoaded, graphLoads
    And entries the batch would not run (a syntax error, an UPDATE, a failed analysis) are failed records,
      counted in neither the medians nor the union, and the exit code is OPERATION_FAILED

  Scenario: conflicting flags are refused before any load
    When --prune-report is combined with --prune-oracle, or (single query) with --dry-run, --explain, --stats or --format other than table
    Then the call is refused before the graph is loaded and nothing is printed to stdout
    And --use-cache reaches the report's load (single and batch), --template reaches the analyzed text,
      and a syntax error is reported with the same context as plain query reports it
```

## Non-goals

- Loading by P' (phase 3b) — the report changes no loading.
- The `--stats` line (phase 4, ticket `c7a94d8e` — it reuses `pruneReport` of this module).
- `run-query --prune-report`; the order of rows (the oracle's job, req `00390739`).
- ASK execution in plain `query` (ticket `3254ccba`).
