# req(exo): under `--json` the stdout of `exosync-parity` and `exosync sync|pull|push` is exactly one JSON document or nothing

## Job Story

When an AI session of the pipeline (acceptance, release) or the bot quarantine watch reads
`exosync-parity --json` or `exosync pull --json` as a machine oracle, I want stdout to be the JSON
document and nothing else, because today a run header precedes it and telemetry lines follow it
(`[ExoSync objects]`, `[ExoSync conditional]`, `[ExoSync quota]`): `json.load(stdout)` fails with
`Expecting value: line 1 column 1`, and every consumer has to write its own workaround (ticket
`0b24c5d1`; 26–27.09 the telemetry tail behind the document made the bot watch read parity as
broken on all 14 vaults — about 22 false alarms a day to the founder).

## Mechanism (read on `origin/main` `b4f1774f`)

`runExosyncParityUnsettled` and `runExosyncSyncUnsettled` print every line through one sink
`out` (= `console.log`, stdout) in both modes: the malformed-list refusal (the helper
`collectVaultSpecsOrRefuse` writes it to stdout AND stderr), `warn:` lines, "Nothing to
check|sync", the run header, `❌ --repo: not among …`, the `--repo: K of N` scope line, and in
parity the three telemetry lines — printed AFTER the document.

## Statement (Gherkin)

```gherkin
Given a vault with materialized sync units
When `exosync-parity --json` or `exosync sync|pull|push --json` runs
Then stdout carries exactly one JSON document (the round record / the per-repo result array)
  and nothing else, or nothing at all when the run refuses or finds nothing to emit
  And every diagnostic line — run header, `warn:` lines, "Nothing to check|sync", `--repo:`
    lines, refusals, `[ExoSync objects|conditional|quota]` — goes to stderr
  And every stderr line of the run is written BEFORE the document
  And a pull-only list warning (req c0810b83) is printed once, on stderr

Given the same commands without `--json`
When they run
Then stdout and stderr carry exactly what they carried before this requirement
```

Notes:

- "Before the document" is a guarantee about the ORDER OF WRITES. A caller that merges the
  streams (`2>&1`) gets the document in one piece as long as the stderr written right before
  it fits the pipe buffer; when more than that (≈64 KiB) goes to stderr first and the reader
  lags, stderr lines can arrive after the document has started. In parity only the header,
  `warn:` lines and 1–3 telemetry lines precede the document; in `exosync pull --json` — the
  pull-only mirrored-path list (it was on stderr before this requirement too). Read the two
  streams separately.
- The document is the LAST write of the run because Node writes a pipe asynchronously: a
  document larger than the pipe buffer goes in parts, and a stderr line written meanwhile
  lands BETWEEN them for a merging caller (measured during planning: quota line after a
  1.7 MB document — 3 of 3 corrupted; before it — intact).

## Non-goals

- ⛔ Telemetry of `exosync sync|pull|push --json` stays suppressed, as before (only parity
  prints it, now on stderr — req `e5e45283` "parity prints the quota line on every run" holds).
- ⛔ Document formats (`version`/`ok`/`repos`/`parked`, the result array) and exit codes do not
  change.
- ⛔ Exceptions through `ErrorHandler` (no token, no vault) — as before: text on stderr, empty
  stdout. A JSON error document on stdout is a separate decision.
- ⛔ `exosync quarantine list --json` — a separate defect (bug `5a1cdf3e`).
- ⛔ The residual merge limit above is not cured in code.
