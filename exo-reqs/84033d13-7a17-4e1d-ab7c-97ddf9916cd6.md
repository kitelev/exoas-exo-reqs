## Зачем

Тикет P22 дорожной карты `9bbda2be` (`01a23606`): цикл опроса личного Telegram-бота стоит 43–82 с (медиана) после каждого ответа, пока идёт `exosync push`. Замер 2026-10-05 на vault бота БЕЗ локальной дельты, CLI 17.8.1: 59 / 66 / 56 с, встроенный профиль `52.7s — restHead 52.4s 99% · localList 278ms 1%`.

Механизм: vault бота монтирует 23 репо, движок обходит их последовательно (намеренно — «Sequential single-flight», защита от rate-limit), по ~2,3 с на репо. Бот за всё время пушил в 6 репо из 23 (`repos_pushed`, 1287 записей журнала). Ограничить прогон нужными репо из CLI нельзя: у `exosync sync / pull / push` нет такого флага.

Требование аддитивно: без нового флага поведение байт-в-байт прежнее.

## Сценарии

### Сценарий 1 — флаг ограничивает прогон перечисленными репо

```gherkin
Given vault с N материализованными репо
When запускаю `exosync push --vault <v> --repo kitelev/exoas-my`
Then движок обрабатывает ТОЛЬКО kitelev/exoas-my
  And заголовок прогона называет 1 repo(s), а не N
  And остальные репо не получают ни одного REST-запроса
```

### Сценарий 2 — флаг повторяемый

```gherkin
Given vault с N материализованными репо
When передаю `--repo A --repo B`
Then обрабатываются ровно A и B, в порядке «дети раньше родителей», как и без флага
```

### Сценарий 3 — без флага ничего не меняется

```gherkin
Given тот же vault
When запускаю `exosync push` без `--repo`
Then обрабатываются все N репо, как до введения флага
```

### Сценарий 4 — неизвестное имя репо отвергается громко и ДО сети

```gherkin
Given среди материализованных репо нет kitelev/nope
When передаю `--repo kitelev/nope`
Then команда завершается с кодом 2, не сделав ни одного REST-запроса
  And сообщение называет отвергнутое имя и перечисляет доступные репо
```

### Сценарий 5 — принимаются обе формы ключа

```gherkin
Given ключ репо в прогоне выглядит как `kitelev/exoas-my#main`
When передаю `--repo kitelev/exoas-my` ИЛИ `--repo kitelev/exoas-my#main`
Then оба значения выбирают это репо
```

## Non-goals

- Распараллеливание обхода репо в движке — отдельный вопрос (защита от rate-limit).
- Подключение флага в бота (какие репо передавать) — отдельная правка; список обязан покрыть все репо записи бота, иначе часть дельты перестанет уезжать.
- Пропуск репо без локальной дельты внутри движка — не проверено, что детекция возможна без обращения к remote.

## Решение о дельте неперечисленных репо

С `--repo` ожидающая дельта неперечисленных репо в этом прогоне НЕ отправляется — это осознанный выбор вызывающего, а не потеря: она уйдёт следующим прогоном без флага или с этим репо в списке. Требование `702e8bda` («push доставляет любую ожидающую дельту») относится к кэшу изменений внутри обрабатываемого репо и этим не затрагивается.
